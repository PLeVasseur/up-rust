# Timing claims rest on a supported configuration, and the item's budgets are the integrator's

`uman~sdk-aou-timing-budgets~2`

Covers:
- aou~seooc-timing-budgets~6

## Status and scope

Draft integrator guidance against the corrected specification input. The quotation states
requirements and assumptions, including future behavior; it is not an assertion
that the current SDK implements them. Revision 6 rests timing claims on a supported configuration's package, ends J at the winning counter update and its visibility with the application's later read outside it, and keeps the narrowed-value watchdog and one-word servicing duties only where a configuration keeps those representations; at this revision no supported profile does, so neither duty binds a current configuration. No configuration establishes a finite J yet. Default mode remains permissive; strict receive routes must declare a deadline or event_only. This documentation does not qualify the monitor or response machinery.

Read [manual status](README.md) before using this entry. A documentary coverage
link neither validates the deployment nor closes an implementation requirement.

## Assumption (verbatim)

<!-- aou-statement:start -->
> Where the item relies on the element within a time, the integrator *SHALL* select a supported configuration whose package states each timing claim it offers, with its endpoint, execution model, workload envelope and evidence, and *SHALL* keep the deployment within that package: its scheduling, priorities, CPU budgets, affinity and interrupt load. The integrator *SHALL* allocate the item's fault tolerant time interval, declare each route's semantic traffic, deadline, TTL and wait timeouts and the reaction budget it needs, and show that the package's bounds and the item's own reaction fit that interval. A configuration that offers no finite bound for an endpoint gives none: the element then operates and reports functionally, and the item *SHALL NOT* rely on that endpoint within a time. The integrator allows for the following:
>
> * *TTL resolution.* A frame is refused at the latest when its TTL, rounded up to a whole millisecond, plus one more millisecond has passed since the time its message ID records (`+req~ssr-qos-ttl~4+`). An ID made while the sender's wall clock could not be read records the last good time, so its frame can be refused early: by up to the time the clock was unreadable, and, for a generator that keeps the last good time only to 64 ms, by up to 64 ms more (`+req~ssr-ids-unique~4+`).
> * *When an RPC failure is seen.* Where the element can report a failure, a call's outcome is set as soon as the element's answer arrives (`+req~ssr-peer-rpc-no-server~1+`, `+req~ssr-peer-rpc-undecodable-answered~5+`, `+req~ssr-streamer-rpc-error-response~4+`); when the application observes that outcome is a timing claim of its configuration. A request that the E2E wire refuses is answered, final or advisory; only a corrupt one is not. On an RPC route with the E2E wire, a response the client refuses at arrival, including the Streamer's best-effort error response with no E2E header, gives the claimed call slot back to await another response (`+req~ssr-rpc-check-at-arrival~2+`). That refusal does not complete the call. A later acceptable response or protected final refusal answer can complete it before TTL; a call with no such later response or final answer ends at its TTL, naming the refusal. The TTL remains the guarantee when no earlier completion occurs.
> * *Fail-silent routes.* The Streamer's safe state is fail-silent per route, so a receiver sees a gated route as silence. An RPC client whose request arrives on a gated route gets the best-effort `+Unavailable+` response when the reverse route can carry it (`+req~ssr-streamer-rpc-error-response~4+`), and otherwise its call's outcome becomes expiry once its TTL has passed. A client that uses the E2E wire refuses that response as unprotected and counts the refusal apart from corruption; it gives the slot back, and its call ends at TTL naming the refusal only if no later acceptable response or protected final answer completes it. Every safety-related receiver whose safety reaction depends on detecting silence *SHALL* declare a deadline. An explicit `+event_only()+` declaration permits a route without a deadline, but supplies no deadline-based silence or delay detection; the integrator *SHALL NOT* rely on that route's deadline monitor for such a reaction.
> * *Priority inversion through middleware locks.* iceoryx2, for example, holds its port lock for up to a wait's bound, and takes it briefly when a frame is dropped (its README).
> * *Watchdog and reuse.* Where a configuration's representation keeps the narrowed generations that `+req~ssr-atomic-windows~2+` lists for the predecessor 32-bit-word representation, which no current profile's does, the integrator's watchdog supervises every thread that calls the element, and detects one that makes no progress inside the element for longer than its period `+T_wd+`. `+T_wd+` times the highest reuse rate of any one call slot stays below 2^28^, and of any one peer-table entry below 2^22^. Its reaction restarts the process, or on an MCU the partition or OS-Application, that holds the element's memory, before the stalled thread can act inside the element again. It also covers the wrap windows that remain: a stalled `+expire+` or `+fail_older+` that would end a later call early, and a stalled `+retire+` that would act as a spurious `+peer_lost+`. A configuration whose package documents full-width values in their place needs no watchdog for these windows. Whatever the representation, a frame queued behind a producer that stalls before linking its own frame is delivered when that producer resumes, so where the item relies on such a frame within a time, a supervisor bounds that stall.
> * *Retry loops.* Each compare-exchange loop in the element retries only after another write to the same reservation granule succeeded or, on load-linked/store-conditional cores, after an exception taken inside the loop. On a multi-core part, a write by another core anywhere in the granule counts. Its worst-case execution time under the configuration's interrupt load and contention belongs to the configuration's timing analysis; a measurement on the target can refute that analysis, but does not by itself establish a maximum.
> * *Deadline detection.* Where a configuration establishes J, a missed deadline is counted and visible at the latest D + 2L + resolution + J after the last true arrival (`+req~ssr-qos-deadline~4+`). The arrival latency L is the binding's declared one, including the time a recording thread can be preempted between reading the clock and storing the arrival, which the configuration's execution model bounds. The application's later read adds its own delay, outside J, and the item's reaction budget includes it. Where no configuration establishes J, there is no finite detection bound, and the item cannot rely on one.
> * *The monitor's wait bound.* Where a route's monitor uses the one-word tick representation, which at this revision only the model tests do, a thread inside the element waits less than 2^28^ ticks of the shortest-scaled monitored route between reading the clock and storing an arrival or a check: under the watchdog above, `+T_wd+` below 0.27 s when a route uses the shortest admitted threshold (1.024 µs), and below 2.3 minutes at 1 ms. A full-width monitor, the runtime monitor of every current profile, has no such bound (`+req~ssr-atomic-windows~2+`).
>
> The element bounds its work per call in frames and iterations, not in time (`+req~ssr-bound-work~2+`). Execution time belongs to a supported configuration's timing analysis, which its maintainers supply with the package; a measured maximum is evidence that can refute that analysis, not a bound by itself. Default mode remains permissive and refuses no route solely for lacking a deadline. In strict mode every ASIL receive route declares a deadline or an explicit `+event_only()+`, with its absence of deadline-based silence and delay detection, and a receive route on the E2E wire does at every level; the Enforce state refuses one that declares neither. The report lists each route's detection bound, with J where its configuration establishes J and otherwise the statement that none is established, and its TTL, against the reaction budget the integrator declares for it, and, where a configuration's representation needs them, each transport's servicing and watchdog bounds; the Enforce state refuses a route that requires a finite detection bound its configuration does not establish, a route whose bound exceeds its declared budget, and a declared servicing period longer than its transport's bound.

## Integrator actions

The integrator SHALL complete and retain the following checklist for the item:

- [ ] For each route the item relies on within a time, record the supported configuration and package version, the claimed endpoint and its bound (D, L, resolution and J where established), the item reaction interval, TTL, wait bound, counter-read period and application reaction time. Keep scheduling, priorities, affinity, CPU and interrupt load inside the package's envelope. Worst-case execution time comes from the package's timing analysis; target measurements can refute it, not replace it; iteration bounds are not time bounds.
- [ ] Include TTL rounding (whole milliseconds plus the extra millisecond in the quoted requirement), synchronized clock error and the early expiry of IDs made while the clock was unreadable, by up to the outage and, for a generator that keeps the last good time only to 64 ms, by up to 64 ms more. Do not rely on those proposed ID/TTL details until the corresponding implementation is qualified.
- [ ] Only where a configuration keeps the predecessor narrowed values (no current profile does; the narrowed-value requirement records each profile's representation), supervise every calling thread, establish T_wd × per-slot reuse rate < 2^28 and T_wd × per-peer-entry reuse rate < 2^22, and restart the whole memory-owning unit before a stalled thread can resume, covering stale expire/fail_older/retire work. Whatever the representation, bound ready-queue producer stalls where the item relies on those frames within a time.
- [ ] Only where a route's monitor uses the one-word tick representation (only its model tests do at this revision), check its inequalities separately: every in-element observation-to-store delay < 2^28 ticks of the shortest-scaled route; route servicing at least once per 2^29 ticks. Convert ticks to time from the actual implementation configuration; the quoted 0.27 s and 2.3 min examples are not target measurements. A full-width monitor has neither inequality.
- [ ] Budget middleware lock contention, frame release, retries, notification failures and fail-silent routes. Every safety-related receiver whose safety reaction depends on detecting silence must declare a deadline. Qualified peer-specific progress checks complement aggregate monitoring; they do not substitute for that deadline duty. An explicitly event-only route supplies no deadline-based silence/delay detection.
- [ ] Treat a refused RPC response as one refused copy: its slot is given back to await another response, and a later acceptable response or protected final refusal answer can complete the call. Only if neither completes it does TTL provide the outcome. Include unprotected Streamer errors in this budget; verify that behavior on the implementing release.
- [ ] Where no configuration establishes J for a route, record that the route has no finite detection bound and that the item does not rely on one; keep its functional monitoring.

## Violation manifestations

The item may react too late despite bounded per-call work. Where narrowed values or a one-word monitor remain, a missed service or watchdog window can invalidate wrap/reuse assumptions. Queue traffic can continue while useful work is starved; lock delays can consume the reaction budget.

## Detection limits

Without a supported configuration's timing package, the SDK establishes no WCET, scheduler guarantee or finite J. Aggregate queue-arrival deadlines do not prove application consumption or each peer’s progress. An event-only declaration supplies no deadline-based silence/delay detection. The quoted default/strict/monitor behavior includes unimplemented requirements.
