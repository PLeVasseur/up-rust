== Best Current Practices (BCPs)

The following section will elaborate on the best practices we (the contributor community) will apply to each repositories in the Eclipse-uProtocol project. 

* Projects that are intended to be used in production *MUST* adhere to BCPs listed below. 

If the project is _not_ intended to be used for production:

* *MUST* clearly labeled in your repos README.adoc as `NOT INTENDED FOR PRODUCTION USE`


=== Code Reviews
Code reviews *MUST* be performed by at least one committer before a pull request can be merged.

Reviewers *SHOULD* make suggestions in lieu of comments, for issues found in a pull request following https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request[GitHub's guidelines].


=== Commits & Pull Requests
Below are the requirements for a commit (or set of commits) to be merged into the main branch:

* Commit messages and pull request descriptions, *MUST* contain a well described summary description followed by detailed description of the change
* New features/functions *SHOULD* have an associated GitHub issue linked in the pull request
* Developer facing API *MUST* have full descriptive documentation
* Non-developer facing APIs, *SHOULD* have full descriptive documentation
* *SHOULD* have 100% test coverage
* *MUST* update the projects README.adoc if any of the instructions to build or use the software has changed
* Pull Requests *MUST NOT* be merged till all reviewer's comments and/or suggestions have been acknowledged by the commit author or reviewer, either by accepting, rejecting (with explanation), or filing a separate issue for unresolved comments and/or suggestions.


=== Repositories
The following are BCPs for newly created repositories under the Eclipse-uProtocol project:

* GitHub actions *MUST* be used to create CI/CD workflows for validating build, test, and documentation for every pull request for main branch
* "Branch Protection Rules" *MUST* be enabled with the minimal settings below (replace `verify-pr` for the target that runs the build, test, and documentation workflows):

```
branch_protection_rules: [
        orgs.newBranchProtectionRule('main') {
          required_approving_review_count: 1,
          required_status_checks+: [
            "verify-pr"
          ],
        },
      ],
```
* Release *MUST* follow http://semver.org requirements and begin with `v0.1.0-dev`. Each subsequent release will have the `MAJOR`, `MINOR`, and `PATCH` number incremented following semver requirements 

* Initial commit *MUST* include the following legal documents:
** `LICENSE` *MUST* be Apache 2.0 or Eclipse Public License 2.0 (_see why below_)
** `CONTRIBUTING.adoc` *MUST* link to https://github.com/eclipse-uprotocol/up-spec/CONTRIBUTING.adoc
** `CODE_OF_CONDUCT.adoc` *MUST* link to https://github.com/eclipse-uprotocol/up-spec/CODE_OF_CONDUCT.adoc
** `README.adoc` *MUST* Clearly document how to build and use your software
** `SECURITY.adoc` *MUST* link to https://github.com/eclipse-uprotocol/.github/SECURITY.adoc

* *SHOULD NOT* contain `CONTRIBUTORS.adoc` as the information can be fetched from the git history

If `NOTICE` information cannot be autogenerated:
* *MUST* include `NOTICE.adoc`

* *SHOULD* have a software testing framework (tools) that can measure test code coverage (ex. jacoco, gtest, ctest, etc...)

=== Tracing Requirements

A repository that implements the specification can use link:https://github.com/itsallcode/openfasttrace[OpenFastTrace] (OFT) to make sure that it covers the requirements of the specification that are relevant for its component (xref:README.adoc[the specification's README], "Tracing Requirements").
The link:https://github.com/eclipse-uprotocol/ci-cd[uProtocol CI/CD repository] contains a reusable GitHub Action workflow for tracing requirements which can be used for that purpose. The link:https://github.com/eclipse-uprotocol/up-rust[uProtocol Rust Language Library] also makes use of this workflow in its nightly build and can serve as a blueprint.

=== Why Apache 2.0 and not MIT?

The Apache 2.0 License and the MIT License are both popular open-source licenses, but they have some differences in terms of their requirements and provisions. Here are the key distinctions:

* *Scope:* The Apache 2.0 License is more comprehensive and covers patents, trademarks, and attribution requirements, while the MIT License is simpler and primarily focuses on copyright.

* *Patent Grant:* The Apache 2.0 License includes a patent grant (its section 3): each contributor grants a license for the patent claims, licensable by that contributor, that its contribution necessarily infringes, alone or combined with the work to which it was submitted. That license ends for a licensee who files patent litigation, including a cross-claim or counterclaim, alleging that the work or a contribution in it infringes a patent. The MIT License does not include a specific patent grant.

* *Redistribution:* Both licenses allow for the redistribution of the software. The Apache 2.0 License sets conditions on it (its section 4): a redistributor gives recipients a copy of the license; marks each file that it modified with a prominent notice of the change; keeps, in the source form of a derivative work, the copyright, patent, trademark and attribution notices of the source form of the work that pertain to the derivative work; and, where the work includes a `NOTICE` file, includes in each derivative work that it distributes a readable copy of the attribution notices of that file that pertain to that derivative work, in one of the places that section 4 names.

* *No copyleft:* Both licenses are permissive. Neither requires modifications or derivative works to be licensed under the same license: section 4 of the Apache 2.0 License lets a licensee provide additional or different license terms for its own modifications, or for a derivative work as a whole, provided that its use, reproduction and distribution of the work otherwise comply with the license.

* *Compatibility:* Both licenses are generally considered compatible with other open-source licenses.

== Changing contract-family requirements and safety pages

Items of the up-rust SEooC requirement family (`+req~ssr-*+` and `+aou~seooc-*+`) and the owned-frame SDK contract (`+req~sdk-owned-frame-*+`) are filed by responsibility across `basics/`, `up-l1/`, `up-l2/` and `languages/`, with contract-family governance in xref:contract-generations.adoc[Which requirements an implementation follows] and assurance views, profiles and element boundaries in xref:safety/README.adoc[Safety and Assurance View].
Items of the up-rust SEooC requirement family are written and read by the conventions of xref:safety/README.adoc[Safety and Assurance View].
This section says what a contributor to the specification does to keep those conventions.
It binds the contributors and committers of this repository, and no implementation.

=== Statements, allocations and verification lines

* A new or revised statement *MUST* name the actor that answers for each of its duties, with every condition, qualifier and exclusion, and *MUST* state each duty with a key word (xref:contract-generations.adoc#req-ssr-requirements-bind[A requirement binds the actors to which it gives a duty]; xref:contract-generations.adoc#req-ssr-item-reading[How an item is read]).
A clause that only defines a term carries no key word.
* The "Allocated to" line of a requirement *MUST* agree with its statement, and *MUST NOT* introduce a part, a condition, a qualifier or an exclusion that the statement lacks.
A disagreement between the statement and the line is a defect of the requirement, and *MUST* be corrected by a reviewed change of the specification.
* The "Verification" line of a requirement *MUST* name one or more methods of the vocabulary and no other method, and *MUST NOT* state a duty (xref:safety/assurance.adoc#req-ssr-verification-methods[The verification methods, and what a Verification line asks for]; xref:contract-generations.adoc#req-ssr-item-reading[How an item is read]).
Where a method cannot show a duty of the statement, the line *MUST* be changed, in a reviewed change, to a method that can: the duty is not waived, and the requirement is not recorded as verified.
* A duty, a permission, a condition or a definition that an item relies on *MUST* stand in an item's statement.
A table, an index or a summary *MUST NOT* restate a duty: it links to the item under its title, or it is a labelled worked example that adds no duty.
* Text that refers to an item *MUST* link to the item's anchor, which is its type and name without its revision, and the text of the link *MUST* be the item's title.
A replacement names the earlier revision that it replaces as "revision N of" a link to the item, or of "this item".
An item of a protocol chapter that has no anchor or no title is named by its identifier, with its revision, beside a link to its page.
* One requirement that is specific to a binding may name several accepted instances of that binding's middleware panic paths, each with its own scope and bounds; instances whose applicability or verification differs are best stated in requirements of their own.
* No item gives software a duty to change the specification.
A rule on the specification's own text belongs in this section.

These rules bind the specification's contributors and committers, and no part: each item keeps only the rule of reading that they protect.

=== Revisions and replacements

* An item's name *MUST NOT* be changed or reused, and an item that is filed in another part or file keeps its name and its revision.
* A change of an item's meaning *MUST* raise its revision by one.
A change of wording that provably keeps the meaning keeps the revision, and where that cannot be shown, the revision rises.
A repair that only brings a requirement's statement and its "Allocated to" line into agreement, and changes nothing that the requirement binds, keeps the revision.
* A change that gives a duty to another actor, or that retires a duty, *MUST* name the rule that it replaces, reallocates or retires, the actors that the rule bound, and the implementations and the behaviour for which it does so, which is what a replacement names under xref:contract-generations.adoc#req-ssr-contract-transition[What a part declares and claims, and when a replacement takes effect]; so *MUST* a change after which an item no longer gives a duty to an actor to which its earlier revision gave one.
A duty that moves to another item, for an actor to which both revisions of the item that it leaves give a duty, needs no such sentence.
No duty is retired by being left out of a new revision.
* When an item's meaning changes, each item that links to it *MUST* be read again against the new text.
When the meaning or the default scope of a verification method changes, each "Verification" line that names the method *MUST* be read again.

=== Filing, tags and tracing

* A new item is filed where xref:safety/README.adoc#layout[the responsibility-led filing layout] places it across `basics/`, `up-l1/`, `up-l2/`, `languages/`, `contract-generations.adoc` and `safety/`.
* A requirement carries the tag of each part to which its statement gives a duty, and `SafetyBindingPull` as well where its statement holds a duty of pull bindings only; a shared governance or family-wide item carries the tags of the parts that rely on it; an assumption of use carries `SafetyManual`.
A binding or a wire gets a tag of its own with the first item that is allocated to it alone, and a language-agnostic safety requirement, if one is added, gets a tag of its own.
A tag decides nothing about whom an item binds (xref:safety/README.adoc#tags[Tags]).
* No item of the up-rust SEooC requirement family links to a classic protocol-chapter item through OFT, so that classic protocol-chapter items gain no coverage obligation from the up-rust SEooC requirement family.
* An item gets a repository's gate tag once that repository covers it with at least one coverage link of each type that the item needs.
* A change of the specification that defines, gates or refiles an item *MUST* land before a repository that covers the item tags it, or names the part that now holds it.
How a covering repository then moves its copy of the specification, and records which change it copied, is stated in that repository's trace record.

=== Sources and rationales

* A rationale gives the reason for the rule as it stands.
It *MUST NOT* state a duty, recount earlier revisions or report the state of an implementation.
* A rationale or a source note cites only public sources: the specification, public standards by part and clause number, and the published documents and code of other projects, each at an exact revision or edition, with the place in it.
It *MUST NOT* cite the code of an SDK that implements the item.
* Where a rule or a contract-affecting definition relies on an external source, its item *MUST* keep a source note that names the exact file or document, its revision or edition, and the place in it.
A verbatim quotation, a copied table, a comparison of sources, a measurement and a pin of evidence or of an implementation of the item are kept outside the specification; the revision that a source note names is no such pin.
* ISO 26262 is cited by part and clause number only, in the edition that xref:safety/README.adoc[Safety and Assurance View] names.
No text of the standard is quoted or closely paraphrased, and no table maps it.
* Decisions, reviews, evidence results, delivery status and an item's history are kept outside the specification.

=== The owned-frame SDK contract

Items of the owned-frame SDK contract (xref:contract-generations.adoc#owned-frame-conventions[Owned-frame SDK conventions and tags]) are filed by responsibility across `basics/`, `up-l1/` and `up-l2/` and follow the same rules for statements, allocation, verification lines, revisions, replacements, links, sources and rationales, with the differences that those conventions state: its items are requirements only, carry no ASIL line and use the tags `OwnedFrameSdk`, `OwnedFrameProvider` and `OwnedFrameScheduler`.
