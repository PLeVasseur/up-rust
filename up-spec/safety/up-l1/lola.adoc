[[lola]]
== LoLa

NOTE: LoLa is the `+mw::com+` communication middleware of Eclipse S-CORE, in the repository https://github.com/eclipse-score/communication[`eclipse-score/communication`].

* *One revision.*
The facts that this page states about LoLa are taken from LoLa's own published documents at commit `72fe936e4d1e091181134ebdb8dbfed7f6574dc9` of that repository, and describe that revision.
The binding's qualification record states the revision of LoLa that the binding is built against, and governs for it (xref:bindings.adoc#req-ssr-binding-readme[A binding's qualification record states its limits and its failures]).
* *Facts and duties.*
A fact about LoLa is what those documents say.
It is no duty of the binding and no promise of this specification: the duties are those that the items state.
* *Qualification.*
LoLa's README states that the safety qualification of its elements is not provided (https://github.com/eclipse-score/communication/blob/72fe936e4d1e091181134ebdb8dbfed7f6574dc9/README.md[`+README.md+` at that commit], section Safety qualification).

[[lola-assumptions]]
=== LoLa's published assumptions of use

LoLa publishes assumptions of use for whoever uses it, and the binding is such a user.
The table lists some of them, each under LoLa's own name for it in https://github.com/eclipse-score/communication/blob/72fe936e4d1e091181134ebdb8dbfed7f6574dc9/score/mw/com/dependability/safety_analysis/aou.trlc[`+aou.trlc+` at that commit], and names what it meets here.
The second column says in this page's words what the assumption states, and for some what LoLa's note to it adds.
LoLa's own text governs what an assumption means: the last column says what the binding does about it.
The table is no list of all that LoLa publishes: <<req-ssr-binding-lola-assumptions,The LoLa binding keeps each of LoLa's assumptions of use, or names who does>> requires the binding to keep, or to name who keeps, every one of LoLa's assumptions of use that applies to it.

[cols="3,5,4",options="header"]
|===
| LoLa's assumption | What it states, in this page's words | What it meets here

| `+OneProducerOnlyOneAllocateePtr+`
| At any time, a producer instance is to hold only one loan for each event
| <<req-ssr-binding-lola-assumptions,The LoLa binding keeps each of LoLa's assumptions of use, or names who does>>, "An assumption that limits a route"; <<req-ssr-binding-lola-capacity,On LoLa, a route's counts are declared and its storage is established at setup>>

| `+NoCopySendWhileHoldingAllocateePtr+`
| `+Send(const& value)+` is not to be invoked while a loan is held
| <<req-ssr-binding-lola-assumptions,The LoLa binding keeps each of LoLa's assumptions of use, or names who does>>, "What the binding keeps itself"; xref:payload-paths.adoc#req-ssr-payload-written-once[A payload is written once, into the storage that carries it]

| `+CheckForAllocationError+`
| Whether `+Allocate()+` returns an error is to be checked. Where it returns one, the system is to go to a safe state. LoLa's note calls such an error non-recoverable, and a sign of an issue in the memory control
| <<req-ssr-binding-lola-assumptions,The LoLa binding keeps each of LoLa's assumptions of use, or names who does>>, "An error that LoLa calls non-recoverable"; xref:../seooc-up-rust/assumptions-of-use.adoc#aou-seooc-application-reacts[The application reacts to what the element reports]

| `+EventSubscriptionActiveWhileHoldingSamplePtr+`
| `+Unsubscribe()+` is not to be called on a proxy event while any sample that it provided is still held, and the proxy of that proxy event is to be kept alive, because destroying the proxy would unsubscribe. LoLa's note gives the reason: unsubscribing invalidates the memory that such a sample points to
| <<req-ssr-binding-lola-sample-lifetime,On LoLa, no subscription ends while one of its samples is held>>

| `+SkeletonAliveWhileItsAllocateePtrBeingUsed+`
| A skeleton is to be kept alive while any loan that it returned is used. LoLa's note gives the reason: destroying the skeleton invalidates the memory that such a loan points to
| <<req-ssr-binding-lola-assumptions,The LoLa binding keeps each of LoLa's assumptions of use, or names who does>>, "What the binding keeps itself"; xref:bindings.adoc#req-ssr-binding-lent-storage[Lent storage is exclusive, disjoint and stable for as long as it is held], "A transmit loan"

| `+ValidityOfPointerOnLoLaPointer+`
| No pointer into the memory of a loan or of a received sample is to be used once the loan or the sample is no longer valid. LoLa's note: such memory is then unmanaged, and any access to it is undefined behaviour
| xref:lola-envelope.adoc#req-ssr-binding-lola-envelope-lifetime[On LoLa, a loan exposes only its payload, and a receive view lives within its sample]; xref:bindings.adoc#req-ssr-binding-lent-storage[Lent storage is exclusive, disjoint and stable for as long as it is held]

| `+NoneTerminatingCallbacks+`
| No callback that is passed to LoLa for invocation is to throw. LoLa's note: a callback that throws makes the behaviour undefined
| <<req-ssr-binding-lola-foreign-boundary,Nothing unwinds across the LoLa binding's boundary, and a termination path is a panic path>>, "The boundary"

| `+ValidCallbacksWhileProxyAlive+`
| Every callback that is passed to LoLa is to be valid for as long as its proxy is alive
| <<req-ssr-binding-lola-callbacks,What the LoLa binding gives LoLa stays valid for as long as LoLa can use it>>. The assumption is a minimum: it says for how long a callback stays valid at least, and it names no point after which LoLa no longer uses one

| `+NoStaticContextSupport+`
| LoLa is not to be used in a static context in {cpp}
| <<req-ssr-binding-lola-assumptions,The LoLa binding keeps each of LoLa's assumptions of use, or names who does>>, "What the binding keeps itself": the assumption is about the binding's own {cpp} code. It says nothing about how long a callback is used, and nothing about what LoLa's threads do when a process ends

| `+NoGuaranteeOnExecutionTime+`
| No execution time is guaranteed for any function call that LoLa provides
| <<aou-seooc-lola-assumptions-kept,A deployment on LoLa keeps the assumptions of LoLa that the binding names for the integrator>>; xref:../seooc-up-rust/assumptions-of-use.adoc#aou-seooc-timing-budgets[Timing claims rest on a supported configuration, and the item's budgets are the integrator's]

| `+NoApisFromImplementationNamespace+`
| Nothing in LoLa's implementation namespace is to be called directly, and no type in it is to be used directly. LoLa gives `+impl+` as an example of that namespace
| <<req-ssr-binding-lola-assumptions,The LoLa binding keeps each of LoLa's assumptions of use, or names who does>>, "What the binding keeps itself": the assumption is about the binding's own calls
|===

[[req-ssr-binding-lola-terms]]
== What LoLa, the LoLa binding, a loan and a sample are

[.specitem,oft-sid="req~ssr-binding-lola-terms~1",oft-title="What LoLa, the LoLa binding, a loan and a sample are",oft-needs="uman",oft-tags="SafetyLola"]
--
*LoLa.*
LoLa is the shared-memory communication middleware that <<lola>> identifies.

*The LoLa binding.*
The LoLa binding is the binding that adapts the element to LoLa (xref:bindings.adoc#req-ssr-binding-scope[What a binding is, and the binding contract]).
Where an item that names the LoLa binding speaks of what LoLa publishes, provides or does, it speaks of the revision and the configuration of LoLa that the binding is built against, which the binding's qualification record states (xref:bindings.adoc#req-ssr-binding-readme[A binding's qualification record states its limits and its failures]).

*A sample.*
A _sample_ is the storage of one value of an event in LoLa's shared memory.
A producer obtains it from LoLa, writes it and sends it, and LoLa then provides it to each consumer that subscribes to the event.
On the LoLa binding one sample carries one frame (xref:lola-envelope.adoc#req-ssr-binding-lola-envelope-layout[On LoLa, a frame is one envelope in one sample, in a fixed order]).

*A loan.*
A _loan_ is a sample for as long as a producer holds it in order to write it: from the moment LoLa provides its storage, which the producer holds through LoLa's `+AllocateePtr+`, until the binding sends it or gives it back.

*A received sample.*
A consumer holds a received sample through LoLa's `+SamplePtr+`, from the moment LoLa provides it until the binding has returned it to LoLa (<<req-ssr-binding-lola-sample-lifetime,On LoLa, no subscription ends while one of its samples is held>>).
--

*Rationale.*
The items of the LoLa binding speak of loans and samples, and these words tie them to LoLa's own types.
LoLa's assumptions of use speak of a producer that holds the storage of an event's sample through an `+AllocateePtr+`, and of a proxy event that provides each received sample through a `+SamplePtr+` (source: `+aou.trlc+` at the commit that <<lola>> names, the assumptions `+OneProducerOnlyOneAllocateePtr+`, `+SkeletonAliveWhileItsAllocateePtrBeingUsed+`, `+EventSubscriptionActiveWhileHoldingSamplePtr+` and `+ValidityOfPointerOnLoLaPointer+`).

[[req-ssr-binding-lola-profiles]]
== The LoLa binding carries native and serialized routes, each as itself

[.specitem,oft-sid="req~ssr-binding-lola-profiles~3",oft-title="The LoLa binding carries native and serialized routes, each as itself",oft-needs="impl,utest",oft-tags="SafetyLola"]
--
*Two kinds of route.*
The LoLa binding *MUST* be able to carry both kinds of route, and it *MUST* lend LoLa's storage for both:

* a _native_ route, on which a sender initializes its payload in a loan and a receiver reads the payload in the sample that holds it (xref:native-wire.adoc#req-ssr-native-in-place[A native payload is written and read where it is carried, or its route is refused]);
* a _serialized_ route, on which a wire encodes into a loan and decodes from the sample (xref:serialized-wires.adoc#req-ssr-wire-encode-decode[A serialized wire encodes once into the storage it is given, and decodes into a value that its slot owns]).

*Preparation.*
For each declared route the binding *MUST* compare what the route declares with the capability that the binding declares: the payload's bound and its alignment, the counts and the QoS settings (xref:bindings.adoc#req-ssr-binding-qos-capability[A binding honors or refuses each declared setting]; <<req-ssr-binding-lola-capacity,On LoLa, a route's counts are declared and its storage is established at setup>>).

* Where its capability serves all of it, the binding *MUST* prepare the route as it is declared.
What the element then admits is stated in xref:payload-paths.adoc#req-ssr-payload-route-form[A route's form is fixed at setup, by what the route declares and never by a name].
* The heap class that the binding states for the route, and the element's comparison of it with what the route declares, are stated in xref:../seooc-up-rust/heap.adoc#req-ssr-heap-declared[The heap class is declared, with no default].
* The binding *MUST* declare the class none for a route only where accepted evidence in its qualification record covers both the binding's and LoLa's runtime paths that the route uses, and shows that neither acquires or releases heap memory on them (xref:bindings.adoc#req-ssr-binding-readme[A binding's qualification record states its limits and its failures]).
That evidence covers the first locks and the lazy primitives of LoLa that those paths can reach.
Without that evidence the binding *MUST* declare allocation inside LoLa under a named permit.
The waiver that then admits the route is stated in xref:../seooc-up-rust/waivers.adoc#req-ssr-waiver-required[Middleware heap needs a named waiver].
A permit changes neither xref:bindings.adoc#req-ssr-binding-no-heap[Binding code allocates nothing in runtime mode on a native path] nor the allocation that a serialized route declares and that setup admits, and it establishes no stronger guarantee (xref:../seooc-up-rust/heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name, and admitted or refused]).
* Where the route needs a capability that the binding or LoLa does not have, the binding *MUST* refuse the route in route preparation, naming the route and that capability.

*LoLa's first locks and lazy state.*
The first locks and the lazy primitives of LoLa that a runtime path of the binding can reach are taken and forced, on every route, as xref:bindings.adoc#req-ssr-binding-lazy-forced[Lazy state is forced, and threads are idle, before running] requires.

*What is a reason to refuse.*
A reason is always something that the route declares and that the binding, or LoLa, does not have.
The reasons are those that the items of the binding contract and the requirements that are specific to the LoLa binding state, those of xref:lola-envelope.adoc[the LoLa physical envelope] included.
Among them are:

* a payload bound or an alignment that LoLa's storage for the route does not hold, or a payload alignment that the binding cannot establish in every mapping of a sample (xref:lola-envelope.adoc#req-ssr-binding-lola-envelope-layout[On LoLa, a frame is one envelope in one sample, in a fixed order]);
* a count or a QoS setting that the binding does not serve;
* a limit that follows from an assumption of LoLa (<<req-ssr-binding-lola-assumptions,The LoLa binding keeps each of LoLa's assumptions of use, or names who does>>);
* storage that the binding cannot establish (<<req-ssr-binding-lola-capacity,On LoLa, a route's counts are declared and its storage is established at setup>>), or cannot keep as lent storage has to be kept (xref:bindings.adoc#req-ssr-binding-lent-storage[Lent storage is exclusive, disjoint and stable for as long as it is held]);
* a writer's level below the level that the service records (xref:bindings.adoc#req-ssr-binding-integrity-level[A lending binding records and reports the writer's level]).

The element's own setup checks, and their reasons, are stated in xref:payload-paths.adoc#req-ssr-payload-route-form[A route's form is fixed at setup, by what the route declares and never by a name].

*A setup operation that fails.*
An operation that route preparation needs from LoLa or from the operating system can fail for a cause that is no capability of the route.
The binding *MUST* report such a failure as a failure of setup, naming the route and the operation that failed, and *MUST NOT* report it as a capability that the route lacks (xref:../seooc-up-rust/runtime-modes.adoc#req-ssr-mode-init-failure[Initialization failure]; xref:../seooc-up-rust/runtime-modes.adoc#req-ssr-mode-bounded-startup[Setup never waits without a bound]).

*Excluded reasons.*
The binding *MUST NOT* admit, refuse or change a route because of the name of its wire or of its payload encoding.
It *MUST NOT* refuse a serialized route because its wire declares allocation, or because its decoded values own heap memory (xref:../seooc-up-rust/heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name, and admitted or refused]).

*Native routes.*

* The binding *MUST NOT* serve a route that is declared native by a serialized encoding, by a staged copy or by storage that LoLa did not lend.
* The binding *MUST NOT* report or count a copied or serialized route as a native one.

*A serialized route's allocation.*
The binding *MUST NOT* let what a serialized route allocates reach a native route on the same transport, or work that the two share (xref:../seooc-up-rust/heap.adoc#req-ssr-heap-declared[The heap class is declared, with no default]).

*What each route got.*
What each route's report states is stated in xref:../seooc-up-rust/errors.adoc#req-ssr-error-route-report[Each route reports what it got], and how a refusal is reported in xref:payload-paths.adoc#req-ssr-payload-route-form[A route's form is fixed at setup, by what the route declares and never by a name] and xref:integrity.adoc#req-ssr-integrity-zero-copy[Zero-copy only from a writer at or above the reader].
--

*Rationale.*
A deployment on shared memory mostly sends values as they lie in memory, and it also carries serialized messages on the same transport.

_Capability and declarations._
To be able to carry both kinds of route is the binding's capability.
Whether one declared route is carried depends on what that route asks: a payload that is larger than LoLa's storage for it cannot be carried, whichever wire wrote it.
A wire that allocates asks nothing of LoLa's storage that a binding could lack.

_Choice of wire._
Which wire a message uses is decided where the message is declared, and the same wire runs on another transport (xref:payload-paths.adoc#independent[a wire and a transport are chosen apart]).
A binding that admitted routes by the name of a wire would tie the two together.

_Genuine native routes._
A native route that was served by a copy would still deliver correct values, and nothing in a test of values would show the difference.
Its resource behaviour would differ, and a deployment that relies on a route being native relies on that behaviour.

[[req-ssr-binding-lola-capacity]]
== On LoLa, a route's counts are declared and its storage is established at setup

[.specitem,oft-sid="req~ssr-binding-lola-capacity~2",oft-title="On LoLa, a route's counts are declared and its storage is established at setup",oft-needs="impl,utest",oft-tags="SafetyLola"]
--
*The counts.*
For each route that it prepares, the LoLa binding *MUST* declare to the element, each as what it is:

* on a transmit route, how many loans the route can hold at once, a loan whose lease safe code forgot included;
* on a receive route, how many samples the route can retain at once, a sample whose return is pending and one whose lease safe code forgot included;
* how many samples LoLa keeps for the route, and what happens to a new sample when they are all in use.

*What each count states.*
Each count is declared as xref:bindings.adoc#req-ssr-binding-qos-capability[A binding honors or refuses each declared setting], "What a declaration says", requires.
For each count the binding *MUST* also state the setting or the storage of LoLa that the count is taken from.
It *MUST NOT* present one of the three counts as another.

*Established at setup.*
Before its transition returns, the binding *MUST* establish that the storage which LoLa provides for a route holds what the route declares, as an amount that the binding guarantees to be available to the route.
An upper limit does not meet what a route declares.
Where that storage does not hold it, or where the binding cannot establish it, the binding *MUST* refuse the route in route preparation, naming the route, the count and the values it found (xref:../seooc-up-rust/runtime-modes.adoc#req-ssr-mode-entry-no-latent-refusal[Nothing is refused at runtime for a reason setup already knew]).

*A count that an assumption of LoLa limits.*
A limit that an assumption of use of LoLa sets on a count, such as the number of loans that a producer holds at once for one event, is declared and kept as <<req-ssr-binding-lola-assumptions,The LoLa binding keeps each of LoLa's assumptions of use, or names who does>> states.

*In runtime mode.*

* The binding *MUST NOT* obtain more storage from LoLa.
* The binding *MUST* return an error for a request beyond a route's count, and *MUST* decide it from its own count, without asking LoLa for the storage (xref:../seooc-up-rust/errors.adoc#req-ssr-refuse-before-heap[Refuse before touching the heap]).
* What a full route does with a new frame is its declared overflow policy.
The binding honors that policy, or it refused the route at setup (xref:../seooc-up-rust/qos.adoc#req-ssr-qos-overflow[Overflow acts as declared]; xref:bindings.adoc#req-ssr-binding-qos-capability[A binding honors or refuses each declared setting]).
--

* *test*
** A route that needs more than the binding declares, refused in route preparation by name.
** LoLa configured with less storage than a route declares, refused in route preparation with both values.

** A route whose declared overflow policy the binding cannot honor: refused at setup.
* *review*: how the binding establishes LoLa's storage for a route, and where each declared count is taken from, at source level.

*Rationale.*
A route that runs out of storage in runtime mode cannot get more there, so the storage is settled before the transition (xref:../seooc-up-rust/runtime-modes.adoc#req-ssr-mode-no-setup-at-runtime[Setup is impossible in runtime mode]).
The element computes its own storage from deployment data (xref:../seooc-up-rust/startup-memory.adoc#req-ssr-memory-computable[Startup storage is computable before start]).
The storage that LoLa provides is LoLa's, and only the binding can compare it with what a route needs.

_Each count as what it is._
A number of loans, a number of retained samples and a number of samples that LoLa keeps are three figures, and a deployment sizes each of them (xref:../seooc-up-rust/assumptions-of-use.adoc#aou-seooc-capacity-sizing[Capacities are sized for the worst case]).
An amount that is guaranteed to be available and an upper limit are different promises.
A report that gave one for the other would let a deployment size against a number that means something else.

_Count values._
How many loans or samples a route needs is a deployment's choice, and what LoLa serves is a fact of the revision that the binding is built against.

_Exhaustion and an error from LoLa._
LoLa's assumptions of use call an error from `+Allocate()+` non-recoverable (<<lola-assumptions>>, `+CheckForAllocationError+`, its note).
So a route that is merely full is refused from the binding's own count, and the binding never learns it by asking LoLa for one loan more.

[[req-ssr-binding-lola-foreign-boundary]]
== Nothing unwinds across the LoLa binding's boundary, and a termination path is a panic path

[.specitem,oft-sid="req~ssr-binding-lola-foreign-boundary~3",oft-title="Nothing unwinds across the LoLa binding's boundary, and a termination path is a panic path",oft-needs="impl,utest",oft-tags="SafetyLola"]
--
*The boundary.*
LoLa is {cpp} code, and the LoLa binding calls it, and is called back by it, across a language boundary.
The binding *MUST NOT* let a call across that boundary, in either direction, be left by unwinding:

* the binding's {cpp} code *MUST* catch a {cpp} exception that a call into LoLa raises, and return it as an error value;
* Rust code of the binding that LoLa calls back *MUST NOT* panic.

*Errors.*
The binding *MUST* make each error that crosses the boundary a fixed-size value.
The binding *MUST* return it as the refusal of the operation that met it, or count it on its route (xref:../seooc-up-rust/errors.adoc#req-ssr-error-no-silent-loss[No silent loss, and each loss counted once]).
It *MUST NOT* turn it into a panic, and *MUST NOT* drop it.
The binding *MUST* report a result of LoLa that it cannot classify as a failure, and never as the more favourable reading.

*Named results.*
The binding *MUST* give each refusal and each counter that a result of LoLa becomes a name that states its cause.
It *MUST* state in its qualification record which refusal or counter each result of LoLa that it can tell apart becomes (xref:bindings.adoc#req-ssr-binding-readme[A binding's qualification record states its limits and its failures]).

*Termination.*
A path on which LoLa, or the binding's own {cpp} code, ends the process is a panic path under xref:bindings.adoc#req-ssr-binding-no-panic[No panic on any peer input] and xref:bindings.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do]: a call that ends the process, such as one to terminate, to abort or to exit, and an exception that nothing catches.
The LoLa binding has no accepted panic path: no requirement of this area accepts one for it.
Each such path that a peer's input, death or restart can reach is a known failure of the binding.
Where a known failure is stated, and which routes strict mode refuses for it, are stated in xref:bindings.adoc#req-ssr-binding-readme[A binding's qualification record states its limits and its failures] and xref:../seooc-up-rust/build.adoc#req-ssr-strict-ack-revision[An acknowledgement names a deviation by ID and revision].

*Where it holds.*
The binding *MUST* state in its qualification record the builds of its {cpp} code, and the ways of loading it, for which the first two clauses are established (xref:bindings.adoc#req-ssr-binding-readme[A binding's qualification record states its limits and its failures]).
It *MUST* state them as target profiles, each with the operating system and the means by which LoLa's processes notify one another on it, the C library and the {cpp} standard library, the compilers and whether the {cpp} code is built with exceptions, the way the binding's {cpp} code is linked and loaded into the process, and the width of pointers and of atomics.
The binding *MUST NOT* claim either clause for a build, a way of loading or a target that the record does not state, and *MUST NOT* claim a target by the name of an operating system alone.
--

ID:: `+req~ssr-binding-lola-foreign-boundary~3+`
ASIL:: B
Allocated to:: the LoLa binding
Verification:: test, fault-injection, review
* *test*
** An exception injected behind each entry of the boundary that the binding uses: returned as the refusal of the operation that met it, or counted on its route.
** An error value of each kind that the boundary can return, reported under the name of its own cause.
** A result of LoLa that the binding cannot classify, injected behind the boundary: reported as a failure.
* *fault-injection*: malformed frames, and peers killed and restarted, with no termination of a process that stays up.
* *review*
** Each function of the boundary, at source level: what it catches, what it returns, and that nothing it calls back can unwind.
** The termination paths that the binding's calls into LoLa can reach, listed for the revision of LoLa that the binding is built against.
** The qualification record's target profiles, with the builds and the ways of loading of each, and its mapping of LoLa's results to named refusals and counters.

*Rationale.*
The rule of every binding speaks of a panic.
In place of a panic, a middleware written in {cpp} throws, or it ends the process.

_Unwinding._
An unwind from {cpp} code into Rust code through a function declared with a non-unwinding ABI, such as `+"C"+`, is undefined behaviour, and so is a Rust unwind into code that does not support unwinding (source: the Rust Reference, Rust 1.98.1, chapter https://doc.rust-lang.org/1.98.1/reference/panic.html[Panic], section Unwinding across FFI boundaries, rule panic.unwind.ffi.undefined).
Nothing is guaranteed when {cpp} code disposes of or rethrows a Rust panic: only ending the process, or catching the panic in the same Rust runtime, has a defined outcome (source: the same section, rule panic.unwind.ffi.dispose-panic).
LoLa's assumptions of use ask the same of each callback that is passed to LoLa: none is to throw (<<lola-assumptions>>, `+NoneTerminatingCallbacks+`).

_Termination._
A process that LoLa ends is as lost as one that panicked, and xref:../README.adoc#req-ssr-peer-fault-model[The requirements hold against a faulty peer] requires that a faulty peer be able to cause neither.
So a termination path that a peer's input, death or restart can reach is a known failure of the binding, never a limit that a deployment accepts.

_Builds and loading._
Whether an exception that LoLa raises reaches a handler in the binding's {cpp} code depends on how that code and LoLa were built and loaded.
An exception that reaches the outermost block of a function declared not to throw calls `+std::terminate+` before any outer handler is found, and a handler is found only in the thread that raised the exception (source: the {cpp} standard's working draft N4861, {cpp}20, [except.spec] and [except.handle]).
Code built without exception support can keep an exception from passing through it, and between shared libraries, catching an exception depends on how the {cpp} runtime is linked and on the visibility of the exception's type (source: the libstdc++ manual of GCC 15.2.0, chapter Exceptions, section Doing without; the GCC 15.2.0 manual, sections Options for Linking and Options for Code Generation Conventions).
So the binding's qualification record names the builds and the ways of loading for which it is established.

[[req-ssr-binding-lola-sample-lifetime]]
== On LoLa, no subscription ends while one of its samples is held

[.specitem,oft-sid="req~ssr-binding-lola-sample-lifetime~1",oft-title="On LoLa, no subscription ends while one of its samples is held",oft-needs="impl,utest",oft-tags="SafetyLola"]
--
*The rule.*
While any sample that a LoLa subscription provided is still held, the LoLa binding *MUST NOT* end that subscription.
Unsubscribing the proxy event ends it, and so does destroying the proxy event or its proxy.

*Held.*
A sample is held from the moment LoLa provides it until the binding has returned it to LoLa.
That covers:

* a frame that the element or an application retains;
* a frame whose return is pending cleanup (xref:bindings.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do]);
* a frame whose lease safe code forgot, which is held for the life of the process.

*Any sequence of calls.*
The binding *MUST* keep the rule for every sequence of safe calls, in any order and from any thread.
It *MUST NOT* rely on an application returning its frames first.

*In runtime mode.*
A subscription is a binding resource, which stays attached in runtime mode (xref:../seooc-up-rust/release.adoc#req-ssr-release-none[Nothing is released in runtime mode]).
--

[horizontal]
ID:: `+req~ssr-binding-lola-sample-lifetime~1+`
ASIL:: B
Allocated to:: the LoLa binding
Verification:: test, compile-fail, review
* *test*
** A frame held across every operation of the binding that an application can reach, with its subscription still active afterwards.
** A forgotten lease, with its subscription still active and its sample never reused.
* *compile-fail*, or *test* where the sequence compiles: in initialization, a sequence that would end a subscription while a frame is held: it does not compile, or it is refused.
* *review*: every path of the binding that unsubscribes a proxy event or destroys one or its proxy, at source level, against every way a sample can still be held.

*Rationale.*
LoLa's assumptions of use ask that a proxy event not be unsubscribed, and its proxy not destroyed, while a sample that it provided is still held, and LoLa's note gives the reason: unsubscribing invalidates the memory that the sample points to (<<lola-assumptions>>, `+EventSubscriptionActiveWhileHoldingSamplePtr+`, its description and its note).

A frame that the element retains on a native route is a view into that memory (xref:integrity.adoc#req-ssr-integrity-zero-copy[Zero-copy only from a writer at or above the reader]).
If the subscription ended first, safe code would hold a view of invalid memory, which xref:../seooc-up-rust/memory-safety.adoc#req-ssr-unsafe-sound[Safe code cannot cause undefined behaviour] forbids.

LoLa addresses that assumption to its user, and the binding is that user.
An application can hold a frame for as long as it likes, and can forget one.

[[req-ssr-binding-lola-callbacks]]
== What the LoLa binding gives LoLa stays valid for as long as LoLa can use it

[.specitem,oft-sid="req~ssr-binding-lola-callbacks~2",oft-title="What the LoLa binding gives LoLa stays valid for as long as LoLa can use it",oft-needs="impl,utest",oft-tags="SafetyLola"]
--
*The rule.*
The LoLa binding gives LoLa callables that LoLa invokes, and with them the addresses of what those callables use.
The binding *MUST* keep each of them valid until LoLa can no longer use it.

*A no-use point.*
LoLa can no longer use a callable from a _no-use point_: a point that LoLa's own published documentation names, for the revision that the binding is built against, as one after which LoLa neither invokes the callable nor reads it.

* Where LoLa's documentation names a no-use point for a callable, the binding *MUST* keep the callable, and what it uses, valid until that point at least.
* Where it names none, the binding *MUST* keep them valid until the process is gone.

*Excluded points.*

* A statement of how long a callable has to stay valid at least is not one.
It is a minimum, and the binding *MUST* keep it as well.
* What one revision of LoLa is seen to do, in a test or in its source, is not one.

The binding's memory safety *MUST NOT* rest on LoLa giving a callable up at any other point.

*Through exit.*
A process can end while threads of LoLa still run in it.
While any of them can still run, the binding *MUST* keep valid everything that it, or a callable that it invokes, can reach in the binding.
That holds from the moment an exit begins until the process is gone, and it *MUST NOT* depend on the order in which exit handlers and static destructors run.

*What a callable does.*
A callable that LoLa invokes is binding code on a runtime path.
It keeps the rules of that path: it does not unwind (<<req-ssr-binding-lola-foreign-boundary,Nothing unwinds across the LoLa binding's boundary, and a termination path is a panic path>>), and it acquires and releases no heap memory on a native path (xref:bindings.adoc#req-ssr-binding-no-heap[Binding code allocates nothing in runtime mode on a native path]).
The binding *MUST NOT* let a callable that LoLa invokes wait without a bound.
The waits without a finite logical deadline that xref:bindings.adoc#req-ssr-binding-bounded[A binding bounds its own work and its waits] allows other binding work do not extend to such a callable.
--

[horizontal]
ID:: `+req~ssr-binding-lola-callbacks~2+`
ASIL:: B
Allocated to:: the LoLa binding
Verification:: test, heap-window, review
* *test*
** Each callable that the binding registers, invoked after every operation of the binding that an application can reach, with what it uses still valid.
** A process that ends by a return from `+main+`, by a call that exits and by a signal, each while LoLa's threads run and frames are held, under a tool that reports a use of freed or destroyed memory.
** Each callable run by the binding contract suite, with any panic in it failing the suite.
* *heap-window*, on each target and configuration that the binding's qualification record claims: each callable that LoLa invokes on a native path, run by the binding contract suite.
* *review*
** For each callable and each address that the binding gives LoLa, at source level: the no-use point that LoLa's documentation names for it, with its source, or else the process lifetime.
** That no argument takes a minimum for a no-use point.
** Each way the process can end while LoLa's threads can still run, against what they can still reach: exit handlers and the destructors of static objects; the stack destructors that a direct exit does not run; the destruction of thread-local objects; and an exit, a quick exit or a return from `+main+` in Rust code at the same time as one in C or {cpp} code or in another copy of the Rust runtime, against what the binding's own code calls and against <<aou-seooc-lola-assumptions-kept,A deployment on LoLa keeps the assumptions of LoLa that the binding names for the integrator>>, "Exits".
** Each callable's waits, at source level: none without a bound.

*Rationale.*
A callable that LoLa holds is a pointer into the binding that only LoLa decides when to follow.
If what it points to has ended, the next call uses invalid memory, and the application's safe code caused it (xref:../seooc-up-rust/memory-safety.adoc#req-ssr-unsafe-sound[Safe code cannot cause undefined behaviour]).

_The published minimum._
LoLa publishes that every callback passed to it is to be valid for as long as its proxy is alive (<<lola-assumptions>>, `+ValidCallbacksWhileProxyAlive+`).
That is a minimum: it says for how long the binding owes validity at least.
It does not say that LoLa stops invoking a callback when its proxy ends, or at any other point.
None of the assumptions listed on this page names such a point.
So, unless another published document of LoLa names one, the life of the process is the bound, and it is always long enough.

_Exit._
The element offers no shutdown, and a process in runtime mode leaves by exit, crash or kill (xref:../seooc-up-rust/runtime-modes.adoc#req-ssr-mode-no-shutdown[No shutdown in runtime mode]).
An exit runs exit handlers and the destructors of objects with static storage duration, and destroys no object on any thread's stack, while other threads can still run (source: the {cpp} standard's working draft N4861, {cpp}20, [basic.start.term] and [support.start.term]; the standard library documentation, Rust 1.98.1, https://doc.rust-lang.org/1.98.1/std/process/fn.exit.html[`+std::process::exit+`], its description).
A thread of LoLa that then called into state the binding had already destroyed would corrupt the process while it still shares memory with its peers.
So what such a thread can reach outlives it, whatever the order of destruction.
On Unix an exit from Rust code calls the C library's `+exit+`, and the lock with which a copy of the Rust runtime orders its own exits orders neither an exit from C or {cpp} code nor one from another copy of the Rust runtime (source: the standard library documentation, Rust 1.98.1, https://doc.rust-lang.org/1.98.1/std/process/fn.exit.html#safe-interop-with-c-code[`+std::process::exit+`], section Safe interop with C code).
A program that calls `+exit+` more than once has undefined behaviour (source: the C standard's working draft N3096, C23, 7.24.4.4 The exit function).

[[req-ssr-binding-lola-assumptions]]
== The LoLa binding keeps each of LoLa's assumptions of use, or names who does

[.specitem,oft-sid="req~ssr-binding-lola-assumptions~2",oft-title="The LoLa binding keeps each of LoLa's assumptions of use, or names who does",oft-needs="impl,utest",oft-tags="SafetyLola"]
--
*Who keeps each assumption.*
LoLa publishes assumptions of use for whoever uses it, and the LoLa binding is such a user.
For each one that applies to the revision and the configuration of LoLa that the binding is built against, and for each part of it where it asks more than one thing, the LoLa binding *MUST* do one of two things:

* keep it itself;
* state in its README that the integrator keeps it, and what the integrator does for that (<<aou-seooc-lola-assumptions-kept,A deployment on LoLa keeps the assumptions of LoLa that the binding names for the integrator>>).

The binding *MUST NOT* break an assumption that applies, and *MUST NOT* leave one, or a part of one, without a keeper.

*What the binding keeps itself.*
The binding *MUST* keep itself every assumption, and every part of one, that asks something of how its own code calls or uses LoLa, and every one that code of the element or of an application could otherwise break through safe calls.
It *MUST* keep it for every sequence of safe calls, in any order and from any thread, and *MUST NOT* leave it to the order in which an application calls it.

*What the binding names for the integrator.*
The binding *MUST NOT* state that the integrator keeps an assumption, or a part of one, unless it is a condition of the system or of its environment that the binding's code cannot establish, such as supervising time, configuring LoLa's storage, or reacting to a failure that the binding reports.
The binding *MUST NOT* pass an assumption on as a rule about how an application calls the element.

*An assumption that limits a route.*
Where keeping an assumption limits what a route can be served, the binding *MUST* declare the limit as its capability (xref:bindings.adoc#req-ssr-binding-qos-capability[A binding honors or refuses each declared setting]; <<req-ssr-binding-lola-capacity,On LoLa, a route's counts are declared and its storage is established at setup>>), and refuse what exceeds it:

* in route preparation, by name, where the route's declaration shows it;
* as a returned error otherwise (xref:../seooc-up-rust/errors.adoc#req-ssr-refuse-before-heap[Refuse before touching the heap]).

The binding *MUST NOT* serve what exceeds the limit in another way, out of the caller's sight.

*Where a limit applies.*
A limit that follows from an assumption applies to routes on LoLa, for the revision and the configuration to which LoLa applies that assumption.
The binding *MUST* report it as a limit of its own, for that revision and that configuration.
The binding *MUST NOT* report it as a limit of the element, of another binding or of a route on another transport.

*An error that LoLa calls non-recoverable.*
Where LoLa publishes that an error means a failure that its user does not recover from, the binding *MUST* return it to the caller and count it (xref:../seooc-up-rust/errors.adoc#req-ssr-error-no-silent-loss[No silent loss, and each loss counted once]).
It *MUST NOT* retry it out of the caller's sight, and *MUST NOT* report it as a condition that passes, as a route that is briefly full, or as an accepted limit or deviation.

*The README.*
The binding *MUST* list in its README each assumption that applies, under LoLa's own name for it, with who keeps it, or each of its parts, and by what means (xref:bindings.adoc#req-ssr-binding-readme[A binding's qualification record states its limits and its failures]).
--

[horizontal]
ID:: `+req~ssr-binding-lola-assumptions~2+`
ASIL:: B
Allocated to:: the LoLa binding
Verification:: test, compile-fail, review
* *test*
** A limit that follows from an assumption: declared in the binding's capability, refused by name beyond it, and absent from the same route on a test double of another binding.
** An error that LoLa calls non-recoverable, injected behind the boundary: returned and counted once under its own cause, never reported as a route that is briefly full, and not retried.
* *compile-fail*, or *test* where the sequence compiles: for each assumption, or part of one, that the binding keeps itself, a sequence of safe calls that would break it: it does not compile, or it is refused as this item states.
* *review*
** The README's list against LoLa's published assumptions at the revision that the binding is built against, one by one, with the keeper of each part where an assumption asks more than one thing.
** For each assumption, or part of one, that the binding keeps itself, the code that keeps it, at source level.
** For each assumption, or part of one, that the README names for the integrator, that it is a condition of the system or of its environment that the binding's code cannot establish.
** That no assumption is passed on as a rule for an application, and that no path serves in another way what exceeds a limit.
** The qualification record: each limit that follows from an assumption, reported for the revision and the configuration of LoLa to which it applies; and each error that LoLa calls non-recoverable, classed as a failure and never as a limit or a deviation.

*Rationale.*
LoLa addresses its assumptions of use to whoever uses it, as conditions for using it safely.
The binding is that user, so whatever the binding passes on from LoLa to the element holds only while every one of them is kept.

_Who can keep one._
Some assumptions are about how LoLa's interface is called: how many loans a producer holds, or when a subscription ends.
An application reaches LoLa only through safe calls of the element, so only the binding can keep these, and it keeps them whatever the application does.
Others are about the system: that timing is supervised, or what the system does after a failure.
The binding cannot keep those, so it names them for the integrator.
One assumption can ask both: `+CheckForAllocationError+` asks that an error from `+Allocate()+` be checked, which the binding does, and that the system then go to a safe state, which the integrator arranges.
The integrator already reacts to what the element reports (xref:../seooc-up-rust/assumptions-of-use.adoc#aou-seooc-application-reacts[The application reacts to what the element reports]), and the timing budgets of the item, in ISO 26262's sense, are the integrator's (xref:../seooc-up-rust/assumptions-of-use.adoc#aou-seooc-timing-budgets[Timing claims rest on a supported configuration, and the item's budgets are the integrator's]).

_What the binding passes on._
A rule that an application had to follow in order to keep LoLa safe would be a condition of memory safety that safe code could break.
So no assumption reaches an application as a rule: the binding enforces it, or the integrator arranges the system for it.

_Limits on a route._
An assumption can make LoLa serve less than a route asks: one loan at a time, for example (<<lola-assumptions>>, `+OneProducerOnlyOneAllocateePtr+`).
The binding then says so as its capability and refuses the rest.
The limit is LoLa's, at one revision and in one configuration.
The element has no such limit, and another binding, or another revision of LoLa, may serve more.

_An error from allocating._
LoLa's assumptions of use ask that an error from `+Allocate()+` be checked and that the system then go to a safe state, and LoLa's note calls such an error non-recoverable (<<lola-assumptions>>, `+CheckForAllocationError+`, its description and its note).
A binding that retried it, or reported it as a route that is briefly full, would keep the application from the reaction that LoLa asks for.

[[aou-seooc-lola-assumptions-kept]]
== A deployment on LoLa keeps the assumptions of LoLa that the binding names for the integrator

[.specitem,oft-sid="aou~seooc-lola-assumptions-kept~1",oft-title="A deployment on LoLa keeps the assumptions of LoLa that the binding names for the integrator",oft-needs="uman",oft-tags="SafetyManual"]
--
For a deployment that uses LoLa, the integrator *SHALL* keep each assumption of use of LoLa, and each part of one, that the LoLa binding's README states the integrator keeps, by the means that the README states for it (<<req-ssr-binding-lola-assumptions,The LoLa binding keeps each of LoLa's assumptions of use, or names who does>>).

*LoLa's configuration.*
The integrator *SHALL* keep the configuration that LoLa itself reads, the sizes of its storage for a route among it, as xref:../seooc-up-rust/assumptions-of-use.adoc#aou-seooc-deployment-data[Deployment data is in range, verified and protected] states for deployment data.

*Assurance of LoLa.*
LoLa's own documents provide no safety qualification of its elements (<<lola>>).
The integrator *SHALL* establish each assurance claim that it makes over LoLa itself.

*Exits.*
In a process that uses the LoLa binding, the integrator *SHALL* ensure that no exit, quick exit or return from `+main+` in Rust code runs at the same time as one in C or {cpp} code, or in another copy of the Rust runtime, unless a documented guarantee of the C library that the process uses makes such calls safe.
--

*Violation:*

* LoLa storage for a route that holds less than the route declares is *refused at setup* by the LoLa binding, which names the route, the count and the values that it found (<<req-ssr-binding-lola-capacity,On LoLa, a route's counts are declared and its storage is established at setup>>).
* A breach of any other part of this assumption is *undetectable* by the element and by the LoLa binding.

[horizontal]
ID:: `+aou~seooc-lola-assumptions-kept~1+`
ASIL:: B

*Rationale.*
LoLa addresses its assumptions of use to its user.
The binding keeps those that its own code can keep, and the others are conditions of the system, which only the integrator can arrange.
An assumption, or a part of one, that the binding names for the integrator has a keeper only where an assumption of use binds the integrator to keep it.

_Exits._
The binding keeps valid what LoLa's threads can reach through an exit, but no binding keeps memory valid through undefined behaviour, and two exits that run at the same time without synchronization are undefined behaviour (<<req-ssr-binding-lola-callbacks,What the LoLa binding gives LoLa stays valid for as long as LoLa can use it>>, its rationale "Exit").
Which code of a process can call an exit, and how many copies of the Rust runtime a process holds, are decided where the process is built and integrated, which the binding's code cannot establish.
