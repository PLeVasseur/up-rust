= uP-L1 safety: Allocated to each binding
:toc: preamble

The key words "*MUST*", "*MUST NOT*", "*REQUIRED*", "*SHALL*", "*SHALL NOT*", "*SHOULD*", "*SHOULD NOT*", "*RECOMMENDED*", "*MAY*", and "*OPTIONAL*" in this document are to be interpreted as described in https://www.rfc-editor.org/info/bcp14[IETF BCP14 (RFC2119 & RFC8174)]

Conventions and tags: xref:../README.adoc[the safety area's README].
This layer, and whom its items bind: xref:README.adoc[safety at uP-L1].
The element whose contract these duties belong to: xref:../seooc-up-rust/README.adoc[the up-rust SEooC's README].

These requirements give duties to every binding, or to every binding of one kind; requirements filed elsewhere in this area give a binding duties too (xref:README.adoc[safety at uP-L1]).
Each item's statement says whom it binds: every binding or some of them, and the element where an item's statement gives it a duty (xref:../README.adoc#req-ssr-requirements-bind[A requirement binds the actors to which it gives a duty]).

[NOTE]
====
* They carry the tag `SafetyBinding`, and an item whose statement holds a duty of pull bindings only also carries `SafetyBindingPull`.
The tags say which repositories cover an item (xref:../README.adoc#tags[the tags]).
====

* They name no middleware.
What only one binding must meet is stated with that binding, in requirements that are specific to it (xref:README.adoc#one-binding[what is specific to one binding]).
* What a binding is, and what is not one: <<req-ssr-binding-scope,What a binding is, and the binding contract>>.

[[req-ssr-binding-scope]]
== What a binding is, and the binding contract

[.specitem,oft-sid="req~ssr-binding-scope~2",oft-title="What a binding is, and the binding contract",oft-needs="uman",oft-tags="SafetyBinding"]
--
*What a binding is.*
A binding is a uP-L1 transport implementation that adapts the element to one middleware and is written against the element's lending or handoff runtime contract, part E2 of the element (xref:../seooc-up-rust/README.adoc#req-ssr-element-boundary[The parts of the element, and element code]).

*The binding contract.*
The binding contract of a binding is that runtime contract together with every duty that the statement of a requirement of this area gives that binding (xref:../README.adoc#req-ssr-requirements-bind[A requirement binds the actors to which it gives a duty]), wherever the requirement is filed:

* each duty that a statement gives each binding;
* each duty that a statement gives the bindings of its kind or of its profile, such as each lending binding or each binding on a route that it serves by pull;
* each duty that a statement gives that binding itself.

A duty that a statement gives another part, such as the element, is not part of a binding's contract, even where the same requirement gives that binding a duty too.

*A requirement that is specific to one binding.*
A requirement that is specific to one binding names that binding and no other binding.
It can give another part, such as the element, a duty of its own.

*What is not a binding.*
A transport implementation that is not written against that runtime contract is not a binding.
The in-memory bindings that the contract suites run on are test doubles: fixtures for evidence, and not bindings.

*Lending and handoff.*
A lending binding is one on which a reader can be given shared memory that a writer wrote.
A handoff binding is one that hands the element a private copy.
These are the two families of bindings, and a test double belongs to the family whose runtime contract it implements.

*Push and pull.*
A binding serves each receive route in one of two ways.
It serves a route by _push_ where it hands each frame to the element in a call that the binding makes, a _delivery_.
It serves a route by _pull_ where it keeps the frames that arrive in a queue of its own, or of its middleware, under the route's QoS, its overflow policy included, and the element takes each frame that the queue holds in a call that the element makes.
A push binding, or a pull binding, is a binding on a route that it serves so, and a push route, or a pull route, is such a route.
One binding can serve some routes by push and others by pull.

*Frames that the element receives.*
A _pulled_ frame is one that the element took by pull.
A _retained_ frame is a received frame that the element keeps after the call that gave it, until the frame's lease is dropped: a pulled frame, or a frame that a delivery passes to the element to keep.
A _borrowed_ frame is one that a delivery lends to the element for the duration of that call only.

*A frame's envelope.*
A frame's _envelope_ is the form in which a binding carries the frame through its middleware: the parts that make up that form, such as a header, the frame's metadata and its payload, their order and where each lies.
The envelope of a route, or of a leg, is the envelope in which its binding carries its frames.
Where a binding's envelope is stated, it is stated with that binding (xref:README.adoc#one-binding[what is specific to one binding]).

*Middleware and binding code.*
A binding's middleware is the communication software that it adapts the element to.
Binding code is the binding's own code, and the middleware's code is not binding code.

*A separate element.*
A binding is not part of the element.
--

*Rationale.*
Whom a duty of a binding binds depends on what a binding is, and of which kind it is.
The items use these words in their statements and allocations.
A binding's code runs in the element's process, inside the element's calls and on threads that it starts, but each binding is developed and verified on its own, against the binding contract suite.

_The measure of the contract._
A binding's contract is read from the statements that give that binding a duty.
So a duty that an item gives the element, the page on which an item is filed and the repository that holds a binding add nothing to it.

[[req-ssr-binding-no-heap]]
== Binding code allocates nothing in runtime mode on a native path

[.specitem,oft-sid="req~ssr-binding-no-heap~3",oft-title="Binding code allocates nothing in runtime mode on a native path",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
*Native paths.*
In runtime mode, binding code *MUST NOT* acquire or release heap memory on any path that a native payload operation causes, errors, cancellation, retirement and deferred release included.

*Every other path.*
In runtime mode, binding code *MUST NOT* acquire or release heap memory on any other path, except as a serialized route's declared heap class permits and setup admits (xref:../seooc-up-rust/heap.adoc#req-ssr-heap-declared[The heap class is declared, with no default]).

*Middleware.*
Each binding *MUST* have any allocation inside its middleware declared as a permit on the routes that the allocation affects, and reported separately.
A permit discloses that allocation and establishes no heap-free guarantee.
The heap class that a binding states for a route covers the middleware work that its calls cause there (xref:../seooc-up-rust/heap.adoc#req-ssr-heap-declared[The heap class is declared, with no default]), so a route with a permit does not have the class none.

*When the rules apply.*
These rules bind the binding's transport from its own transition.
--

[horizontal]
ID:: `+req~ssr-binding-no-heap~3+`
ASIL:: B
Allocated to:: each binding
Verification:: heap-window (on each target and configuration that the binding's qualification record claims)
* For each binding, over native traffic with errors, cancellation, retirement and deferred release, with middleware allocation reported apart under its permit.
* On every other path, a serialized route's included: binding code acquiring and releasing heap memory only as a route's declared heap class permits and setup admits, and not at all where no class admits it.
* On a serialized route, the binding's declared allocation reported, as xref:../seooc-up-rust/heap.adoc#req-ssr-heap-declared[The heap class is declared, with no default] states.

*Rationale.*
Binding code runs inside the process on every runtime path.
So heap use there on a native path breaks runtime mode, as heap use in the element does (xref:../seooc-up-rust/heap.adoc#req-ssr-heap-none[No heap in runtime mode on a native path]).

A serialized route may allocate where it declares it and setup admits it.
That permission cannot reach native work or metadata a native route shares.

Allocation inside middleware is outside the binding's own code.
So it is declared as a permit, admitted only by a waiver (xref:../seooc-up-rust/waivers.adoc#req-ssr-waiver-required[Middleware heap needs a named waiver]), and reported apart from the binding's own.

[[req-ssr-binding-lazy-forced]]
== Lazy state is forced, and threads are idle, before running

[.specitem,oft-sid="req~ssr-binding-lazy-forced~2",oft-title="Lazy state is forced, and threads are idle, before running",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
A binding *MUST* take every first lock at construction or route preparation, and force every lazy primitive, before its transition to running returns.
That holds for the binding's own locks and lazy primitives, and for each one of its middleware that a runtime path of the binding can reach, on every route.

The binding *MUST* have every thread that it starts reach its idle loop by then.
--

[horizontal]
ID:: `+req~ssr-binding-lazy-forced~2+`
ASIL:: B
Allocated to:: each binding
Verification:: heap-window (first traffic, through the binding contract suite, on each target and configuration that the binding's qualification record claims), fault-injection, review (each first lock and each lazy primitive of the binding's middleware that a runtime path of the binding can reach, at source level for the revision of the middleware that the binding is built against: taken or forced before the transition returns)

*Rationale.*
The element's own rule (xref:../seooc-up-rust/heap.adoc#req-ssr-heap-lazy-forced[Lazy state is forced before runtime mode]) would not hold if a binding left a lock or a thread to set itself up on first traffic, inside runtime mode.

A lock or a lazy primitive of the middleware that sets itself up on first traffic does the same set-up work on the binding's runtime path, so the rule reaches each one that such a path can reach.

A serialized route's declared allocation excuses no lazy first use on any path.

[[req-ssr-binding-frame-drop]]
== What a received frame's destructor may do

[.specitem,oft-sid="req~ssr-binding-frame-drop~10",oft-title="What a received frame's destructor may do",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
*No blocking.*
Each binding *MUST* ensure that dropping one of its received frames does not block, with the one exception that this item states for a declared allocation domain.
The binding *MUST* ensure that the drop takes no lock that can wait behind other work, in the binding or in its middleware, and that any retry in it is lock-free and bounded by other threads' progress.

*Native and heap-free routes.*
On a native route, and on any route whose heap class is none, the binding *MUST* ensure that the drop frees no heap.

*Routes that admit the binding's allocation.*
On a serialized route whose declared heap class admits the binding's allocation (xref:../seooc-up-rust/heap.adoc#req-ssr-heap-declared[The heap class is declared, with no default]), the binding *MUST* ensure that the drop releases, exactly once, only the storage that the binding allocated for that frame under that class:

* on a route that does not require non-waiting release (xref:../seooc-up-rust/heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name, and admitted or refused]), on the drop's own path under the binding's declared policy, where it may wait inside the allocation domain that the policy names, the one wait a drop may meet;
* on a route that requires it, at once only where it is established that this release cannot wait, and otherwise through the binding's deferred return, as for a retained owner.

The binding *MUST* ensure that the drop releases no other binding resource and revokes no retained owner.

*Deferred return.*
Where the middleware's own release of a retained frame can wait, the binding *MUST* have the drop instead hand the frame, without waiting, to the binding's deferred return.

A release that the deferred return performs is pending cleanup, charged until it completes and isolated as xref:../seooc-up-rust/release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else] states.
On a native route, the binding *MUST* ensure that such a release frees no heap, in binding code and in the middleware work that it causes, and never frees the backing that the frame lives in.

*What a route requires.*
Releasing the binding's allocation is part of the route's cleanup.
Whether setup admits that allocation on a route that requires panic-free cleanup or non-waiting release, through the allocator and every dependency that the release reaches, or refuses the route by name, is the element's to decide, as xref:../seooc-up-rust/heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name, and admitted or refused] states.
That item also states that the element refuses no route for that allocation where the route requires neither.
What the element shows of the binding's declared policy in each route's report is stated in xref:../seooc-up-rust/heap.adoc#req-ssr-heap-declared[The heap class is declared, with no default], "Reporting".
For the element, those two requirements replace the share that revision 9 of this item gave it: the setup that admits or refuses a route by what the route requires of the release of the binding's allocation, and that route's report of the binding's declared policy.

*No panic.*
The binding's own code *MUST NOT* panic, on the drop or in the deferred return that completes it.

A middleware panic path that the drop or that return can reach is allowed only as an accepted instance of <<req-ssr-binding-no-panic,No panic on any peer input>>.
The requirement that accepts it is specific to its binding, says that the instance applies to a frame's drop, and states all five parts that the rule asks of an instance.
On a native route no accepted instance covers a path that the drop or that return can reach, because there the drop cannot panic (xref:../seooc-up-rust/release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else], "Native routes").
Any other middleware panic path that the drop or that return can reach is a known failure of the binding.

An accepted instance is never a waiver, and covers no other middleware panic path, no owned value's destructor and no allocator or provider failure.
--

* *test*
** The binding contract suite.
** On a serialized route that admits the binding's allocation, one release per frame of exactly what the binding allocated for it.
** A retained frame whose release in the middleware can wait, taken off the drop through the deferred return, on every route.
** On a route that does not require non-waiting release, the release of the binding's allocation on the drop's own path under the declared policy.
** On a route that requires it, a release of that allocation that can wait taken off the drop through the deferred return.

* *heap-window*, on each target and configuration that the binding's qualification record claims
** No free on a native route, on the drop and in a release that the deferred return performs, the middleware's work in it included.
** On a serialized route, only the declared release.
* *fault-injection*: for a binding with an accepted instance on this path, peer input, death and restart never reach it, as that binding's own item states.
* *review*
** The binding's lock use, for every call sequence the element allows.
** For a binding with an accepted instance on this path, its known-anomaly entry in the binding's qualification record.

*Rationale.*
_What the destructor releases._
The storage a binding allocated for a frame is owned like any other value of the route.
So its release follows what the route requires, as an owned value's destruction does (xref:../seooc-up-rust/heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name, and admitted or refused]).

_Why a waiting release is deferred._
Returning a received frame is part of the application runtime path.
So a middleware lock that can wait is still a blocking operation even when its uncontended release is brief.

Where the middleware's own release can wait, the binding defers it.
A lock-free queue whose capacity covers every admitted retained owner is one hand-off to the deferred return that meets this.
Whatever the mechanism, every clause of the statement binds it, and so does every clause of xref:../seooc-up-rust/release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else] that binds pending cleanup, a binding's deferred return included: the hand-off to that return does not wait, it has room for every retained owner that the route admits, ownership passes exactly once, and the owner stays charged until its return completes.

_Isolation._
A worker of its own does not by itself isolate a deferred return.
What pending cleanup may hold while it waits is stated in xref:../seooc-up-rust/release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else].

A measured lock delay is not an accepted wait.

_Panics._
A panic path inside one middleware is stated, with its bounds, in a requirement that is specific to its binding.

[[req-ssr-binding-no-panic]]
== No panic on any peer input

[.specitem,oft-sid="req~ssr-binding-no-panic~9",oft-title="No panic on any peer input",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
*The rule.*
Binding code *MUST NOT* panic on any frame, length or sequence a peer produces, or when a peer dies or restarts.
Each binding *MUST* have each panic path inside its middleware made unreachable by a setup check or by sizing, unless the path is an accepted instance.

*Each binding's account.*
Each binding *MUST* state, in its qualification record (<<req-ssr-binding-readme,A binding's qualification record states its limits and its failures>>), its account of the middleware panic paths that it can reach: that it has no accepted panic path, or each accepted instance by name.

*Accepted instances.*
A middleware panic path is an accepted instance only where all of these hold:

* a requirement of this area that is specific to the binding names the instance and states the five parts below;
* the binding's qualification record discloses the instance as a known anomaly;
* no frame, length or sequence that a peer produces, no peer's death or restart and no write of a faulty peer into shared memory can reach the path.

The five parts are:

* the operation, or the path inside the middleware, that can panic;
* the binding, profile or configuration to which it applies;
* the conditions that can reach it;
* the exclusions that are relevant to it, among peer input, a peer's death or restart, and the sequences of calls that an application can make through the element;
* the setup check, sizing, invariant or limit of the target that bounds it or excludes it.

Where one requirement names several instances, each is accepted only with its own scope and its own bounds, which can be verified by themselves.
An accepted instance is not a waiver, and it accepts no other path and no violation of another requirement.

*Any other path.*
Any other middleware panic path, including another one that only a broken OS can reach, is a known failure of its binding.
So is a path whose requirement does not state all five parts, or that its binding's qualification record does not disclose.
An acknowledgement makes no known failure an accepted instance.
--

[horizontal]
ID:: `+req~ssr-binding-no-panic~9+`
ASIL:: B
Allocated to:: each binding
Verification:: fault-injection, test, review
* *fault-injection*: malformed frames; peers killed and restarted; a faulty peer's writes into shared memory.
* *test*: the binding contract suite.
* *review*: for each binding, the account in its qualification record: that it says that the binding has no accepted panic path, or names each accepted instance; for each accepted instance, the requirement that accepts it, with all five of its parts, against the source of its middleware in the configuration that the instance names, and that no peer input, death, restart or shared-memory write reaches the path; and the disclosure of each accepted instance in the binding's qualification record.

*Rationale.*
A heap waiver cannot excuse a panic.
A peer can produce its input again at any time, and can die or restart at any time, so nothing bounds a path that a peer can reach.
Such a path is a known failure, whatever is disclosed or acknowledged.

Each binding states its account, so that no binding's silence is read as one.
The paths of one middleware, and a setup check or a sizing that makes one of them unreachable, are stated with its binding.

[[req-ssr-binding-peer-identity]]
== Peer identity is stable, and incarnations rise

[.specitem,oft-sid="req~ssr-binding-peer-identity~1",oft-title="Peer identity is stable, and incarnations rise",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
A binding *MUST* give each frame a peer identity that is stable across that peer's restarts, with an incarnation that starts at 1 and only rises.
It *MUST* report a peer's loss or restart where its middleware allows.

A binding that cannot identify peers *MUST* say so, and its routes then rely on deadlines only.
--

[horizontal]
ID:: `+req~ssr-binding-peer-identity~1+`
ASIL:: B
Allocated to:: each binding
Verification:: test (a test double that restarts; a real restart), review (whether the binding can identify peers, and, where it cannot, that it says so)

*Rationale.*
A stable identity with a rising incarnation lets the element tell a restarted peer from its earlier self, and refuse a frame from the earlier one as stale (xref:peers.adoc#req-ssr-peer-stale-rejected[Stale peers are rejected]).

A binding that cannot identify peers cannot report a peer's loss or restart, so only deadlines can show that a peer has gone.

[[req-ssr-binding-qos-capability]]
== A binding honors or refuses each declared setting

[.specitem,oft-sid="req~ssr-binding-qos-capability~2",oft-title="A binding honors or refuses each declared setting",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
A binding *MUST* declare its capability (xref:payload-paths.adoc#req-ssr-payload-route-form[A route's form is fixed at setup, by what the route declares and never by a name]), its QoS capability among it, truthfully, honor every route setting it admits, and in route preparation refuse any setting it cannot serve: QoS, peer-table size, payload bound, alignment, smallest payload, a count, a requirement to lend or truncation.

It *MUST NOT* replace a declared setting silently.

*What a declaration says.*
For each count, size or bound that a binding declares, the binding *MUST* state what it measures: the resource, the unit and the scope that it holds for, and whether it is an upper limit or an amount that the binding guarantees to be available.
A binding *MUST NOT* declare or report an upper limit, or a computed capacity, as guaranteed availability.

*Arrival reports.*
Whether a binding can report the arrivals of a pull route, and the arrival latency that it declares for one, are part of its QoS capability (<<req-ssr-binding-arrival-reports,A binding reports each arrival within the latency that it declares, and each event as what it is>>).
--

[horizontal]
ID:: `+req~ssr-binding-qos-capability~2+`
ASIL:: B
Allocated to:: each binding
Verification:: test, review
* *test*
** The QoS contract suite and the binding contract suite on each binding, observing what an application receives from the documented read call alone.
** A handoff binding that does not apply the route's policy in its own queue must fail it.
** A declared upper limit that the binding cannot always make available, declared and reported as a limit and never as guaranteed availability.
* *review*: each count, size and bound that the binding declares, against what its declaration says that it measures.

*Rationale.*
The element admits a route on what its binding declares.
A figure that is read as more than it measures admits a route that the binding cannot serve: an upper limit says how much a route can ever use, and nothing about what is free when the route asks.

[[req-ssr-binding-arrival-reports]]
== A binding reports each arrival within the latency that it declares, and each event as what it is

[.specitem,oft-sid="req~ssr-binding-arrival-reports~1",oft-title="A binding reports each arrival within the latency that it declares, and each event as what it is",oft-needs="impl,utest",oft-tags="SafetyBinding,SafetyBindingPull"]
--
*Scope.*
The duties of this item on the declared latency, on arrival reports and on failed reads bind a binding on each receive route that it serves by pull (<<req-ssr-binding-scope,What a binding is, and the binding contract>>).
What the element records on a route that a binding serves by push, and that route's arrival latency, are stated in xref:../seooc-up-rust/qos.adoc#req-ssr-qos-deadline[Deadlines are monitored].

*The declared latency.*
For each pull route on which it can report arrivals, a binding *MUST* declare its arrival latency L, as xref:../seooc-up-rust/qos.adoc#req-ssr-qos-deadline[Deadlines are monitored] defines it under "Terms", in its QoS capability, with its unit.
The binding *MUST* keep that latency on every target and in every configuration that its qualification record claims.
A binding that cannot report every arrival of a pull route within a declared latency *MUST* declare that it cannot report arrivals on that route.

*Arrival reports.*
An arrival is what xref:../seooc-up-rust/qos.adoc#req-ssr-qos-deadline[Deadlines are monitored] defines under "Terms".
On a pull route that declares a deadline, the binding *MUST* report every arrival to the element through the runtime port, each within L of the time at which its frame reached the route's queue.
One report *MAY* stand for several arrivals, where the binding makes it within L of each of them.
The binding *MUST NOT* report an arrival without evidence that a frame reached the route's queue: that a frame entered it, or that its overflow policy discarded one.
A wake hint alone is no such evidence, and is not an arrival.

*Failed reads.*
On every pull route, the binding *MUST* report to the element, through the runtime port's receive-failure report, each failure to read its own queue, and each data connection of the route that its middleware drops or fails to set up without an error.
It *MUST NOT* report such a failure as an arrival, and *MUST NOT* leave it unreported.

*Each event as what it is.*
In what it reports to the element and in what it counts, every binding *MUST* keep these events apart: an arrival; a wake hint; a receive failure, which is a failed read of its queue or a data connection that the clause "Failed reads" names; a failure of a call that notifies or wakes a peer; any other fault of a connection to a peer; and the loss of a frame.
It *MUST NOT* report one of them as another, or infer one from another.
What a call that notifies a peer returns shows what that call did: it shows neither that a frame arrived, was read or was consumed, nor that one was lost, and an error of the call does not show that no peer was notified.

*The element's side.*
What the element records, monitors and counts from these reports is stated in xref:../seooc-up-rust/qos.adoc#req-ssr-qos-deadline[Deadlines are monitored] and xref:../seooc-up-rust/errors.adoc#req-ssr-error-no-silent-loss[No silent loss, and each loss counted once].
What setup does with a deadline on a pull route whose binding cannot report arrivals is stated in xref:../seooc-up-rust/qos.adoc#req-ssr-qos-invalid-refused[Meaningless QoS is refused at setup].
--

[horizontal]
ID:: `+req~ssr-binding-arrival-reports~1+`
ASIL:: B
Allocated to:: each binding; for the declared latency, or the declaration that it cannot report arrivals, and for the reports of failed reads, on each receive route that it serves by pull; for the arrival reports, on each such route that declares a deadline
Verification:: test, fault-injection, review
* *test*
** The QoS contract suite's deadline checks on a pull route, on a subscriber and on a carrier ingress: an arrival reported for each frame that reaches the queue, one that the overflow policy discards included, each within the declared latency.
** Several frames that reach the queue close together: each reported within the declared latency, and, on a binding that lets one report stand for several arrivals, that report made within the declared latency of each of them.
** A wake hint with no frame: no arrival reported, as the negative control.
* *fault-injection*
** A failing read of the binding's own queue: reported through the receive-failure report, and not as an arrival.
** A data connection that the middleware drops, and one that it fails to set up, without an error: each reported through the receive-failure report.
** A failing call that notifies a peer: no arrival and no lost frame reported or counted for it, and, where the binding reports or counts the failure, reported or counted as that failure.
* *review*
** The declared latency against the mechanism by which the binding reports arrivals, on each target and in each configuration that its qualification record claims; a measured delay alone does not establish it.
** For a binding that cannot report every arrival of a pull route within a declared latency, its declaration that it cannot report arrivals there.

*Rationale.*
On a pull route the element sees an arrival only when the binding reports it, and it counts a route's deadline from the arrivals that it records.
A report that is missing, or later than the declared latency, shows a miss that did not happen, and a report without an arrival hides one that did.
So the binding answers for every arrival, within a latency that it declares and keeps.

A wake hint says that there may be something to read, and not that a frame arrived.
A failed read is neither an arrival nor a loss that the element can see for itself, so the binding reports it as what it is.

What a call that notifies a peer returns says what that call did.
Read as an arrival, a delivery or a loss, it would put into a count an event that nobody observed.

[[req-ssr-binding-response-delivery]]
== A binding delivers one response route from one thread at a time

[.specitem,oft-sid="req~ssr-binding-response-delivery~1",oft-title="A binding delivers one response route from one thread at a time",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
On a response route that it serves by push, a binding *MUST* make its deliveries one at a time: it *MUST NOT* start a delivery on that route while another delivery on the same route is in progress, on any thread.

The element's checks of an arriving response are stated in xref:../up-l2/interaction.adoc#req-ssr-rpc-check-at-arrival[A response completes its call only once its wire accepts it], and this item relaxes none of them.
On a response route that a binding serves by pull, the element takes each frame itself, and this item gives the binding no duty.
--

[horizontal]
ID:: `+req~ssr-binding-response-delivery~1+`
ASIL:: B
Allocated to:: each binding, for each response route that it serves by push
Verification:: test (the binding contract suite: on a response route served by push, responses from several peers at once, with no two deliveries on that route overlapping), review (the binding's delivery path of a response route, for every thread that can deliver on it)

*Rationale.*
The element runs the arrival checks of one response route one at a time, and on a push route it runs them inside the binding's delivery.
Two deliveries on one response route at once would put two of those checks side by side.
On a pull route the element takes the frames itself.

[[req-ssr-binding-receiver-count]]
== A binding that declares an exact receiver count reports it for each request

[.specitem,oft-sid="req~ssr-binding-receiver-count~1",oft-title="A binding that declares an exact receiver count reports it for each request",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
*The declaration.*
A binding declares an exact receiver count where it declares, in its capability, that it reports to the element, for each request that it hands over, the exact number of servers that received the request at that handover.
A binding *MUST NOT* declare an exact receiver count unless it establishes that number at each handover, on every target and in every configuration that its qualification record claims.

*The report.*
A binding that declares an exact receiver count *MUST* report that number to the element for each request that it hands over.
It *MUST NOT* report in its place a count of notification listeners, a discovery result or a count that it took at another time.

*The element's side.*
What the element does with that report, and on a binding that declares no exact receiver count, is stated in xref:../up-l2/interaction.adoc#req-ssr-peer-rpc-no-server[A call with no server fails at once].
--

[horizontal]
ID:: `+req~ssr-binding-receiver-count~1+`
ASIL:: B
Allocated to:: each binding, for what it declares; each binding that declares an exact receiver count, for its report
Verification:: test, fault-injection, review
* *test*: the binding contract suite, on a binding that declares an exact receiver count: a request handed over with no server, with one server and with several, the reported number being that of the servers that received it; a request handed over with listeners present and no server, and one handed over while discovery still lists a server that has left, with no other server to receive it: zero reported for each.
* *fault-injection*: a server killed before the handover of a request: not counted in the report for that request.
* *review*: the mechanism by which the binding establishes the number at the handover, on each target and in each configuration that its qualification record claims; for a binding whose middleware gives it only a listener count or a discovery result, that it declares no exact receiver count.

*Rationale.*
The element fails a call at once only on a report that its request reached no server.
A count of listeners, or what discovery last found, says who might receive a request, and not who received this one, so a call that failed at once on it could have reached a server.
So a binding declares the count only where it establishes it at the handover.
Without that count the element fails no call at once for want of a server, and a call that is still pending at its TTL ends then.

[[req-ssr-binding-bounded]]
== A binding bounds its own work and its waits

[.specitem,oft-sid="req~ssr-binding-bounded~5",oft-title="A binding bounds its own work and its waits",oft-needs="impl,utest",oft-tags="SafetyBinding,SafetyBindingPull,SafetyUpRustCore"]
--
*Bounded receive.*
On a route that it serves by pull, a binding *MUST* give up at most the route's bound in each call of its receive, and keep the rest in a bounded queue under the route's QoS.

*Bounded waits.*
A binding *MUST NOT* let a call of its own wait without a bound, except as the next paragraph allows, or wait for a deferred return to complete.

*Waits without a deadline.*
Apart from a deliberate idle wait (xref:../seooc-up-rust/bounded-work.adoc#req-ssr-bound-wait[Every bounded wait has a logical deadline]), a binding *MAY* let its work wait without a finite logical deadline in two cases only:

* a release that its deferred return performs as pending cleanup (<<req-ssr-binding-frame-drop,What a received frame's destructor may do>>), isolated as xref:../seooc-up-rust/release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else] states;
* on a serialized route whose declared heap class admits the binding's allocation, a wait inside the allocation domain that the binding's declared policy names, as xref:../seooc-up-rust/bounded-work.adoc#req-ssr-bound-wait[Every bounded wait has a logical deadline] states and limits.

A binding *MUST* bound its other work, its worker loops, dispatch and wake paths included.
A binding *MUST NOT* let anything that a binding call, an arrival report or a health report needs wait behind a pending release.

*Carrier ingress.*
At the ingress of a carrier route (xref:../up-l2/streamer.adoc#req-ssr-carrier-route[A carrier route takes each frame at its ingress and sends it at its egress]), the element *MUST* take pulled or retained frames, and never a borrowed frame whose carriage would need a staged copy.
--

[horizontal]
ID:: `+req~ssr-binding-bounded~5+`
ASIL:: B
Allocated to:: each binding; the element, for the frames that it takes at the ingress of a carrier route
Verification:: fault-injection, test
* *fault-injection*
** A flood.
** A deferred return held behind the middleware's lock while the binding's calls, arrival reports and health reports continue.
* *test*
** No binding call waits for a deferred return.
** A carrier ingress taking pulled or retained frames, and never a borrowed frame whose carriage would need a staged copy.

*Rationale.*
A receive that gave up any number of frames per call could hold its caller for as long as a peer keeps sending.

The bound on a binding's waits is logical, as every wait of its own is (xref:../seooc-up-rust/bounded-work.adoc#req-ssr-bound-wait[Every bounded wait has a logical deadline]).
A physical bound on when the caller resumes is a timing claim of a supported configuration.

A borrowed delivery's bytes live only for that call, so carrying them beyond it would need a staged copy, which a carrier may not make.

_The two waits without a deadline._
A deferred return of a retained owner can wait behind the middleware's own lock (<<req-ssr-binding-frame-drop,What a received frame's destructor may do>>), and a call that waits for a lock cannot observe a deadline from inside it.
So that release is named as a wait without a deadline, no binding call or report waits behind it, and the binding's other work is bounded.

A binding that allocates for a serialized route does so through an allocator, which may take a lock.
That wait is the allocation domain's, on the terms that xref:../seooc-up-rust/bounded-work.adoc#req-ssr-bound-wait[Every bounded wait has a logical deadline] sets.
With no place for it, such a binding would be refused on a route that requires nothing stronger.

[[req-ssr-binding-predecessor-cleanup]]
== A binding cleans up after a dead predecessor, in initialization

[.specitem,oft-sid="req~ssr-binding-predecessor-cleanup~2",oft-title="A binding cleans up after a dead predecessor, in initialization",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
*In initialization.*
A binding *MUST* recover or remove the resources that a dead predecessor left, in its own initialization, before any route is prepared.
Where it cannot recover or remove something that a dead predecessor left, the binding *MUST* refuse setup with an error that names what it could not recover or remove, and *MUST NOT* prepare a route over it.
The binding *MUST NOT* refuse setup merely because something that a predecessor left is present.
For each binding, this item replaces the clauses of revision 2 of xref:../seooc-up-rust/runtime-modes.adoc#req-ssr-mode-restart[A restart is an initialization] on what a dead predecessor left, and on reaching runtime mode with stale predecessor state present.

*Not in a surviving process.*
Once its transport is in runtime mode, a binding *MUST NOT* clean up after a dead peer: it recovers, removes and takes over nothing that the dead peer left.
That cleanup belongs to the initialization of the process that replaces the peer (xref:../seooc-up-rust/runtime-modes.adoc#req-ssr-mode-restart[A restart is an initialization]).

*What stays in force.*
What a surviving process releases of its own, and how it accounts for the peer's failure, are stated in xref:peers.adoc#req-ssr-peer-failure-normal[Peer failure is normal input] and xref:../seooc-up-rust/release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else].
--

[horizontal]
ID:: `+req~ssr-binding-predecessor-cleanup~2+`
ASIL:: B
Allocated to:: each binding
Verification:: fault-injection (a peer killed; a restart with its leftovers present, recovered or removed, and setup not refused for their presence; a restart whose recovery fails, with setup refused by an error that names what was not recovered, and no route prepared), review (no cleanup after a dead peer on any runtime path of the binding)

*Rationale.*
Cleanup in runtime mode would put work of unknown size, and perhaps the heap, on a survivor's runtime path, while initialization may do both (xref:../seooc-up-rust/runtime-modes.adoc#req-ssr-mode-restart[A restart is an initialization]).
So this item places that recovery in the binding's construction, before any route.

A binding that went on over leftovers that it could not recover would run on state that nothing checked, so it refuses setup.

The means of recovery depend on the middleware.

[[req-ssr-binding-readme]]
== A binding's qualification record states its limits and its failures

[.specitem,oft-sid="req~ssr-binding-readme~3",oft-title="A binding's qualification record states its limits and its failures",oft-needs="uman",oft-tags="SafetyBinding"]
--
*The record.*
Each binding *MUST* keep a qualification record, versioned with the binding, that states for each revision of the binding:

* each target and configuration for which the binding claims its binding contract;
* every runtime guarantee that its middleware cannot make, with measured figures where they exist;
* the permits that it declares, which only a named waiver admits (xref:../seooc-up-rust/waivers.adoc#req-ssr-waiver-required[Middleware heap needs a named waiver]);
* its limits, its deviations and its known failures, each classed as this item defines them;
* the revision of its middleware, and of every other source that an entry relies on;
* the evidence of the runs that its entries rest on, each with the target and the configuration that it ran on, and the history of each entry.

The record is the authoritative statement of each of these.

*Limits, deviations and known failures.*
These definitions apply to the qualification record of each part.
An entry has one of three classes:

* a _limit_: something that the part does not serve, or serves only within a stated bound, where the requirements of this area let that part declare what it serves;
* a _deviation_, which this area also calls a _known anomaly_, and once it is accepted an accepted anomaly: a departure from a requirement that binds that part, with an exact scope and exact bounds, which no requirement of this area excludes from acceptance, such as a binding's accepted instance of <<req-ssr-binding-no-panic,No panic on any peer input>>;
* a _known failure_: any other violation of a requirement that binds that part.

For each deviation the binding *MUST* state in the record an identifier and a revision, its exact scope and bounds, the evidence that it rests on and the date on which it lapses.
In the record, the binding *MUST* keep its known failures apart from its limits and its deviations.
Nothing makes a known failure a limit or a deviation: not its disclosure, not an acknowledgement and not a waiver.

*Whose defect.*
For each limit, deviation and known failure, the binding *MUST* say in the record whether its cause lies in the binding's own code or in its middleware, and *MUST* name the exact source that the entry relies on: the document or file, its revision and the place in it.
Which routes a known failure affects for strict mode is stated in xref:../seooc-up-rust/build.adoc#req-ssr-strict-ack-revision[An acknowledgement names a deviation by ID and revision].

*Shared memory.*
Where a binding or its middleware uses shared memory, the binding *MUST* disclose in its record that:

* a write racing a zero-copy read is undefined behaviour even for a type that accepts every bit pattern;
* the setup integrity check catches misdeployment, not a peer that lies about its level;
* a private payload copy does not validate middleware-owned offsets, lengths or other shared state;
* end-to-end protection, OS partitioning and timing budgets remain the integrator's duties.

*The README.*
The binding's README is a concise profile and index of the binding, and the binding *MAY* have its README link to the record.
Where the README speaks of a matter that the record states, the record governs.
--

[horizontal]
ID:: `+req~ssr-binding-readme~3+`
ASIL:: B
Allocated to:: each binding, for its record and README; each part, as the subject of the definitions of limit, deviation and known failure
Verification:: review (every binding's record: the targets and configurations that it claims; each entry and its class; the identifier, revision, scope, bounds, evidence and lapse date of each deviation; the cause and the exact source of each limit, deviation and known failure; what its README says of the matters that the record states; and the definitions applied to entries of a binding, a wire and the element, each against the requirements that bind that part)

*Rationale.*
A deployment decision needs the limits of the middleware underneath the binding, including limits that setup declarations cannot remove.

The timing budgets that the record discloses as the integrator's duty are the system's allocation.
A timing package that a supported configuration offers is the element's supplier's (xref:../seooc-up-rust/assumptions-of-use.adoc#aou-seooc-timing-budgets[Timing claims rest on a supported configuration, and the item's budgets are the integrator's]).

The end-to-end protection that the record discloses as the integrator's duty is whatever the system supplies.

A limit is something that the requirements let a binding declare.
A deviation departs from a requirement within a scope and bounds that can be checked, so that an integrator can decide on it.
A known failure is any other violation, and nothing can accept it, however exactly it is bounded.

Whether a defect is the binding's or its middleware's decides who can repair it, so the record says which, with the source that shows it.

*The inventory.*
Each binding *MUST* state, at each `+unsafe+` site of its own code, the memory-safety obligation that the site relies on, and *MUST* keep each such site under a reviewed row of its own inventory.

Each binding *MUST* keep each `+unsafe+` site of the code that a generator, such as a derive, emits into the binding under a reviewed inventory row, its own or the generator's.

[[req-ssr-binding-lent-storage]]
== Lent storage is exclusive, disjoint and stable for as long as it is held

[.specitem,oft-sid="req~ssr-binding-lent-storage~2",oft-title="Lent storage is exclusive, disjoint and stable for as long as it is held",oft-needs="impl,utest",oft-tags="SafetyBinding,SafetyUpRustCore"]
--
*Scope.*
This item binds a lending binding, whatever wire a route uses.

*Held.*
A loan is _held_ from the moment the binding lends it until it is sent or given back.
A received frame is _held_ from the moment the binding hands it to the element until it is returned.
A loan or a frame whose lease safe code forgot is never sent, given back or returned, so it is held for the life of the process.

*A transmit loan.*
For as long as a loan is held, the binding *MUST* keep its storage:

* live, mapped and at one address;
* valid for writes of at least the size that the route declares, in one piece, at an address with the alignment that the route declares;
* apart from every other held loan and from every held frame of this process;
* handed out in this process through that loan alone, with no second way for safe code to read or write it.

The binding *MAY* lend the storage of a fresh loan uninitialized, and promises no value of its bytes.
The element *MUST NOT* read a fresh loan's storage as a typed value, or make a reference to it as a value, before a value is initialized there (xref:native-wire.adoc#req-ssr-native-in-place[A native payload is written and read where it is carried, or its route is refused]; xref:payload-paths.adoc#req-ssr-payload-written-once[A payload is written once, into the storage that carries it]).

*A received frame.*
For as long as a frame is held, the binding *MUST* keep its storage:

* live, mapped and at one address;
* valid for reads of the frame's whole length, in one piece, at an address with the route's alignment;
* unwritten by the binding and by its middleware in this process.

What another process writes there is covered by xref:integrity.adoc#req-ssr-integrity-zero-copy[Zero-copy only from a writer at or above the reader] and xref:deployment.adoc#aou-seooc-peer-access[Only authorized processes reach the transport].

*How a loan and a frame end.*
Three transitions end a held loan or frame.
The binding *MUST* ensure that each one that happens ends it exactly once:

* a send consumes the loan, so that no safe call can write its storage afterwards;
* the drop of an unsent loan's lease gives the loan back (xref:../seooc-up-rust/release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]);
* the drop of a frame's lease returns the frame to the middleware, through the frame's destructor or the deferred return that completes it (<<req-ssr-binding-frame-drop,What a received frame's destructor may do>>).

The binding *MUST NOT* end a loan or a frame in any other way.

*A forgotten lease.*
None of these transitions happens for a loan or a frame whose lease safe code forgot.
The binding cannot tell a forgotten lease from one that is still in use, and it treats both alike.
The binding *MUST* keep such a loan or frame charged to its route for the life of the process.
The binding *MUST NOT* lend or deliver its storage again, give it a second owner, or return or destroy it by another path.
The binding *MUST* keep each property of this item without relying on a destructor to run.

*Fixed before the transition.*
The binding *MUST* have sized and mapped the storage that it lends from before its transition returns.
Where its middleware can enlarge, move or map again such storage after the binding's transition, the binding *MUST* turn that off, or refuse in route preparation every route that would use it.

*An empty payload.*
The binding *MUST* give a loan or a frame of zero bytes an address that is not null and has the route's alignment.

*How the claim is made.*
A lending binding *MUST NOT* state these properties to the element other than through the `+unsafe+` interface of the binding contract, and *MUST* keep each site that makes the claim under a reviewed row of its own inventory (xref:../seooc-up-rust/memory-safety.adoc#req-ssr-unsafe-binding-untrusted[No binding written in safe code can break the element's memory safety]; <<req-ssr-binding-unsafe-inventory,A binding inventories its own `+unsafe+`>>).
A declaration, a capability value or a passed test does not establish them.

*Refusal to lend.*
A binding that cannot keep these properties for a route *MUST* refuse to lend for it, in route preparation, naming the route and the property.
It *MUST NOT* present storage that it copies into or out of as lent (<<req-ssr-binding-qos-capability,A binding honors or refuses each declared setting>>).
--

[horizontal]
ID:: `+req~ssr-binding-lent-storage~2+`
ASIL:: B
Allocated to:: each lending binding; the element, for no typed read of, and no reference as a value to, a fresh loan's storage before a value is initialized there
Verification:: test, compile-fail, miri, review
* *test*
** The binding contract suite: every held loan at its own address, apart from every other held loan and from every held frame, with the declared size and alignment; every held frame at one address, readable for its whole length, with the route's alignment.
** A loan whose lease is dropped unsent, and a frame whose lease is dropped: the storage goes back once, counted by the suite.
** A loan and a frame whose leases safe code forgot: each is still charged at the end of the run, its storage is never lent or delivered again, and nothing is returned or destroyed for it.
** A loan and a frame of zero bytes, each with an aligned address that is not null.
** A middleware that could enlarge, move or map again its storage after the binding's transition: turned off, or every route that would use it refused in route preparation.
** A route for which the binding cannot keep these properties: lending refused in route preparation, naming the route and the property.
* *compile-fail*: a loan sent twice, and a write after a send.
* *miri*: the lending test double, under the same suite, forgotten leases included, and a fresh loan left uninitialized until a value is written, with no typed read of it and no reference to it as a value before then.
* *review*: each site of the binding that makes the claim, at source level; each path that ends a loan or returns a frame; that no property rests on a destructor running; and that no storage that the binding copies into or out of is presented as lent.

*Rationale.*
The element builds a writer on a loan and a typed view on a received frame.
Both are sound only if the storage is exclusive, disjoint and stable, as the binding says.
Safe code cannot check that, so the element takes it only through an `+unsafe+` interface with stated obligations (xref:../seooc-up-rust/memory-safety.adoc#req-ssr-unsafe-binding-untrusted[No binding written in safe code can break the element's memory safety]).

_A forgotten lease._
A loan or a frame ends once, by the send, the give-back or the return.
Forgetting a lease is safe code, and it runs no destructor (source: the standard library documentation, Rust 1.98.1, `+std::mem::forget+`, its description and its section "Safety": https://doc.rust-lang.org/1.98.1/std/mem/fn.forget.html#safety[`+std::mem::forget+`]).
So a forgotten loan or frame never ends, its slot stays charged to its route, and its storage is never handed out again.
The element's own leases follow the same rule (xref:../seooc-up-rust/release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]; xref:../seooc-up-rust/heap.adoc#req-ssr-heap-slot-types[A decoded value is destroyed once, as its route's class admits]).

_The source-level argument._
A suite shows the loans that it took.
Whether two loans can ever overlap, or a frame's storage can go back twice, is a property of every path of the binding, and it is argued at the source.

_Fixed before the transition._
Nothing is set up in runtime mode (xref:../seooc-up-rust/runtime-modes.adoc#req-ssr-mode-no-setup-at-runtime[Setup is impossible in runtime mode]).
A middleware that grew or moved its storage there would do set-up work on a runtime path, and could move a frame under a view.

[[req-ssr-binding-shared-state]]
== A lending binding says which way its ports write shared state

[.specitem,oft-sid="req~ssr-binding-shared-state~1",oft-title="A lending binding says which way its ports write shared state",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
*The binding's statement.*
A lending binding *MUST* state, for each kind of port that it opens, whether that port writes shared state that another process of the same service reads.

* A binding on which a receiving port writes such state is a binding whose ports write shared state both ways.
* The binding *MUST* state it to the element at setup, and *MUST* repeat it in its README (<<req-ssr-binding-readme,A binding's qualification record states its limits and its failures>>).

*Where it is not established.*
Where it is not established which way a kind of port writes, the binding *MUST* state that its ports write both ways.

*What rests on it.*
The element's refusals for two-way shared state (xref:integrity.adoc#req-ssr-integrity-zero-copy[Zero-copy only from a writer at or above the reader]) and a deployment's rule for such a binding (xref:deployment.adoc#aou-seooc-peer-access[Only authorized processes reach the transport]) rest on this statement.
--

[horizontal]
ID:: `+req~ssr-binding-shared-state~1+`
ASIL:: B
Allocated to:: each lending binding
Verification:: test, review
* *test*
** The binding contract suite: a binding that states two-way shared state has a port of another level refused at setup, on every port kind.
** A binding that states one-way shared state: a receiving port of the suite's double that writes shared state fails the suite.
* *review*
** The middleware's shared state, by kind of port, at the revision that the binding is built against.
** Where it is not established which way a kind of port writes, the binding's statement that its ports write both ways.
** The binding's README, which repeats the statement that the binding makes at setup.

*Rationale.*
A process that writes shared state which a higher process reads can corrupt that process, whatever the payload rules say.
The rules for that case are stated for "a binding whose ports write shared state both ways".
Only the binding knows whether its middleware is one.

An answer that is not established is given as the unfavourable one, as an unknown writer's level is (<<req-ssr-binding-integrity-level,A lending binding records and reports the writer's level>>).
So a binding never gains a cross-level view by leaving the question open.
