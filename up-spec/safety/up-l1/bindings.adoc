= uP-L1 safety: Allocated to each binding
:toc: preamble

The key words "*MUST*", "*MUST NOT*", "*REQUIRED*", "*SHALL*", "*SHALL NOT*", "*SHOULD*", "*SHOULD NOT*", "*RECOMMENDED*", "*MAY*", and "*OPTIONAL*" in this document are to be interpreted as described in https://www.rfc-editor.org/info/bcp14[IETF BCP14 (RFC2119 & RFC8174)]

Conventions, tags and status words: xref:../README.adoc[the safety area's README].
This layer, and whom it binds: xref:README.adoc[safety at uP-L1].
The element whose contract these duties belong to: xref:../seooc-up-rust/README.adoc[the up-rust SEooC's README].

These are the duties of the binding contract.
Each binding meets them in its own code, and covers them in its own repository, by running the contract suites against itself.

* They carry the tag `SafetyBinding`.
* A duty of pull-form bindings also carries `SafetyBindingPull`.
* The iceoryx2 binding's own requirements carry `SafetyIceoryx2`, and are in xref:iceoryx2.adoc[the iceoryx2 page].
The two assumptions of use on that page bind a deployment on that binding, and carry `SafetyManual` only.
* A transport that is not written against the element's binding contract is not bound by them.

== Binding code allocates nothing in runtime mode

[.specitem,oft-sid="req~ssr-binding-no-heap~2",oft-title="Binding code allocates nothing in runtime mode on a native path",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
*Native paths.*
In runtime mode, binding code *MUST NOT* acquire or release heap memory on any path that a native payload operation causes, errors, cancellation, retirement and deferred release included.

*Every other path.*
In runtime mode, binding code *MUST NOT* acquire or release heap memory on any other path, except as a serialized or owned route's declared heap class permits and setup admits (`+req~ssr-heap-declared~3+`).

*Middleware.*
Allocation inside the binding's middleware *MUST* be declared as a permit on the routes it affects, and be reported separately.

*When the rules apply.*
These rules bind the binding's transport from its own transition.
--

[horizontal]
ASIL:: B
Allocated to:: each binding
Verification:: heap-window
* For each binding, over native traffic with errors, cancellation, retirement and deferred release, with middleware allocation reported apart under its permit.
* On a serialized route, the binding's declared allocation reported, never hidden.
Status:: Draft

*Rationale.*
Binding code runs inside the process on every runtime path.
So heap use there on a native path breaks runtime mode as surely as heap use in the element (`+req~ssr-heap-none~3+`).

A serialized or owned route may allocate where it declares it and setup admits it.
That permission cannot reach native work or metadata a native route shares.

Allocation inside middleware is outside the binding's own code.
So it is declared as a permit, admitted only by a waiver (`+req~ssr-waiver-required~1+`), and reported apart from the binding's own.

== Lazy state is forced, and threads are idle, before running

[.specitem,oft-sid="req~ssr-binding-lazy-forced~1",oft-title="Lazy state is forced, and threads are idle, before running",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
A binding *MUST* take every first lock at construction or route preparation, and force every lazy primitive, before its transition to running returns.

Every thread it starts *MUST* have reached its idle loop by then.
--

[horizontal]
ASIL:: B
Allocated to:: each binding
Verification:: heap-window (first traffic, through the binding contract suite), fault-injection
Status:: Draft

*Rationale.*
The element's own rule (`+req~ssr-heap-lazy-forced~1+`) would not hold if a binding left a lock or a thread to set itself up on first traffic, inside runtime mode.
The binding contract states the same rule, and its contract suite checks it.

A serialized route's declared allocation excuses no lazy first use on any path.

== A frame's destructor frees only what its route admits, never blocks outside a declared allocation domain, and cannot panic in binding code but for one bounded exception

[.specitem,oft-sid="req~ssr-binding-frame-drop~6",oft-title="A frame's destructor frees only what its route admits, never blocks outside a declared allocation domain, and cannot panic in binding code but for one bounded exception",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
*No blocking.*
Dropping a binding's received frame *MUST NOT* block, with the one exception that this item states for a declared allocation domain.
It takes no lock that can wait behind other work, in the binding or in the underlying transport, and any retry is lock-free and bounded by other threads' progress.

*Native and heap-free routes.*
On a native route, and on any route whose heap class is none, it *MUST* free no heap.

*Routes that admit the binding's allocation.*
On a serialized or owned route whose declared heap class admits the binding's allocation (`+req~ssr-heap-declared~3+`), it releases, exactly once, only the storage the binding allocated for that frame under that class:

* on a route that does not require non-waiting release (`+req~ssr-heap-guarantees~1+`), on the drop's own path under the binding's declared policy, where it may wait inside the allocation domain that the policy names, the one wait a drop may meet;
* on a route that requires it, at once only where it is established that this release cannot wait, and otherwise through the binding's deferred return, as for a retained owner.

It releases no other binding resource and revokes no retained owner.

*Deferred return.*
Where the underlying transport's own release of a retained frame can wait, the drop instead hands the frame, without waiting, to the binding's deferred return.

A release that the deferred return performs is pending cleanup, charged until it completes and isolated as `+req~ssr-release-lease-drop~4+` states.
On a native route it frees no heap and never frees the backing that the frame lives in.

*What a route requires.*
Releasing the binding's allocation is part of the route's cleanup.

* Where the route requires panic-free cleanup or non-waiting release, setup admits that allocation only where the guarantee is established for it, through the allocator and every dependency the release reaches (`+req~ssr-heap-guarantees~1+`).
Otherwise setup refuses the route by name.
* A route that requires neither is not refused for it, and its report shows the binding's declared policy.

*No panic, with one exception.*
The binding's own code cannot panic, on the drop or in the deferred return that completes it, with one exception.
That exception is the iceoryx2 binding's per-port mutex, and `+req~ssr-binding-iceoryx2-panic-paths~1+` states it with its bounds.
No other binding has one.

The exception is never a waiver, and covers no other middleware panic path, no owned value's destructor and no allocator or provider failure.
--

[horizontal]
ASIL:: B
Allocated to:: each binding
Verification:: test, heap-window, fault-injection, review
* *test*
** The binding contract suite.
** On a serialized route that admits the binding's allocation, one release per frame of exactly what the binding allocated for it.
** A retained frame whose release in the underlying transport can wait, taken off the drop through the deferred return, on every route.
** On a route that does not require non-waiting release, the release of the binding's allocation on the drop's own path under the declared policy.
** On a route that requires it, a release of that allocation that can wait taken off the drop through the deferred return.
** A route that requires panic-free cleanup, whose binding allocation's release is not established not to panic, refused at setup by name, and the same route admitted without that requirement.
** A deferred return held behind one port's lock while the binding's calls, arrival reports and the returns of owners on other ports continue.
* *heap-window*
** No free on a native route.
** On a serialized route, only the declared release.
* *fault-injection*: for the binding that has the exception, peer input, death and restart never reach the panic path.
* *review*
** The binding's lock use, for every call sequence the element allows.
** For the binding that has the exception, the README's known-anomaly row.
Status:: Draft

*Rationale.*
_What the destructor releases._
On a serialized route that admits a binding's allocation, a frame's destructor releases what the binding allocated for that frame, once, under the declared class.
On a native or heap-free route it frees nothing.

The storage a binding allocated for a frame is owned like any other value of the route.
So its release follows what the route requires, as an owned value's destruction does (`+req~ssr-heap-guarantees~1+`).

_Why a waiting release is deferred._
Returning a received frame is part of the application runtime path.
So a middleware lock that can wait is still a blocking operation even when its uncontended release is brief.

Where the middleware's own release can wait, the binding defers it.
The drop pushes the retained owner onto a lock-free queue whose capacity covers every admitted retained owner, and the binding's deferred return performs the release as pending cleanup.

_Isolation._
A worker of its own is not by itself the isolation that pending cleanup needs.
While it waits for the port's lock, it holds nothing that a binding call, an arrival report or the return of an owner on another port needs, and one stalled return does not stop the others.

_Not a second queue._
That queue holds ownership awaiting return, never unread traffic, so it is not a second receive queue.
A stalled worker shows as counted capacity pressure, never as a drop that waits.

A measured lock delay is not an accepted wait.

_Why revision 6._
Revision 5 stated the bounds of its one exception, a panic path of iceoryx2's per-port mutex, inside this rule of every binding.
The exception is one binding's, so `+req~ssr-binding-iceoryx2-panic-paths~1+` states it now, with the same bounds.
This revision keeps every other clause as it was.
The rule still has exactly that one exception, and no binding is allowed anything it was not allowed before.

== No panic on any peer input

[.specitem,oft-sid="req~ssr-binding-no-panic~5",oft-title="No panic on any peer input",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
*The rule.*
Binding code *MUST NOT* panic on any frame, length or sequence a peer produces, or when a peer dies or restarts.
A panic path inside the middleware is made unreachable by a setup check or by sizing.

*Allowed paths.*
A path is allowed only as a named instance, stated in an item that is allocated to its binding alone, and disclosed as a known anomaly in that binding's README.
None is a waiver.
The iceoryx2 binding's instances are in `+req~ssr-binding-iceoryx2-panic-paths~1+`, and no other binding has one.

*Static data segments.*
Every publisher on a service the binding uses has a static data segment: the binding records that on the service, its own peers require it when they open the service, and it checks the publishers present at setup.

*Any other path.*
Any other middleware panic path, including another one that only a broken OS can reach, needs its own explicit acceptance decision.
--

[horizontal]
ASIL:: B
Allocated to:: each binding
Verification:: fault-injection, test, gate
* *fault-injection*: malformed frames; peers killed and restarted.
* *test*: the binding contract suite.
* *gate*: for a binding with named instances, the gate that its own item states.
Status:: Draft

*Rationale.*
A heap waiver cannot excuse a panic.
Each accepted middleware anomaly needs its own bounded instance, and peer-triggered known failures cannot be reclassified as accepted anomalies.

A faulty peer's shared-memory writes that reach a middleware panic are known failures too, whatever anomaly is acknowledged.

_Why revision 5._
Revision 4 listed the allowed panic paths of one binding, iceoryx2, inside this rule of every binding, with that binding's tests and gate.
They are one binding's, so `+req~ssr-binding-iceoryx2-panic-paths~1+` states them now, with the same wording.
This revision keeps the rule, the static-data-segment duty and the need for an explicit acceptance decision.
A path is allowed exactly where it was before, and an acceptance decision is still an item of this specification that names the path.

== Peer identity is stable, and incarnations rise

[.specitem,oft-sid="req~ssr-binding-peer-identity~1",oft-title="Peer identity is stable, and incarnations rise",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
A binding *MUST* give each frame a peer identity that is stable across that peer's restarts, with an incarnation that starts at 1 and only rises.
It *MUST* report a peer's loss or restart where its middleware allows.

A binding that cannot identify peers *MUST* say so, and its routes then rely on deadlines only.
--

[horizontal]
ASIL:: B
Allocated to:: each binding
Verification:: test (a test double that restarts; a real restart)
Status:: Draft

*Rationale.*
A stable identity with a rising incarnation lets the element tell a restarted peer from its earlier self, and refuse a frame from the earlier one as stale (`+req~ssr-peer-stale-rejected~3+`).

A binding with no peer identity reports the peer as unknown, and then only deadlines can show that a peer has gone.

== A binding honors or refuses each declared setting

[.specitem,oft-sid="req~ssr-binding-qos-capability~1",oft-title="A binding honors or refuses each declared setting",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
A binding *MUST* declare its QoS capability truthfully, honor every route setting it admits, and in route preparation refuse any setting it cannot serve: QoS, peer-table size, payload bound or truncation.

It *MUST NOT* replace a declared setting silently.
--

ASIL:: B
Allocated to:: each binding
Verification:: test
* The QoS contract suite and the binding contract suite on each binding, observing what an application receives from the documented read call alone.
* A handoff binding that does not apply the route's policy in its own queue must fail it.
Status:: Draft

*Rationale.*

== A binding bounds its own work and its waits

[.specitem,oft-sid="req~ssr-binding-bounded~3",oft-title="A binding bounds its own work and its waits",oft-needs="impl,utest",oft-tags="SafetyBinding,SafetyBindingPull"]
--
*Bounded receive.*
A binding's receive *MUST* give up at most the route's bound per call and keep the rest in a bounded queue under the route's QoS.

*Bounded waits.*
A binding call *MUST NOT* wait without a bound, except as the next paragraph allows, and *MUST NOT* wait for a deferred return to complete.

*Waits without a deadline.*
Apart from a deliberate idle wait (`+req~ssr-bound-wait~3+`), binding work *MAY* wait without a finite logical deadline in two cases only:

* a release that its deferred return performs as pending cleanup (`+req~ssr-binding-frame-drop~6+`), isolated as `+req~ssr-release-lease-drop~4+` states;
* on a serialized or owned route whose declared heap class admits the binding's allocation, a wait inside the allocation domain that the binding's declared policy names, as `+req~ssr-bound-wait~3+` states and limits.

The binding's other work, its worker loops, dispatch and wake paths included, is bounded.
Nothing that a binding call, an arrival report or a health report needs waits behind a pending release.

*Carrier ingress.*
A carrier ingress *MUST* take pulled or retained frames, never borrowed ones whose carriage would need a staged copy.
--

[horizontal]
ASIL:: B
Allocated to:: each binding
Verification:: fault-injection, test
* *fault-injection*
** A flood.
** A deferred return held behind the middleware's lock while the binding's calls, arrival reports and the returns of owners that do not need that lock continue.
* *test*
** No binding call waits for a deferred return.
** On a route that requires non-waiting acquisition, a binding whose allocation can wait refused at setup by name.
Status:: Draft

*Rationale.*
A receive that gave up any number of frames per call could hold its caller for as long as a peer keeps sending.

The bound on a binding's waits is logical, as every wait of its own is (`+req~ssr-bound-wait~3+`).
A physical bound on when the caller resumes is a timing claim of a supported configuration.

A carrier ingress refuses a borrowed delivery, because its bytes live only for that call and a carrier may not stage a copy.

_Why revision 2._
Revision 1 bounded every binding call but did not say what a binding's deferred return of a retained owner may wait for.
That release can wait behind the middleware's own lock (`+req~ssr-binding-frame-drop~6+`).
So that revision named it as the one binding wait without a deadline, kept every binding call and report from waiting behind it, and bounded the binding's other work.

_Why revision 3._
A binding that allocates for a serialized route does so through an allocator, which may take a lock.
Revision 2 left no place for that wait, so it refused such a binding on a route that had required nothing stronger.
This revision names it as the second wait without a deadline, on the terms that `+req~ssr-bound-wait~3+` sets, and changes nothing else.

== A binding cleans up after a dead predecessor, in initialization

[.specitem,oft-sid="req~ssr-binding-predecessor-cleanup~1",oft-title="A binding cleans up after a dead predecessor, in initialization",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
A binding *MUST* recover or remove the resources a dead predecessor left, before any route is prepared, in its own initialization.

Survivors in runtime mode *MUST NOT* clean up after a dead peer.
--

[horizontal]
ASIL:: B
Allocated to:: each binding
Verification:: fault-injection (a peer killed; a restart with its leftovers present)
Status:: Draft

*Rationale.*
Cleanup in runtime mode would put work of unknown size, and perhaps the heap, on a survivor's runtime path, while initialization may do both (`+req~ssr-mode-restart~1+`).
So the binding contract places that recovery in the binding's construction, before any route.

On iceoryx2, creating a node checks for dead nodes and cleans up their stale resources by default (https://github.com/eclipse-iceoryx/iceoryx2/blob/806442b5273d87380511bb5ffcab316d129af31c/iceoryx2/src/config.rs[`+config.rs+` in iceoryx2 0.9.2]).
So the cleanup runs in the successor's initialization.

== The README says what the middleware cannot guarantee

[.specitem,oft-sid="req~ssr-binding-readme~1",oft-title="The README says what the middleware cannot guarantee",oft-needs="uman",oft-tags="SafetyBinding"]
--
Each binding's README *MUST* list every runtime guarantee its middleware cannot make, with measured figures where they exist and the permit a deployment *MUST* waive.

For shared memory, it discloses that:

* a write racing a zero-copy read is undefined behaviour even for a type that accepts every bit pattern;
* the setup integrity check catches misdeployment, not a peer that lies about its level;
* a private payload copy does not validate middleware-owned offsets, lengths or other shared state;
* end-to-end protection, OS partitioning and timing budgets remain the integrator's duties.
--

[horizontal]
ASIL:: B
Allocated to:: each binding
Verification:: review (checks every README)
Status:: Draft

*Rationale.*
A deployment decision needs the limits of the middleware underneath the binding, including limits that setup declarations cannot remove.

Timing budgets here are the system's allocation.
Where a supported configuration offers a timing package, that package is its maintainers' (`+aou~seooc-timing-budgets~7+`).

End-to-end protection means whatever the system supplies.
The SDK's E2E wire is deferred and not part of this delivery.

== A lending binding records and reports the writer's level

[.specitem,oft-sid="req~ssr-binding-integrity-level~1",oft-title="A lending binding records and reports the writer's level",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
*Lending bindings.*

* A lending binding *MUST* record each writer's integrity level in the shared definition of its service, where its middleware can.
* It *MUST* report to the element the level it finds there.
* A level it cannot record or read *MUST* be reported as unknown.
* A publisher whose level is below the level the service records *MUST* be refused at its own setup, naming the route and both levels.

*Handoff bindings.*
A handoff binding hands the element a private copy, so the check does not apply to it, and its README *MUST* say so.
--

[horizontal]
ASIL:: B
Allocated to:: each binding
Verification:: test (the binding contract suite), fault-injection (a publisher below the recorded level, with real processes)
Status:: Draft

*Rationale.*
The element can compare levels only if each binding records them where every process of a service can read them.
A level nobody can read counts as unknown, as on a receive route (`+req~ssr-integrity-zero-copy~4+`).

== A binding this project ships inventories its own `+unsafe+`

[.specitem,oft-sid="req~ssr-binding-unsafe-inventory~1",oft-title="A binding this project ships inventories its own `unsafe`",oft-needs="impl,utest",oft-tags="SafetyBinding"]
--
Every `+unsafe+` site in a binding this project ships *MUST* state the memory-safety obligation it relies on, and sit under a reviewed row of the binding's own inventory, checked by the same gate as the element's.

CI *MUST* refuse a new, changed or vanished site until the inventory is updated.
--

[horizontal]
ASIL:: B
Allocated to:: each binding this project ships
Verification:: gate (the binding's copy of the inventory check, with a negative control)
Status:: Draft

*Rationale.*
A binding's `+unsafe+` code runs on the same runtime paths as the element's.
So its obligations need the same record and the same gate (`+req~ssr-unsafe-inventory~3+`).
