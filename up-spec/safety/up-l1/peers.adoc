== Peer failure is normal input

[.specitem,oft-sid="req~ssr-peer-failure-normal~3",oft-title="Peer failure is normal input",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*What a peer's failure must not cause.*
A peer process that dies at any instruction, or restarts, *MUST NOT* cause any of the following in element code in any process that stays up:

* a panic;
* a heap acquisition;
* an unbounded wait;
* a heap release on a native route, on a route whose heap class is none or in work they share.

*The one exception to the unbounded wait.*
The one exception to the unbounded wait is the release of what the failure ends.
It waits for no peer, and what it releases stays charged until it completes.

* Where it is pending cleanup, a retained owner's deferred return included, it is isolated as `+req~ssr-release-lease-drop~4+` states.
So no survivor's operation, arrival, deadline or expiry accounting, health report or other owner's return waits for it.
* On a serialized or owned route whose declared heap class admits allocation, and which does not require non-waiting release (`+req~ssr-heap-guarantees~1+`), an owned value's release runs under the route's declared policy on a path of that route, after the failure's outcome has been recorded (`+req~ssr-heap-slot-types~3+`).
* An owned value's destruction never runs in a native operation, in the work one causes or in work that a native route shares.

*What survivors see.*
Those processes *MUST* see the failure only as silence, counted deadline misses, call errors, or a reported peer loss or restart.
Each is due without waiting for that release, and each is recorded before the release of what it ended starts.

*Routes that declare allocation.*
On a serialized or owned route whose declared heap class admits allocation, a call or frame that such an outcome ends releases what it owns exactly once as `+req~ssr-heap-slot-types~3+` states.
That is the only heap use the failure causes there.
It releases no route, role, table, startup region or other runtime resource and revokes no surviving owner.
--

ASIL:: B
Allocated to:: the element
Verification:: fault-injection inside a heap-window
* A peer killed and restarted during traffic, on real iceoryx2 and on in-memory bindings of both families.
* On a serialized route that admits owning values, a restart report that fails a call holding a decoded response, with that one release under the declared class and nothing else.
* On such a route that requires non-waiting release, the call error reported while that release is held pending.
* On one that does not, the call error recorded before that release starts.
Status:: Draft
ISO 26262:: 9-7.4.4 g, 6-Annex D.2.4 (part-clause numbers only)

*Rationale.*
Peers run in other processes, often over middleware this project does not control.
So each process has to protect itself from their failures rather than rely on them.
A peer dying or restarting is therefore normal input to a transport, and a frame from an earlier incarnation of a peer is refused as stale (`+req~ssr-peer-stale-rejected~3+`).

_Why revision 2._
Revision 1 forbade any heap use in a surviving process.
A serialized route cannot meet that when a peer's failure ends a call that holds a decoded owned response: that value must still be destroyed, once.

This revision keeps the failure's own handling free of heap acquisition everywhere, and of heap release on native and heap-free routes.
It confines the release of what the failure ends to the route's declared class (`+req~ssr-heap-none~3+`).

_Why revision 3._
Revision 2 kept every such release pending and apart, which needs a release service wherever a value is owned.
An ordinary owning route has none and requires none (`+req~ssr-heap-guarantees~1+`).
That release can wait behind an allocator's lock like any other.
So this revision keeps it pending and apart on a route that requires non-waiting release, and elsewhere lets it run under the route's declared policy, after the failure's outcome is recorded and never in native or shared work.

== A native representation never crosses an ABI

[.specitem,oft-sid="req~ssr-native-abi-agreed~1",oft-title="A native representation never crosses an ABI",oft-needs="impl,utest",oft-tags="SafetyUpRustCore,SafetyBinding"]
--
*The fingerprint.*
The element *MUST* state an ABI fingerprint of its target:

* its byte order;
* its pointer width;
* the size and alignment of each scalar its stable payloads admit, `+u128+` and `+i128+` included.

*Refusal at setup.*
At setup, a route whose wire carries a native representation is refused when a peer's fingerprint differs.
The refusal names both ABIs and the copying route as the fix.

*Recording.*
Every peer of a route that admits a native wire records its fingerprint when it creates its side.
A native peer refuses one that records none, by name.

*Scope.*
A serialized wire is not affected.

*Bindings.*
Each binding that carries native frames between processes exchanges the fingerprint at setup.
--

[horizontal]
ASIL:: B
Allocated to:: the element; each binding that carries native frames between processes
Verification:: test
* The binding contract's refusal of an ABI mismatch at setup, on the test doubles and on iceoryx2 with two processes.
* The fingerprint's unit tests.
* Each Miri lane's logged fingerprint, on three targets with three values.
Status:: Draft

*Rationale.*
Equal message identity does not imply equal in-memory layout.
An explicit ABI agreement prevents interpreting one target layout as another.

== Stale peers are rejected

[.specitem,oft-sid="req~ssr-peer-stale-rejected~3",oft-title="Stale peers are rejected",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*Stale frames.*
A frame from an earlier incarnation of a peer *MUST* be recognized by its full incarnation and refused as stale, never treated as current, and counted.

*Identity and incarnation.*
A peer's identity is stable across its restarts, and the incarnation the element records for it only rises.

*One exclusive step.*
The element *MUST* compare a frame's full peer identity and incarnation with the recorded ones, and record a newer incarnation, as one exclusive step of its configuration's mechanism, so that no concurrent classification, restart, loss or restart report can:

* make a stale incarnation current;
* move the recorded incarnation back; or
* bind one peer's frames to another peer's entry.

*No limit on concurrent classification.*
Classification places no limit on how many frames of one peer are classified at once.
A frame is refused only as stale, as undeclared (`+req~ssr-peer-admission~2+`), or because the table that its declaration sized is genuinely full.

*Restart reports.*
A binding's restart report fails the calls bound to older incarnations of that peer, and is counted.

*No admission from a stale incarnation.*
No frame is admitted as current from a stale incarnation.
--

[horizontal]
ASIL:: B
Allocated to:: the element
Verification:: test, fault-injection, review
* *test*
** A stale incarnation refused and counted.
** A newer one recorded, with the calls of older incarnations failed.
** Frames of one peer classified concurrently from several threads, and on an MCU from an interrupt handler where its configuration admits one, with no misclassification and no limit on concurrent classifications.
** The loss of an old incarnation racing the current incarnation's frames.
** An unknown identity that is never a wildcard.
** A genuinely full table refused as full.
* *fault-injection*: a restart on real iceoryx2, and a test double that restarts.
* *review*: the exclusive step's source argument for each configuration's mechanism, against every participant that can reach the table.
Status:: Draft

*Rationale.*
A restarted peer must not inherit frames or calls from its predecessor, and contention must not turn a stale incarnation into a current one.

_Why revision 3._
Revision 2 named the mechanism of one representation: 32-bit words, a contended raise refused as contention, and at most 255 concurrent classifications of one peer.
Those limits belonged to that mechanism, not to the product.
A mechanism that keeps each peer's full 64-bit identity and incarnation in one exclusive record has neither limit.
So the requirement states the outcome that every mechanism keeps instead.

Full width removes a wrap window.
It does not by itself establish the exclusion argument, which the review of each mechanism supplies (`+req~ssr-atomic-width~2+`).

== Undeclared peers cannot lock out declared ones

[.specitem,oft-sid="req~ssr-peer-admission~2",oft-title="Undeclared peers cannot lock out declared ones",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
On a route with a declared list of peers, a frame from an undeclared source *MUST* be refused and counted before it takes a peer-table entry.

* The table is sized from the declaration, and a declaration that the table or the binding cannot hold is refused at setup.
* A lost peer's entry is returned.
* Returning it never makes a later peer's frames be refused as stale, whatever frames of the lost peer are in flight at that moment.
--

[horizontal]
ASIL:: B
Allocated to:: the element
Verification:: fault-injection (strangers first, then declared clients; a lost peer racing its own last frame, on two threads), miri, test
Status:: Draft

*Rationale.*
Undeclared sources must not consume the entries reserved for declared peers.
Concurrent reuse must preserve the identity of each entry.
