= Safety requirements for traceability
:toc: preamble

This area holds safety requirements that SDKs trace with OpenFastTrace (OFT), apart from the protocol specification.
It is laid out like the protocol specification: what is shared comes first, then a part for each protocol layer, then a part for each SDK element.
Its first content is the software safety requirements and assumptions of use of the up-rust SEooC, and of the transports, wires and Streamer that work with it.

It is a draft on a feature branch.
Every item in it is still Draft.

Each obligation is stated in one place, and tables, indexes and safety manuals summarize it and link to it.

=== Where a new item goes

* *Protocol requirements*, which every SDK of a kind must meet, stay in the protocol chapters (`basics/`, `up-l1/`, `up-l2/`, `up-l3/`), tagged as those chapters tag them.
* *A safety obligation of a protocol layer* goes in that layer's part here.
A restriction that only one transport has goes in that transport's file, beneath its layer.
* *An SDK element's own scope, boundary and implementation-specific rules* go in a directory of their own here, named `seooc-<sdk>/`.
They are written for one element and its parts, and no other SDK has to meet them.
* *A concept or fault model that several parts rely on* is described on this page, with its scope.
* *A part is added when it has content.*
No empty directory mirrors a protocol chapter.

[[filing]]
=== Filing an item does not widen it

Where an item is filed says which protocol responsibility it concerns.
Who must meet it is a separate matter, which the item's type, tags and allocation state.

* *An item binds the part its tags name* (<<tags>>), and nobody else.
* *Every item here was written for the up-rust SEooC* and for the parts that work with it.
An item in `up-l1/` or `up-l2/` is therefore no requirement on every transport, or on the SDK of another language.
Another SDK or transport takes one on only by adopting its tag.
* *An assumption of use keeps `seooc` in its ID wherever it is filed.*
It is that element's assumption, and it binds an integrator that claims that element's safety-assurance scope.
* *A language-agnostic safety requirement*, if one is added, gets a tag of its own and says whom it binds.
* *Nothing here weakens the protocol.*
A requirement of the protocol chapters, a security requirement included, stays in force beside every item of this area.

[[concepts]]
== Shared concepts and fault models

Several parts of this area rely on the concepts below.
Each entry says what the concept is, where it applies, and which items state it.
An entry summarizes those items and adds no duty: the items govern.

=== Software obligations and deployment duties

[cols="2,4,3",options="header"]
|===
| Kind | Who meets it | How an item shows it

| Software safety requirement | The part that its tags and its "Allocated to" line name: the element, a binding, a wire, a platform backend or the Streamer | Type `req`, with *MUST* and *MUST NOT*
| Assumption of use | The integrator, including what its application, platform and deployment owner provide | Type `aou`, with *SHALL* and *SHALL NOT*
|===

* *Scope.*
Every item of this area.
* *The two do not stand in for each other.*
A deployment's promise meets no software requirement, and the software discharges no deployment duty.
* *An assumption of use obliges no software.*
Where one describes what the software does, the description is a summary for the integrator.
A software obligation is stated only by a requirement.

[[integrity-level]]
=== Integrity levels

A transport declares one integrity level: QM, A, B, C or D, in that order.

* *Scope.*
Every transport of the up-rust SEooC, and every route on it.
* *A level is a label.*
Setup checks it.
It neither raises an element's capability nor qualifies the process that declares it.
* *A level is not a request.*
An integrity level or an ASIL label requests no timing bound and no assurance scope, and it is neither a request nor evidence for a resource guarantee.
* *Stated in.*
`+req~ssr-integrity-declared~3+` for the software, `+aou~seooc-integrity-levels~5+` for the integrator, and xref:seooc-up-rust/README.adoc#claims[the SEooC's claims] for what a label is not.

[[faulty-peer]]
=== The faulty-peer model

Every peer is treated as faulty, never malicious.
A faulty peer may send any content, at any time and in any volume, may choose any source URI, and may write values its own middleware never writes into shared memory it can write.
The requirements hold against all of it.

* *Scope.*
The peers of the up-rust SEooC, on every transport.
The model applies within the access restriction that the integrator provides: only the processes deployed to use a transport's resources reach them.
* *What it excludes.*
Deliberate exploitation, such as engineering a peer-ID hash collision, which is a security matter.
* *What it does not relax.*
The model bounds the safety argument and nothing else.
It lifts no security requirement of the protocol: a transport still provides the means against address spoofing and unauthorized access that xref:../up-l1/README.adoc[uP-L1] requires.
It also does not make a lower-assurance process harmless because it runs apart: the rules for lending and copying cover what such a process can write into shared memory.
* *Stated in.*
`+aou~seooc-peer-access~4+` for the model and the access restriction.
`+req~ssr-peer-failure-normal~3+`, `+req~ssr-refuse-no-panic~1+`, `+req~ssr-peer-admission~2+` and `+req~ssr-integrity-zero-copy~4+` for the software's side.

[[process-failure]]
=== Process failure and restart

A process leaves runtime mode only by exit, crash or kill.
There is no recovery inside the process: a supervisor outside it restarts the whole process or partition, or takes the item to its safe state.
A peer's death or restart is normal input to the processes that stay up.

* *Scope.*
Every process that uses the up-rust SEooC, the Streamer included.
* *Stated in.*
`+aou~seooc-supervisor-restart~4+` for the supervisor.
`+req~ssr-mode-no-shutdown~1+` and `+req~ssr-mode-restart~1+` for the element, `+req~ssr-peer-failure-normal~3+` for the survivors, and `+req~ssr-binding-predecessor-cleanup~1+` for a binding.

[[memory-separation]]
=== Memory separation

The requirements assume that a faulty process cannot write another process's private memory.
Shared memory exists only where a binding maps it, and the faulty-peer model covers what a peer writes there.

* *Scope.*
Every process or partition that uses the up-rust SEooC.
* *Who provides it.*
The integrator, through the memory protection of the OS or, on an MCU, the partition boundary its configuration states.
The element can neither provide nor check it.
* *Stated in.*
`+aou~seooc-process-isolation~3+`.

[[violation]]
=== How a violated assumption shows up

A violated assumption of use is refused at setup, counted, or undetectable by the element.

* *Scope.*
The assumptions of use of the up-rust SEooC, wherever they are filed.
* *Stated in.*
xref:seooc-up-rust/assumptions-of-use.adoc#violation-classes[The element's assumptions of use].

[[claims-model]]
=== Claims and guarantees

Functional communication, native resource behaviour, a finite timing bound and safety assurance are four independent properties.
A stronger resource guarantee is reported as required or not, established or not, and admitted or not, and it is admitted only where it is both required and established.

* *Scope.*
The up-rust SEooC, and each route of it.
It is that element's model, and no rule of a protocol layer.
* *Stated in.*
xref:seooc-up-rust/README.adoc#claims[The SEooC's claims] and `+req~ssr-heap-guarantees~1+`.

[[spec-first]]
== The specification comes first

The items here say what an implementation must satisfy.
An implementation's code, tests and reviews trace to the items, never the other way round.

* No statement, rationale or verification entry rests on an implementation's source files, internal names, review records or current state.
* A rationale gives the product or safety reason for its statement.
It cites other items of up-spec, public standards and the published contracts of other projects.
* A statement may name something the element must provide, such as an operation, a setting, a counter or a crate.
That name is part of the specification, not a citation of code.
* An SDK that implements an item keeps its own record of where it does so, outside this repository, as non-normative traceability.

== Why this area cannot break an SDK's run

An OFT run keeps the items in the files its patterns name and its tag filter selects, and reports each kept item that lacks coverage.
So:

* *An SDK reads this area only by naming it.*
Each SDK names up-spec files and directories in its OFT patterns.
One that adopts these items names the parts that hold them, as up-rust names `safety/up-l1`, `safety/up-l2` and `safety/seooc-up-rust`, and no SDK names `safety/` as a whole.
Nothing here sits at the top of the repository, where a pattern such as `up-spec/*.adoc` would reach it.
* *Every item here carries a tag from the table below, and no tag of the protocol chapters.*
A run that keeps untagged items (`_`), or items tagged `LanguageLibrary`, `TransportLayerImpl` and the like, keeps none of them.
The patterns are the first guard: a run whose tag filter is missing keeps every item its patterns reach, and still none from here.
* *A layer part holds items of several repositories.*
A run that names one keeps only the items whose tags its filter selects.
So the tags, not the directories, decide what a repository covers.
* *Nothing here links to the protocol chapters through OFT,* so they gain no coverage obligations from it.

== The items

=== Artifact types

`req` for a software safety requirement, `aou` for an assumption of use, the types up-spec already uses.

=== IDs

`+req~ssr-<area>-<name>~<revision>+` and `+aou~seooc-<name>~<revision>+`.

* A name is never changed or reused.
* A revision rises when the meaning of a statement changes, not for a wording fix.
* Filing an item in another part or file changes neither its name nor its revision.

=== Markup

As in the protocol chapters: a block attribute line that gives the item its `specitem` role and its `oft-sid`, `oft-title`, `oft-needs` and `oft-tags` attributes, then an open block that holds the statement.

* Inside the block, a statement may use short paragraphs, labels in bold and lists.
All of it is the statement.
* Text after the block is not part of the item: the ASIL, the allocation, the verification methods, the status, the ISO 26262 references and the rationale.
* A rationale cites only public sources: up-spec, public standards by part and clause number, and the published documents and code of other projects, each at a fixed version.
It does not cite the code of the SDK that implements the item (<<spec-first>>).

=== Key words

Statements use the key words of BCP 14 as up-spec does (xref:../basics/payload_encoding_registry.adoc[the payload encoding registry], "Requirement Ownership"):

* *MUST* and *MUST NOT* for the element and its parts;
* *SHALL* and *SHALL NOT* for an assumption of use, whose duty falls on the integrator.

Both keep BCP 14's meaning of an absolute requirement.
An item not yet rewritten for publication states its duties without key words, and binds just the same.

=== Needs

* A requirement met in code needs `impl,utest`: the code that meets it, and the tests that show it, carry coverage tags.
* A requirement shown only by reviewing a document needs `uman`.
* A requirement met in code that also makes the element state something for integrators needs `impl,utest,uman`.
* An assumption of use needs `uman`: the safety manual states it.
A document covers it with an item of its own that covers the assumption, because OFT reads no coverage tag in a Markdown file.

=== Status

* "Draft" until the requirements are signed off.
* "Draft, pending owner (S0 O-n)" marks text that waits on an owner decision of the S0 document.
* The words "record pending" mark text that cites a binding's record that is not committed yet: its ID is filled in when it is.
* "Revision pending" beside a record's ID marks text that already relies on that record's next revision.

=== (b)

In the end-to-end protection items, *(b)* marks text that the chosen restart design brought in: the full version, with both sender kinds.
That text holds.

=== Gate tags

Each repository that covers items here gets one gate tag, named after it: `SafetyGateUpRust`, `SafetyGateStreamer`, `SafetyGateIceoryx2`, `SafetyGateXcdrV2`, and so on.

* An item gets a repository's gate tag once that repository covers it in OFT's sense, with at least one coverage link of each type the item needs.
* Coverage in OFT's sense says nothing about whether an item is verified, which its verification methods decide.
* A repository's gating runs keep only the items that carry its gate tag, so they stay green while it covers the rest, and a report-only run keeps them all.
* Bindings and wires share items, so each gets a gate tag of its own.
* Gate tags present on items record the repository mappings admitted with them.

[[tracing]]
== How a repository starts tracing these items

. Its OFT patterns add the parts that hold the items it covers, for example `up-spec/safety/up-l1`, `up-spec/safety/up-l2` and `up-spec/safety/seooc-up-rust` for up-rust.
. Its gating runs add its gate tag to their filter, for example `SafetyGateUpRust`, and not the tags of the table.
Every item they keep is then covered, and every coverage tag in the repository resolves.
. A report-only run, which fails nothing, adds the tags of the table it covers as well, for example `SafetyUpRustCore`, and shows every item still to cover.
. Code and tests carry OFT's own coverage tags, `+[impl->req~ssr-…~N]+` and `+[utest->req~ssr-…~N]+`, only for items its gating runs keep, because a tag naming an item the run did not keep is a broken link.
A review log in the repository records who mapped each tag.
. The up-spec change that defines or gates an item lands first.
The repository moves its copy of up-spec, a submodule or a pinned copied snapshot as that repository packages it, to that change in the same merge as the commit that tags the item.
It records which change it copied, so that no run sees a tag without its item.
. A change that files items in another part lands the same way.
The repository's patterns name the new part in the same merge, so that no run loses an item it kept before.

== ISO 26262

Items and text in this area cite ISO 26262 by part and clause number only, written `part-clause`, for example `6-7.4.13`, or `part-Table n`.
No text of the standard appears here, quoted or closely paraphrased, and no table that maps it.

== Source

The items of this area were first written outside this repository, for the up-rust SEooC, and are being rewritten for publication.

* A rewritten item's statement uses the key words above, with its meaning unchanged.
* Its rationale is written from public sources alone: up-spec, public standards, and the published documents and code of other projects, each linked at a fixed version.
ISO 26262 is cited by part and clause number only.
* A rationale names each source where it uses it, and an item ID is one of up-spec's.
* A rationale does not cite the code of the SDK that implements the item (<<spec-first>>).

An item not yet rewritten keeps only the rationale sentences that cited public sources, so its rationale may be short or absent.

The decisions each item rests on, the reviews that shaped it and its history are kept outside this repository, with the rationale sentences that cited them.
Rationale sentences that cited ISO 26262 were left out, and their part-clause numbers are kept in each item's ISO 26262 line.
