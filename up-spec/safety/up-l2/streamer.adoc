= uP-L2 safety: Streamer
:toc: preamble

The key words "*MUST*", "*MUST NOT*", "*REQUIRED*", "*SHALL*", "*SHALL NOT*", "*SHOULD*", "*SHOULD NOT*", "*RECOMMENDED*", "*MAY*", and "*OPTIONAL*" in this document are to be interpreted as described in https://www.rfc-editor.org/info/bcp14[IETF BCP14 (RFC2119 & RFC8174)]

Conventions, tags and status words: xref:../README.adoc[the safety area's README].
This layer, and whom it binds: xref:README.adoc[safety at uP-L2].
Scope and element boundary: xref:../seooc-up-rust/README.adoc[the up-rust SEooC's README].

Allocated to the Streamer and its binary, in `up-streamer` (tag `SafetyStreamer`).

The last two sections are the two assumptions of use about operating the Streamer.

* They are the up-rust SEooC's assumptions, as `seooc` in their IDs says.
They bind an integrator that claims its safety-assurance scope (xref:../seooc-up-rust/assumptions-of-use.adoc#who[who the assumptions bind]).
* They are deployment duties.
No requirement on the Streamer is met by them, and they replace none.
* Each "Violation" text uses the three classes of xref:../seooc-up-rust/assumptions-of-use.adoc#violation-classes[how a violation shows up].
* They carry `SafetyManual` only (xref:../seooc-up-rust/assumptions-of-use.adoc#coverage[tags and coverage]).
* Their sentences about strict mode concern the element's strict mode, and apply where it is used (xref:../seooc-up-rust/build.adoc#req-ssr-strict-report[Strict mode reports on every run] in xref:../seooc-up-rust/build.adoc[build and shipped content]).

[[req-ssr-streamer-route-lock]]
== Routes and subscriptions are locked at activation

[.specitem,oft-sid="req~ssr-streamer-route-lock~3",oft-title="Routes and subscriptions are locked at activation",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
*Routes.*
A route *MUST NOT* be added to or removed from the Streamer after it is activated, and a route's definition *MUST NOT* change: its filters, legs, QoS and wires.
A route's gate (<<req-ssr-streamer-route-gate,Each route has a heap-free gate>>) is the only route state that changes in runtime mode.

*Subscriptions.*
The subscription directory *MUST* be read once at setup and then frozen, and a live subscription source *MUST* be refused at setup.

*The runtime type.*
The runtime Streamer type *MUST NOT* have a route, listener or subscription operation, and misuse *MUST NOT* compile.

*Before activation.*
A frame *MUST NOT* be forwarded before activation.
--

[horizontal]
ID:: `+req~ssr-streamer-route-lock~3+`
ASIL:: B
Allocated to:: the Streamer
Verification:: compile-fail (add or delete after activation; forward before activation; activate with a setup value), test (a live subscription source is refused)
Status:: Draft
ISO 26262:: 6-7.4.3, 6-6.4.2 g (part-clause numbers only)

*Rationale.*
A route added or changed while traffic flows would run without the setup checks that admitted the others, through a configuration nobody validated (xref:../seooc-up-rust/runtime-modes.adoc#req-ssr-mode-no-setup-at-runtime[Setup is impossible in runtime mode]).

A live subscription source would change the routes in effect from outside, at run time.
So the directory is read once and frozen.

[[req-ssr-config-exact-addresses]]
== ASIL Streamer routes name exact source addresses

[.specitem,oft-sid="req~ssr-config-exact-addresses~1",oft-title="ASIL Streamer routes name exact source addresses",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
In the ASIL Streamer:

* every route's source filter *MUST* name one exact address;
* every lending leg *MUST* name its physical service exactly.

A wildcard source *MUST* be refused at setup, naming the route.

A frame from an address that no route reserved *MUST* be refused and counted.
--

[horizontal]
ID:: `+req~ssr-config-exact-addresses~1+`
ASIL:: B
Allocated to:: the Streamer
Verification:: test
Status:: Draft

*Rationale.*
An exact source filter bounds route matching and lets the Streamer refuse and count frames carrying an undeclared address.

It does not authenticate a sending process: a faulty process using a reserved address can pass the filter.
Physical service selection does not establish that identity either.
Access control, peer qualification and end-to-end protection retain their separate assumptions and limits.

The carrier primitives require the same of a lending leg.
A lending route names one physical service, and a wildcard filter on one needs an explicit physical source or is refused.

[[req-ssr-streamer-heap-free]]
== The Streamer allocates nothing in runtime mode

[.specitem,oft-sid="req~ssr-streamer-heap-free~1",oft-title="The Streamer allocates nothing in runtime mode",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
The Streamer's own code *MUST NOT* acquire or release heap memory in runtime mode, on every forwarding path:

* the first frame on every route;
* a full egress;
* a failed egress;
* a refused or expired frame;
* a disabled route;
* a peer dying or restarting.
--

[horizontal]
ID:: `+req~ssr-streamer-heap-free~1+`
ASIL:: B
Allocated to:: the Streamer
Verification:: heap-window (Rust guard and C-level observer, on Linux and macOS; QNX once a target exists), fault-injection
Status:: Draft
ISO 26262:: 6-Table 6 1b (part-clause numbers only)

*Rationale.*
The Streamer forwards every frame between its transports.
So heap use on its path would break runtime mode for every route it carries (xref:../seooc-up-rust/heap.adoc#req-ssr-heap-none[No heap in runtime mode]).

An ASIL route through the Streamer is only as sound as the Streamer, so it cannot be left as a QM carrier.

A serialized leg's declared allocation belongs to that leg's wire or binding and is reported per route.
It never reaches the Streamer's own forwarding, control or error paths, or a native leg.

[[req-ssr-streamer-byte-identity]]
== Carriage keeps the bytes

[.specitem,oft-sid="req~ssr-streamer-byte-identity~2",oft-title="Carriage keeps the bytes",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
*Identifier, presence and bytes.*
A carrier *MUST* keep identifier and payload bytes unchanged on every hop, with at most one payload copy per hop and no automatic negotiation or transcoding.
An absent payload *MUST* stay absent, and a present payload *MUST* stay present with its identifier, a zero-length payload included.

*No reader is needed.*
A payload whose frame names no native representation is a serialized payload: a carrier carries its bytes without reading them, whatever its encoding identifier is.
For such a payload, a carrier:

* *MUST NOT* require a wire, a decoder or any other reader of the encoding;
* *MUST NOT* refuse the frame because the identifier is reserved, unassigned, private or unknown to it, or because no wire of the route names it;
* *MUST NOT* give the identifier a meaning of its own, so `0xFFFF` is carried as any other identifier is.

*The one refusal by identifier.*
A route's encoding filter is the only reason for which a carrier refuses a serialized payload by its identifier (<<req-ssr-streamer-qos-per-leg,Both legs are checked, at setup and per frame>>).
A route has no filter unless its deployment data states one, and a route without one refuses no serialized payload for its identifier.

*No staging.*
Already-serialized input *MUST NOT* be staged:

* a byte-only egress receives the ingress bytes directly;
* a lending egress takes one copy into its loan.

A different egress envelope *MUST* re-encode the metadata only.
--

[horizontal]
ID:: `+req~ssr-streamer-byte-identity~2+`
ASIL:: B
Allocated to:: the Streamer
Verification:: test
* *test*
** Byte identity on every route kind, and the loan-address checks.
** On a route with no encoding filter, a serialized payload under an identifier that no wire of the route names, carried with its identifier and bytes unchanged: an assigned identifier, an unassigned one, a reserved one, a private-use one, `0` and `0xFFFF`.
** An absent payload kept absent, and a present zero-length payload kept present with its identifier, between two different envelopes.
** The same frames carried the same way after a wire that reads their encoding is added to the route.
** A control: a carrier that refuses a frame because no wire of the route names its identifier fails.
Status:: Draft

*Rationale.*
up-spec makes a component that only carries or forwards a message keep its identifier and payload bytes unchanged, with no decoder needed (xref:../../basics/payload_encoding_registry.adoc#acceptance[the payload encoding registry, "Carrying a Payload versus Reading It"]).

_No reader._
The same rule keeps such a component from refusing carriage because an identifier is reserved, unassigned, private or unknown to it.
The registry states it as an assumption of use, and leaves a component's own requirement to that component's specification (xref:../../basics/payload_encoding_registry.adoc#obligations[the payload encoding registry, "Requirement Ownership"]).
So this item states it for the Streamer.

A route's wires are named when the route is set up (<<req-ssr-streamer-route-lock,Routes and subscriptions are locked at activation>>).
If carriage depended on them, a payload that only its endpoints read could cross a Streamer only after the Streamer's deployment data had been changed for it.
Learning later what an identifier means must not change how a payload is carried, so adding a wire to a route changes nothing for the frames that the route already carried.

_The one refusal by identifier._
A deployment can still decide which encodings one of its routes forwards.
That is a choice about the route, and it is stated as one: an encoding filter in the route's deployment data, which <<req-ssr-streamer-qos-per-leg,Both legs are checked, at setup and per frame>> bounds.
It is kept apart from what a carrier can read, so that no route starts to refuse an identifier because a wire or a decoder is missing.
Whether a route with a filter still meets up-spec's rule for a component that only carries is not decided, and this item does not say that it does (xref:../../contract-generations.adoc#transition[the transition table]).

_Presence._
A payload and its identifier are present together or absent together (xref:../../basics/uattributes.adoc#common-attributes[UAttributes], `payloadEncodingId`).
So keeping the identifier unchanged keeps the presence too.
The statement says so because a different egress envelope writes the metadata again, and an envelope that could not tell an absent payload from an empty one would lose the difference.

_A native representation._
A reader borrows a native representation in place, so a frame that names one is not carried as bytes under this item.
<<req-ssr-streamer-qos-per-leg,Both legs are checked, at setup and per frame>> says when a leg carries it.

Unchanged bytes let a check made at the endpoints, such as end-to-end protection, cover every hop (xref:../seooc-up-rust/e2e-wire.adoc#req-ssr-e2e-survives-hops[Protection survives every allowed hop]).
A copy staged on the way would add work and a buffer for nothing.

The carrier primitives hold to it: a byte-only egress receives the ingress bytes directly, and a lending egress takes one copy into its loan.

[[req-ssr-streamer-no-ingress-block]]
== An egress never blocks an ingress

[.specitem,oft-sid="req~ssr-streamer-no-ingress-block~1",oft-title="An egress never blocks an ingress",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
A slow, full or failed egress *MUST NOT* block an ingress or a worker beyond its bound.

The Streamer *MUST*:

* check egress capacity before it takes a frame;
* park frames only within the route's retained budget;
* otherwise apply the egress route's overflow policy and count every drop.
--

[horizontal]
ID:: `+req~ssr-streamer-no-ingress-block~1+`
ASIL:: B
Allocated to:: the Streamer
Verification:: fault-injection (a slow egress; a dead egress), test
Status:: Draft
ISO 26262:: 6-Annex D.2.2 (part-clause numbers only)

*Rationale.*
The carrier primitives ask for capacity before taking a frame.
They can park a frame from a lending ingress in fixed storage, within the route's retained budget.

[[req-ssr-streamer-containment]]
== A fault stays on its route

[.specitem,oft-sid="req~ssr-streamer-containment~1",oft-title="A fault stays on its route",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
A fault on one route (a dead or slow egress, a malformed header, a flood, exhausted slots, a killed peer) *MUST* be counted on that route and *MUST NOT* delay any other route beyond its declared budget.
--

[horizontal]
ID:: `+req~ssr-streamer-containment~1+`
ASIL:: B
Allocated to:: the Streamer
Verification:: fault-injection
Status:: Draft
ISO 26262:: 6-7.4.12, 6-Annex D (part-clause numbers only)

*Rationale.*
Counting the fault on its own route shows where it is, while the other routes keep their budgets.

The budget the Streamer enforces is a route's work and capacity: slots, retained frames and the work each pass may do for it.
A bound on another route's delay in time is a timing claim of a supported configuration, with its scheduler and resource argument.

[[req-ssr-streamer-qos-per-leg]]
== Both legs are checked, at setup and per frame

[.specitem,oft-sid="req~ssr-streamer-qos-per-leg~2",oft-title="Both legs are checked, at setup and per frame",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
*At setup.*
When a route is set up, the QoS of both its legs *MUST* be checked, and a refusal *MUST* name the leg.
Setup *MUST* report, for each route, whether it has an encoding filter and which identifiers the filter names.

*Per frame.*
Before each frame is forwarded, it *MUST* be checked against the egress leg's own limits on every forwarding path, and against its TTL.
A leg's limits are:

* the payload size;
* the token length;
* what the leg's envelope can represent;
* for a frame whose header names a native representation, the native representations that the route's wires name;
* the route's encoding filter, where its deployment data states one.

*A native representation.*
A frame whose header names a native representation that none of the route's wires names *MUST* be refused.
It *MUST NOT* be carried as serialized bytes, and what names its representation *MUST NOT* be removed or changed.

*The encoding identifier.*
The encoding identifier of a payload that a leg carries as serialized bytes is not a limit of the leg.
A leg *MUST NOT* refuse such a payload for its identifier, except through the route's encoding filter.

*An encoding filter.*
A route's deployment data *MAY* state an encoding filter: the list of the encoding identifiers of the serialized payloads that the route forwards.

* A route has no filter unless its deployment data states one.
A filter *MUST NOT* be derived from the route's wires, from the decoders that a build contains or from any other reader.
* A route with a filter *MUST* refuse a serialized payload whose identifier the list does not name.
It *MUST* forward one whose identifier the list names exactly as a route without a filter does, with or without a reader of that encoding.
* The refusal *MUST* be counted under a cause of its own, which names the filter.
It *MUST NOT* be reported as an unknown, unsupported or invalid encoding, or as a failure to decode.
* A filter names identifiers and nothing else.
It gives none of them a meaning: `0xFFFF` in a filter names that one identifier and matches no other.
It *MUST NOT* apply to a frame whose header names a native representation.
A frame with no payload has no identifier, and a filter does not refuse it.
* A filter is part of its route's definition, which does not change after activation (<<req-ssr-streamer-route-lock,Routes and subscriptions are locked at activation>>).
--

[horizontal]
ID:: `+req~ssr-streamer-qos-per-leg~2+`
ASIL:: B
Allocated to:: the Streamer
Verification:: test
* *test*
** Each limit refusing its frame on every forwarding path, counted under a cause of its own.
** A frame that names a native representation which none of the route's wires names: refused, with no part of it carried as serialized bytes.
** On a route with no encoding filter, a serialized payload under an identifier that no wire of the route names: forwarded.
** A route whose deployment data states no filter has none, whatever wires and decoders the build contains.
** On a route with an encoding filter, a serialized payload whose identifier the filter names: forwarded with its identifier, presence and bytes unchanged, with and without a wire that reads it.
** On a route with an encoding filter, a serialized payload whose identifier the filter does not name: refused, and counted under the filter's cause and under no other.
** On a route with an encoding filter, a frame that names a native representation: admitted or refused by the route's wires alone.
** The setup report of each route's filter, and of a route that has none.
** Controls: a filter refusal counted as an unknown or invalid encoding fails, and so does a filter derived from the route's wires.
Status:: Draft

*Rationale.*
A limit checked on one forwarding path and not on another lets a frame through on the path that skips it, so every path checks.

_What a leg can refuse._
A leg refuses what it cannot hold or cannot express: a payload longer than its storage, a token longer than its bound, a head that its envelope cannot represent.
Each refusal is counted under its cause (xref:../seooc-up-rust/errors.adoc#req-ssr-error-no-silent-loss[No silent loss, and each loss counted once]).

_A native representation._
A reader borrows a native representation in place, so carrying one is not carrying bytes.
It is carried only where the route's setup agreed it (xref:../up-l1/peers.adoc#req-ssr-native-abi-agreed[A native representation never crosses an ABI]; xref:../up-l1/integrity.adoc#req-ssr-integrity-checked-at-admission[In-place frames are checked once, at admission]).
Carrying it as bytes, or under another name, would hand a reader memory that nothing agreed.
An encoding identifier is no part of that agreement, and a filter that names one admits no native representation.
That a route's wires name a representation selects a frame for carriage and proves nothing about it.
A layout, initialized storage and ownership are established by the reader's own admission, never by a name that a frame carries (xref:../up-l1/integrity.adoc#req-ssr-integrity-zero-copy[Zero-copy only from a writer at or above the reader]).

_The encoding identifier._
A carrier does not read a payload.
So the identifier of a serialized payload changes nothing that a leg holds or expresses, and by itself it is no reason to refuse a frame (xref:../../basics/payload_encoding_registry.adoc#acceptance[the payload encoding registry, "Carrying a Payload versus Reading It"]).

_Why a filter is stated, and off unless stated._
A deployment may want a route to forward only the encodings that it names.
A route that did so through its list of wires would refuse a payload because a reader is missing, and nobody could tell that refusal from a decision.
So the filter is a statement of its own in the deployment data: it is absent unless stated, it is reported at setup, and its refusal has a cause that names it.
A refused frame is then a deployment's recorded choice, and an identifier that a carrier cannot read is never refused for that.

_A filter and up-spec's rule._
up-spec's rule keeps a component that only carries from refusing carriage because an identifier is reserved, unassigned, private or unknown to it.
It does not say whether a deployment's own choice of what a route forwards is such a refusal.
So this item does not claim that a route with a filter meets that rule, and xref:../../contract-generations.adoc#transition[the transition table] records the question as open.
A route with no filter refuses no serialized payload for its identifier.

_What becomes of a refused frame._
This item says when a leg refuses a frame.
What becomes of a frame that is not forwarded, and what an RPC client is told, are stated by <<req-ssr-streamer-dispatch-obligations,Undeliverable messages are counted, never sent as dead letters>> and <<req-ssr-streamer-rpc-error-response,An RPC request that cannot be dispatched is answered, best effort>>, which this item leaves as they are.

[[req-ssr-streamer-startup-report]]
== The startup report says what will run

[.specitem,oft-sid="req~ssr-streamer-startup-report~3",oft-title="The startup report says what will run",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
Once `+enter_runtime_all+` has returned, and before the Streamer activates, it *MUST* produce a report, without heap, as fixed-size records.
The report lists:

* every route, with its kind, its wires and QoS, the send mode it got, its reserved storage, its heap class (naming the permit where middleware allocates), its integrity level and its worker;
* every active waiver;
* the digest of the deployment data it applied.

A refused startup names the route and the limit.
--

[horizontal]

ASIL:: B
Allocated to:: the Streamer
Verification:: test, heap-window
Status:: Draft

*Rationale.*

[[req-ssr-streamer-config-integrity]]
== The deployment data is checked before it is applied

[.specitem,oft-sid="req~ssr-streamer-config-integrity~1",oft-title="The deployment data is checked before it is applied",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
Before it applies any of its deployment data, the Streamer *MUST* check the data against an integrity code delivered with it.

Data whose code does not match its content *MUST* be refused, naming the mismatch, and *MUST NOT* be applied in any part.
--

[horizontal]
ID:: `+req~ssr-streamer-config-integrity~1+`
ASIL:: B
Allocated to:: the Streamer
Verification:: test (a mismatched code; a truncated file; a code computed over other content)
Status:: Draft
ISO 26262:: 6-C.4.10, 6-Table C.1 (part-clause numbers only)

*Rationale.*
Deployment data can be truncated or altered on its way to the Streamer, and a wrong route table or limit would then be applied as if it were right.

A code delivered with the data detects such a change only if it is compared before any of the data is used.
So the check comes first and refuses the whole file.

[[req-ssr-streamer-sync-data-plane]]
== The Streamer's data plane is synchronous

[.specitem,oft-sid="req~ssr-streamer-sync-data-plane~1",oft-title="The Streamer's data plane is synchronous",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
The Streamer's runtime forwarding path *MUST* be synchronous or polled.

It *MUST* use:

* no async runtime;
* none of `+core::future+`, `+core::task+` or `+core::pin+`;
* no boxed futures;
* no channel types.

The transports' reserved slots *MUST* be its only queues.
--

[horizontal]
ID:: `+req~ssr-streamer-sync-data-plane~1+`
ASIL:: B
Allocated to:: the Streamer
Verification:: gate (the crate's dependency set, and the token scan of xref:../seooc-up-rust/crate-isolation.adoc#req-ssr-crate-sync-path[Traffic is synchronous or polled]), heap-window
Status:: Draft

*Rationale.*
The Streamer is built from the element's carrier primitives, which offer traffic in synchronous or polled form with no futures, tasks or pinning (xref:../seooc-up-rust/crate-isolation.adoc#req-ssr-crate-sync-path[Traffic is synchronous or polled]).
An async runtime on top would bring back the heap they avoid.

A channel adds a queue beside the transports' reserved slots, where a frame could wait under no route's depth or overflow policy.

The synchronous form is the product's own rule.
It does not depend on which library modules a toolchain's qualification covers (xref:../seooc-up-rust/crate-isolation.adoc#req-ssr-crate-sync-path[Traffic is synchronous or polled]).

[[req-ssr-streamer-workers]]
== Workers are fixed at initialization

[.specitem,oft-sid="req~ssr-streamer-workers~1",oft-title="Workers are fixed at initialization",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
*At initialization.*
The Streamer's worker threads *MUST* be created during initialization, with their number, priority and affinity from deployment data.
Each route *MUST* be assigned to one worker there.

*In runtime mode.*
In runtime mode a worker *MUST NOT* be created, stopped or joined, and a worker's loop *MUST NOT* return.
--

[horizontal]
ID:: `+req~ssr-streamer-workers~1+`
ASIL:: B
Allocated to:: the Streamer binary
Verification:: test, review
Status:: Draft

*Rationale.*
Creating or joining a thread in runtime mode would bring the heap and an unbounded wait into the data path (xref:../seooc-up-rust/heap.adoc#req-ssr-heap-none[No heap in runtime mode]; xref:../seooc-up-rust/bounded-work.adoc#req-ssr-bound-wait[Every wait is bounded]).

A fixed assignment of routes to workers, made at setup, lets each route's latency be analysed before start.

Creating threads needs the operating system.
So the `+std+` binary creates the workers, outside the `+no_std+` crate that holds the route table and the forwarding loop (xref:../seooc-up-rust/README.adoc[the SEooC's README]).

[[req-ssr-streamer-route-gate]]
== Each route has a heap-free gate

[.specitem,oft-sid="req~ssr-streamer-route-gate~2",oft-title="Each route has a heap-free gate",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
*Three states.*
Each Streamer route *MUST* have a gate with three states, held in fixed storage: enabled, disabled by an operator, and tripped by a monitor.

*While the gate is not enabled.*
While a route's gate is not enabled, its frames *MUST* be dropped at admission and counted.
An RPC request among them *MUST* get the best-effort `+Unavailable+` response of <<req-ssr-streamer-rpc-error-response,An RPC request that cannot be dispatched is answered, best effort>>.

*What a gate changes.*
A gate *MUST* change its route's state only, never its definition (<<req-ssr-streamer-route-lock,Routes and subscriptions are locked at activation>>).

*Cost of a change.*
Changing a gate *MUST* allocate nothing, block nothing, release nothing and change no other route, and each change *MUST* be counted with its cause.

*A trip stays.*
A tripped gate *MUST* stay tripped until an operator re-enables the route.
--

[horizontal]
ID:: `+req~ssr-streamer-route-gate~2+`
ASIL:: B
Allocated to:: the Streamer
Verification:: test, heap-window
Status:: Draft

*Rationale.*
The Streamer's safe state is fail-silent per route, through its route gates (xref:../seooc-up-rust/README.adoc[the SEooC's README]).
So a gate silences one route while every other route carries on (<<req-ssr-streamer-containment,A fault stays on its route>>).

The gate is the only route state that changes in runtime mode (<<req-ssr-streamer-route-lock,Routes and subscriptions are locked at activation>>), and fixed storage lets it change without heap (xref:../seooc-up-rust/heap.adoc#req-ssr-heap-none[No heap in runtime mode]).

A gated request is answered `+Unavailable+` where the reverse route can carry it.
So a client without the E2E wire learns of the outage at once, not at its TTL (<<req-ssr-streamer-rpc-error-response,An RPC request that cannot be dispatched is answered, best effort>>).

With its cause counted, each change shows in the reports as an operator's disable or as a monitor's trip (<<req-ssr-streamer-operator-control,Operator changes go through a declared interface>>; <<req-ssr-streamer-monitors,Worker and transport monitors trip routes>>).

[[req-ssr-streamer-operator-control]]
== Operator changes go through a declared interface

[.specitem,oft-sid="req~ssr-streamer-operator-control~1",oft-title="Operator changes go through a declared interface",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
An operator *MUST NOT* be able to disable or re-enable a route in runtime mode other than through an interface declared at setup.

* The interface *MUST* name the routes it may change.
* The interface *MUST* use fixed-size records and no heap.
* Every change made through it *MUST* be counted, and shown in the route's report and in the mode report.
--

[horizontal]
ID:: `+req~ssr-streamer-operator-control~1+`
ASIL:: B
Allocated to:: the Streamer
Verification:: test, heap-window
Status:: Draft

*Rationale.*
Disabling an ASIL route removes its function.
So the only way to do it at run time is declared at setup, bounded and shown in the reports.
Who may use it is <<aou-seooc-operator-access,Only authorized operators reach the Streamer's operator interface>>.

Only an operator's re-enable clears a monitor's trip (<<req-ssr-streamer-monitors,Worker and transport monitors trip routes>>).
A route outside the declared interface stays disabled until the Streamer restarts.

[[req-ssr-streamer-monitors]]
== Worker and transport monitors trip routes

[.specitem,oft-sid="req~ssr-streamer-monitors~4",oft-title="Worker and transport monitors trip routes",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
*What is monitored.*
The Streamer *MUST* monitor each worker and each transport leg.
Each monitor's trip condition *MUST* be stated in its specification, with its thresholds from deployment data.

*Completion, not activity.*
A monitor *MUST* observe the completion of the work it supervises.
A timer tick, an interrupt or a heartbeat that continues whether or not that work completes is not completion.

*Minimum trip conditions.*
At the least, a monitor *MUST* trip on:

* a worker that completes no forwarding pass within its declared budget;
* an egress that fails every send for a declared time.

*What a trip does.*
A trip:

* *MUST* set the gates of the affected routes only;
* *MUST* keep their storage and resources in place (xref:../seooc-up-rust/release.adoc#req-ssr-release-none[Nothing is released in runtime mode]);
* *MUST* be counted with the condition that caused it.

*A trip latches.*
A trip *MUST* latch: a monitor *MUST NOT* re-enable a route, even once its condition clears, and only an operator's re-enable clears it (<<req-ssr-streamer-operator-control,Operator changes go through a declared interface>>).
A tripped route that the operator interface does not name stays disabled until the Streamer restarts, and <<aou-seooc-monitor-thresholds,Monitor thresholds allow for peers' restarts>> gives the integrator's part.

*Reaction bound.*
Where a configuration claims a safety reaction, its bound from the fault to the safe state is that configuration's claim.
The bound covers detection, the monitor's own execution, observation of the trip, the decision, isolation or reset and the physical safe state.
The claim is made against the system's allocated fault tolerant time interval and includes the monitor's clock and common-cause dependencies.

Without such a claim, the monitors still operate, and the Streamer's report *MUST* state that no reaction bound is established.
--

[horizontal]
ID:: `+req~ssr-streamer-monitors~4+`
ASIL:: B
Allocated to:: the Streamer
Verification:: fault-injection, test
* *fault-injection*
** A worker stalled while its timer keeps running.
** An egress killed.
** A peer restarted within and beyond a monitor's threshold.
* *test*
** A tripped route that the operator interface does not name stays disabled.
** A trip keeps its routes' storage.
** The report without a reaction claim.
Status:: Draft
ISO 26262:: 6-7.4.12 (part-clause numbers only)

*Rationale.*
A trip turns a stalled worker or a failing egress into a counted, reported change of just the routes it affects, instead of silence with no cause on record (<<req-ssr-streamer-mode-report,The Streamer reports degraded>>).

_Why a trip latches._
Because a trip latches, a route whose fault comes and goes cannot flap between forwarding and silence.
The operator, who sees the cause, decides when it returns (<<req-ssr-streamer-operator-control,Operator changes go through a declared interface>>).

The latch turns a peer's normal restart into an outage where a threshold is shorter than that restart.
So the thresholds are the integrator's to set (<<aou-seooc-monitor-thresholds,Monitor thresholds allow for peers' restarts>>).

_Why completion._
A heartbeat from an interrupt can keep ticking while the forwarding loop is stuck, so only completed work counts as progress.

_Reaction time._
A monitor can support a fail-silent reaction even where delivery itself has no hard deadline.
But only a configuration that bounds the whole chain, with a monitor that does not share the fault it detects, can claim a reaction time.
A monitor alone cannot repair memory unsoundness or prove future service.

[[req-ssr-streamer-mode-report]]
== The Streamer reports degraded

[.specitem,oft-sid="req~ssr-streamer-mode-report~1",oft-title="The Streamer reports degraded",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
The Streamer *MUST* report, without heap, its process incarnation and a mode: running, or degraded when at least one route's gate is not enabled.

Degraded is a report only, and *MUST NOT* change any route's behaviour.
--

[horizontal]
ID:: `+req~ssr-streamer-mode-report~1+`
ASIL:: B
Allocated to:: the Streamer
Verification:: test, heap-window
Status:: Draft

*Rationale.*
The incarnation lets a reader see that a restart has reset the counters it compares.

A degraded mode that changed behaviour would let one route's fault act on the others (<<req-ssr-streamer-containment,A fault stays on its route>>), so it only reports.

[[req-ssr-streamer-watchdog-hook]]
== A watchdog hook shows progress

[.specitem,oft-sid="req~ssr-streamer-watchdog-hook~1",oft-title="A watchdog hook shows progress",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
The Streamer *MUST* offer a hook through which an external watchdog or supervisor learns that each worker's loop is making progress.

Serving the hook *MUST* use no heap and *MUST NOT* block a worker.

A worker that stops making progress stops reporting through it.
--

[horizontal]
ID:: `+req~ssr-streamer-watchdog-hook~1+`
ASIL:: B
Allocated to:: the Streamer
Verification:: test (a stalled worker is seen through the hook), heap-window
Status:: Draft
ISO 26262:: 6-7.4.12 (part-clause numbers only)

*Rationale.*
A worker that is stuck, or looping without progress, can look alive from inside the process.
So only a watchdog outside it, told of progress, can see the stall and act on it.

A worker's loop never returns (<<req-ssr-streamer-workers,Workers are fixed at initialization>>), so progress, not exit, is what a watchdog can check.
Progress here is a completed forwarding pass, so a timer or interrupt that keeps running while the loop is stuck cannot report for it.

The hook reports progress.
It establishes neither the watchdog's independence nor a bounded reaction, which a configuration that claims one has to argue (<<req-ssr-streamer-monitors,Worker and transport monitors trip routes>>).

[[req-ssr-streamer-dispatch-obligations]]
== Undeliverable messages are counted, never sent as dead letters

[.specitem,oft-sid="req~ssr-streamer-dispatch-obligations~2",oft-title="Undeliverable messages are counted, never sent as dead letters",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
In ASIL mode the Streamer *MUST* report undeliverable messages through fixed counters, never through a dead-letter message.

* It retries no longer than the route's bounded wait.
* A carrier egress cannot declare a wait (xref:../seooc-up-rust/bounded-work.adoc#req-ssr-bound-wait[Every wait is bounded]), so its only retry is resending a parked frame, within the route's retained budget and the frame's TTL.
* An RPC request it cannot dispatch also gets the best-effort error response of <<req-ssr-streamer-rpc-error-response,An RPC request that cannot be dispatched is answered, best effort>>.
--

[horizontal]

ASIL:: B
Allocated to:: the Streamer
Verification:: test
Status:: Draft

*Rationale.*
Fixed counters preserve bounded fault reporting.
A retry, parked-frame resend and best-effort error answer each retain their separately specified limits.

[[req-ssr-streamer-rpc-error-response]]
== An RPC request that cannot be dispatched is answered, best effort

[.specitem,oft-sid="req~ssr-streamer-rpc-error-response~4",oft-title="An RPC request that cannot be dispatched is answered, best effort",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
*The error response.*
When the Streamer cannot dispatch an RPC request, it *MUST* send the client an error response, as up-spec's dispatcher chapter requires, with the commstatus code that chapter gives for the cause.
A request that arrives on a gated route counts as one it cannot dispatch, and gets `+Unavailable+`.

*Best effort.*
The response is best effort:

* it is sent from capacity reserved at setup on the reverse route, and only when that route's gate is enabled and the route reports capacity;
* it uses no heap, never blocks, and is never retried;
* it is counted whether or not it was sent.

*The TTL remains the guarantee.*
The request's TTL remains the guarantee.
When no error response was sent, the call's outcome becomes its expiry once its TTL has passed.
The client observes that outcome when it next services or waits on the call, within a bound only where a supported configuration establishes one.

*Clients that use the E2E wire.*
On a route whose client uses the E2E wire, the response carries no end-to-end protection, because the Streamer never opens a payload.
That client refuses it as unprotected (xref:../seooc-up-rust/e2e-wire.adoc#req-ssr-e2e-rpc-echo[An E2E response answers exactly its call]) and counts the refusal apart from corruption, and its call ends at its TTL with an outcome that names the refusal.
--

[horizontal]
ID:: `+req~ssr-streamer-rpc-error-response~4+`
ASIL:: B
Allocated to:: the Streamer
Verification:: test (each cause; a full egress; a full reverse route; a call whose error response was not sent ends as expired), heap-window
Status:: Draft

*Rationale.*
The dispatcher can report a known delivery failure promptly without forwarding through a disabled route.
The response is best effort and the request TTL remains the bound.

That bound is logical (xref:../seooc-up-rust/bounded-work.adoc#req-ssr-bound-wait[Every wait is bounded]): it decides the call's outcome, while when a descheduled client sees it depends on the client running.

The clause about the E2E wire binds only a route whose client uses it.
That wire is deferred and not part of this delivery, and every other clause binds now.

[[aou-seooc-operator-access]]
== Only authorized operators reach the Streamer's operator interface

[.specitem,oft-sid="aou~seooc-operator-access~2",oft-title="Only authorized operators reach the Streamer's operator interface",oft-needs="uman",oft-tags="SafetyManual"]
--
The integrator *SHALL* restrict the Streamer's operator interface (<<req-ssr-streamer-operator-control,Operator changes go through a declared interface>>) to the parties allowed to disable or re-enable routes.

It *SHALL* treat an operator's disable of an ASIL route as a loss of that route's function, which the item *SHALL* tolerate.

In strict mode, the Streamer's own checks refuse an operator interface that names an ASIL route unless `+operator_may_disable+` acknowledges it, and the report lists which ASIL routes an operator can disable.
--

*Violation:*

* Every change made through the interface is *counted* and reported with its cause, so an unintended disable is seen.
* In strict mode, an operator interface that names an ASIL route without `+operator_may_disable+` is *refused at setup*.
* Who made a change is *undetectable* by the element.

[horizontal]
ID:: `+aou~seooc-operator-access~2+`
ASIL:: B
Status:: Draft

*Rationale.*
The operator interface can switch an ASIL route off at run time (<<req-ssr-streamer-operator-control,Operator changes go through a declared interface>>).
So whoever can reach it can remove that route's function.

The element counts and reports every change with its cause, but cannot tell who made it.
So who may make one is the integrator's to control.

[[aou-seooc-monitor-thresholds]]
== Monitor thresholds allow for peers' restarts

[.specitem,oft-sid="aou~seooc-monitor-thresholds~2",oft-title="Monitor thresholds allow for peers' restarts",oft-needs="uman",oft-tags="SafetyManual"]
--
The integrator *SHALL* set each Streamer monitor's thresholds, in deployment data, above the worst-case restart time of the peers on the routes that monitor trips, or accept that a peer's normal restart trips such a route.

A tripped route stays disabled until an operator re-enables it, and a route that the operator interface does not name can then be re-enabled only by restarting the Streamer.

In strict mode, the deployment data *SHALL* also declare each peer's worst-case restart time: in the Enforce state, setup refuses a monitor threshold below the declared restart time of a peer on that monitor's routes, unless `+outage_on_restart+` names the accepted outage, and strict mode's report lists every monitored route that only a Streamer restart clears.
--

*Violation:*

* A threshold below a peer's worst-case restart trips the route on that restart.
* The trip is *counted* with its cause, and the mode report shows degraded.
* The route stays disabled until an operator re-enables it, or, where the operator interface does not name it, until the Streamer restarts.
* In strict mode, a threshold below a peer's declared restart time is *refused at setup* in the Enforce state, unless `+outage_on_restart+` names the accepted outage.
* Whether that outage is acceptable for the item is *undetectable* by the element.

[horizontal]
ID:: `+aou~seooc-monitor-thresholds~2+`
ASIL:: B
Status:: Draft

*Rationale.*
A peer recovers from a fault by restarting, since the element has no recovery inside a process (xref:../seooc-up-rust/assumptions-of-use.adoc#aou-seooc-supervisor-restart[A supervisor outside the process restarts it]).
A monitor's trip holds until an operator re-enables the route (<<req-ssr-streamer-monitors,Worker and transport monitors trip routes>>).
So a threshold below a peer's worst-case restart turns that peer's normal restart into an outage of the route, and only the item's own analysis can say whether that outage is acceptable.

Declared restart times make the duty checkable.
Setup can compare every threshold with them, and refuse a short one unless its outage is accepted by name, before any route carries traffic.
