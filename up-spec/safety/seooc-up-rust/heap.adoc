[[req-ssr-heap-none]]
== No heap in runtime mode

[.specitem,oft-sid="req~ssr-heap-none~3",oft-title="No heap in runtime mode on a native path",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*Native paths.*
In runtime mode, element code *MUST NOT* acquire or release heap memory on any path that a native payload operation causes.

*Every other path.*
In runtime mode, element code *MUST NOT* acquire or release heap memory on any other path, except as a serialized or owned route's declared heap class permits and setup admits (<<req-ssr-heap-declared,The heap class is declared, with no default>>).

*What the native rule covers.*
The native rule covers:

* traffic;
* refusals and error returns;
* cancellation;
* lease drops, retirement and deferred release;
* waits and wake-ups;
* deadline service;
* a peer dying and a peer restarting;
* the wire, binding and control work that these cause.

Work that a native route shares with a serialized one *MUST* meet the native rule.

*What counts as heap use.*

* A free counts as heap use.
* General allocator activity inside a region obtained at startup counts as heap use.
* Returning a fixed pool slot is not heap use.

*Serialized and owned routes.*
On a serialized or owned route whose declared class admits allocation, heap use is limited to two kinds:

* an acquisition at an allocation point that the class names, made only after the operation's refusals that can come first (xref:errors.adoc#req-ssr-refuse-before-heap[Refuse before touching the heap]);
* the release, exactly once, of what such an acquisition produced, when the ownership it created ends, by whichever transition ends it (<<req-ssr-heap-slot-types,Decoded values and their destructors>>).

Deciding, reporting and counting any outcome acquires and releases nothing.
Such a release never releases a route, role, table, startup region or other runtime resource, and it revokes no owner.

*What a declaration does not do.*
A declaration makes a route's allocation visible.
It admits the route's ordinary ownership, and it establishes nothing more:

* It excuses no lazy first-use initialization (<<req-ssr-heap-lazy-forced,Lazy state is forced before runtime mode>>).
* It reaches no native operation, none of the work one causes and none of the work a native route shares.
* It relaxes no duty of element code, which keeps xref:errors.adoc#req-ssr-refuse-no-panic[No panic on runtime paths]; xref:bounded-work.adoc#req-ssr-bound-work[Work per call is bounded by setup data] and xref:bounded-work.adoc#req-ssr-bound-wait[Every wait is bounded] on every route.
* It establishes none of the stronger guarantees that <<req-ssr-heap-guarantees,A stronger resource guarantee is required by name>> names: panic-free cleanup, non-waiting acquisition, non-waiting release and recoverable exhaustion.
The element promises a route one of them only where the route requires it and setup admits it.
Otherwise the route's report shows the guarantee as not admitted, and states separately whether it is established.
* It does not make an allocator whose contract can end the process on exhaustion recoverable.

*When the rules apply.*
These rules bind each transport from its own transition.
--

*Rationale.*
Taking or returning heap memory while traffic flows could crash the process or corrupt the memory that runtime traffic relies on.
Runtime mode works instead in startup memory, placed during initialization and never freed.

A serialized or owned route may allocate through its wire, its binding or its allocation provider where it declares it and setup admits it.
It may destroy the owned values it admitted, with its resource and failure policy visible.
That permission is the route's.
It cannot reach native work or metadata a native route shares, and it does not make the route's runtime infrastructure releasable.

Ending an owned value is the only release a serialized route makes.
Every transition that can end one uses that one rule: a release, a refusal, an overflow, a cancellation, an expiry or a peer's failure.
So no transition needs heap of its own (xref:errors.adoc#req-ssr-refuse-before-heap[Refuse before touching the heap]; xref:qos.adoc#req-ssr-qos-overflow[Overflow acts as declared]; xref:../up-l1/peers.adoc#req-ssr-peer-failure-normal[Peer failure is normal input]).

An allocator working inside a pre-obtained region still allocates and frees, so the backing region's origin does not make it admissible on a native path.

_What a declaration is._
A declaration is a truthful statement of the route's heap use, and no more.
Owning a value is ordinary for a serialized wire.
So a declaring route is not made to show that its cleanup can neither panic nor wait: that would refuse ordinary communication for want of evidence that it never asked for.
What a route needs beyond its declaration it requires by name, and it is then admitted on evidence or refused (<<req-ssr-heap-guarantees,A stronger resource guarantee is required by name>>).

[[req-ssr-heap-lazy-forced]]
== Lazy state is forced before runtime mode

[.specitem,oft-sid="req~ssr-heap-lazy-forced~1",oft-title="Lazy state is forced before runtime mode",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Every primitive that would allocate or initialize itself on first use *MUST* be forced during initialization, or be absent from the runtime path.
This covers:

* the first lock of an OS lock on pthread targets;
* thread-local state;
* caches;
* message ID state;
* wake hooks.
--

[horizontal]
ID:: `+req~ssr-heap-lazy-forced~1+`
ASIL:: B
Allocated to:: the element
Verification:: heap-window, fault-injection
* *heap-window*: on a pthread target (macOS) over first traffic.
* *fault-injection*: a control that leaves one primitive lazy must make the window fail, on every target.
Status:: Draft
ISO 26262:: 6-9.4.5, 6-10.4.7 (part-clause numbers only)

*Rationale.*
A primitive that sets itself up on first use moves that work, and any allocation in it, from initialization into the first message.
There <<req-ssr-heap-none,No heap in runtime mode>> forbids it on a native path.

A serialized route's declared allocation covers the owned values that route admits.
It never covers a primitive's first-use setup, which this item requires to be forced on every route.

[[req-ssr-heap-declared]]
== The heap class is declared, with no default

[.specitem,oft-sid="req~ssr-heap-declared~3",oft-title="The heap class is declared, with no default",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*Who declares.*

* Every wire *MUST* state its runtime heap class for each direction.
* Every binding *MUST* state its own for each route it serves.
* Every prepared route *MUST* state its own.

*What a class covers.*
A class covers every heap acquisition and release that its subject can cause on the route in runtime mode.

* For a wire's decode direction that is the whole life of a decoded value: its initialization, its replacement in a slot and its destruction.
* A wire whose decoded value can release heap memory when it is replaced or destroyed states allocation for that direction, even where decoding itself acquires none.

*The classes.*
A heap class is one of:

* none;
* allocation inside middleware under a named permit;
* on a serialized or owned route only, allocation by its wire, its binding or its allocation provider.

A declaration of the third class names each that allocates and the allocation domain it uses.
It is declared with the resource and failure policy it follows:

* what exhaustion does;
* whether an acquisition can wait and, if it can, the dependency it waits for;
* whether a release can wait and, if it can, the dependency it waits for and whether it returns by a finite logical deadline;
* whether a destruction or release can panic or end the process;
* the contexts it may be called from.

Where one of these is not known, the declaration states it as unknown.
An unknown is never read or reported as the favourable answer.

*The policy is the allocator's.*
That policy *MUST* be the one its allocator's stated contract establishes on every path the route can reach: allocation, growth, shrink, destruction and deallocation, dependencies included.
A fallible calling interface does not make exhaustion recoverable for an allocator whose contract may end the process.
An allocation never falls back silently to another domain.

*Disclosure is not a guarantee.*
Stating a policy discloses it.
It admits the route's ordinary ownership under that policy and establishes no stronger guarantee:

* Setup admits a route's decoded types, and their destruction, as <<req-ssr-heap-slot-types,Decoded values and their destructors>> states.
* The element promises a route panic-free cleanup, non-waiting acquisition, non-waiting release or recoverable exhaustion only where the route requires it and setup admits it (<<req-ssr-heap-guarantees,A stronger resource guarantee is required by name>>).
* A stated policy that shows such a guarantee violated, or does not exclude the violation, refuses by name a route that requires the guarantee, and never a route that does not.
* A release that is handed to a release service, or to a binding's deferred return, is pending cleanup, isolated as xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else] states.

A release returns by a finite logical deadline only where its own mechanism does.
Running it on another thread, or timing it from outside, does not make it do so.

*No default.*
A heap class and its policy have no default.

*Refusal at the transition.*
The transition *MUST* refuse, naming the route and the reason:

* a native route whose wire or binding declares allocation in a direction the route uses;
* a serialized route whose wire or binding declares allocation that the route does not declare;
* a route that requires a stronger guarantee that is not established for it (<<req-ssr-heap-guarantees,A stronger resource guarantee is required by name>>).

*Scope of the permission.*
A serialized route's allocation permission *MUST NOT* extend to a native route or to metadata it shares with one.

*Reporting.*
The startup report *MUST* show each route's admitted heap class, naming which of its wire, binding and allocation provider allocate.

* It shows every wire the route uses, in each direction, with the route's binding and each allocation provider.
A route with several wires shows each of them, never the first alone.
* It shows the declared policy of each that allocates, an unknown as unknown.
* It shows, for each stronger guarantee, whether the route requires it, whether it is established and whether it is admitted (<<req-ssr-heap-guarantees,A stronger resource guarantee is required by name>>).
--

** Refusal at the transition of a serialized route that does not declare its wire's or its binding's allocation.
** Admission of a serialized route that declares it, with an owning decoded type and no stronger guarantee required.
** A wire whose decoded value frees memory when it is destroyed, declaring none for its decode direction, failing its heap-free check.

* *review*

*Rationale.*
A claim of no heap use can be checked only if it is stated.
So each wire states the heap class of both directions, with no default.
A default would let a wire that allocates pass as one that does not, and the transition could not refuse it.

Refusing every allocating wire on every route would also refuse serialized routes whose allocation is declared and admissible.
So the refusal follows the route's declared class instead.
The refusal names the route and the wire's reason, so that whoever configured the route can correct it.
A binding's own allocation for a serialized route is declared the same way, so an undeclared one is refused rather than hidden.

A decoded value's memory is often returned when the value ends, not when it is made.
So a class covers the value's whole life.
A wire that decodes into a value which later frees memory uses the heap in that direction, whatever its decoding call does.

A standard allocation interface can permit an allocator to end the process on exhaustion, and an interface that returns an error cannot intercept that.
So the declared policy comes from the allocator's stated contract, not from the shape of the call.
An ordinary allocator may also take a lock, in an acquisition as in a release, and the policy says so.

A declaration tells the reader what the route does.
It is not evidence for a stronger guarantee, which a route that requires one is admitted on separately (<<req-ssr-heap-guarantees,A stronger resource guarantee is required by name>>).
Nor is a timer around a release evidence that it returns by a deadline: a call that waits for a lock without one completes when the lock is free, whatever the timer reports.

_What a stated policy refuses._
An ordinary allocator's contract seldom excludes a panic or a process end in its cleanup.
Refusing every route whose stated policy shows one, or does not exclude one, would refuse ordinary serialized routes for stating the truth.
So a stated policy refuses only a route that requires the guarantee it violates.

[[req-ssr-heap-guarantees]]
== A stronger resource guarantee is required by name

[.specitem,oft-sid="req~ssr-heap-guarantees~1",oft-title="A stronger resource guarantee is required by name, and admitted or refused",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*Ordinary ownership.*
A serialized or owned route whose declared heap class admits allocation (<<req-ssr-heap-declared,The heap class is declared, with no default>>) carries message types whose values own resources, heap memory included.
Setup *MUST NOT* refuse such a route, or a message type, wire, binding or allocation provider on it:

* because its values own resources;
* because a destructor runs when one of them ends; or
* because a guarantee of this item, a timing bound or an assurance scope is not established for it.

A decoded type is admitted as <<req-ssr-heap-slot-types,Decoded values and their destructors>> states.

*What holds whatever a route requires.*
The following are selected by nothing and waived by nothing:

* memory safety and the ownership rules: one destruction of each initialized value, no reuse of storage while it is owned, and no reclamation behind a forgotten owner (xref:memory-safety.adoc#req-ssr-unsafe-sound[Safe code cannot cause undefined behaviour]; <<req-ssr-heap-slot-types,Decoded values and their destructors>>; xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]);
* the functional semantics that a route offers: true arrival, identity, TTL and logical deadlines, the declared overflow policy, and truthful errors, capacity and charges (xref:qos.adoc#req-ssr-qos-no-downgrade[QoS is honored or refused, never weakened]; xref:bounded-work.adoc#req-ssr-bound-wait[Every wait is bounded]; xref:errors.adoc#req-ssr-error-no-silent-loss[No silent loss, and each loss counted once]);
* the native rule, for every native operation, the work it causes and the work a native route shares (<<req-ssr-heap-none,No heap in runtime mode>>);
* the duties of element code itself: no panic, bounded work, and waits of its own that take a logical deadline (xref:errors.adoc#req-ssr-refuse-no-panic[No panic on runtime paths]; xref:bounded-work.adoc#req-ssr-bound-work[Work per call is bounded by setup data]; xref:bounded-work.adoc#req-ssr-bound-wait[Every wait is bounded]);
* a truthful declaration of the heap class and its policy (<<req-ssr-heap-declared,The heap class is declared, with no default>>).

A fault against one of these is a defect on every route.
It is never reported as a guarantee that is merely not established.

*The guarantees a route may require.*
Four guarantees are stronger than ordinary ownership.
Each is a property of the route's own allocation and cleanup, and each is separate from the others:

* _Panic-free cleanup._
Destroying each initialized value that the route can own, and releasing what it owns, cannot panic or abort, through every destructor, allocator and dependency operation that this can reach and in every context that can run it.
* _Non-waiting acquisition._
No acquisition that the route's declared class admits waits for a lock or other dependency.
* _Non-waiting release._
No call, transition or drop that ends a value the route owns waits for that value's release.
The release cannot wait, or it leaves that path as pending cleanup, isolated as xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else] states.
* _Recoverable exhaustion._
Exhaustion at every allocation point that the route can reach is returned as that operation's refusal, and cannot panic or end the process.

Each guarantee limits only the operations that its own definition names.
Non-waiting acquisition limits acquisitions and no release, and non-waiting release limits the calls, transitions and drops that end a value and no acquisition.
Requiring one does not require another, and a route is never refused over a guarantee that it does not require because it requires a different one.
Two apply together only where the route requires both, by naming both or through a claim whose package states that it depends on both.

A finite timing bound and a safety-assurance scope are the claims of xref:qos.adoc#req-ssr-qos-no-downgrade[QoS is honored or refused, never weakened], required and admitted as that item states.

*When a guarantee is required.*
A route requires one of these guarantees only where:

* the route's declaration names it; or
* a timing bound or an assurance scope that the route requires depends on it, as the package of that claim's configuration states.

A route requires none by default.

None of the following is a requirement: an integrity level, an ASIL label, a strict-mode state, an operating system, a toolchain, or the name of a crate, package, wire format or provider.
None of them is evidence for a guarantee either, and none exempts a route from a guarantee that it requires.

*When a guarantee is established.*
A guarantee is established for a route only by evidence that a supported configuration's package, or an explicit extension with evidence of its own, binds to all of:

* the exact message type, and each wire that the route uses, in each direction;
* the route's binding and each allocation provider, with every dependency that their acquisitions, destructions and releases can reach;
* the build, and each context that can run them.

None of the following establishes one:

* a declaration or a disclosure;
* a record, whether by being present or by matching a type or a wire;
* a fallible calling interface, or an implementation of an interface;
* a name or a label.

A type whose values have no destructor destroys nothing.
That fact alone establishes panic-free cleanup and non-waiting release for the destruction of its decoded values, and for nothing else.
The route's binding, each allocation provider, and each other wire and direction still need the evidence above before either is established for the route.
The presence of a destructor is not evidence that a value owns heap memory, that its destruction waits or that it can panic.

*Admitted, refused or not required.*
Whether a route requires a guarantee and whether that guarantee is established for the route are separate facts.
Neither is inferred from the other, and a guarantee is admitted only where both hold.
For each guarantee and each route:

* Where the route requires the guarantee and it is established, setup admits it.
* Where the route requires it and it is not established, setup *MUST* refuse the route.
The refusal names the route, the guarantee and the type, wire, direction, binding, provider or dependency for which it is not established.
* Where the route does not require it, the guarantee is not admitted, and setup *MUST NOT* refuse the route for its absence.
That holds whether or not it is established: evidence that establishes a guarantee which the route does not require stays reported as established, and promises the route nothing.

A guarantee is not established where a stated policy shows it violated, or where the configuration lacks the mechanism that it needs, such as a release service.
Either refuses a route under the second point, and no route under the third.

The element *MUST NOT* state, report or rely on a guarantee as held for a route unless it is established for that route.
No declaration, record or label turns a guarantee that is not established into an established or admitted one, at setup or in runtime mode.

*Setup.*
A guarantee that a route requires covers what setup takes or creates for that route as well.
A refusal disposes of it as xref:runtime-modes.adoc#req-ssr-mode-init-failure[Initialization failure] states.

*Reporting.*
The startup report and each route's report *MUST* state separately, for each of the four guarantees:

* whether the route requires it;
* whether it is established for the route, with the configuration it rests on, or not established;
* whether it is admitted, which it is only where it is both required and established.

Each answer is reported for what it is.
A guarantee that is established and not required is reported as established and not admitted.
A guarantee is reported as not established only where its evidence is absent or insufficient, never because the route does not require it.
--

*Rationale.*
Most wire formats decode into values that own what they hold: strings, sequences and nested messages.
Ending such a value runs its destructor and returns its memory.
That is ordinary ownership, and a route that declares it gets it.

Stronger properties of that cleanup are different in kind.
Whether a destruction can panic, whether a release can wait and whether exhaustion is recoverable depend on the exact type, wire, binding, provider and build.
So they can be shown only for a named composition.

* Demanding that evidence of every owning route would make a safety package a prerequisite for ordinary use (xref:README.adoc#claims[the SEooC's claims]).
* Granting a guarantee without it would be a silent downgrade of the guarantee (xref:qos.adoc#req-ssr-qos-no-downgrade[QoS is honored or refused, never weakened]).

So a guarantee is required by name, and is then admitted or refused.

_Required, established and admitted._
What a route asks for and what its configuration can show are different questions, so the report answers them apart.
Evidence does not vanish because no route asked for it, and asking does not create it.
Only a guarantee that is both asked for and shown is one that the item can rely on.

_Separate guarantees._
An acquisition and a release are different operations, often with different dependencies.
A route can need one of them not to wait and accept the declared wait of the other.
So each guarantee limits its own operations, and none is refused or imposed on account of another.

_Labels._
A label is neither a request nor evidence.
An integrity level or a strict-mode state says what a deployment intends, not what its allocator does.
Nor does the absence of a label excuse anything.
The rules that keep memory safe and reports truthful hold on every route, and a fault against them is a defect, not a missing package.

_The whole composition._
The evidence names the whole composition because each part can change the answer.
A record that matches a type says nothing about the provider behind it.
A wire's record says nothing about a second wire on the same route.

_Destructors._
A destructor is a measure of nothing but itself.
A value can have one and own no heap memory, as a value that only updates a counter does.
A value's destruction can also free memory though its decoding acquired none (<<req-ssr-heap-declared,The heap class is declared, with no default>>).
So the heap class states heap use, the type states whether anything runs at all, and neither is inferred from the other.

_Mechanisms._
A release service is how a configuration gives non-waiting release over a dependency that can wait (xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]).
A configuration that has none cannot give that guarantee, and refuses a route that requires it.
That is no reason to refuse a route that does not.

[[req-ssr-heap-slot-types]]
== Decoded values and their destructors

[.specitem,oft-sid="req~ssr-heap-slot-types~3",oft-title="A decoded value is destroyed once, as its route's class admits",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*Native routes.*
On a native route, a message type whose values run a destructor when they end *MUST* be refused at setup wherever it decodes into a startup slot.
So overwriting a slot in runtime mode never runs a destructor there.

The native rule imposes this restriction because it is sufficient and the type alone decides it (<<req-ssr-heap-none,No heap in runtime mode>>).
It is not a finding about what a refused type's destructor does.

*Heap-free routes.*
On a serialized or owned route whose heap class is none, a decoded type is admitted on its wire's heap-free claim for that direction (<<req-ssr-heap-declared,The heap class is declared, with no default>>).

* That claim covers replacing and destroying the type's decoded values, and the wire's contract suite checks it (xref:../up-l1/wires.adoc#req-ssr-wire-heap-claim-tested[A heap-free claim passes the wire contract]).
* So a type whose values run a destructor is admitted there where its wire makes that claim, and a type whose values run none needs nothing more.
* Setup *MUST* refuse the route, naming it, the type and the wire, where the wire states allocation for that direction.

A destruction on such a route acquires and releases no heap memory.

*Routes that declare allocation.*
On a serialized or owned route whose declared heap class admits allocation, a type whose values own resources, heap memory included, is admitted as <<req-ssr-heap-guarantees,A stronger resource guarantee is required by name>> states.

* Setup does not refuse it for having a destructor, for owning heap memory or because a stronger guarantee is not established for it.
* Destroying its values frees what the route's wire, binding or allocation provider allocated, under the declared policy.

*What a route requires.*
Where a route requires panic-free cleanup or non-waiting release, setup admits a type on it only where that guarantee is established for the type with the route's wires, binding and allocation provider (<<req-ssr-heap-guarantees,A stronger resource guarantee is required by name>>).
Otherwise setup *MUST* refuse the route by name.

A declaration, a disclosure, a fallible calling interface or an implementation of an interface establishes neither.

*Never in native work.*
Ending an owned value *MUST NOT* run in a native operation, in the work one causes or in work that a native route shares: not its destructor, not its release and not a wait for either.
Setup *MUST* refuse by name a composition that offers no other path on which to end such a value.

*Exactly one destruction.*
Each initialized value of an admitted type is destroyed exactly once, under that declared policy, by whichever transition ends its ownership:

* a refusal after decode;
* an overwrite or discard by the overflow policy;
* the release of the lease that holds it;
* the cancellation or expiry of the call that awaits it;
* a peer's failure that ends that call or frame.

A slot that holds no initialized value runs no destructor.
A decode that fails leaves no value half-owned: what it acquired is either part of the slot's valid value or released by that decode, once, under the declared class.

*Where a destruction runs.*
The transition decides and records its outcome before the destruction starts.
The destruction never changes that outcome.

* On a route that does not require non-waiting release, the destruction then runs on a path of that route, under the declared policy: the path that performed the transition or, where that path is native or shared work, a later operation of the same route.
Until it runs, the value stays owned and charged.
It may wait inside the allocation domain that the policy names, and the element promises no time for it.
* On a route that requires non-waiting release, the destruction runs at once only where it is established that it cannot wait.
Otherwise the transition *MUST* hand the value, without waiting or panicking, to the route's release service, which performs the same destruction as pending cleanup (xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]).

The route's report thereby states, for each destruction the route can perform, where it runs and whether it can wait.
Nothing promises a completion deadline for a destruction.

*Element state around a destruction.*
A destructor, and each wire, binding or provider operation that a destruction reaches, is code the element does not control.
It may wait, call back into the element, unwind or never return.

The element *MUST* call it only with its own invariants restored and while holding no lock or exclusion of its own.
So none of these leaves element state inconsistent or adds an element lock to a wait.

*Capacity and charge.*

* The route's capacity covers every value the route can own at once, a value whose destruction is in progress or pending included.
* The value stays charged to its route until its destruction completes.
* A destruction that stalls or fails shows as capacity pressure on that route and never lets a slot be reused early.
* Destroying a value returns its slot to the fixed table and releases no other runtime resource.

*No reuse while owned.*
A slot is never reused while its value is still owned:

* A value whose destruction never runs, because safe code forgot the lease that holds it or the process ended, keeps its slot charged and is destroyed by no other owner.
* A destructor that unwinds, calls back into the element or does not return never lets the value be destroyed twice or its slot be reused while still owned.

These protections keep memory safe whatever a destructor does.
They hold on every route, they establish no guarantee, and they never let an unfinished destruction count as completed.

*Unfinished is not completed.*
A destruction in progress, or pending on a release service, is not a completed one.
Its value stays owned and charged, and is never reported as released, until the destruction completes.

*Rationale.*
A destructor is code that runs when a value ends, and nothing more can be read from its presence.
It may free heap memory, wait for a lock, update a counter or do nothing that a route's class would notice.
So this item keeps three things apart:

* whether anything runs, which the type states;
* whether heap memory is used, which the class states;
* how the destruction behaves, which only evidence can state.

_Native routes._
A destructor on a native route would be unexamined code inside the native rule.
It could free, wait or panic where <<req-ssr-heap-none,No heap in runtime mode>> forbids each.
Refusing every type that has one is sufficient, and a type alone decides it.
A native payload type has no need of one.

_Heap-free routes._
A route whose class is none promises no heap use, and a destructor that uses none keeps that promise.
The wire's heap-free claim covers the decoded value's whole life, and its contract suite checks it inside a heap window (xref:../up-l1/wires.adoc#req-ssr-wire-heap-claim-tested[A heap-free claim passes the wire contract]).
So a type with a destructor is admitted there on that claim, and refused without it.

_Routes that declare allocation._
A serialized route that declares its allocation may free what it allocated.
An ordinary decoded message owns strings, sequences and nested messages, and ending it returns their memory through the route's provider.
Refusing such a type for want of a proof about its destruction would refuse ordinary serialized communication, which every profile offers (<<req-ssr-heap-guarantees,A stronger resource guarantee is required by name>>).

The value's destruction is part of that route's resource policy; it is not a release of the reservation that holds it.
Every transition that ends a value uses this one rule, so the refusal, overflow and peer-failure items need no release of their own (xref:errors.adoc#req-ssr-refuse-before-heap[Refuse before touching the heap]; xref:qos.adoc#req-ssr-qos-overflow[Overflow acts as declared]; xref:../up-l1/peers.adoc#req-ssr-peer-failure-normal[Peer failure is normal input]).

_Waiting._
Waiting and panicking are different properties, and neither follows from ownership.

An ordinary allocator's release can take a lock that waits.
On a route that does not require non-waiting release, that wait is the declared policy's, on the path that ended the value.
A route that requires non-waiting release moves it off that path, in the same way as a retained owner's deferred return (xref:../up-l1/bindings.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do]).

That hand-off holds ownership awaiting destruction, not unread traffic, so it is not a second receive queue.
Deferral bounds nothing: the release may still wait behind the allocator's own lock, which no deadline can interrupt from outside.
The value therefore stays owned and charged while it is pending (xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]).

_Panicking._
A destruction that could panic or abort would do so wherever it runs.
So deferral cannot establish panic-free cleanup, and a route that requires it is admitted only on evidence for its whole destruction chain.
Stating a policy, catching an unwind or aborting on panic shows neither that a panic cannot happen nor that a destruction finished.

_What holds for every destructor._
A destructor that panics, calls back or never returns is still type-correct safe code.
So the element keeps memory safe against all of it on every route, holds nothing of its own across it, and counts no unfinished destruction as completed.
That protection is not a guarantee about the destructor.

Rust does not promise that a destructor runs (xref:runtime-modes.adoc#req-ssr-mode-no-shutdown[No shutdown in runtime mode]): a forgotten value is leaked with its slot, never reclaimed behind a live reference.

_In sum._
A destructor is not read as heap use, and the strongest cleanup guarantees are no condition of ordinary ownership.
Ordinary ownership is admitted, the two guarantees bind the routes that require them, and every memory-safety rule holds on every route.
