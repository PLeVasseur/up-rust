[[req-ssr-heap-none]]
== No heap in runtime mode on a native path

[.specitem,oft-sid="req~ssr-heap-none~4",oft-title="No heap in runtime mode on a native path",oft-needs="impl,utest",oft-tags="SafetyUpRustCore,SafetyWire"]
--
*Native paths.*
In runtime mode, no part acquires or releases heap memory on a path that a native payload operation causes, except for the middleware allocation covered by "Named middleware allocation" below, and each part answers for its own work on such a path:

* element code *MUST NOT* acquire or release heap memory on it;
* each wire that the native route uses declares a heap class of none in each direction that the route uses, and answers for that claim in all its work there, as xref:../up-l1/wires.adoc#req-ssr-wire-heap-claim-tested[A heap-free claim is true, and encoding is repeatable] states;
* each binding's code keeps the same rule, as xref:../up-l1/bindings.adoc#req-ssr-binding-no-heap[Binding code allocates nothing in runtime mode on a native path] states;
* the element applies the native-route refusal of <<req-ssr-heap-declared,The heap class is declared, with no default>>, and, for allocation inside a binding's middleware under a named permit, the transition check of xref:waivers.adoc#req-ssr-waiver-required[Middleware heap needs a named waiver].

What an allocation provider is, is stated in xref:../../sdk/owned-frame/providers.adoc#req-sdk-owned-frame-provider-selection[The selected memory provider is the only one used, and selecting it claims nothing].
The rule follows the cause, whichever part's code does the work: it reaches the work that the operation causes on another thread or at a later time as well.

*Named middleware allocation.*
Allocation inside a binding's middleware is an exception to this item's general native-path prohibition only for the operations and bound of a named permit that a matching named waiver admits, within the scope of xref:waivers.adoc#req-ssr-waiver-scope[A waiver covers middleware and nothing else].
This exception does not apply to a native lease drop, frame return or other native release operation, retirement and deferred release included (xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]; xref:../up-l1/bindings.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do]).
It replaces no other requirement on an operation.
What the binding declares and what a permit establishes are stated in xref:../up-l1/bindings.adoc#req-ssr-binding-no-heap[Binding code allocates nothing in runtime mode on a native path], under "Middleware".

*Every other path.*
In runtime mode, element code *MUST NOT* acquire or release heap memory on any other path, except as a serialized route's declared heap class permits and setup admits (<<req-ssr-heap-declared,The heap class is declared, with no default>>).

*What the native rule covers.*
The native rule covers:

* traffic;
* refusals and error returns;
* cancellation;
* lease drops, retirement and deferred release;
* waits and wake-ups;
* deadline service;
* a peer dying and a peer restarting;
* the wire, binding and control work that these cause, in whichever part's code it runs.

The element and each wire *MUST* keep the native rule in work that a native route shares with a serialized one.

*What counts as heap use.*

* A free counts as heap use.
* General allocator activity inside a region obtained at startup counts as heap use.
* Returning a fixed pool slot is not heap use.

*Serialized routes.*
A route is native or serialized, as its wire decides (xref:../up-l1/payload-paths.adoc#req-ssr-payload-route-form[A route's form is fixed at setup, by what the route declares and never by a name]).
On a serialized route whose declared class admits allocation, the element *MUST* confine heap use to two kinds:

* an acquisition at an allocation point that the class names, made only after the operation's refusals that can come first (xref:errors.adoc#req-ssr-refuse-before-heap[Refuse before touching the heap]);
* the release, exactly once, of what such an acquisition produced, when the ownership it created ends, by whichever transition ends it (<<req-ssr-heap-slot-types,A decoded value is destroyed once, as its route's class admits>>).

The element *MUST NOT* acquire or release anything in deciding, reporting or counting any outcome.
The element *MUST NOT* let such a release release a route, role, table, startup region or other runtime resource, or revoke an owner.

*What a declaration does not reach.*
A declaration makes a route's allocation visible.
It admits the route's ordinary ownership, and it establishes nothing more:

* It excuses no lazy first-use initialization (<<req-ssr-heap-lazy-forced,Lazy state is forced before runtime mode>>).
* It does not reach a native operation, the work one causes or the work a native route shares.
* It does not reach an operation that its own item requires to use no heap on every route, such as the generation of a message ID (xref:../up-l2/interaction.adoc#req-ssr-ids-unique[Message IDs are unique]) or the acquisition, copy and validation of an integrity copy route (xref:../up-l1/integrity.adoc#req-ssr-integrity-zero-copy[Zero-copy only from a writer at or above the reader]).
* It relaxes no duty of element code, which keeps xref:errors.adoc#req-ssr-refuse-no-panic[No panic on runtime paths]; xref:bounded-work.adoc#req-ssr-bound-work[Work per call is bounded by setup data] and xref:bounded-work.adoc#req-ssr-bound-wait[Every bounded wait has a logical deadline] on every route.
* What it establishes of the stronger guarantees, and what a route's report shows of them, is stated in <<req-ssr-heap-guarantees,A stronger resource guarantee is required by name, and admitted or refused>>.

*When the rules apply.*
These rules bind each transport from its own transition.

ISO 26262:: 6-Table 6 1b (part-clause numbers only)

*Rationale.*
Taking or returning heap memory while traffic flows could crash the process or corrupt the memory that runtime traffic relies on.
Runtime mode works instead in startup memory, placed during initialization and not released in runtime mode.

The rule follows what a native operation causes, because heap use in a wire's work, in a binding's code or in shared control work harms the same process as heap use in element code.

Ending an owned value is the only release a serialized route makes.
Every transition that can end one uses that one rule: a release, a refusal, an overflow, a cancellation, an expiry or a peer's failure.
So no transition needs heap of its own (xref:errors.adoc#req-ssr-refuse-before-heap[Refuse before touching the heap]; xref:qos.adoc#req-ssr-qos-overflow[Overflow acts as declared]; xref:../up-l1/peers.adoc#req-ssr-peer-failure-normal[Peer failure is normal input]).

An allocator working inside a pre-obtained region still allocates and frees, so the backing region's origin does not make it admissible on a native path.

_What a declaration is._
A declaration is a truthful statement of the route's heap use.
Owning a value is ordinary for a serialized wire.
So a declaring route is admitted without evidence that its cleanup cannot panic or wait.
Requiring that would refuse ordinary communication for want of evidence of a guarantee that the route does not require.
What a route needs beyond its declaration it requires by name, and it is then admitted on evidence or refused (<<req-ssr-heap-guarantees,A stronger resource guarantee is required by name, and admitted or refused>>).

[[req-ssr-heap-lazy-forced]]
== Lazy state is forced before runtime mode

[.specitem,oft-sid="req~ssr-heap-lazy-forced~1",oft-title="Lazy state is forced before runtime mode",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
The element *MUST* have every primitive that would allocate or initialize itself on first use forced during initialization, or absent from the runtime path.
This covers:

* the first lock of an OS lock on pthread targets;
* thread-local state;
* caches;
* message ID state;
* wake hooks.
--

[horizontal]
ID:: `+req~ssr-heap-lazy-forced~1+`
ASIL:: B
Allocated to:: the element
Verification:: heap-window, fault-injection, review
* *heap-window*: over first traffic, on a pthread target and on every other target that a supported configuration names.
* *fault-injection*: a control that leaves one primitive lazy makes the window fail, on each of those targets.
* *review*: each primitive on the runtime path that would allocate or initialize itself on first use, the five that the statement lists among them, forced during initialization or absent from the runtime path.
ISO 26262:: 6-9.4.5, 6-10.4.7 (part-clause numbers only)

*Rationale.*
A primitive that sets itself up on first use moves that work, and any allocation in it, from initialization into the first message.
On a native path, <<req-ssr-heap-none,No heap in runtime mode on a native path>> forbids that allocation.

A serialized route's declared allocation covers the owned values that route admits.
It never covers a primitive's first-use setup.

[[req-ssr-heap-declared]]
== The heap class is declared, with no default

[.specitem,oft-sid="req~ssr-heap-declared~4",oft-title="The heap class is declared, with no default",oft-needs="impl,utest",oft-tags="SafetyUpRustCore,SafetyWire,SafetyBinding"]
--
*Who declares.*

* Each wire *MUST* state its runtime heap class for each direction.
* Each binding *MUST* state its own for each route it serves.
* Each allocation provider that a route uses *MUST* state, for that route, its runtime heap class and the resource and failure policy that it follows.
* The element *MUST* require each prepared route's declaration to state the route's own class.

Each wire, each binding and each allocation provider *MUST* state what it does, and *MUST* keep within what it states.
The element *MUST* derive each prepared route's heap class from the classes that every wire direction, the route's binding and each allocation provider that the route uses state, and *MUST* check it against the class that the route's declaration states, as the refusals at the transition below state.

*What a class covers.*
A class covers every heap acquisition and release that its subject can cause on the route in runtime mode.

* For a wire's decode direction that is the whole life of a decoded value: its initialization, its replacement in a slot and its destruction.
* A wire whose decoded value can release heap memory when it is replaced or destroyed *MUST* state allocation for that direction, even where decoding itself acquires none.

*The classes.*
A heap class is one of:

* none;
* allocation inside middleware under a named permit;
* on a serialized route only, allocation by its wire, its binding or its allocation provider.

A wire or a binding that states the third class *MUST* name each that allocates and the allocation domain it uses.
Each that allocates *MUST* state the resource and failure policy it follows:

* what exhaustion does;
* whether an acquisition can wait and, if it can, the dependency it waits for;
* whether a release can wait and, if it can, the dependency it waits for and whether it returns by a finite logical deadline;
* whether a destruction or release can panic or end the process;
* the contexts it may be called from.

Where one of these is not known, the one that states the policy *MUST* state it as unknown.
The element *MUST NOT* read or report an unknown as the favourable answer.

*The allocator's contract.*
Each that states a policy *MUST* state the one that its allocator's stated contract establishes on every path the route can reach: allocation, growth, shrink, destruction and deallocation, dependencies included.
A fallible calling interface does not make exhaustion recoverable for an allocator whose contract may end the process.
Each wire, each binding and each allocation provider *MUST NOT* let an allocation of its own fall back silently to another domain, and the element *MUST NOT* substitute one.

*Effect of disclosure.*
Stating a policy discloses it.
It admits the route's ordinary ownership under that policy and establishes no stronger guarantee:

* How setup admits a route's decoded types, and their destruction, is stated in <<req-ssr-heap-slot-types,A decoded value is destroyed once, as its route's class admits>>.
* Which guarantees a route is promised, and which routes a stated policy leads the element to refuse, is stated in <<req-ssr-heap-guarantees,A stronger resource guarantee is required by name, and admitted or refused>>.
* A release that is handed to a release service, or to a binding's deferred return, is pending cleanup, isolated as xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else] states.

A release returns by a finite logical deadline only where its own mechanism does.
Running it on another thread, or timing it from outside, does not make it do so.

*No default.*
The element *MUST NOT* supply a default for a heap class or for a policy, and each wire, each binding and each allocation provider *MUST NOT* state one by default.

*Refusal at the transition.*
The element *MUST* refuse at the transition, naming the route and the reason:

* a native route whose wire or allocation provider declares allocation in a direction the route uses, or whose binding declares allocation in its own code in such a direction;
* a serialized route whose wire, binding or allocation provider declares allocation that the route does not declare;
* a route for which a wire, its binding, an allocation provider or the route's own declaration states no class, or for which a wire, a binding or an allocation provider states no resource and failure policy where this item requires one.

The element applies xref:waivers.adoc#req-ssr-waiver-required[Middleware heap needs a named waiver] to the runtime transition of a transport with a route whose binding declares allocation inside its middleware under a named permit, a native route included; the waiver's scope is stated in xref:waivers.adoc#req-ssr-waiver-scope[A waiver covers middleware and nothing else].

A route that requires a stronger guarantee that is not established for it is refused as <<req-ssr-heap-guarantees,A stronger resource guarantee is required by name, and admitted or refused>> states.

*Scope of the permission.*
The element *MUST NOT* extend a serialized route's allocation permission to a native route or to metadata it shares with one.

*Reporting.*
The element's startup report is what the element reports of a transport's setup at its transition.
The element *MUST* show in it each route's admitted heap class, naming which of its wire, binding and allocation provider allocate.

* It *MUST* show every wire the route uses, in each direction, with the route's binding and each allocation provider.
* It *MUST* show the declared policy of each that allocates, an unknown as unknown.
* It *MUST* show the declared policy of each memory source and each allocation provider that the element's setup relied on, also where no route uses it (xref:runtime-modes.adoc#req-ssr-mode-init-failure[Initialization failure]; what a memory source is, is stated in xref:../../sdk/owned-frame/providers.adoc#req-sdk-owned-frame-provider-selection[The selected memory provider is the only one used, and selecting it claims nothing]).
* What it shows for each stronger guarantee is stated in <<req-ssr-heap-guarantees,A stronger resource guarantee is required by name, and admitted or refused>>.

In each route's report, the element *MUST* show the declared policy of the route's binding where the binding allocates on the route, whatever the route requires (the release of a received frame's storage: xref:../up-l1/bindings.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do]).

*Rationale.*
A claim of no heap use can be checked only if it is stated.
So each wire states the heap class of both directions, with no default.
A default would let a wire that allocates pass as one that does not, and the transition could not refuse it.

Refusing every allocating wire on every route would also refuse serialized routes whose allocation is declared and admissible.
So the refusal follows the route's declared class instead.
The refusal names the route and the wire's reason, so that whoever configured the route can correct it.
A binding's own allocation for a serialized route is declared the same way, so an undeclared one is refused rather than hidden.

A decoded value's memory is often returned when the value ends, not when it is made.
So a class covers the value's whole life.
A wire that decodes into a value which later frees memory uses the heap in that direction, whatever its decoding call does.

A standard allocation interface can permit an allocator to end the process on exhaustion, and an interface that returns an error cannot intercept that (source: the standard library documentation, Rust 1.98.1, section Errors of `+std::alloc::GlobalAlloc::alloc+`: https://doc.rust-lang.org/1.98.1/std/alloc/trait.GlobalAlloc.html#errors[`+std::alloc::GlobalAlloc::alloc+`]; and section Errors of `+std::alloc::Allocator::allocate+`: https://doc.rust-lang.org/1.98.1/std/alloc/trait.Allocator.html#errors[`+std::alloc::Allocator::allocate+`]).
So the declared policy is the one that the allocator's stated contract establishes, whatever the shape of the call.
An ordinary allocator may also take a lock, in an acquisition as in a release, and the policy says so.

A declaration tells the reader what the route does.
It is not evidence for a stronger guarantee, which a route that requires one is admitted on separately (<<req-ssr-heap-guarantees,A stronger resource guarantee is required by name, and admitted or refused>>).
A timer around a release is no evidence that it returns by a deadline, because a call that waits for a lock without a deadline completes when the lock is free, whatever the timer reports.

_What a stated policy refuses._
An ordinary allocator's contract seldom excludes a panic or a process end in its cleanup.
Refusing every route whose stated policy shows one, or does not exclude one, would refuse ordinary serialized routes for stating the truth.
So a stated policy refuses only a route that requires the guarantee it violates.

[[req-ssr-heap-guarantees]]
== A stronger resource guarantee is required by name, and admitted or refused

[.specitem,oft-sid="req~ssr-heap-guarantees~2",oft-title="A stronger resource guarantee is required by name, and admitted or refused",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*Ordinary ownership.*
A serialized route whose declared heap class admits allocation (<<req-ssr-heap-declared,The heap class is declared, with no default>>) carries message types whose values own resources, heap memory included.
The element *MUST NOT* refuse at setup such a route, or a message type, wire, binding or allocation provider on it:

* because its values own resources;
* because a destructor runs when one of them ends; or
* because a guarantee of this item, a timing bound or an assurance scope that the route does not require is not established for it.

A refusal that another item states for a reason of its own is no refusal for ownership: such is the refusal of a route that needs the integrity copy route on a wire that allocates when it decodes (xref:../up-l1/integrity.adoc#req-ssr-integrity-zero-copy[Zero-copy only from a writer at or above the reader]).
A decoded type is admitted as <<req-ssr-heap-slot-types,A decoded value is destroyed once, as its route's class admits>> states.

*What holds whatever a route requires.*
Nothing selects or waives the following:

* memory safety and the ownership rules: one destruction of each initialized value, no reuse of storage while it is owned, and no reclamation behind a forgotten owner (xref:memory-safety.adoc#req-ssr-unsafe-sound[Safe code cannot cause undefined behaviour]; <<req-ssr-heap-slot-types,A decoded value is destroyed once, as its route's class admits>>; xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]);
* the functional semantics that a route offers: true arrival, identity, TTL and logical deadlines, the declared overflow policy, and truthful errors, capacity and charges (xref:qos.adoc#req-ssr-qos-no-downgrade[QoS is honored or refused, never weakened]; xref:bounded-work.adoc#req-ssr-bound-wait[Every bounded wait has a logical deadline]; xref:errors.adoc#req-ssr-error-no-silent-loss[No silent loss, and each loss counted once]);
* the native rule, for every native operation, the work it causes and the work a native route shares (<<req-ssr-heap-none,No heap in runtime mode on a native path>>);
* the duties of element code itself: no panic, bounded work, and waits of its own that take a logical deadline (xref:errors.adoc#req-ssr-refuse-no-panic[No panic on runtime paths]; xref:bounded-work.adoc#req-ssr-bound-work[Work per call is bounded by setup data]; xref:bounded-work.adoc#req-ssr-bound-wait[Every bounded wait has a logical deadline]);
* a truthful declaration of the heap class and its policy (<<req-ssr-heap-declared,The heap class is declared, with no default>>).

A fault against one of these is a defect on every route.
The element *MUST NOT* report a fault against one of these as a guarantee that is not established.

*The guarantees a route may require.*
Four guarantees are stronger than ordinary ownership.
Each is a property of the route's own allocation and cleanup, and each is separate from the others:

* _Panic-free cleanup._
Destroying each initialized value that the route can own, and releasing what it owns, cannot panic or abort, through every destructor, allocator and dependency operation that this can reach and in every context that can run it.
* _Non-waiting acquisition._
No acquisition that the route's declared class admits waits for a lock or other dependency.
* _Non-waiting release._
No call, transition or drop that ends a value the route owns waits for that value's release.
The release cannot wait, or it leaves that path as pending cleanup, isolated as xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else] states.
* _Recoverable exhaustion._
Exhaustion at every allocation point that the route can reach is returned as that operation's refusal, and cannot panic or end the process.

Each guarantee limits only the operations that its own definition names.
Non-waiting acquisition limits acquisitions and no release, and non-waiting release limits the calls, transitions and drops that end a value and no acquisition.
Two apply together only where the route requires both, by naming both or through a claim whose package states that it depends on both.

A finite timing bound and a safety-assurance scope are the claims of xref:qos.adoc#req-ssr-qos-no-downgrade[QoS is honored or refused, never weakened], required and admitted as that item states.

*When a guarantee is required.*
A route requires one of these guarantees only where:

* the route's declaration names it; or
* a timing bound or an assurance scope that the route requires depends on it, as the package of that claim's configuration states.

A route requires none by default.

None of the following is a requirement: an integrity level, an ASIL label, a strict-mode state, an operating system, a toolchain, or the name of a crate, package, wire format or provider.
None of them is evidence for a guarantee either, and none exempts a route from a guarantee that it requires.

*When a guarantee is established.*
A guarantee is established for a route only by evidence that a supported configuration's package, or an explicit extension with evidence of its own, binds to all of:

* the exact message type, and each wire that the route uses, in each direction;
* the route's binding and each allocation provider, with every dependency that their acquisitions, destructions and releases can reach;
* the build, and each context that can run them.

None of the following establishes one:

* a declaration or a disclosure;
* a record, whether by being present or by matching a type or a wire;
* a fallible calling interface, or an implementation of an interface;
* the absence of an observed failure;
* a name or a label.

A type whose values have no destructor destroys nothing.
That fact alone establishes panic-free cleanup and non-waiting release for the destruction of its decoded values, and for nothing else.
The route's binding, each allocation provider, and each other wire and direction still need the evidence above before either is established for the route.
The presence of a destructor is not evidence that a value owns heap memory, that its destruction waits or that it can panic.

*Admitted, refused or not required.*
Whether a route requires a guarantee and whether that guarantee is established for the route are separate facts.
The element *MUST NOT* infer either fact from the other, and a guarantee is admitted only where both hold.
For each guarantee and each route:

* Where the route requires the guarantee and it is established, the element *MUST* admit it at setup.
* Where the route requires it and it is not established, the element *MUST* refuse the route at setup.
The element *MUST* name in the refusal the route, the guarantee and the type, wire, direction, binding, provider or dependency for which it is not established.
* Where the route does not require it, the guarantee is not admitted, and the element *MUST NOT* refuse the route for its absence.
That holds whether or not it is established, and evidence that establishes a guarantee which the route does not require promises the route nothing.

A guarantee is not established where a stated policy shows it violated, or where the configuration lacks the mechanism that it needs, such as a release service.
Where a stated policy does not exclude the violation, the guarantee is established only by evidence, bound as above to the exact provider and configuration, that the admitted configuration cannot reach it.
A declaration, or a passing test of something else, is no such evidence.

The element *MUST NOT* state, report or rely on a guarantee as held for a route unless it is established for that route.

*Setup.*
A guarantee that a route requires covers what setup takes or creates for that route as well.
How a refusal disposes of it is stated in xref:runtime-modes.adoc#req-ssr-mode-init-failure[Initialization failure].

*Reporting.*
The element *MUST* state separately, in its startup report and in each route's report, for each of the four guarantees:

* whether the route requires it;
* whether it is established for the route, with the configuration it rests on, or not established;
* whether it is admitted, which it is only where it is both required and established.

The element *MUST* report a guarantee that is established and not required as established and not admitted.
The element *MUST* report a guarantee as not established only where its evidence is absent or insufficient, and never because the route does not require it.

** For each of the four guarantees, required and established varied independently, with admitted true only where both are.
** The same route refused by name once it requires a guarantee that is not established, the refusal naming the route, the guarantee and what lacks it.
** A route that requires non-waiting acquisition over a binding whose allocation can wait, refused at setup by name, the refusal naming that binding, and the same route admitted without that requirement.
** A route that requires non-waiting release over a dependency that can wait, refused by name on a configuration without a release service, and the same route admitted without that requirement.
** A route that requires only non-waiting acquisition, admitted on a configuration with a declared release that can wait and no release service, and a route that requires only non-waiting release, admitted with a declared acquisition that can wait.
** A requirement that follows from a required timing bound or assurance scope, admitted or refused with that claim.
** An integrity level, a strict-mode state and the name of a wire or provider, each changing neither what a route requires nor what is established.
** A record that matches a type and a wire, without its evidence, admitting no guarantee.
** A type without a destructor, with panic-free cleanup and non-waiting release established for the destruction of its decoded values and for nothing else, and a route that requires either still decided over its binding, providers and other wires.
** A route with several wires, with each guarantee decided and reported over all of them.
** A route that requires a guarantee, with what setup takes or creates for it held to that guarantee, and a refusal disposing of it as xref:runtime-modes.adoc#req-ssr-mode-init-failure[Initialization failure] states.
* *review*
** Each admitted guarantee's evidence against the exact type, wires, directions, binding, provider, dependencies, build and contexts that it names.
** No path on which the element states, reports or relies on a guarantee as held for a route for which it is not established, and none on which it reports as admitted a guarantee that is not both required and established.
** No path on which a report drops or changes what is established because the route does not require it, or shows a guarantee as required because it is established.
** No path on which a fault against what holds whatever a route requires is reported as a guarantee that is not established.
** A stated policy that does not exclude a violation, with the guarantee treated as established only on evidence that the admitted configuration cannot reach it.

*Rationale.*
Most wire formats decode into values that own what they hold: strings, sequences and nested messages.
Ending such a value runs its destructor and returns its memory.
That is ordinary ownership.

Stronger properties of that cleanup are different in kind.
Whether a destruction can panic, whether a release can wait and whether exhaustion is recoverable depend on the exact type, wire, binding, provider and build.
So they can be shown only for a named composition.

* Demanding that evidence of every owning route would make a safety package a prerequisite for ordinary use (xref:README.adoc#claims[the SEooC's claims]).
* Granting a guarantee without it would be a silent downgrade of the guarantee (xref:qos.adoc#req-ssr-qos-no-downgrade[QoS is honored or refused, never weakened]).

So a guarantee is required by name, and is then admitted or refused.

_Required, established and admitted._
What a route asks for and what its configuration can show are different questions, so the report answers them apart.
Evidence does not vanish because no route asked for it, and asking does not create it.
Only a guarantee that is both asked for and shown is admitted, and only an admitted guarantee supports a deployment's claim.

_Separate guarantees._
An acquisition and a release are different operations, often with different dependencies.
A route can need one of them not to wait and accept the declared wait of the other.
So each guarantee limits its own operations, and none is refused or imposed on account of another.

_Labels._
An integrity level or a strict-mode state says what a deployment intends, not what its allocator does.

_The whole composition._
The evidence names the whole composition because each part can change the answer.
A record that matches a type says nothing about the provider behind it.
A wire's record says nothing about a second wire on the same route.

_Destructors._
The presence of a destructor shows only that code runs when a value ends.
A value can have one and own no heap memory, as a value that only updates a counter does.
A value's destruction can also free memory though its decoding acquired none (<<req-ssr-heap-declared,The heap class is declared, with no default>>).
So the heap class states heap use, the type states whether anything runs at all, and neither is inferred from the other.

_Mechanisms._
A release service is how a configuration gives non-waiting release over a dependency that can wait (xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]).
A configuration that has none cannot give that guarantee.

[[req-ssr-heap-slot-types]]
== A decoded value is destroyed once, as its route's class admits

[.specitem,oft-sid="req~ssr-heap-slot-types~4",oft-title="A decoded value is destroyed once, as its route's class admits",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*Native routes.*
On a native route, the element *MUST* refuse at setup a message type whose values run a destructor when they end, wherever it decodes into a startup slot.
So overwriting a slot in runtime mode never runs a destructor there.

*Heap-free routes.*
On a serialized route whose heap class is none, the heap class admits a decoded type on its wire's heap-free claim for that direction (<<req-ssr-heap-declared,The heap class is declared, with no default>>).
That is one condition of the type's admission: what the route requires still applies (clause "What a route requires").

* That claim covers replacing and destroying the type's decoded values (xref:../up-l1/wires.adoc#req-ssr-wire-heap-claim-tested[A heap-free claim is true, and encoding is repeatable], "A heap-free claim").
* The element *MUST* refuse the route at setup, naming it, the type and the wire, where the wire states allocation for that direction.

The element *MUST NOT* acquire or release heap memory in a destruction on such a route, and the wire's claim covers what the value's own destructor does.

*Routes that declare allocation.*
On a serialized route whose declared heap class admits allocation, a type whose values own resources, heap memory included, is admitted as <<req-ssr-heap-guarantees,A stronger resource guarantee is required by name, and admitted or refused>> states.

* Destroying its values frees what the route's wire, binding or allocation provider allocated, under the declared policy.

*What a route requires.*
Where a route requires panic-free cleanup or non-waiting release, a type on it is admitted, or the route is refused by name, as <<req-ssr-heap-guarantees,A stronger resource guarantee is required by name, and admitted or refused>> states: the guarantee has to be established for the type with the route's wires, binding and allocation provider.

*Never in native work.*
The element *MUST NOT* run the ending of an owned value, its destructor, its release and a wait for either included, in a native operation, in the work one causes or in work that a native route shares.
The element *MUST* refuse at setup, by name, a composition that offers no other path on which to end such a value.

*Exactly one destruction.*
The element *MUST* destroy each initialized value of an admitted type exactly once, under that declared policy, by whichever transition ends its ownership:

* a refusal after decode;
* an overwrite or discard by the overflow policy;
* the release of the lease that holds it;
* the cancellation or expiry of the call that awaits it;
* a peer's failure that ends that call or frame.

The element *MUST NOT* run a destructor for a slot that holds no initialized value.
The element *MUST NOT* leave a value half-owned after a decode that fails: what the decode acquired is either part of the slot's valid value or released by that decode, once, under the declared class.

*Where a destruction runs.*
The element *MUST* decide and record a transition's outcome before the destruction starts, the acquisition of any lock that the destruction or its release needs included.
The element *MUST NOT* let the destruction change that outcome.

* On a route that does not require non-waiting release, the element *MUST* then run the destruction on a path of that route, under the declared policy: the path that performed the transition or, where that path is native or shared work, a later operation of the same route.
The destruction may wait inside the allocation domain that the policy names.
* On a route that requires non-waiting release, the destruction runs at once only where it is established that it cannot wait.
Otherwise the value goes, without waiting or panicking, to the route's release service, which performs the same destruction as pending cleanup: where a lease's drop ends the value on a route whose declared heap class admits allocation, the drop hands it over as xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else] states, and in every other case the element *MUST* hand it over in the same way.

The element *MUST* state in the route's report, for each destruction the route can perform, where it runs and whether it can wait; which waits are admitted is stated in xref:bounded-work.adoc#req-ssr-bound-wait[Every bounded wait has a logical deadline].
A destruction has no general completion deadline: one holds only where a supported configuration's package establishes it through the destruction's own mechanism (xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]).

*Element state around a destruction.*
A destructor, and each wire, binding or provider operation that a destruction reaches, is code that the element does not own.
It may wait, call back into the element, unwind or never return.

The element *MUST* call it only with its own invariants restored and while holding no lock or exclusion of its own.
So none of these leaves element state inconsistent or adds an element lock to a wait.

*Capacity and charge.*
How a route's capacity covers a value whose destruction is in progress or pending, how the value stays owned and charged, and is not reported as released, until its destruction completes, and how a destruction that stalls or fails shows as capacity pressure, in every transition and wherever the destruction runs, is stated in xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else], clause "Every decoded value", with what a release service, pending cleanup and a retained owner add.
In destroying a value, the element *MUST* return its slot to the fixed table and *MUST NOT* release any other runtime resource.

*No reuse while owned.*
The element *MUST NOT* reuse a slot while its value is still owned:

* A value whose destruction never runs, because safe code forgot the lease that holds it or the process ended, keeps its slot charged, and the element *MUST NOT* destroy it through any other owner.
* A destructor that unwinds, calls back into the element or does not return never lets the value be destroyed twice or its slot be reused while still owned.
* The element *MUST NOT* let a destruction that stalls or fails make a slot reusable early.

*Rationale.*
A destructor is code that runs when a value ends.
It may free heap memory, wait for a lock, update a counter or do nothing that a route's class would notice.
So three things are kept apart:

* whether anything runs, which the type states;
* whether heap memory is used, which the class states;
* how the destruction behaves, which only evidence can state.

_Native routes._
A destructor on a native route would be unexamined code inside the native rule.
It could free heap memory, which <<req-ssr-heap-none,No heap in runtime mode on a native path>> forbids there.
It could also wait or panic when a lease on a native route is dropped, and that drop never waits and cannot panic (xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]).
Refusing every type that has one is sufficient, and a type alone decides it.
A native payload type has no need of one.

_Heap-free routes._
A route whose class is none promises no heap use, and a destructor that uses none keeps that promise.
The wire's heap-free claim covers the decoded value's whole life, and the wire answers for it (xref:../up-l1/wires.adoc#req-ssr-wire-heap-claim-tested[A heap-free claim is true, and encoding is repeatable]).
So a type with a destructor is admitted there on that claim, and refused without it.

_Routes that declare allocation._
A serialized route that declares its allocation may free what it allocated.
An ordinary decoded message owns strings, sequences and nested messages, and ending it returns their memory through the route's provider.
Refusing such a type for want of a proof about its destruction would refuse ordinary serialized communication (<<req-ssr-heap-guarantees,A stronger resource guarantee is required by name, and admitted or refused>>).

The value's destruction is part of that route's resource policy; it is not a release of the reservation that holds it.
Every transition that ends a value uses this one rule, so the refusal, overflow and peer-failure items need no release of their own (xref:errors.adoc#req-ssr-refuse-before-heap[Refuse before touching the heap]; xref:qos.adoc#req-ssr-qos-overflow[Overflow acts as declared]; xref:../up-l1/peers.adoc#req-ssr-peer-failure-normal[Peer failure is normal input]).

_Waiting._
Waiting and panicking are different properties, and neither follows from ownership.

An ordinary allocator's release can take a lock that waits.
On a route that does not require non-waiting release, that wait is the declared policy's, on a path of that route: the path that ended the value or, where that path is native or shared work, a later operation of the same route.
A route that requires non-waiting release moves it off that path, in the same way as a retained owner's deferred return (xref:../up-l1/bindings.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do]).

That hand-off to the route's release service holds ownership awaiting destruction, not unread traffic, so it is not a second receive queue.
Deferral does not bound the release.
It may still wait behind the allocator's own lock, which no deadline can interrupt from outside.
The value therefore stays owned and charged while it is pending (xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]).

_Panicking._
A destruction that could panic or abort would do so wherever it runs.
So deferral cannot establish panic-free cleanup, and a route that requires it is admitted only on evidence for its whole destruction chain.
Stating a policy, catching an unwind or aborting on panic shows neither that a panic cannot happen nor that a destruction finished.

_What holds for every destructor._
A destructor that panics, calls back or never returns is still type-correct safe code.
So the element keeps memory safe against all of it on every route, holds nothing of its own across it, and counts no unfinished destruction as completed.

Rust does not promise that a destructor runs (xref:runtime-modes.adoc#req-ssr-mode-no-shutdown[No shutdown in runtime mode]).
So a forgotten value is leaked with its slot and never reclaimed behind a live reference.
