== No heap in runtime mode

[.specitem,oft-sid="req~ssr-heap-none~2",oft-title="No heap in runtime mode on a native path",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
In runtime mode, element code *MUST NOT* acquire or release heap memory on any path that a native payload operation causes, and *MUST NOT* do so on any other path except as a serialized or owned route's declared heap class permits and setup admits (`+req~ssr-heap-declared~2+`). The native rule covers traffic, refusals and error returns, cancellation, lease drops, retirement and deferred release, waits and wake-ups, deadline service, a peer dying and a peer restarting, and the wire, binding and control work that these cause. Work that a native route shares with a serialized one *MUST* meet the native rule. A free counts as heap use, and so does general allocator activity inside a region obtained at startup; returning a fixed pool slot is not heap use. On a serialized or owned route whose declared class admits allocation, heap use is limited to two kinds: an acquisition at an allocation point that the class names, made only after the operation's refusals that can come first (`+req~ssr-refuse-before-heap~2+`); and the release, exactly once, of what such an acquisition produced, when the ownership it created ends, by whichever transition ends it (`+req~ssr-heap-slot-types~2+`). Deciding, reporting and counting any outcome acquires and releases nothing. Such a release never releases a route, role, table, startup region or other runtime resource, and it revokes no owner. A declaration makes a route's allocation visible and waives nothing: it excuses no lazy first-use initialization (`+req~ssr-heap-lazy-forced~1+`); it admits no panic or abort anywhere in the destruction and release of what the route owns, on whichever thread performs them, which setup admits only as `+req~ssr-heap-slot-types~2+` states (`+req~ssr-refuse-no-panic~1+`); it permits no waiting release on an application's call, transition or drop, where a release that may wait is handed to the route's release service, whose pending cleanup is the only element work that may wait for one, isolated as `+req~ssr-release-lease-drop~3+` states; and it does not make an allocator whose contract can end the process on exhaustion recoverable. These rules bind each transport from its own transition.
--

Allocated to:: the element
Verification:: heap-window (Rust guard and C-level observer, all threads, allocations and frees, on Linux and on macOS, over native traffic including errors, cancellation, retirement and deferred release; on a serialized route, its declared allocation and the release of what it admitted, including each release its release service performs, are reported, never hidden, with no heap use in deciding, reporting or counting a refusal, a discard or a peer's failure), gate (the crate builds without `+alloc+`)
Status:: Draft
ISO 26262:: 6-Table 6 1b (part-clause numbers only)

*Rationale.* Taking or returning heap memory while traffic flows could crash the process or corrupt the memory that runtime traffic relies on. Runtime mode works instead in startup memory, placed during initialization and never freed (`+core/src/memory.rs+`: "Objects placed here are never dropped or freed"). A serialized or owned route may allocate through its wire, its binding or its allocation provider where it declares it and setup admits it, and may destroy the owned values it admitted, with its resource and failure policy visible; that permission is the route's, so it cannot reach native work or metadata a native route shares, and it does not make the route's runtime infrastructure releasable. Ending an owned value is the only release a serialized route makes, and every transition that can end one, a release, a refusal, an overflow, a cancellation, an expiry or a peer's failure, uses that one rule, so no transition needs heap of its own (`+req~ssr-refuse-before-heap~2+`, `+req~ssr-qos-overflow~3+`, `+req~ssr-peer-failure-normal~2+`). An allocator working inside a pre-obtained region still allocates and frees, so the backing region's origin does not make it admissible on a native path. A release service keeps an allocator's wait off the application's path; it cannot make a destruction that panics or aborts acceptable, because that destruction would do the same on the service, so admission, not deferral, keeps panics out of a route's cleanup.

== Lazy state is forced before runtime mode

[.specitem,oft-sid="req~ssr-heap-lazy-forced~1",oft-title="Lazy state is forced before runtime mode",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Every primitive that would allocate or initialize itself on first use *MUST* be forced during initialization, or be absent from the runtime path: the first lock of an OS lock on pthread targets, thread-local state, caches, message ID state and wake hooks.
--

[horizontal]
ASIL:: B
Allocated to:: the element
Verification:: heap-window on a pthread target (macOS) over first traffic, fault-injection (a control that leaves one primitive lazy must make the window fail, on every target)
Status:: Draft
ISO 26262:: 6-9.4.5, 6-10.4.7 (part-clause numbers only)

*Rationale.* A primitive that sets itself up on first use moves that work, and any allocation in it, from initialization into the first message, where `+req~ssr-heap-none~2+` forbids it on a native path. A serialized route's declared allocation covers the owned values that route admits, never a primitive's first-use setup, which this item requires to be forced on every route. In the code, the platform layer needs no state with first-use setup, and message IDs need no thread-local generator (`+core/src/platform/mod.rs+`, `+core/src/transport/ids.rs+`).

== The heap class is declared, with no default

[.specitem,oft-sid="req~ssr-heap-declared~2",oft-title="The heap class is declared, with no default",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Every wire *MUST* state its runtime heap class for each direction, and every binding *MUST* state its own for each route it serves, and every prepared route *MUST* state its own: none; allocation inside middleware under a named permit; or, on a serialized or owned route only, allocation by its wire, its binding or its allocation provider, naming each that allocates and the allocation domain it uses, declared with the resource and failure policy it follows: what exhaustion does, whether a release can wait and, if it can, the dependency it waits for and whether it returns by a finite logical deadline, whether a destruction or release can panic or end the process, and the contexts it may be called from. That policy *MUST* be the one its allocator's stated contract establishes on every path the route can reach, allocation, growth, shrink, destruction and deallocation, dependencies included; a fallible calling interface does not make exhaustion recoverable for an allocator whose contract may end the process, and an allocation never falls back silently to another domain. Stating a policy discloses it and admits nothing: setup admits a route's destruction and release only as `+req~ssr-heap-slot-types~2+` states, and a release that can wait only as pending cleanup isolated as `+req~ssr-release-lease-drop~3+` states, and refuses by name a route whose stated policy shows, or does not exclude, a panic or a process end in a destruction or release that the route can reach. A release returns by a finite logical deadline only where its own mechanism does; running it on another thread, or timing it from outside, does not make it do so. None of these has a default. The transition *MUST* refuse, naming the route and the reason, a native route whose wire or binding declares allocation in a direction the route uses, and a serialized route whose wire or binding declares allocation that the route does not declare. A serialized route's allocation permission *MUST NOT* extend to a native route or to metadata it shares with one. The startup report *MUST* show each route's admitted heap class, naming which of its wire, binding and allocation provider allocate.
--

[horizontal]
ASIL:: B
Allocated to:: the element
Verification:: test (refusal at the transition of a native route with an allocating wire or binding, and of a serialized route that does not declare its wire's or its binding's allocation; admission of a serialized route that declares it; the startup report's heap class per route, naming who allocates), review (no default in the declaration; each declared policy against its allocator's stated contract on every reachable path; a stated panic or process end in a release refused, not merely reported; a waiting release's named dependency and any claimed deadline against the allocator's own mechanism)
Status:: Draft

*Rationale.* A claim of no heap use can be checked only if it is stated, so `+WireInfo::new+` takes the heap class of both directions, with no default (`+core/src/wire/mod.rs+`). A default would let a wire that allocates pass as one that does not, and the transition could not refuse it. The transition refuses such a native route with `+StartupError::RouteNeedsHeapAtRuntime+`, which carries the route and the wire's reason (`+core/src/transport/error.rs+`). Refusing every allocating wire on every route would also refuse serialized routes whose allocation is declared and admissible, so the refusal follows the route's declared class instead. A binding's own allocation for a serialized route is declared the same way, so an undeclared one is refused rather than hidden. A standard allocation interface can permit an allocator to end the process on exhaustion, and an interface that returns an error cannot intercept that, so the declared policy comes from the allocator's stated contract, not from the shape of the call. A declaration tells the reader what the route does; it is not evidence that a release cannot panic, which admission requires separately. Nor is a timer around a release evidence that it returns by a deadline: a call that waits for a lock without one completes when the lock is free, whatever the timer reports.

== Decoded types run no destructor

[.specitem,oft-sid="req~ssr-heap-slot-types~2",oft-title="Decoded types run no destructor on a heap-free route",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
On a native route, and on any route whose heap class is none, a message type whose values need dropping *MUST* be refused at setup wherever it decodes into a startup slot, so overwriting a slot in runtime mode never runs a destructor there. On a serialized or owned route whose declared heap class admits allocation, such a type *MAY* be admitted only where setup establishes, for that type with the route's wire, binding and allocation provider, that destroying each initialized value and releasing what it owns, through every destructor, allocator and dependency operation that this can reach, cannot panic or abort, whether it runs at once on the path that ends the value or later on the route's release service. A declaration, a disclosure, a fallible calling interface or an implementation of an interface does not establish this. Where it is not established, setup *MUST* refuse the route, naming it and the type, wire, binding or provider whose destruction is not established, before acquiring any value or storage that it would then have to destroy. Each initialized value of an admitted type is destroyed exactly once, under that declared policy, by whichever transition ends its ownership: a refusal after decode, an overwrite or discard by the overflow policy, the release of the lease that holds it, the cancellation or expiry of the call that awaits it, or a peer's failure that ends that call or frame. A slot that holds no initialized value runs no destructor, and a decode that fails leaves no value half-owned: what it acquired is either part of the slot's valid value or released by that decode, once, under the declared class. Where an admitted value's destruction may wait, the transition *MUST* hand the value, without waiting or panicking, to the route's release service (`+req~ssr-release-lease-drop~3+`); that moves only the waiting, and the service performs the same admitted destruction as pending cleanup. Setup admits such a destruction only where the route's declared policy names the dependency it waits for and setup establishes the isolation that `+req~ssr-release-lease-drop~3+` requires of its pending cleanup; otherwise setup *MUST* refuse the route, naming it and the dependency it cannot isolate, before acquiring any value that would need it. The declared policy thereby states, for each destruction the route can perform, whether it completes at once or becomes pending cleanup, and it promises no completion deadline for pending cleanup. The route's capacity covers every value the route can have pending at once, and the value stays charged to its route until its destruction completes; a stalled or failed service shows as capacity pressure on that route and never lets a slot be reused early. Destroying a value returns its slot to the fixed table and releases no other runtime resource. A slot is never reused while its value is still owned: a value whose destruction never runs, because safe code forgot the lease that holds it or the process ended, keeps its slot charged and is destroyed by no other owner, and a destructor that nevertheless unwinds never lets the value be destroyed twice or its slot be reused while still owned. These protections keep memory safe after a defect; they make no such panic acceptable, and they never let an unfinished destruction count as completed. A destruction pending on the release service is permitted pending cleanup, not a completed one: its value stays owned and charged, and is never reported as released, until the destruction completes.
--

[horizontal]
ASIL:: B
Allocated to:: the element
Verification:: test (refusal on a native and on a heap-free route; on an admitting serialized route, one destructor run per initialized value refused after decode, overwritten, discarded, released, cancelled, expired or ended by a peer's failure, none for an uninitialized slot, a failed decode that leaves nothing half-owned, a destruction that can wait handed to the release service with its slot charged until it completes, a stalled release service shown as capacity pressure with no slot reused, a pending destruction that waits indefinitely while deadlines, reports and independent owners' returns progress, a route whose waiting destruction cannot be isolated refused at setup by name, a forgotten lease whose slot stays charged, the slot returned with no other resource released, and a type, wire, binding or provider whose destruction is not established refused at setup by name before any value is acquired), heap-window (the serialized route's destruction, at once and on the release service, reported under its declared class), review (each admitted type's, wire's, binding's and provider's destruction chain and its evidence in every context that runs it; each waiting destruction's named dependency and its isolation; unwind, forget, partial-initialization and reentrancy paths of every admitted type)
Status:: Draft

*Rationale.* A value that needs dropping usually owns heap memory, so overwriting it in a slot would free that memory in runtime mode, which `+req~ssr-heap-none~2+` forbids on a native or heap-free route. A receive route's startup check refuses such a type with the reason "the decoded type owns heap memory" (`+core/src/transport/inbound.rs+`). A serialized route that declares its allocation may free what it allocated, so the refusal applies where the route's class forbids it, not to every type with drop glue. The value's destruction is part of that route's resource policy; it is not a release of the reservation that holds it. Every transition that ends a value uses this one rule, so the refusal, overflow and peer-failure items need no release of their own (`+req~ssr-refuse-before-heap~2+`, `+req~ssr-qos-overflow~3+`, `+req~ssr-peer-failure-normal~2+`). Waiting and panicking are different properties, so admission and deferral are separate rules. An ordinary allocator's release can take a lock that waits, so a destruction that its declared policy does not show to be wait-free leaves the path that ended the value, in the same way as a retained owner's deferred return (`+req~ssr-binding-frame-drop~4+`); that hand-off holds ownership awaiting destruction, not unread traffic, so it is not a second receive queue. Deferral bounds nothing: the release may still wait behind the allocator's own lock, which no deadline can interrupt from outside. The value therefore stays owned and charged while it is pending, no deadline, report or other owner's return waits for it, and setup refuses a waiting destruction that it cannot keep apart from them (`+req~ssr-release-lease-drop~3+`). A destruction that could panic or abort would still do so on the release service, ending the process in the shipped build or stopping the service, so deferral cannot make it acceptable: setup admits only a type, wire, binding and provider whose whole destruction chain is shown not to, and refuses the others by name before taking any value it would have to destroy. Refusing every type that needs dropping would also refuse ordinary owned values whose destruction is shown safe, so the refusal follows the evidence, not the presence of a destructor; and stating a policy, catching an unwind or aborting on panic shows neither that a panic cannot happen nor that a destruction finished. Rust does not promise that a destructor runs (`+req~ssr-mode-no-shutdown~1+`): a forgotten value is leaked with its slot, never reclaimed behind a live reference.
