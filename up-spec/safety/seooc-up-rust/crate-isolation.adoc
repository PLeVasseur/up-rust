[[req-ssr-crate-isolated]]
== The safety crate cannot be tainted

[.specitem,oft-sid="req~ssr-crate-isolated~1",oft-title="The safety crate cannot be tainted",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
The element *MUST* keep its runtime path in one crate, the safety crate, which is `+no_std+`, uses no `+alloc+`, has no dependencies and declares no Cargo features.
So no other crate in a build can switch `+std+` or `+alloc+` on inside it.
--

[horizontal]
ID:: `+req~ssr-crate-isolated~1+`
ASIL:: B
Allocated to:: the element
Verification:: gate (the manifest has no `+[features]+` and no `+[dependencies]+`; the crate builds on a sysroot with neither `+alloc+` nor `+std+`)

*Rationale.*
Where several packages of a build depend on one crate, Cargo builds that crate with the union of the features that they enable, apart from the situations in which its version 2 resolver keeps features apart (source: the Cargo Book, Rust 1.98.1, chapter https://doc.rust-lang.org/1.98.1/cargo/reference/features.html[Features], sections Feature unification and Feature resolver version 2).
A crate with neither features nor dependencies offers no feature that another package can enable and has no dependency whose features a build can change.
So nothing outside it can switch `+std+` or `+alloc+` on inside it, whatever other crates ask for and whichever resolver a build uses: the item chooses these restrictions as a boundary that holds by construction.
Code that needs `+std+`, such as an asynchronous runtime or a Protobuf codec, therefore lives in other crates.

[[req-ssr-crate-sync-path]]
== Traffic is synchronous or polled

[.specitem,oft-sid="req~ssr-crate-sync-path~2",oft-title="Traffic is synchronous or polled",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
The element *MUST* offer every traffic operation of its runtime path in synchronous or polled form, and *MUST* use none of `+core::future+`, `+core::task+` or `+core::pin+` on that path.

Each asynchronous layer *MUST* sit above the runtime path, in a crate of its own.
The element *MUST NOT* take an asynchronous layer into the safety crate, and *MUST NOT* depend on one.
--

[horizontal]
ID:: `+req~ssr-crate-sync-path~2+`
ASIL:: B
Allocated to:: the element; each asynchronous layer, for its place above the runtime path, in a crate of its own
Verification:: gate (a token scan for `+async+`, `+.await+`, `+Future+`, `+Pin+`, `+Poll+`, `+Waker+` and `+Context+`, and for grouped `+use core::{…}+` paths, with a negative control for each), review (each asynchronous layer's crate, which sits above the runtime path and is no dependency of the element)

*Rationale.*
Offering traffic in synchronous or polled form, with no futures, tasks or pinning, keeps it independent of any executor and of library modules that a given qualification scope may not cover.

Which compiler releases, targets, library modules and options a qualification covers is stated by its supplier for an exact release.

[[req-ssr-crate-core-only-binary]]
== The checked policy stays in the safety crate, and no admitted optional layer bypasses or reimplements it

[.specitem,oft-sid="req~ssr-crate-core-only-binary~4",oft-title="The checked policy stays in the safety crate, and no admitted optional layer bypasses or reimplements it",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*The checked policy.*
The element's checked policy is the set of safety invariants and admission checks that the element's requirements give the element itself: the checks that each transport and route passes at its build and at the transition, and the invariants that the element's runtime path keeps.
Strict mode's evaluation and its report are not part of it (xref:build.adoc#req-ssr-strict-states[Strict mode has four states]).

*Isolation.*
The element *MUST* keep its checked policy in the safety crate (<<req-ssr-crate-isolated,The safety crate cannot be tainted>>), usable without any optional allocation, host, application, scheduler or memory-provider layer.

*Non-bypass.*
The element *MUST NOT* offer a way to build a transport or a route, to enter runtime mode or to carry traffic without passing the checks of its checked policy.
It *MUST NOT* let another crate switch one of those checks off, and *MUST NOT* let its strict mode lift or replace one: strict mode reads the element's declarations and adds only refusals and reports of its own.

*Strict mode's component.*
The element *MUST* keep its strict mode in a component of its own, which needs no `+std+` and depends on no software component other than the safety crate (part E7: xref:README.adoc#req-ssr-element-boundary[The parts of the element, and element code]).

*Optional layers.*
An optional layer that a configuration admits *MUST NOT* bypass or reimplement the checked policy.

*Admission.*
A configuration admits an optional layer only with that layer's own allocated requirements and its own evidence.
The ASIL path admits no optional layer (xref:README.adoc#req-ssr-element-configurations[The ASIL path and supported configurations]).
--

[horizontal]
ID:: `+req~ssr-crate-core-only-binary~4+`
ASIL:: B
Allocated to:: the element; each optional layer that a configuration admits, for not bypassing or reimplementing the checked policy
Verification:: gate, test, review
* *gate*: strict mode's component, whose manifest names no dependency other than the safety crate, and which builds on a sysroot without `+std+`.
* *test*: a link fixture that uses only the safety crate, a binding and a wire.
* *review*
** Each check of the element's checked policy, which stands in the safety crate.
** Each public way to build a transport or a route, to enter runtime mode and to carry traffic, which passes those checks.
** Strict mode's use of the element's declarations, which adds refusals and reports and lifts no check.
** Each optional layer that a configuration admits, which neither bypasses those checks nor reimplements them.

*Rationale.*
The safety crate's own build, and so the checked policy in it, cannot be changed by another crate's features (<<req-ssr-crate-isolated,The safety crate cannot be tainted>>).
Usable without any optional layer, the policy applies in full to a configuration that admits none.
A check that a caller could go around, or that another crate could switch off, would protect only the callers that chose to pass it.
Kept in a component that needs no `+std+` and depends only on the safety crate, strict mode can take part in a claimed graph without bringing another dependency into it.

_Optional layers._
With the checked policy in the safety crate, a claimed configuration can admit an independently specified optional layer, such as an allocation-aware or asynchronous layer, for functions outside that policy.
A layer that bypassed the policy would let a configuration run without its checks, and a layer that reimplemented it would run checks that the element's requirements and evidence do not cover.
A layer that no configuration admits stays out of every claimed graph (xref:assumptions-of-use.adoc#aou-seooc-build-configuration[The ASIL binary is built from its claimed graph, with the ASIL profile]; xref:build.adoc#req-ssr-strict-lock[The locked build allows only enforcement]).

[[req-ssr-crate-streamer-isolated]]
== The ASIL Streamer is its own untaintable crate

[.specitem,oft-sid="req~ssr-crate-streamer-isolated~4",oft-title="The ASIL Streamer is its own untaintable crate",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
The Streamer *MUST* keep the ASIL Streamer's route table, admission, validation and forwarding loop in a crate of their own, which:

* is `+no_std+`;
* uses no `+alloc+`;
* declares no Cargo features;
* depends on no crate other than the safety crate;
* uses no 64-bit atomic type.

The Streamer *MUST* keep that crate so that no feature, dependency or build setting outside it can bring classic routes, `+std+`-only paths or heap use into it.

The Streamer *MUST* have its `+std+` loader only parse deployment data, and *MUST* validate that data in this crate.
What that validation covers is stated in xref:../up-l2/streamer.adoc#req-ssr-streamer-config-validated[The Streamer validates its deployment data in full].

So bindings and wires are linked by the binary that uses the crate, not by the crate.
--

[horizontal]
ID:: `+req~ssr-crate-streamer-isolated~4+`
ASIL:: B
Allocated to:: the Streamer
Verification:: gate (the gates of the safety crate applied to this crate: its manifest, a build on a sysroot with neither `+alloc+` nor `+std+`, its resolved dependency closure, which holds only the safety crate, and its own panic-link fixture, which gives evidence for xref:../up-l2/streamer.adoc#req-ssr-streamer-no-panic[The Streamer does not panic in runtime mode]; a build for a bare-metal 32-bit target without 64-bit atomics), review (the `+std+` loader, which only parses deployment data, with all validation of it in this crate)

*Rationale.*
Separating the data plane keeps a convenience dependency, or a feature that another package of the build enables on a dependency that they share, from bringing heap use into it (source: the Cargo Book, Rust 1.98.1, chapter https://doc.rust-lang.org/1.98.1/cargo/reference/features.html[Features], sections Feature unification and Feature resolver version 2).
