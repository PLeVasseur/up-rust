[[req-ssr-waiver-required]]
== Middleware heap needs a named waiver

[.specitem,oft-sid="req~ssr-waiver-required~1",oft-title="Middleware heap needs a named waiver",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
The element *MUST NOT* let a transport with a route whose prepared heap class is allocation inside middleware enter runtime mode unless a named waiver matches each permit its binding declares.

Otherwise the element *MUST* refuse the transition, naming the transport, the route and the permit.
--

[horizontal]
ID:: `+req~ssr-waiver-required~1+`
ASIL:: B
Allocated to:: the element
Verification:: test (refused without the waiver, admitted with it)

*Rationale.*
Allocation inside middleware is outside the element's control.
So it enters runtime mode only as a deployment's explicit, recorded decision (<<req-ssr-waiver-record,Waivers are recorded and can be found>>).

A refusal that names the transport, the route and the permit tells the deployment which decision is missing.

[[req-ssr-waiver-scope]]
== A waiver covers middleware and nothing else

[.specitem,oft-sid="req~ssr-waiver-scope~1",oft-title="A waiver covers middleware and nothing else",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
The element *MUST NOT* let a waiver admit more than allocation inside middleware, for the operations and the bound its permit names.

The element *MUST NOT* let a waiver admit:

* allocation in element, binding or wire code;
* a wire that declares allocation;
* a panic.

Allocation that a serialized route declares for its wire, its binding or its allocation provider (xref:../../sdk/owned-frame/providers.adoc#req-sdk-owned-frame-provider-selection[The selected memory provider is the only one used, and selecting it claims nothing] states what an allocation provider is) is admitted by that route's heap class (xref:heap.adoc#req-ssr-heap-declared[The heap class is declared, with no default]), and by no waiver; allocation inside middleware under a permit needs a waiver on every route, as <<req-ssr-waiver-required,Middleware heap needs a named waiver>> states.
--

[horizontal]
ID:: `+req~ssr-waiver-scope~1+`
ASIL:: B
Allocated to:: the element
Verification:: test (a wire that declares allocation on a native route is refused even with a waiver), review

*Rationale.*
The element can answer only for its own code.
So a waiver covers only what middleware does inside itself, for the operations and the bound its permit states.

A known anomaly or a known failure of middleware, such as a panic that it can reach, is outside what a permit names, so no waiver covers it (xref:assumptions-of-use.adoc#aou-seooc-waiver-approval[Waivers are approved with an interference argument]).

A serialized route's heap class admits only the allocation that the route declares, and nothing that a native operation causes.

[[req-ssr-waiver-record]]
== Waivers are recorded and can be found

[.specitem,oft-sid="req~ssr-waiver-record~3",oft-title="Waivers are recorded and can be found",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
The element *MUST* hold each waiver as a record compiled into the program, with a name and a scope, and for each waiver *MUST*:

* apply it only where it can be found in the code;
* record it at the transition, and, where deployment data selects it and the transition admits it, report it there as active, with its name and its scope, in the element's startup report (xref:heap.adoc#req-ssr-heap-declared[The heap class is declared, with no default]);
* keep it readable in runtime mode without heap;
* refuse it by name at the transition, unless it names an approver other than its author.

*The interference argument.*
In the Enforce and Locked states, the element *MUST* refuse at the transition, by name, as a forbidden finding (xref:build.adoc#req-ssr-strict-states[Strict mode has four states]), a waiver that does not name its interference argument's kind and a reference.
In the Report state, the element *MUST* record that as that finding and *MUST NOT* refuse the waiver for it (xref:assumptions-of-use.adoc#aou-seooc-waiver-approval[Waivers are approved with an interference argument]).

*The compliance report.*
What the compliance report lists of each active waiver is stated in xref:build.adoc#req-ssr-strict-report[Strict mode reports on every run].
A report that lists a waiver records it; it is not the waiver's approval.

*Deployment data.*
The element *MUST NOT* let deployment data create a waiver: deployment data selects a waiver compiled into the program by its id, and nothing more.
--

[horizontal]
ID:: `+req~ssr-waiver-record~3+`
ASIL:: B
Allocated to:: the element
Verification:: test (the runtime lists the waiver; a record that names its author as approver is refused; in the Enforce and Locked states, a waiver that does not name its interference argument's kind and a reference is refused, and in the Report state it is admitted with a finding; the element's startup report lists each waiver that deployment data selects and the transition admits, as active, and does not report as active a selected waiver that the transition refuses, for its author named as approver and, in the Enforce and Locked states, for a missing interference argument, and a compiled-in waiver that deployment data does not select is recorded at the transition and not reported as active; deployment data that names an id that no compiled-in waiver has creates no waiver), review (findable)
ISO 26262:: 9-7 (part-clause numbers only)

*Rationale.*
A binding ships a permit that states the use it needs, and a deployment files a waiver against it.
So accepting the allocation is the deployment's recorded decision.

Keeping waivers compiled in and selected by id limits deployment data to a choice among approved waivers.

An approver other than the author gives each waiver a second person's check.

A waiver that names its interference argument's kind and a reference leads a reviewer to the argument that interference from its allocation is excluded.
The element can check that the argument is named, but not that it holds.
