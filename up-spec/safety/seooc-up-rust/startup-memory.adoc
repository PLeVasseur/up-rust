== ASIL-path storage is static or caller-provided

[.specitem,oft-sid="req~ssr-memory-static~2",oft-title="ASIL-path storage is static or caller-provided",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*Where storage comes from.*
On the ASIL path, all storage the runtime path uses *MUST* be placed during initialization from static or caller-provided memory, with its size, alignment and arithmetic checked when it is placed.

*Checks before an object is reachable.*
Before placed storage becomes reachable as an object, placement *MUST* have established that it:

* lies within its region;
* is aligned and sized for the object;
* is owned by no other live object.

A refused placement *MUST* expose no object.

*What this covers.*
That covers slots, startup slots, queues, peer and call tables, waker storage, route state and the Streamer's route table.

*Startup memory from a heap.*
Startup memory obtained from a heap *MUST* exist only outside the ASIL path: from `+up-rust-std+`, or from an allocation provider that the configuration declares through `+up-rust-alloc+`.

Either way:

* the source or provider hands core each region exclusively and for the life of the process;
* core checks and owns the region, places from it as from any other, and never frees it in runtime mode.
--

[horizontal]
ASIL:: B
Allocated to:: the element
Verification:: test, gate, review
* *test*
** A runtime path over static memory only.
** A region from a declared allocation provider placed and checked like a static one.
** Refused placements, zero-length and over-aligned requests, exposing no object.
* *gate*: the crate builds on a sysroot without `+alloc+`.
* *review*: the live ownership and lifetime of each region a source or provider supplies.
Status:: Draft
ISO 26262:: 6-Table 6 1b (part-clause numbers only)

*Rationale.*
The safety crate is `+no_std+` with no `+alloc+` (`+req~ssr-crate-isolated~1+`).
So its storage can come only from a static region or from bytes the caller provides.
Every placement goes through one checked reservation, which checks bounds, alignment and exclusivity.

Static or caller-provided memory is the element's chosen policy for configurations that claim its assurance scope.
It is not a prohibition on obtaining startup regions from a heap in ordinary use.
There `+up-rust-std+` provides them automatically, and `+up-rust-alloc+` lets an application supply its own allocation provider, as on a fixed-memory board.

Exclusivity is a property of live ownership, not of numeric addresses: a region may occupy addresses that an earlier, ended owner used.

== Startup memory is sealed

[.specitem,oft-sid="req~ssr-memory-sealed~3",oft-title="Startup memory is sealed",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
A startup memory *MUST* be sealed when the last live setup that uses it enters runtime mode, and in any case when `+enter_runtime_all+` returns.

Once it is sealed:

* no further placement from it succeeds;
* a refused placement asks no region source for memory;
* a setup built on it is refused.

`+enter_runtime_all+` reports any setup that is still alive on that memory and has not entered runtime mode.

A failed `+enter_runtime_all+` seals the memory as well, so setup cannot be retried on it in the process (`+aou~seooc-supervisor-restart~4+`).
--

[horizontal]
ASIL:: B
Allocated to:: the element
Verification:: test (including a setup kept alive with `+mem::forget+`), heap-window
Status:: Draft

*Rationale.*
A shared startup allocator must stop serving new requests once initialization ends, including failure paths that leave some transports active.

== Startup storage is computable before start

[.specitem,oft-sid="req~ssr-memory-computable~3",oft-title="Startup storage is computable before start",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*The computation.*
The element *MUST* provide a computation that gives, from a deployment's data alone and before the process starts, the startup memory that deployment needs.
The result includes the storage for:

* the registrations of pending asynchronous operations;
* every backlog of retained owners, deferred releases and deferred destructions that its routes admit.

Placement at startup *MUST NOT* need more than the computation gives.

*Each figure says what it measures.*
Each figure that the element computes or reports *MUST* state what it measures, and *MUST NOT* be presented as another.
The measures are:

* usable object capacity;
* storage reserved in placed regions;
* retained backing, including what alignment, growth or a lost race leaves claimed;
* transient setup memory or stack.

A count of live objects is neither the retained backing nor the physical footprint.

*Figures that are not established.*
Where a figure depends on allocator overhead, scheduler storage, concurrency or growth history that the configuration does not bound, the report *MUST* say that it is not established instead of stating a bound.
--

[horizontal]
ASIL:: B
Allocated to:: the element
Verification:: test, review
* *test*
** The computation against what placement used, for each route kind and for whole deployments, including registration and deferred backlogs.
** Repeated refused setups, growth histories and lost races that leave backing claimed, against what the report states.
* *review*: each reported figure's stated measure.
Status:: Draft
ISO 26262:: 6-7.4.13 (part-clause numbers only)

*Rationale.*
An integrator who places startup memory in a static region or a linker section has to size it before the process starts, and a request that does not fit is refused only at startup.
A size that anyone could work out in principle helps no one, so the element provides the computation itself.
Each route's reserved storage is reported under `+req~ssr-error-route-report~2+`.

_Why revision 3._
Revision 2 asked for the startup memory alone.
A report that counted only live objects would understate two things:

* the backing that refused setups, growth and lost races leave claimed;
* the storage that asynchronous registrations and deferred work need.

So each figure now says what it measures, and a figure that the configuration cannot bound is reported as not established.

Sizes that depend on a scheduler's tasks and timers, an allocator's overhead or a thread's stack are the supported configuration's package to state (xref:README.adoc#claims[the SEooC's claims]).
