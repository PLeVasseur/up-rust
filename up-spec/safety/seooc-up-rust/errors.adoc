[[req-ssr-refuse-before-heap]]
== Refuse before touching the heap

[.specitem,oft-sid="req~ssr-refuse-before-heap~2",oft-title="Refuse before touching the heap",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*Refusals are errors.*
An operation that cannot proceed in runtime mode *MUST* return an error.
All of these *MUST* be errors:

* exhaustion of slots, depth, held messages, the peer table or the call table;
* a payload or token that is too long;
* an expired TTL;
* an unreadable clock;
* a bounded wait that ran out.

*Order.*
Each refusal that can be decided before an operation's first heap acquisition *MUST* be decided before it.

*Cost of refusing.*
Deciding a refusal, producing its error and counting it *MUST NOT* acquire or release heap memory, abort or panic.

*Native and heap-free routes.*
On a native route, and on any route whose heap class is none, a refusal does nothing else.

*Serialized and owned routes.*
On a serialized or owned route, some refusals are reached only after the operation acquired heap memory under its declared heap class.
Examples are a check after decode, a failed allocation at a declared allocation point, or a wire check whose acceptance event falls after its deadline.
Such a refusal acquires nothing more.
It ends the ownership already created, and what that ownership holds is released exactly once as xref:heap.adoc#req-ssr-heap-slot-types[Decoded values and their destructors] and xref:../up-l1/bindings.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do] state.
That release is the route's declared heap use, not part of producing the refusal.
--

[horizontal]
ID:: `+req~ssr-refuse-before-heap~2+`
ASIL:: B
Allocated to:: the element
Verification:: heap-window, test
* *heap-window*
** Every refusal inside the window.
** On a serialized route, a refusal before the first declared allocation acquires nothing.
** On a serialized route, a refusal after it releases only what was already admitted, once, under the declared class.
* *test*
** Each named refusal.
** A check after decode, a failed declared allocation and a response first accepted after its deadline, each ending the admitted ownership exactly once.
Status:: Draft
ISO 26262:: 6-7.4.12 (part-clause numbers only)

*Rationale.*
A refusal that needed the heap, or that panicked, would turn an ordinary condition such as a full queue into a failure, at the moment the system is most loaded.
Runtime errors are fixed-size values with no heap data (<<req-ssr-error-fixed-size,Errors are fixed-size diagnoses>>), so returning one needs no allocation.

_Refusals after an admitted value._
Not every refusal can come before the heap is touched.
A serialized route that has already admitted an owned value must still end it on a refusal after decode, or on a response first accepted after its deadline, and ending it frees what the route's wire allocated.

So the item keeps three things apart:

* deciding, reporting and counting a refusal is heap-free on every route;
* every refusal that can come first comes ahead of the first allocation;
* the release of what was already admitted belongs to the route's declared class (xref:heap.adoc#req-ssr-heap-none[No heap in runtime mode]), so it is that route's declared heap use and never the refusal's.

An allocation failure follows the failure policy the route declares (xref:heap.adoc#req-ssr-heap-declared[The heap class is declared, with no default]).
A declaration does not make an infallible library allocation fail gracefully.
A route that needs exhaustion to be a refusal requires that guarantee by name (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name]).

[[req-ssr-refuse-no-panic]]
== No panic on runtime paths

[.specitem,oft-sid="req~ssr-refuse-no-panic~1",oft-title="No panic on runtime paths",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Element code reachable in runtime mode *MUST NOT* panic or abort:

* not for any bytes, length or sequence a peer sends;
* not for any clock reading;
* not for any sequence of calls through the public API.

Arithmetic on runtime paths *MUST* be checked, saturating or wrapping by intent, and *MUST NOT* reach an overflow panic.
--

[horizontal]
ID:: `+req~ssr-refuse-no-panic~1+`
ASIL:: B
Allocated to:: the element
Verification:: gate, fault-injection, test
* *gate*
** The panic-link check over the runtime path on both compilers.
The inbound metadata, payload, peer reference and TTL are fed as opaque inputs, so that no panic branch can be proven dead from constant inputs.
** The workspace lints.
* *fault-injection*: malformed and truncated frames.
Status:: Draft
ISO 26262:: 6-Table 1 (part-clause numbers only)

*Rationale.*
In the build that ships, a panic aborts the process (xref:build.adoc#req-ssr-build-panic-abort[The ASIL build aborts on panic and checks overflow]).
So a panic reachable in runtime mode is a crash that a peer's bytes or a clock reading could set off.

No waiver can cover a panic: a waiver covers allocation inside middleware only (xref:waivers.adoc#req-ssr-waiver-scope[A waiver covers middleware and nothing else]).

Code that runs on a runtime path but that the element does not own is not element code.
Examples are the destructor of an owned value, an allocator's release or a dependency they reach.

* The element keeps memory safe whatever that code does (xref:heap.adoc#req-ssr-heap-slot-types[Decoded values and their destructors]).
* It promises nothing about that code's panics on a route that does not require panic-free cleanup: the guarantee is not admitted there, and the route's report states separately whether evidence establishes it.
* On a route that requires it, setup admits such code only where it is established that it cannot panic or abort in any context that runs it, and refuses the route by name otherwise (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name]).

Moving such work to another thread does not change this.
A panic in element code is a defect on every route, whatever the route requires.

[[req-ssr-error-fixed-size]]
== Errors are fixed-size diagnoses

[.specitem,oft-sid="req~ssr-error-fixed-size~1",oft-title="Errors are fixed-size diagnoses",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Every error and report the element returns in runtime mode *MUST* be a fixed-size value that can be copied, name its cause, and name the route and the setting where there is one.

Producing it *MUST* format nothing, log nothing and allocate nothing.

Text for people *MUST* be formatted only in initialization mode.
--

[horizontal]
ID:: `+req~ssr-error-fixed-size~1+`
ASIL:: B
Allocated to:: the element
Verification:: gate (a compile-time `+Copy+` assertion for each runtime error type), heap-window (the error paths), review
Status:: Draft
ISO 26262:: 6-7.4.12 (part-clause numbers only)

*Rationale.*
A fixed-size error that can be copied carries no heap data, so reporting a refused send cannot touch the heap.

An error that names its cause, its route and the setting at fault tells the integrator what to change, with no log to search.

Text for people is produced only from initialization errors, where formatting is allowed.

[[req-ssr-error-no-silent-loss]]
== No silent loss, and each loss counted once

[.specitem,oft-sid="req~ssr-error-no-silent-loss~3",oft-title="No silent loss, and each loss counted once",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*Every loss is returned or counted.*
Every frame the element refuses, drops, evicts or expires in runtime mode *MUST* be either returned to its caller as an error, or counted exactly once in its route's fixed counters, under a counter that names the cause.

* A retry is not a drop.
* The counters can be read in runtime mode without heap.

*Losses the binding cannot observe.*
A loss entirely inside middleware that the binding cannot observe is not a counted event.
That route's report *MUST* explicitly disclose the unobservable-loss limitation.

Observable overflow discards *MUST* be counted as specified by xref:qos.adoc#req-ssr-qos-overflow[Overflow acts as declared].
This exception does not excuse missing observable counts.

*Counter behaviour.*

* A fault counter saturates at 2^32^ − 1 and stays there, and an increment below that is never dropped.
* A flow counter (`+carried+`, `+busy+`, `+parked+`) wraps, and readers take differences (xref:assumptions-of-use.adoc#aou-seooc-application-reacts[The application reacts to what the element reports]).

*Double release.*
A free slot released twice with no take between the two releases is counted as a fault, never absorbed silently.
One released, taken and released again is not detected.

*Pull bindings.*
A pull binding's failure to read its own queue is counted on the route (`+receive_failed+`).
So is a data connection that its middleware drops or fails to set up without an error.

*E2E clients.*
An E2E client counts a response with no E2E header in a route counter of its own, `+unprotected+`, never in the E2E counter.
--

[horizontal]
ID:: `+req~ssr-error-no-silent-loss~3+`
ASIL:: B
Allocated to:: the element
Verification:: test, heap-window
* *test*
** One counter per cause.
** Each observable loss counted once or returned as specified, under contention and under `+Wait+` too.
** Unobservable middleware losses disclosed rather than represented as complete counts.
* *heap-window*: counters read inside the window.
Status:: Draft
ISO 26262:: 6-Annex D.2.4 (part-clause numbers only)

*Rationale.*
A named count or an error gives each observable local loss an observation point.
Saturating fault counts avoid turning an overflow into apparent recovery.

A declared middleware visibility limit is not a measurement of its losses, and counter fields alone do not establish that every discard is observable.

_End-to-end protection._

* The E2E wire's figures count, as lost, each frame of the reference's incarnation that left the receiver's window without arriving, or was still open when the reference changed (xref:e2e-wire.adoc#req-ssr-e2e-figures[The E2E wire's figures cover the stretch from encode to decode]).
* An end-to-end refusal is counted in its own route counter, not in `+refused+` (xref:e2e-wire.adoc#req-ssr-e2e-refusal-counted[End-to-end refusals are named, and counted once]).
* The `+unprotected+` clause binds only a client of the E2E wire, which is deferred and not part of this delivery.
It takes effect when that wire is delivered, and no other clause depends on it.

[[req-ssr-error-route-report]]
== Each route reports what it got

[.specitem,oft-sid="req~ssr-error-route-report~2",oft-title="Each route reports what it got",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
For every route, the element *MUST* report in runtime mode, without heap:

* the send mode it got (lent or handed off);
* the QoS in force;
* its reserved storage;
* its heap class, naming the permit where middleware allocates.

The transport's waiver list *MUST* map every such permit to the waiver that admitted it.

A report *MUST NOT* state a setting the route does not have.
--

[horizontal]
ID:: `+req~ssr-error-route-report~2+`
ASIL:: B
Allocated to:: the element
Verification:: test (the send mode, QoS, reserved storage, heap class and permit, and the join to the waiver list, each asserted)
Status:: Draft

*Rationale.*
Each report names its permit through its heap class, and the runtime keeps the waivers it recorded.
So each permit joins to the waiver that admitted it.
