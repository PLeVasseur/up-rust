[[req-ssr-release-none]]
== Nothing is released in runtime mode

[.specitem,oft-sid="req~ssr-release-none~2",oft-title="Nothing is released in runtime mode",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
In runtime mode each route, role, slot table, binding resource, worker and transport *MUST* remain allocated and attached for the life of the process.

* Workers created during initialization keep running and are never joined in runtime mode.
* A route keeps its slots and its binding resources when its gate disables it.
* A route gate (xref:../up-l2/streamer.adoc#req-ssr-streamer-route-gate[Each route has a heap-free gate]) may change the route's state, and nothing else about it.
--

[horizontal]
ID:: `+req~ssr-release-none~2+`
ASIL:: B
Allocated to:: the element
Verification:: compile-fail (for the Streamer, a delete after activation), review
Status:: Draft
ISO 26262:: 6-Table 6 1b (part-clause numbers only)

*Rationale.*
A gate changes forwarding state without changing storage reservations or releasing resources.
So disabling a route remains compatible with retaining its runtime storage.

[[req-ssr-release-inert-drop]]
== Dropping a runtime handle does nothing

[.specitem,oft-sid="req~ssr-release-inert-drop~1",oft-title="Dropping a runtime handle does nothing",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Every runtime-mode handle type *MUST* hold only `+'static+` data and indices, and *MUST NOT* have drop glue.
The handle types are:

* the transport runtime;
* every activated L2 handle;
* the carrier routes;
* the Streamer with its gate and counter handles.

This *MUST* be proved for each type at compile time.
--

[horizontal]
ID:: `+req~ssr-release-inert-drop~1+`
ASIL:: B
Allocated to:: the element
Verification:: gate (the const assertion for each handle type)
Status:: Draft

*Rationale.*
A handle that held a reference count, such as an `+Arc+`, could free memory when the last one is dropped, which runtime mode forbids (xref:heap.adoc#req-ssr-heap-none[No heap in runtime mode]).
A proof at compile time holds for every build of every handle type, where a test could only sample it.

A per-message operation, such as a lease or an asynchronous operation still in flight, is not such a handle.
Its drop follows <<req-ssr-release-lease-drop,A lease gives back its slot and nothing else>> and xref:build.adoc#req-ssr-async-seam[The asynchronous interface has a written, executor-independent contract].

[[req-ssr-release-lease-drop]]
== A lease gives back its slot and nothing else

[.specitem,oft-sid="req~ssr-release-lease-drop~4",oft-title="A lease gives back its slot and nothing else",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*The drop.*
Dropping a per-message lease (a received message, an RPC call, a request, a parked frame, a loan) *MUST* give its slot back to a fixed table exactly once:

* at once where the slot holds nothing whose release is in progress or pending;
* otherwise when that release completes.

The element's own work in the drop *MUST NOT* block or panic.
It takes no lock that can wait.
A lock-free retry, bounded by other threads' progress, is allowed.

*Native routes.*
On a native route the drop does nothing else: it frees no heap, it cannot panic and it never waits.

*Heap-free routes.*
On a serialized or owned route whose heap class is none, the drop frees no heap.
It runs a destructor only for a type that xref:heap.adoc#req-ssr-heap-slot-types[Decoded values and their destructors] admits there.

*Routes that declare allocation.*
On a serialized or owned route whose declared heap class admits allocation, the drop also ends the initialized owned value the lease holds, exactly once, under that class (xref:heap.adoc#req-ssr-heap-slot-types[Decoded values and their destructors]).
That destruction may free what the route's wire, binding or allocation provider allocated.

* On a route that does not require non-waiting release (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name]), the drop destroys the value on its own path, under the route's declared policy.
The destruction may wait inside the allocation domain that the policy names, and the route's report says so.
* On a route that requires non-waiting release, the drop destroys the value at once only where it is established that this destruction cannot wait.
Otherwise it hands the value, without waiting or panicking, through a lock-free hand-off to the route's release service, which destroys it later.

Whichever applies, the drop releases no route, role, table, startup region or other runtime resource, and revokes no other owner.

*When a release service is needed.*
A release service is the mechanism of non-waiting release over a dependency that can wait.

* A route that requires non-waiting release, and whose release can wait, *MUST* have one, or setup refuses the route by name (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name]).
* A configuration without one offers no non-waiting release over such a dependency.
That refuses only a route that requires it, and never a route for owning values.

The rest of this item binds every release service and all pending cleanup, a binding's deferred return of a retained owner included.

*The release service.*
A release service *MUST* be created during initialization and run for the life of the process (<<req-ssr-release-none,Nothing is released in runtime mode>>), with hand-off capacity fixed at setup.

* A route's capacity, its slots together with that hand-off capacity, covers every value the route can own at once, counting a hand-off in progress, a value queued or in service and a value whose lease was forgotten.
* The service acquires no heap memory and performs only the destructions and slot returns handed to it, without a call from the application.
* Its own work for each value, the hand-off, dispatch, bookkeeping and the change of charge, is bounded as xref:bounded-work.adoc#req-ssr-bound-work[Work per call is bounded by setup data] states.
* It keeps each value charged to its route until that value's destruction completes.

*Pending cleanup.*
A value handed to a release service, and a retained owner handed to a binding's deferred return (xref:../up-l1/bindings.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do]), is _pending cleanup_ from its hand-off until its release completes.
Pending cleanup is ownership awaiting release, neither a completed release nor unfinished traffic.

*A wait without a deadline.*
Pending cleanup *MAY* wait without a finite logical deadline, and only for the dependency that its policy names, such as the lock of an allocation domain or of the underlying transport's port.

* A release handed to the service contains no unbounded computation of its own, which the evidence for non-waiting release establishes.
* Pending cleanup waits for no lock or other primitive shared with another process and for no other process's progress (xref:bounded-work.adoc#req-ssr-bound-no-cross-process-lock[No lock shared with another process]).
* No deadline for its completion is promised unless a supported configuration's package establishes one through the release's own mechanism.
A deadline decides the outcome of the operation that ended the value (xref:bounded-work.adoc#req-ssr-bound-wait[Every wait is bounded]), never whether or when its cleanup completes.

*Ownership and charge.*
Ownership passes to pending cleanup exactly once, and its route's charge and its count of completed releases change only when the release actually completes.

* A pending or partly completed release is never started again as a new destruction.
* No observer, on a timeout or otherwise, revokes its owner, ends its release, reuses its storage, reports it complete or frees its backing.

*Isolation.*
While pending cleanup waits, or if it never completes, it *MUST NOT* hold or occupy a lock, an exclusion section, an execution context, a worker, a task, an interrupt context or any other resource that the element needs for:

* a bounded operation, a drop or a hand-off;
* arrival, deadline, expiry and peer-failure accounting;
* health and capacity observation; or
* the return of any owner whose release does not itself need the dependency that the stalled release waits for.

This holds transitively, through the allocation domain's locks, the underlying transport's port locks, the service's dispatch and wake paths, shared exclusion and every callback that the release can reach.
A separate thread is not by itself this isolation.

Setup *MUST* refuse by name, before taking any value or owner that would need it, a route whose pending cleanup it cannot establish to be isolated in this way.

*Charge and capacity while a release is unfinished.*
A value whose release is in progress or pending stays charged.

* A stalled or failed release leaves its values charged and shows as counted capacity pressure on their routes, never as a slot reused while owned or a value destroyed twice.
On a route that requires non-waiting release it never shows as a drop that waits.
* The capacity it exhausts is refused as the route's genuine exhaustion, never relieved by an early reuse or a new caller limit.
* Fixed capacity contains an unfinished release.
It promises neither that the capacity is recovered within a time nor sustained throughput while a release stays unfinished.
* A claim that needs either is available only in a supported configuration whose package establishes the release progress and sizing it relies on, and is otherwise refused by name.

*Not a second queue.*
The hand-off holds ownership awaiting release, not unread traffic, so it is not a second receive queue.

*Bindings.*
A binding's frame destructor has the same duty (xref:../up-l1/bindings.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do]).

*Rationale.*
Returning a slot permits reuse within the fixed reservation.
Destroying that reservation would introduce a runtime release path.

_Owned values._
A serialized route that admitted an owning value must still destroy it when its lease ends, once, under the policy it declared.
So the no-free rule binds the native and heap-free routes, and a destructor on a heap-free route uses no heap.
The destruction ends that value, never the reservation that held it.

_Where the destruction runs._
An ordinary allocator's release can take a lock that waits.
A route that does not require non-waiting release accepts that wait on the path that ended the value: its policy states it, and its report shows it.
The element's own part of the drop still takes no waiting lock, and the element holds nothing of its own across the destruction (xref:heap.adoc#req-ssr-heap-slot-types[Decoded values and their destructors]).
So a waiting destruction delays the path it runs on, and the element adds no lock to that wait.

A route that requires non-waiting release moves a destruction that could wait off the drop, as a retained owner's return is moved, and the value stays charged until it is destroyed.

Moving it moves only the wait.
A destruction that could panic or abort would do so on the service as well.
So a route that requires panic-free cleanup is admitted on evidence, never on deferral (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name]).
Catching an unwind cannot stand in for that evidence, since it cannot stop an abort, prevent the panic or show that the cleanup finished.

_A release service is a mechanism, not a condition of ownership._
The service exists to give non-waiting release over a dependency that can wait.
A configuration that has none cannot offer that guarantee, and says so by refusing a route that requires it.
It still carries ordinary owning routes, whose destructions run where their values end.

_Deferred return of a retained owner._
Where an underlying transport's own release of a retained sample can wait, the return is deferred.
The drop pushes the retained owner onto a lock-free queue sized for every admitted retained owner and returns, and the binding's own worker completes the release.
That queue holds ownership awaiting return, not unread traffic.
A stalled worker shows as counted capacity pressure, never as a drop that waits (xref:../up-l1/bindings.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do]).

_Why no completion deadline._
Moving a wait off the drop does not bound it.
A release that waits for an allocator's or a middleware's own lock cannot observe a deadline from inside that call.
So the element states when the ending operation's outcome is due, not when its cleanup completes.
It keeps what the cleanup owns charged, and it keeps pending cleanup from holding anything that other work needs.

Two designs would not meet that:

* a worker of its own that one stalled release could stop for every route;
* a release that holds a lock which public allocation also needs while it waits.

_What fixed capacity gives._
Fixed capacity bounds what an unfinished release can consume, but it cannot keep throughput going while a release never completes.
So a claim of recovered capacity within a time rests on a package that establishes release progress.
A measured average delay is not such a bound.

_Native routes._
On a native route that return gives the retained owner back to the underlying transport through its own interface and frees no heap.
Returning a preallocated loan never frees the backing it lives in (xref:heap.adoc#req-ssr-heap-none[No heap in runtime mode]).
