[[req-ssr-release-none]]
== Nothing is released in runtime mode

[.specitem,oft-sid="req~ssr-release-none~3",oft-title="Nothing is released in runtime mode",oft-needs="impl,utest",oft-tags="SafetyUpRustCore,SafetyBinding"]
--
In runtime mode the element *MUST* keep each route, role, slot table, binding resource, worker and transport allocated and attached for the life of the process.
In runtime mode each binding *MUST* keep its resources, its workers and its transport allocated and attached for the life of the process.

* The element *MUST* keep each worker created during initialization running and *MUST NOT* let one be joined in runtime mode.
* Each binding *MUST* keep each of its workers created during initialization running and *MUST NOT* let one be joined in runtime mode.

*The Streamer.*
What the Streamer's routes and gates, and the workers of the Streamer binary, keep in runtime mode is stated with the Streamer (xref:../up-l2/streamer.adoc#req-ssr-streamer-route-lock[Routes and subscriptions are locked at activation]; xref:../up-l2/streamer.adoc#req-ssr-streamer-route-gate[Each route has a heap-free gate]; xref:../up-l2/streamer.adoc#req-ssr-streamer-workers[Workers are fixed at initialization]).
--

[horizontal]
ID:: `+req~ssr-release-none~3+`
ASIL:: B
Allocated to:: the element; each binding, for its resources, its workers and its transport
Verification:: compile-fail (for the Streamer, a delete after activation), review
ISO 26262:: 6-Table 6 1b (part-clause numbers only)

*Rationale.*
A gate changes forwarding state without changing storage reservations or releasing resources.
So disabling a route remains compatible with retaining its runtime storage.

[[req-ssr-release-inert-drop]]
== Dropping a runtime handle does nothing

[.specitem,oft-sid="req~ssr-release-inert-drop~1",oft-title="Dropping a runtime handle does nothing",oft-needs="impl,utest",oft-tags="SafetyUpRustCore,SafetyStreamer"]
--
The element *MUST* have every runtime-mode handle type hold only `+'static+` data and indices, and *MUST NOT* let one have drop glue.
The Streamer *MUST* have its runtime type and its gate and counter handles hold only `+'static+` data and indices, and *MUST NOT* let one of them have drop glue.
The handle types are:

* the transport runtime;
* every activated L2 handle;
* the carrier routes;
* the Streamer with its gate and counter handles.

The element *MUST* have this proved for each type at compile time, and the Streamer *MUST* have it proved at compile time for its runtime type and its gate and counter handles.
--

[horizontal]
ID:: `+req~ssr-release-inert-drop~1+`
ASIL:: B
Allocated to:: the element; the Streamer, for its runtime type and its gate and counter handles
Verification:: gate (the const assertion for each handle type)

*Rationale.*
A handle that held a reference count, such as an `+Arc+`, could free memory when the last one is dropped, which runtime mode forbids (xref:heap.adoc#req-ssr-heap-none[No heap in runtime mode on a native path]).
A proof at compile time holds for every build of every handle type, where a test could only sample it.

A per-message operation, such as a lease or an asynchronous operation still in flight, is not such a handle.
Its drop follows <<req-ssr-release-lease-drop,A lease gives back its slot and nothing else>> and xref:build.adoc#req-ssr-async-seam[The asynchronous interface has a written, executor-independent contract].

[[req-ssr-release-lease-drop]]
== A lease gives back its slot and nothing else

[.specitem,oft-sid="req~ssr-release-lease-drop~6",oft-title="A lease gives back its slot and nothing else",oft-needs="impl,utest",oft-tags="SafetyUpRustCore,SafetyBinding"]
--
*The drop.*
The element *MUST* have the drop of a per-message lease (a received message, an RPC call, a request, a parked frame, a loan) give the lease's slot back to a fixed table exactly once:

* at once where the slot holds nothing whose release is in progress or pending;
* otherwise when that release completes.

The logical completion of an RPC call and the return of its slot are separate events: completing a call returns no slot by itself.

The element *MUST NOT* let its own work in the drop block or panic, or take a lock that can wait.
A lock-free retry is allowed only as xref:bounded-work.adoc#req-ssr-bound-work[Work per call is bounded by setup data] states for each lock-free retry loop of the element.

*Native routes.*
On a native route the element *MUST NOT* let the drop do anything else: the drop frees no heap, cannot panic and never waits.

*Heap-free routes.*
On a serialized route whose heap class is none, the drop frees no heap.
It runs a destructor only for a type that xref:heap.adoc#req-ssr-heap-slot-types[A decoded value is destroyed once, as its route's class admits] admits there.

*Routes that declare allocation.*
On a serialized route whose declared heap class admits allocation, the drop also ends the initialized owned value the lease holds, exactly once, under that class (xref:heap.adoc#req-ssr-heap-slot-types[A decoded value is destroyed once, as its route's class admits]).
That destruction may free what the route's wire, binding or allocation provider allocated (xref:../../sdk/owned-frame/providers.adoc#req-sdk-owned-frame-provider-selection[The selected memory provider is the only one used, and selecting it claims nothing] states what an allocation provider is).

* On a route that does not require non-waiting release (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name, and admitted or refused]), the value is destroyed on a path of that route under the route's declared policy, as xref:heap.adoc#req-ssr-heap-slot-types[A decoded value is destroyed once, as its route's class admits] states: on the drop's own path, or, where that path is native or shared work, on a later operation of the same route.
The destruction may wait inside the allocation domain that the policy names, and the route's report says so.
* On a route that requires non-waiting release, the drop destroys the value at once only where it is established that this destruction cannot wait.
Otherwise the element *MUST* have the drop hand the value, without waiting or panicking, through a lock-free hand-off to the route's release service, which destroys it later.

Whichever applies, the drop releases no route, role, table, startup region or other runtime resource, and revokes no other owner.

*When a release service is needed.*
A release service is the mechanism of non-waiting release over a dependency that can wait.

* A route that requires non-waiting release, whose release can wait and that has no release service, is one for which that guarantee is not established, and the element refuses it at setup as xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name, and admitted or refused] states.
* A configuration without one refuses only a route that requires non-waiting release over such a dependency.

*Every decoded value.*
These duties hold for each decoded value of a type that a route admits, in every transition that ends its ownership (xref:heap.adoc#req-ssr-heap-slot-types[A decoded value is destroyed once, as its route's class admits]), for a destruction on a path of the route as for one handed to a release service:

* The element *MUST* make the route's capacity cover every value that the route can own at once, a value whose destruction is in progress or pending included.
* The element *MUST* keep the value owned and charged to its route until its destruction completes, and *MUST NOT* report it as released before then.
A destruction in progress, or pending on a release service, is not a completed one.
* The element *MUST* show a destruction that stalls or fails as capacity pressure on its route.

The rest of this item binds the element for every release service and all pending cleanup, a binding's deferred return included, and each binding for its deferred return: each for its part.

*The release service.*
Each for its part, the element and each binding *MUST* create each release service that it uses, a binding's mechanism for its deferred return included, during initialization, and run it for the life of the process (<<req-ssr-release-none,Nothing is released in runtime mode>>), with hand-off capacity fixed at setup.

* Each for its part, the element and each binding *MUST* size a route's capacity, its slots together with that hand-off capacity, to cover every value the route can own at once, counting a hand-off in progress, a value queued or in service and a value whose lease was forgotten.
* Each for its part, they *MUST NOT* let the service acquire heap memory, and *MUST* have it perform only the destructions and slot returns handed to it, without a call from the application.
* Each for its part, they *MUST* bound the service's own work for each value, the hand-off, dispatch, bookkeeping and the change of charge, as xref:bounded-work.adoc#req-ssr-bound-work[Work per call is bounded by setup data] states.

*Pending cleanup.*
A value handed to a release service, and a retained owner or the binding's own allocation for a frame handed to a binding's deferred return (xref:../up-l1/bindings.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do]), is _pending cleanup_ from its hand-off until its release completes.
Pending cleanup is ownership awaiting release, neither a completed release nor unfinished traffic.

*A wait without a deadline.*
Each for its part, the element and each binding *MAY* let pending cleanup wait without a finite logical deadline, and only for the dependency that its policy names, such as the lock of an allocation domain or of the middleware's port.

* A release handed to the service contains no unbounded computation of its own, which the evidence for non-waiting release establishes.
* Each for its part, they *MUST NOT* let pending cleanup wait for a lock or other primitive shared with another process, or for another process's progress (xref:bounded-work.adoc#req-ssr-bound-no-cross-process-lock[No lock shared with another process]).
* Pending cleanup has no general finite completion bound.
A supported configuration's package can establish one for an exact release mechanism, and only that package's bound is stated.
A deadline decides the outcome of the operation that ended the value (xref:bounded-work.adoc#req-ssr-bound-wait[Every bounded wait has a logical deadline]), never whether or when its cleanup completes.

*Ownership and charge.*
Each for its part, the element and each binding *MUST* pass ownership to pending cleanup exactly once, and *MUST* change its route's charge and its count of completed releases only when the release completes.

* Each for its part, the element and each binding *MUST NOT* start a pending or partly completed release again as a new destruction.
* They *MUST NOT* let an observer, on a timeout or otherwise, revoke its owner, end its release, reuse its storage, report it complete or free its backing.

*Isolation.*
While pending cleanup waits, or if it never completes, the element and each binding, each for its part, *MUST NOT* let it hold or occupy a lock, an exclusion section, an execution context, a worker, a task, an interrupt context or any other resource that the element needs for:

* a bounded operation, a drop or a hand-off;
* arrival, deadline, expiry and peer-failure accounting;
* health and capacity observation; or
* the return of any owner whose release does not itself need the dependency that the stalled release waits for.

They *MUST* keep this isolation transitively, through the allocation domain's locks, the middleware's port locks, the service's dispatch and wake paths, shared exclusion and every callback that the release can reach.
A separate thread is not by itself this isolation.

The exception in the last entry reaches only an owner whose own release needs the same dependency, the one that the stalled release's policy names.
What a survivor's operations, accounting, health reports and other owners' returns may wait for after a peer's failure is stated in xref:../up-l1/peers.adoc#req-ssr-peer-failure-normal[Peer failure is normal input].

Each for its part, the element and each binding *MUST* refuse at setup, by name, before taking any value or owner that would need it, a route whose pending cleanup it cannot establish to be isolated in this way.

*Charge and capacity while a release is unfinished.*
Each for its part, the element and each binding *MUST* keep a value, a retained owner or a binding's allocation for a frame whose release is in progress or pending charged.

* Each for its part, they *MUST* keep what a stalled or failed release holds charged and show it as counted capacity pressure on its route, never as a slot reused while owned or a value destroyed twice.
On a route that requires non-waiting release it never shows as a drop that waits.
* Each for its part, they *MUST* refuse the capacity that such a release exhausts as the route's genuine exhaustion, never relieving it by an early reuse or a new caller limit.
* Fixed capacity contains an unfinished release.
* A claim that needs capacity recovered within a time, or sustained throughput while a release stays unfinished, is available only in a supported configuration whose package establishes the release progress and sizing it relies on; otherwise, each for its part, they *MUST* refuse it by name.

*The hand-off.*
The hand-off to a release service or to a binding's deferred return holds ownership awaiting release, not unread traffic, so it is not a second receive queue.

*Bindings.*
The duties of a binding's frame destructor are stated in xref:../up-l1/bindings.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do].
--

*Rationale.*
Returning a slot permits reuse within the fixed reservation.
Destroying that reservation would introduce a runtime release path.

_Owned values._
A serialized route that admitted an owning value still destroys it when its lease ends, once, under the policy it declared.
So the no-free rule binds the native and heap-free routes, and a destructor on a heap-free route uses no heap.
The destruction ends that value, and the reservation that held it stays.

_Where the destruction runs._
An ordinary allocator's release can take a lock that waits.
A route that does not require non-waiting release accepts that wait on the path that ended the value: its policy states it, and its report shows it.
The element's own part of the drop still takes no waiting lock, and the element holds nothing of its own across the destruction (xref:heap.adoc#req-ssr-heap-slot-types[A decoded value is destroyed once, as its route's class admits]).
So a waiting destruction delays the path it runs on, and the element adds no lock to that wait.

A route that requires non-waiting release moves a destruction that could wait off the drop, as a retained owner's return is moved, and the value stays charged until it is destroyed.

Moving a destruction to the service changes only where it waits, and a destruction that could panic or abort would do so on the service as well.
So a route that requires panic-free cleanup is admitted only on evidence (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name, and admitted or refused]).
Catching an unwind cannot stand in for that evidence, since it cannot stop an abort, prevent the panic or show that the cleanup finished.

_What a release service gives._
The service exists to give non-waiting release over a dependency that can wait.
A configuration that has none cannot offer that guarantee, and refuses a route that requires it.
It still carries ordinary owning routes, whose destructions run on a path of the route, as xref:heap.adoc#req-ssr-heap-slot-types[A decoded value is destroyed once, as its route's class admits] states.

_Every decoded value._
A value whose destruction has not completed still holds what it owns, whichever transition ended it and wherever its destruction runs.
So its route counts it until then, and a destruction that stalls shows as pressure on that route, not as free capacity.

_Deferred return of a retained owner._
Where a middleware's own release of a retained owner can wait, the return is deferred.
The drop hands the retained owner over without waiting and returns, and the binding's deferred return completes the release.
A stalled return shows as counted capacity pressure, never as a drop that waits (xref:../up-l1/bindings.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do]).

_Completion deadlines._
Moving a wait off the drop does not bound it, and does not by itself isolate it.
A release that waits for an allocator's or a middleware's own lock cannot observe a deadline from inside that call.
So the element states when the ending operation's outcome is due, not when its cleanup completes.
It keeps what the cleanup owns charged, and keeps pending cleanup from holding what the element needs for other work.

.Two designs whose pending cleanup is not isolated
====
* A single worker that serves every route, which one stalled release could stop for all of them.
* A release that, while it waits, holds a lock that an allocation for a bounded operation also needs.
====

_What fixed capacity gives._
Fixed capacity bounds what an unfinished release can consume, but it cannot keep throughput going while a release never completes.
So a claim of recovered capacity within a time rests on a package that establishes release progress.
A measured average delay is not such a bound.

_Native routes._
On a native route, a retained owner's return gives it back to the middleware through the middleware's own interface, and frees no heap.
Returning a preallocated loan never frees the backing it lives in (xref:heap.adoc#req-ssr-heap-none[No heap in runtime mode on a native path]).
