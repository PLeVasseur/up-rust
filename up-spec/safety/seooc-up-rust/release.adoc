== Nothing is released in runtime mode

[.specitem,oft-sid="req~ssr-release-none~2",oft-title="Nothing is released in runtime mode",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
In runtime mode each route, role, slot table, binding resource, worker and transport *MUST* remain allocated and attached for the life of the process.

* Workers created during initialization keep running and are never joined in runtime mode.
* A route keeps its slots and its binding resources when its gate disables it.
* A route gate (`+req~ssr-streamer-route-gate~2+`) may change the route's state, and nothing else about it.
--

[horizontal]
ASIL:: B
Allocated to:: the element
Verification:: compile-fail (for the Streamer, a delete after activation), review
Status:: Draft
ISO 26262:: 6-Table 6 1b (part-clause numbers only)

*Rationale.*
A gate changes forwarding state without changing storage reservations or releasing resources.
So disabling a route remains compatible with retaining its runtime storage.

== Dropping a runtime handle does nothing

[.specitem,oft-sid="req~ssr-release-inert-drop~1",oft-title="Dropping a runtime handle does nothing",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Every runtime-mode handle type *MUST* hold only `+'static+` data and indices, and *MUST NOT* have drop glue.
The handle types are:

* the transport runtime;
* every activated L2 handle;
* the carrier routes;
* the Streamer with its gate and counter handles.

This *MUST* be proved for each type at compile time.
--

[horizontal]
ASIL:: B
Allocated to:: the element
Verification:: gate (the const assertion for each handle type)
Status:: Draft

*Rationale.*
A handle that held a reference count, such as an `+Arc+`, could free memory when the last one is dropped, which runtime mode forbids (`+req~ssr-heap-none~2+`).
A proof at compile time holds for every build of every handle type, where a test could only sample it.

A per-message operation, such as a lease or an asynchronous operation still in flight, is not such a handle.
Its drop follows `+req~ssr-release-lease-drop~3+` and `+req~ssr-async-seam~2+`.

== A lease gives back its slot and nothing else

[.specitem,oft-sid="req~ssr-release-lease-drop~3",oft-title="A lease gives back its slot and nothing else",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*The drop.*
Dropping a per-message lease (a received message, an RPC call, a request, a parked frame, a loan) *MUST NOT* block, and *MUST* give its slot back to a fixed table exactly once:

* at once where the slot holds nothing whose release is pending;
* otherwise when that release completes.

It takes no lock that can wait.
A lock-free retry, bounded by other threads' progress, is allowed.

*Native and heap-free routes.*
On a native route, and on any route whose heap class is none, it does nothing else: it frees no heap and cannot panic.

*Routes that declare allocation.*
On a serialized or owned route whose declared heap class admits allocation, it also ends the initialized owned value the lease holds, exactly once, under that class.
Setup admitted that value's type, wire, binding and provider only because their destruction cannot panic or abort (`+req~ssr-heap-slot-types~2+`).

* The drop destroys the value at once only where the route's declared policy establishes that this destruction cannot wait.
* Otherwise it hands the value, without waiting or panicking, through a lock-free hand-off to the route's release service, which destroys it later.

That destruction may free what the route's wire, binding or allocation provider allocated.

Either way the drop itself neither waits nor panics, releases no route, role, table, startup region or other runtime resource, and revokes no other owner.

*The release service.*
The release service *MUST* be created during initialization and run for the life of the process (`+req~ssr-release-none~2+`), with hand-off capacity fixed at setup.

* A route's capacity, its slots together with that hand-off capacity, covers every value the route can own at once, counting a hand-off in progress, a value queued or in service and a value whose lease was forgotten.
* The service acquires no heap memory and performs only the admitted destructions and slot returns handed to it, without a call from the application.
* Its own work for each value, the hand-off, dispatch, bookkeeping and the change of charge, is bounded as `+req~ssr-bound-work~2+` states.
* It keeps each value charged to its route until that value's destruction completes.

*Pending cleanup.*
A value handed to the release service, and a retained owner handed to a binding's deferred return (`+req~ssr-binding-frame-drop~4+`), is _pending cleanup_ from its hand-off until its release completes.
Pending cleanup is ownership awaiting release, neither a completed release nor unfinished traffic.

*The only wait without a deadline.*
Apart from a deliberate idle wait (`+req~ssr-bound-wait~2+`), pending cleanup is the only element work that *MAY* wait without a finite logical deadline, and only for the dependency that its admitted policy names, such as the lock of an allocation domain or of the underlying transport's port.

* An admitted release contains no unbounded computation of its own.
* Pending cleanup waits for no lock or other primitive shared with another process and for no other process's progress (`+req~ssr-bound-no-cross-process-lock~1+`).
* No deadline for its completion is promised unless a supported configuration's package establishes one through the release's own mechanism.
A deadline decides the outcome of the operation that ended the value (`+req~ssr-bound-wait~2+`), never whether or when its cleanup completes.

*Ownership and charge.*
Ownership passes to pending cleanup exactly once, and its route's charge and its count of completed releases change only when the release actually completes.

* A pending or partly completed release is never started again as a new destruction.
* No observer, on a timeout or otherwise, revokes its owner, ends its release, reuses its storage, reports it complete or frees its backing.

*Isolation.*
While pending cleanup waits, or if it never completes, it *MUST NOT* hold or occupy a lock, an exclusion section, an execution context, a worker, a task, an interrupt context or any other resource that the element needs for:

* a bounded operation, a drop or a hand-off;
* arrival, deadline, expiry and peer-failure accounting;
* health and capacity observation; or
* the return of any owner whose release does not itself need the dependency that the stalled release waits for.

This holds transitively, through the allocation domain's locks, the underlying transport's port locks, the service's dispatch and wake paths, shared exclusion and every callback that the release can reach.
A separate thread is not by itself this isolation.

Setup *MUST* refuse by name, before acquiring any value or owner that would need it, a route whose pending cleanup it cannot establish to be isolated in this way.

*Charge and capacity while pending.*
Pending cleanup stays charged.

* A stalled or failed release leaves its values charged and shows as counted capacity pressure on their routes, never as a drop that waits, a slot reused while owned or a value destroyed twice.
* The capacity it exhausts is refused as the route's genuine exhaustion, never relieved by an early reuse or a new caller limit.
* Fixed capacity contains pending cleanup.
It promises neither that the capacity is recovered within a time nor sustained throughput while a release stays pending.
* A claim that needs either is available only in a supported configuration whose package establishes the release progress and sizing it relies on, and is otherwise refused by name.

*Not a second queue.*
The hand-off holds ownership awaiting release, not unread traffic, so it is not a second receive queue.

*Bindings.*
A binding's frame destructor has the same duty (`+req~ssr-binding-frame-drop~4+`).
--

*Rationale.*
Returning a slot permits reuse within the fixed reservation.
Destroying that reservation would introduce a runtime release path.

_Owned values._
A serialized route that admitted an owning value must still destroy it when its lease ends, once, under the policy it declared.
So the no-free rule binds the native and heap-free routes whose values own nothing.
The destruction ends that value, never the reservation that held it.

_Why a waiting destruction leaves the drop._
An ordinary allocator's release can take a lock that waits.
So a destruction whose declared policy does not exclude that is moved off the drop, as a retained owner's return is, and the value stays charged until it is destroyed.

Moving it moves only the wait.
A destruction that could panic or abort would do so on the service as well, so setup refuses it instead (`+req~ssr-heap-slot-types~2+`).
Catching an unwind cannot stand in for that refusal, since it cannot stop an abort, prevent the panic or show that the cleanup finished.

_Deferred return of a retained owner._
Where an underlying transport's own release of a retained sample can wait, the return is deferred.
The drop pushes the retained owner onto a lock-free queue sized for every admitted retained owner and returns, and the binding's own worker completes the release.
That queue holds ownership awaiting return, not unread traffic.
A stalled worker shows as counted capacity pressure, never as a drop that waits (`+req~ssr-binding-frame-drop~4+`).

_Why no completion deadline._
Moving a wait off the drop does not bound it.
A release that waits for an allocator's or a middleware's own lock cannot observe a deadline from inside that call.
So the element states when the ending operation's outcome is due, not when its cleanup completes.
It keeps what the cleanup owns charged, and it keeps the cleanup from holding anything that other work needs.

Two designs would not meet that:

* a worker of its own that one stalled release could stop for every route;
* a release that holds a lock which public allocation also needs while it waits.

_What fixed capacity gives._
Fixed capacity bounds what stalled cleanup can consume, but it cannot keep throughput going while a release never completes.
So a claim of recovered capacity within a time rests on a package that establishes release progress.
A measured average delay is not such a bound.

_Native routes._
On a native route that return gives the retained owner back to the underlying transport through its own interface and frees no heap.
Returning a preallocated loan never frees the backing it lives in (`+req~ssr-heap-none~2+`).
