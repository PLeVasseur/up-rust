The key words "*MUST*", "*MUST NOT*", "*REQUIRED*", "*SHALL*", "*SHALL NOT*", "*SHOULD*", "*SHOULD NOT*", "*RECOMMENDED*", "*MAY*", and "*OPTIONAL*" in this document are to be interpreted as described in https://www.rfc-editor.org/info/bcp14[IETF BCP14 (RFC2119 & RFC8174)]

Conventions, tags and status words: xref:../README.adoc[the safety area's README]. Scope and element boundary: xref:README.adoc[the SEooC's README].

== Safe code cannot cause undefined behaviour

[.specitem,oft-sid="req~ssr-unsafe-sound~1",oft-title="Safe code cannot cause undefined behaviour",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
A sequence of safe calls through the element's public API, including items hidden from the documentation but reachable from safe code, *MUST NOT* be able to cause undefined behaviour: no use of a slot or frame after its release, no two live mutable references to one value, no data race, no read of an invalid value.
--

[horizontal]
ASIL:: B
Allocated to:: the element
Verification:: miri (Stacked Borrows and Tree Borrows, over the tests and proof programs), compile-fail (each closed misuse), review (a sweep of each defect class)
Status:: Draft
ISO 26262:: 6-Annex D.2.3 (part-clause numbers only)

*Rationale.* Undefined behaviour can corrupt memory in ways that no later check can see, which runtime code must never risk. In Rust, `+unsafe+` marks only code whose memory safety the compiler cannot check, so safe callers rely on the element to keep that promise for them, hidden items included. The promise holds under the faulty-peer model too: a peer that writes values its own middleware never writes must not let a safe call reach undefined behaviour. Miri, tests and target builds are evidence at their own scope; none replaces the source-level argument for each obligation.

== Every `+unsafe+` is inventoried and justified

[.specitem,oft-sid="req~ssr-unsafe-inventory~3",oft-title="Every `unsafe` is inventoried and justified",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Every `+unsafe+` site in the element *MUST* state the memory-safety obligation it relies on, and sit under a reviewed row of the inventory. CI *MUST* refuse a new, changed or vanished site until the inventory is updated. Implementing, wrapping or composing a wire *MUST NOT* need hand-written `+unsafe+`. The wire crates this project ships *MUST* contain none, and the `+unsafe+` a derive generates *MUST* be inventoried in the derive's crate. Each binding this project ships *MUST* keep its own inventory under the same gate (`+req~ssr-binding-unsafe-inventory~1+`). Only a wire or binding from elsewhere with `+unsafe+` code of its own, such as a wire over a C codec, falls outside these inventories, as a separate element whose integrator qualifies its `+unsafe+`.
--

[horizontal]
ASIL:: B
Allocated to:: the element
Verification:: gate (the `+unsafe+` inventory check; the workspace lints), compile-fail (a derive under `+forbid(unsafe_code)+`)
Status:: Draft

*Rationale.* An `+unsafe+` operation requires its author to establish the memory-safety obligations that the compiler cannot prove; ordinary type, reference and borrowing rules still apply. Each site states those obligations, and the workspace lints deny an `+unsafe+` block or function without that documentation (`+Cargo.toml+`). A CI gate fails when the code's `+unsafe+` sites and the checked-in inventory disagree (`+tools/ci/check_unsafe_inventory.py+`). Keeping wires free of hand-written `+unsafe+` lets anyone write one without taking on memory-safety obligations.

== No wire can break the element's memory safety

[.specitem,oft-sid="req~ssr-unsafe-wire-untrusted~1",oft-title="No wire can break the element's memory safety",oft-needs="impl,utest",oft-tags="SafetyUpRustCore,SafetyGateUpRust"]
--
The element's memory safety *MUST NOT* depend on a wire's code being right. Where memory safety depends on a byte count, a length or a claim, the element *MUST NOT* take it from wire code on trust: it checks the writer after encoding and refuses one that was replaced, and gives decoding only a valid mutable reference to an initialized value.
--

[horizontal]
ASIL:: B
Allocated to:: the element
Verification:: test (a replaced writer is refused), miri
Status:: Draft

*Rationale.* A wire is a plain safe trait (`+Wire+` in `+core/src/wire/mod.rs+`), so its code can be wrong without any `+unsafe+`, and the element cannot rely on what it reports. Encoding goes through a checked writer that keeps the count of the bytes written itself, so a safe wire cannot claim more initialized bytes than it wrote (`+core/src/wire/writer.rs+`).

== No binding written in safe code can break the element's memory safety

[.specitem,oft-sid="req~ssr-unsafe-binding-untrusted~1",oft-title="No binding written in safe code can break the element's memory safety",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
The element's memory safety *MUST NOT* depend on a binding's safe methods returning correct values. Where it relies on a claim from a binding, for example that lent storage is exclusive, disjoint and stable, the claim *MUST* be made through an `+unsafe+` trait with stated obligations, listed in the inventory. Everything else a binding hands over, such as lengths, slices, route handles and peer references, *MUST* be checked, or treated as untrusted.
--

[horizontal]
ASIL:: B
Allocated to:: the element
Verification:: review (every value taken from a safe binding method into `+unsafe+` code), miri (adversarial safe doubles: a frame whose lengths or slices change between calls, a route handle out of range, a reused peer reference)
Status:: Draft

*Rationale.* A safe trait's implementation can return any value without breaking Rust's rules, so `+unsafe+` code must not rely on it for memory safety, while an `+unsafe trait+` makes its implementer take on stated obligations. The binding contracts are safe traits today, `+BindingSetup+`, `+LendingRuntime+`, `+HandoffRuntime+` and `+Frame+`, and only `+PreparedTxStorage+` is an `+unsafe trait+` (`+core/src/transport/binding.rs+`, `+core/src/transport/mod.rs+`). up-spec's iceoryx2 chapter asks the same of a Rust payload's author, through iceoryx2's `+ZeroCopySend+` (xref:../../up-l1/iceoryx2.adoc[the iceoryx2 transport]), which iceoryx2 declares as an `+unsafe trait+` (https://github.com/eclipse-iceoryx/iceoryx2/blob/806442b5273d87380511bb5ffcab316d129af31c/iceoryx2-bb/elementary-traits/src/zero_copy_send.rs[`+zero_copy_send.rs+` in iceoryx2 0.9.2]).
