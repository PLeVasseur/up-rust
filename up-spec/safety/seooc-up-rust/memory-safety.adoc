[[req-ssr-unsafe-sound]]
== Safe code cannot cause undefined behaviour

[.specitem,oft-sid="req~ssr-unsafe-sound~1",oft-title="Safe code cannot cause undefined behaviour",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
The element *MUST NOT* let a sequence of safe calls through its public API cause undefined behaviour, items hidden from the documentation but reachable from safe code included:

* no use of a slot or frame after its release;
* no two live mutable references to one value;
* no data race;
* no read of an invalid value.
--

[horizontal]
ID:: `+req~ssr-unsafe-sound~1+`
ASIL:: B
Allocated to:: the element
Verification:: miri (Stacked Borrows and Tree Borrows, over the tests and over programs of safe calls that attempt undefined behaviour, at least one for each kind that the statement lists and every one that demonstrated a defect), compile-fail (each misuse of the public API from which undefined behaviour would follow and that the element's types rule out, every misuse that a fix ruled out among them), review (a sweep of each defect class)
ISO 26262:: 6-Annex D.2.3 (part-clause numbers only)

*Rationale.*
Undefined behaviour can corrupt memory in ways that no later check can see, and no argument about the element's behaviour holds once it has occurred.

In Rust, `+unsafe+` marks only code whose memory safety the compiler cannot check (source: the Rust Reference, Rust 1.98.1, chapter https://doc.rust-lang.org/1.98.1/reference/unsafe-keyword.html[The unsafe keyword], rule unsafe.intro, and chapter https://doc.rust-lang.org/1.98.1/reference/behavior-considered-undefined.html[Behavior considered undefined], rule undefined.soundness).
So safe callers rely on the element to keep that promise for them, hidden items included.

The promise holds under the faulty-peer model too (xref:../README.adoc#req-ssr-peer-fault-model[The requirements hold against a faulty peer]).

Miri, tests and target builds are evidence at their own scope.
None of them replaces the source-level argument for each obligation, which <<req-ssr-unsafe-inventory,Every `unsafe` is inventoried and justified>> requires.

[[req-ssr-unsafe-inventory]]
== Every `+unsafe+` is inventoried and justified

[.specitem,oft-sid="req~ssr-unsafe-inventory~4",oft-title="Every `unsafe` is inventoried and justified",oft-needs="impl,utest",oft-tags="SafetyUpRustCore,SafetyWire"]
--
*The element.*
The element *MUST* have each of its `+unsafe+` sites state the memory-safety obligation it relies on, and sit under a reviewed row of the element's inventory.
The element *MUST* establish at the source, in the review of each row, that the obligation of each site under it holds; a run under Miri, a test or a target build does not replace that argument.
The element *MUST* have an inventory check that refuses a new, changed or vanished site until its row is reviewed, and *MUST* release no build that fails that check.

*Generated code.*
Code that the element's derives generate is held to the element's requirements, as the element's own code is.
Each generator of code for the element, such as a derive, *MUST* keep in its own crate the inventory of the `+unsafe+` that it emits, with the proof of each obligation and the constraints on its input under which that proof holds.
The element *MUST* account for the generated code that its own build admits: the exact generator and configuration that produced it, and the generator's inventory and proof that cover the `+unsafe+` in it, without repeating that inventory's rows.
Generated code in an application's build takes part in that application's image: the integrator accounts for it, with the exact generator and configuration that produced it (xref:assumptions-of-use.adoc#aou-seooc-build-configuration[The ASIL binary is built from its claimed graph, with the ASIL profile]).

*Wires.*

* The element *MUST NOT* require hand-written `+unsafe+` for implementing, wrapping or composing a wire.
* Each wire *MUST NOT* require hand-written `+unsafe+` of whoever implements, wraps or composes it.
* Each wire *MUST* contain no hand-written `+unsafe+`, unless it is a separate element with hand-written `+unsafe+` code of its own, as the clause "Outside these inventories" states.
For each wire, this entry and the clause "Outside these inventories" replace two rules of revision 3 of this item: that the wire crates that this project ships contain no hand-written `+unsafe+`, and that only a wire from elsewhere with `+unsafe+` code of its own falls outside its inventories.
* Each wire *MUST* keep each `+unsafe+` site of its code, generated code included, under a reviewed inventory row, its own or, for generated code, the generator's, and *MUST* have its build and release verification refuse a new, a changed or a vanished site until such a row accounts for it.

*Bindings.*
A binding's `+unsafe+` code is under inventory rows that are no part of the element's inventory: those rows, with the refusal of unreviewed sites, are stated in xref:../up-l1/bindings.adoc#req-ssr-binding-unsafe-inventory[A binding inventories its own `unsafe`].
That item replaces, for each binding, the clause on bindings of revision 3 of this item.
The integrator's use of such a binding on the ASIL path is stated in xref:../up-l1/deployment.adoc#aou-seooc-qualified-bindings-and-wires[Bindings and wires pass their contracts].

*Outside these inventories.*
A wire that is a separate element with hand-written `+unsafe+` code of its own, such as a wire over a C codec, falls outside the element's and the generators' inventories: the integrator's use of such a wire on the ASIL path, and the qualification of its `+unsafe+`, are stated in xref:../up-l1/deployment.adoc#aou-seooc-qualified-bindings-and-wires[Bindings and wires pass their contracts].
--

[horizontal]
ID:: `+req~ssr-unsafe-inventory~4+`
ASIL:: B
Allocated to:: the element; each generator of code for the element, for the inventory, the proof and the input constraints of the `+unsafe+` that it emits, kept in its own crate; each wire, for requiring no hand-written `+unsafe+` of whoever implements, wraps or composes it, for the inventory rows and change detection of its `+unsafe+` sites, and, unless it is a separate element with hand-written `+unsafe+` code of its own, for containing no hand-written `+unsafe+`
Verification:: gate (the element's `+unsafe+` inventory check and each wire's change detection, each with a negative control for a new, a changed and a vanished site; a lint that denies an `+unsafe+` block or function without the documentation of its obligations), compile-fail (a derive under `+forbid(unsafe_code)+`), review (each row of the inventory, with the source-level argument that the obligation of each site under it holds; for generated code, the generator's inventory, proof and input constraints, against the exact generator and configuration that the element's build admits)

*Rationale.*
An `+unsafe+` operation requires its author to establish the memory-safety obligations that the compiler cannot prove.
Ordinary type, reference and borrowing rules still apply (source: the Rust Reference, Rust 1.98.1, chapter https://doc.rust-lang.org/1.98.1/reference/unsafe-keyword.html[The unsafe keyword], section Unsafe blocks; the Rustonomicon, Rust 1.98.1, chapter https://doc.rust-lang.org/1.98.1/nomicon/meet-safe-and-unsafe.html[Meet Safe and Unsafe]).

A generator's author knows the input constraints under which the code that it emits is sound, and the consuming build knows which generator and configuration it admitted, so each answers for its part.

Keeping wires free of hand-written `+unsafe+` lets anyone write one without taking on memory-safety obligations.

[[req-ssr-unsafe-wire-untrusted]]
== No wire can break the element's memory safety

[.specitem,oft-sid="req~ssr-unsafe-wire-untrusted~2",oft-title="No wire can break the element's memory safety",oft-needs="impl,utest",oft-tags="SafetyUpRustCore,SafetyGateUpRust"]
--
The element *MUST NOT* let its memory safety depend on a wire's code being right.

Where memory safety depends on a byte count, a length or a claim, the element *MUST NOT* take it from wire code on trust:

* it *MUST* check the writer after encoding and refuse one that was replaced;
* it *MUST* refuse a frame for which the wire reports more bytes than it wrote, and *MUST NOT* send or read a byte that the wire did not write;
* it *MUST* give decoding only a valid mutable reference to an initialized value.
--

[horizontal]
ID:: `+req~ssr-unsafe-wire-untrusted~2+`
ASIL:: B
Allocated to:: the element
Verification:: test (a replaced writer is refused; a wire that reports more bytes than it wrote has its frame refused, with no byte beyond those that it wrote sent or read), miri

*Rationale.*
A wire can be written in safe code alone, against a safe interface.
So its code can be wrong without any `+unsafe+`, and the element cannot rely on what it reports.

Encoding goes through a checked writer that keeps the count of the bytes written itself.
So a safe wire cannot claim more initialized bytes than it wrote.
A frame sent at a length above that count would carry bytes that nothing wrote, so the element refuses it.

[[req-ssr-unsafe-binding-untrusted]]
== No binding written in safe code can break the element's memory safety

[.specitem,oft-sid="req~ssr-unsafe-binding-untrusted~1",oft-title="No binding written in safe code can break the element's memory safety",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
The element *MUST NOT* let its memory safety depend on a binding's safe methods returning correct values.

* Where it relies on a claim from a binding, the element *MUST* take the claim through an `+unsafe+` trait with stated obligations, listed in the inventory.
* The element *MUST* check, or treat as untrusted, everything else that a binding hands over, such as lengths, slices, route handles and peer references.
--

[horizontal]
ID:: `+req~ssr-unsafe-binding-untrusted~1+`
ASIL:: B
Allocated to:: the element
Verification:: review, miri
* *review*: every value taken from a safe binding method into `+unsafe+` code.
* *miri*: adversarial safe doubles: a frame whose lengths or slices change between calls, a route handle out of range, a reused peer reference.

*Rationale.*
A safe trait's implementation can return any value without breaking Rust's rules.
So `+unsafe+` code cannot rely on it for memory safety, while an `+unsafe trait+` makes its implementer take on stated obligations (source: the Rustonomicon, Rust 1.98.1, chapter https://doc.rust-lang.org/1.98.1/nomicon/safe-unsafe-meaning.html[How Safe and Unsafe Interact]; the Rust Reference, Rust 1.98.1, chapter https://doc.rust-lang.org/1.98.1/reference/unsafe-keyword.html[The unsafe keyword], rule unsafe.trait.intro).

The binding contract therefore keeps its interfaces safe, with their values checked.
It puts each claim that memory safety relies on, such as the exclusivity of lent transmit storage, behind an `+unsafe trait+`.

.Claims made through an unsafe trait
====
The element's memory safety relies on a binding's claim that lent storage is exclusive, disjoint and stable, so the element takes that claim through an `+unsafe+` trait.

up-spec's iceoryx2 chapter asks the same of a Rust payload's author, through iceoryx2's `+ZeroCopySend+` (xref:../../up-l1/iceoryx2.adoc[the iceoryx2 transport]), which iceoryx2 declares as an `+unsafe trait+` (source: the code of iceoryx2, release 0.9.3, https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2-bb/elementary-traits/src/zero_copy_send.rs#L32[`+iceoryx2-bb/elementary-traits/src/zero_copy_send.rs+`, line 32], its declaration of the trait).
