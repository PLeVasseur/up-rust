= up-rust SEooC: Assumptions of use
:toc: preamble

The key words "*MUST*", "*MUST NOT*", "*REQUIRED*", "*SHALL*", "*SHALL NOT*", "*SHOULD*", "*SHOULD NOT*", "*RECOMMENDED*", "*MAY*", and "*OPTIONAL*" in this document are to be interpreted as described in https://www.rfc-editor.org/info/bcp14[IETF BCP14 (RFC2119 & RFC8174)]

Conventions, tags and status words: xref:../README.adoc[the safety area's README].
Scope and element boundary: xref:README.adoc[the SEooC's README].

Each assumption of use is something the integrator must provide or guarantee.
It stays assumed until the integrator validates it for the item.

== Who these assumptions bind

These assumptions bind an integrator that claims the element's safety-assurance scope for a configuration (xref:README.adoc#claims[the SEooC's claims]).

Ordinary use, which claims no such scope, need not carry out these integration procedures.
The element's functional semantics, its honest reports and its native resource rules hold for it all the same.

== How a violation shows up

A violation shows up in one of three classes:

* *Refused at setup*: the element detects it during initialization and refuses with a named error, so runtime mode is never reached.
A build that fails counts here too.
* *Counted*: the element detects it in runtime mode, and returns an error or increments a route counter, without heap.
* *Undetectable*: the element cannot see it.
Only the integrator's own measures can cover it.

== Tags and coverage

Every assumption needs `uman`, because the safety manual states it, and carries the tag `SafetyManual`.

* The seventeen SDK assumptions also carry the gate tag `SafetyGateUpRust`, so the gating run of the repository that covers them keeps them.
* The Streamer's two carry `SafetyManual` only, so only a report-only run, which keeps `SafetyManual`, shows them.

== A supervisor outside the process restarts it

[.specitem,oft-sid="aou~seooc-supervisor-restart~4",oft-title="A supervisor outside the process restarts it",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
The integrator *SHALL* provide a supervisor outside every process that uses the element. It detects that a process has exited, crashed or been killed, and restarts it or takes the item to its safe state, under a restart policy the integrator sets (rate limit, escalation).

* *No in-process recovery.* The element has no in-process recovery. In runtime mode a process leaves only by exit, crash or kill, and in the ASIL build a panic aborts the process (`+req~ssr-build-panic-abort~3+`), which the supervisor handles as a crash.
* *Setup errors.* The element is designed on the assumption that an application treats an initialization or transition error the same way, by exiting so that the supervisor restarts it, rather than by retrying setup in the process.
* *Whole process or partition.* No thread or interrupt handler that calls the element is terminated on its own: the process, or on an MCU the partition or OS-Application that holds the element's memory, is restarted as a whole.
* *Fresh initialization.* A restart is a fresh initialization: it revokes no storage that a surviving peer still retains, and needs no departure notice from the process that died.
* *Reaction time.* Where the item relies on the restart or the safe state within a time, the integrator *SHALL* bound the whole chain, from the detection of the exit through the supervisor's decision and the restart or isolation to the physical safe state, against the allocated fault tolerant time interval, and *SHALL* argue the supervisor's own clock, resources and independence from the process it supervises; a supervisor that can share the failure it detects does not establish that bound.
* *Strict mode.* In strict mode the integrator declares the restart path, a supervisor or, on an MCU, a partition restart, and the report lists it, or warns that none is declared.
--

*Violation:*

* The death itself is *undetectable* by the process that died.
* Survivors see silence.
It is *counted* as missed deadlines on routes that declare a deadline, as RPC calls ending with an error, or as a reported peer loss where the binding reports peers.
On a route with no deadline, silence is *undetectable*.
* An application that retries setup in the process is *undetectable*, except that on the ASIL path startup memory is never given back, so a retry that runs out of it is *refused at setup*.
* What a thread terminated inside the element leaves behind depends on its configuration's exclusion mechanism.
** In the predecessor 32-bit-word representation it could leave a try-lock held or a peer's user count raised, and the element then refused that peer's incarnation raises, that sender's encodes, that route's deliveries or that response route's pulls for good, each refusal *counted*.
** Where the element changes its metadata in exclusive steps, as at this revision, the domain such a step holds stays held, and the work that needs it makes no further progress; survivors and the supervisor see silence, which a deadline or a call's TTL shows only where its own service can still run.
** Recovery is the restart.
* A supervisor that shares the failure it should detect, and a reaction chain without a bound, are *undetectable* by the element.

[horizontal]
ASIL:: B
Status:: Draft
ISO 26262:: 10-9.2.4 (part-clause numbers only)

*Rationale.*
Restarting the entire process or partition also replaces its startup memory and internal synchronization state.
Restarting one thread cannot provide that recovery.

A watchdog or supervisor can support a fail-silent reaction even where delivery has no hard deadline.
But only a chain that is bounded end to end, by a supervisor that does not fail with what it supervises, gives the item a reaction time.

Use that claims no safety scope may run without such a supervisor, and then claims no restart or reaction time.

== Processes or partitions are isolated

[.specitem,oft-sid="aou~seooc-process-isolation~3",oft-title="Processes or partitions are isolated",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
Each process using the element *SHALL* run in its own address space, under an OS that enforces memory protection, so one process cannot write another's private memory.

* *MCUs.* On an MCU without such processes, each partition or OS-Application that holds the element's memory *SHALL* be protected by a memory protection unit or an equivalent mechanism that its configuration states, or the integrator *SHALL* state the boundary that the configuration has instead and make a coexistence argument for everything that shares it.
* *Shared memory.* Shared memory between processes or partitions *SHALL* exist only where a binding maps it, with the permissions the binding requests. A separate address space protects private memory only: a lower-assurance process that shares memory with the element through a binding is not made harmless by running apart, and the faulty-peer model applies to it (`+aou~seooc-peer-access~4+`).
* *ASIL and QM together.* ASIL and QM software *SHALL NOT* share a process or partition unless the integrator makes and verifies a coexistence argument for it.
* *Strict mode.* In strict mode, the report lists the transports that share each process, and warns of every QM transport in an ASIL process, with the coexistence duty that follows.
--

*Violation:* *undetectable* by the element.

[horizontal]
ASIL:: B
Status:: Draft
ISO 26262:: 6-7.4.9, 6-7.4.8, 9-6 (part-clause numbers only)

*Rationale.*
The element's requirements assume that a faulty process cannot write another's private memory.
Only the OS's memory protection can ensure that, and the element can neither provide nor check it.

Threads in one process share its memory.
So ASIL and QM code in one process are kept apart only by an argument the integrator makes and verifies.

An MCU often has no process boundary at all.
So its boundary is whatever its configuration's memory protection provides, and the argument has to say what that is.

== Each transport's integrity level is assigned correctly

[.specitem,oft-sid="aou~seooc-integrity-levels~5",oft-title="Each transport's integrity level is assigned correctly",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
The integrator *SHALL* give each transport one integrity level in the deployment data: QM, A, B, C or D, in that order. Every route on that transport carries the level (`+req~ssr-integrity-declared~3+`). On iceoryx2 a transport runs at its process's level. Each process declares the level it was built to, and is developed to at least that level.

* *Capability.* The element is developed for ASIL B capability, and no configuration claims more for it, whatever OS, middleware or compiler it runs on, so data above ASIL B that crosses the element relies on measures outside it.
* *Decomposition and interference.* End-to-end protection, whichever mechanism the system supplies, can carry part of an ASIL C or D requirement only within a decomposition the integrator argues (9-5), with independence shown by dependent failure analysis. It covers faults in the exchange of information, not the timing and memory interference the element could cause inside an ASIL C or D process: there the integrator shows freedom from interference at the higher ASIL's rigour, or keeps the element out of that partition. The usual pattern is an ASIL B process that relays to the C or D partition over a channel the integrator protects at C or D.
* *Strict mode.* In strict mode, the Enforce state refuses a transport or route at C or D unless `+above_capability+` names the integrator's measures, and refuses C or D data whose only protection is an end-to-end mechanism of ASIL B capability unless `+decomposition+` names the argument; the report lists both duties.
* *A level is a label.* A declared level is a label checked at setup: it neither raises the element's capability nor qualifies the process that declares it.
--

*Violation:*

* On a lending binding that records the writer's level in the shared definition, a writer below a zero-copy reader's level is *refused at setup*, naming the route.
* On a binding whose ports write shared state both ways, such as iceoryx2, a port whose level differs from the service's recorded level is *refused at setup* (`+req~ssr-integrity-zero-copy~4+`).
* On a handoff binding the check does not apply, because the reader gets a private copy.
* A lending binding that cannot record levels reports them as unknown, and an ASIL reader then gets the copy route.
* In strict mode, a level above B without `+above_capability+`, and C or D data protected only by an ASIL B end-to-end mechanism without `+decomposition+`, are *refused at setup* in the Enforce state.
* A process that declares a level it was not built to is *undetectable*, and so is data above ASIL B with no measures outside the element.

[horizontal]
ASIL:: B
Status:: Draft
ISO 26262:: 9-5, 9-6, 6-7.4.8 (part-clause numbers only)

*Rationale.*
A declared integrity level supports setup admission but cannot prove how a process was developed.
The integrator therefore supplies the capability and coexistence arguments.

The decomposition and coexistence duties are about the system's protection, so they hold whatever end-to-end mechanism the system uses.
The SDK's own E2E wire is deferred and not part of this delivery.

== Only authorized processes reach the transport, and peers are faulty, never malicious

[.specitem,oft-sid="aou~seooc-peer-access~4",oft-title="Only authorized processes reach the transport, and peers are faulty, never malicious",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
The integrator *SHALL* restrict access to every transport's resources (shared-memory segments, sockets, service names) to the processes deployed to use them, with OS permissions or equivalent.

* *The fault model.* Within that, this SEooC treats every peer as faulty, never malicious. A peer may send any content, at any time and in any volume, and may choose any source URI, and the requirements hold against all of it. A faulty peer includes one that writes values its own middleware never writes, into shared memory it can write.
* *A peer below a reader's level.* A peer below a reader's level may write its own shared memory at any moment: the reader then takes the copy route (`+req~ssr-integrity-zero-copy~4+`), and the requirements hold.
* *Two-way shared state.* On a binding whose ports write shared state both ways, such as iceoryx2, every process on one service runs at one integrity level; a lower-integrity consumer takes a copy route, and the binding refuses any other at setup, by name. Each level runs in its own iceoryx2 domain, and its processes under their own OS user, so that a faulty lower process cannot open, map or remove a higher level's shared memory.
* *Zero-copy routes.* On a zero-copy route, the element relies on the writer, developed to at least the reader's level, never writing a sample it has sent.
* *Out of scope.* Only deliberate exploitation, such as engineering a peer-ID hash collision, is out of scope, as security.
* *Message IDs.* Message IDs are unique only to a stated residual (`+req~ssr-ids-unique~4+`), and they are not secret, so nothing may rely on them for authentication.
* *Strict mode.* In strict mode, the report lists each route's declared peers and the shared-memory permissions its binding requests, and warns of an ASIL receive route that admits undeclared peers.
--

*Violation:*

* Malformed or undeclared frames are refused and *counted* (`+req~ssr-refuse-no-panic~1+`, `+req~ssr-peer-admission~2+`).
* A racing write on a zero-copy route is undefined behaviour and *undetectable*.
* A peer at another level that the deployment lets onto a two-way service can crash or corrupt its peers' memory: *undetectable* by the element.
* A well-formed frame from a process that should have had no access, and a deliberate exploit, are *undetectable*.

[horizontal]
ASIL:: B
Status:: Draft
ISO 26262:: 6-Annex D.2.4 (part-clause numbers only)

*Rationale.*
A faulty publisher writing to a sample while it is read is the copy route's case, and a lying publisher is not caught at setup.

A shared reference cannot remain valid against an uncontrolled concurrent writer, and bidirectional shared state also exposes a publisher to a faulty consumer.

== Timing claims rest on a supported configuration, and the item's budgets are the integrator's

[.specitem,oft-sid="aou~seooc-timing-budgets~6",oft-title="Timing claims rest on a supported configuration, and the item's budgets are the integrator's",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
Where the item relies on the element within a time, the integrator *SHALL* select a supported configuration whose package states each timing claim it offers, with its endpoint, execution model, workload envelope and evidence, and *SHALL* keep the deployment within that package: its scheduling, priorities, CPU budgets, affinity and interrupt load.

The integrator *SHALL* allocate the item's fault tolerant time interval, declare each route's semantic traffic, deadline, TTL and wait timeouts and the reaction budget it needs, and show that the package's bounds and the item's own reaction fit that interval.

A configuration that offers no finite bound for an endpoint gives none: the element then operates and reports functionally, and the item *SHALL NOT* rely on that endpoint within a time.

The integrator allows for the following:

* *TTL resolution.* A frame is refused at the latest when its TTL, rounded up to a whole millisecond, plus one more millisecond has passed since the time its message ID records (`+req~ssr-qos-ttl~4+`). An ID made while the sender's wall clock could not be read records the last good time, so its frame can be refused early: by up to the time the clock was unreadable, and, for a generator that keeps the last good time only to 64 ms, by up to 64 ms more (`+req~ssr-ids-unique~4+`).
* *When an RPC failure is seen.* Where the element can report a failure, a call's outcome is set as soon as the element's answer arrives (`+req~ssr-peer-rpc-no-server~1+`, `+req~ssr-peer-rpc-undecodable-answered~5+`, `+req~ssr-streamer-rpc-error-response~4+`); when the application observes that outcome is a timing claim of its configuration.
* *Refused RPC copies on the E2E wire.* A request that the E2E wire refuses is answered, final or advisory; only a corrupt one is not. On an RPC route with the E2E wire, a response the client refuses at arrival, including the Streamer's best-effort error response with no E2E header, gives the claimed call slot back to await another response (`+req~ssr-rpc-check-at-arrival~2+`). That refusal does not complete the call. A later acceptable response or protected final refusal answer can complete it before TTL; a call with no such later response or final answer ends at its TTL, naming the refusal. The TTL remains the guarantee when no earlier completion occurs.
* *Fail-silent routes.* The Streamer's safe state is fail-silent per route, so a receiver sees a gated route as silence. An RPC client whose request arrives on a gated route gets the best-effort `+Unavailable+` response when the reverse route can carry it (`+req~ssr-streamer-rpc-error-response~4+`), and otherwise its call's outcome becomes expiry once its TTL has passed. A client that uses the E2E wire refuses that response as unprotected and counts the refusal apart from corruption; it gives the slot back, and its call ends at TTL naming the refusal only if no later acceptable response or protected final answer completes it.
* *Deadlines for detecting silence.* Every safety-related receiver whose safety reaction depends on detecting silence *SHALL* declare a deadline. An explicit `+event_only()+` declaration permits a route without a deadline, but supplies no deadline-based silence or delay detection; the integrator *SHALL NOT* rely on that route's deadline monitor for such a reaction.
* *Priority inversion through middleware locks.* iceoryx2, for example, holds its port lock for up to a wait's bound, and takes it briefly when a frame is dropped (its README).
* *Watchdog and reuse.* Where a configuration's representation keeps the narrowed generations that `+req~ssr-atomic-windows~2+` lists for the predecessor 32-bit-word representation, which no current profile's does, the integrator's watchdog supervises every thread that calls the element, and detects one that makes no progress inside the element for longer than its period `+T_wd+`. `+T_wd+` times the highest reuse rate of any one call slot stays below 2^28^, and of any one peer-table entry below 2^22^.
* *The watchdog's reaction and coverage.* Its reaction restarts the process, or on an MCU the partition or OS-Application, that holds the element's memory, before the stalled thread can act inside the element again. It also covers the wrap windows that remain: a stalled `+expire+` or `+fail_older+` that would end a later call early, and a stalled `+retire+` that would act as a spurious `+peer_lost+`. A configuration whose package documents full-width values in their place needs no watchdog for these windows.
* *A producer that stalls.* Whatever the representation, a frame queued behind a producer that stalls before linking its own frame is delivered when that producer resumes, so where the item relies on such a frame within a time, a supervisor bounds that stall.
* *Retry loops.* Each compare-exchange loop in the element retries only after another write to the same reservation granule succeeded or, on load-linked/store-conditional cores, after an exception taken inside the loop. On a multi-core part, a write by another core anywhere in the granule counts. Its worst-case execution time under the configuration's interrupt load and contention belongs to the configuration's timing analysis; a measurement on the target can refute that analysis, but does not by itself establish a maximum.
* *Deadline detection.* Where a configuration establishes J, a missed deadline is counted and visible at the latest D + 2L + resolution + J after the last true arrival (`+req~ssr-qos-deadline~4+`). The arrival latency L is the binding's declared one, including the time a recording thread can be preempted between reading the clock and storing the arrival, which the configuration's execution model bounds. The application's later read adds its own delay, outside J, and the item's reaction budget includes it. Where no configuration establishes J, there is no finite detection bound, and the item cannot rely on one.
* *The monitor's wait bound.* Where a route's monitor uses the one-word tick representation, which at this revision only the model tests do, a thread inside the element waits less than 2^28^ ticks of the shortest-scaled monitored route between reading the clock and storing an arrival or a check: under the watchdog above, `+T_wd+` below 0.27 s when a route uses the shortest admitted threshold (1.024 µs), and below 2.3 minutes at 1 ms. A full-width monitor, the runtime monitor of every current profile, has no such bound (`+req~ssr-atomic-windows~2+`).

The element bounds its work per call in frames and iterations, not in time (`+req~ssr-bound-work~2+`). Execution time belongs to a supported configuration's timing analysis, which its maintainers supply with the package; a measured maximum is evidence that can refute that analysis, not a bound by itself.

Default mode remains permissive and refuses no route solely for lacking a deadline.

In strict mode every ASIL receive route declares a deadline or an explicit `+event_only()+`, with its absence of deadline-based silence and delay detection, and a receive route on the E2E wire does at every level; the Enforce state refuses one that declares neither.

The report lists each route's detection bound, with J where its configuration establishes J and otherwise the statement that none is established, and its TTL, against the reaction budget the integrator declares for it, and, where a configuration's representation needs them, each transport's servicing and watchdog bounds; the Enforce state refuses a route that requires a finite detection bound its configuration does not establish, a route whose bound exceeds its declared budget, and a declared servicing period longer than its transport's bound.
--

*Violation:*

* A route that declares a deadline *counts* each miss.
* An expired frame is *counted* and not processed, and a failed call ends with an error.
* Silence or delay on a route with no deadline, including `+event_only()+`, supplies no deadline-based detection.
* Slow execution and priority inversion are *undetectable* by this monitor unless they produce a qualifying gap in the route's aggregate arrivals; only such a gap shows as a counted miss.
* Continued arrivals from another peer can conceal an individual peer's starvation (`+aou~seooc-peer-rates~2+`).
* A deployment outside its package's envelope, and a reaction that misses the item's interval, are *undetectable* by the element.
* Where narrowed values remain, a thread that stalls inside the element for longer than the watchdog's bounds can end a later call early or report a spurious peer loss: *undetectable* by the element, and the watchdog's restart is the reaction.
* In strict mode, the following are *refused at setup* in the Enforce state:
** an ASIL receive route that declares neither a deadline nor `+event_only()+`;
** a route that requires a finite detection bound its configuration does not establish;
** a route whose detection bound exceeds its declared reaction budget;
** a declared servicing period longer than its transport's bound.

[horizontal]
ASIL:: B
Status:: Draft
ISO 26262:: 10-4.4.1, 6-7.4.13 (part-clause numbers only)

*Rationale.*
A bounded number of operations is not a bound on elapsed time.
Detection, scheduling, reuse windows and the reaction must fit the same system budget.

Choosing event-only traffic explicitly forgoes deadline-based silence detection.

Returning a refused response's slot preserves the opportunity for a later acceptable response or final answer before TTL.

The scheduling and synchronization argument for a supported configuration is made once by its maintainers, not rediscovered by each application team.
The item's hazards, its fault tolerant time interval and its reaction stay the integrator's.

The clauses about the E2E wire bind only a route that uses it, and that wire is deferred and not part of this delivery.

== The platform provides the clocks

[.specitem,oft-sid="aou~seooc-clock~3",oft-title="The platform provides the clocks",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
The platform *SHALL* provide a monotonic clock and a wall clock through a time provider whose supported configuration states their units, resolution, monotonicity, adjustment and failure behaviour (`+req~ssr-platform-contract~2+`).

* *Synchronization.* The wall clock is synchronized with every peer's time base, to within an error the integrator includes in its TTL and deadline choices, before the element's TTL decisions are relied on.
* *Wall time, not uptime.* UUIDv7 message IDs and TTL are defined in wall time, and uptime *SHALL NOT* stand in for it: a target without a synchronized wall clock supplies one through its provider, or setup refuses (`+req~ssr-mode-entry-clock~2+`).
* *RPC requests.* The TTL bound on an RPC request holds only while the client's and the server's wall clocks agree within the TTL.
* *Strict mode.* In strict mode, the report warns when the wall clock at setup reads earlier than the element's release date, a sign that it is not yet synchronised, and lists the time-sync source where one is declared.
--

*Violation:*

* A wall clock that cannot be read at the transition, and a time provider that fails its setup check, are *refused at setup*.
* A wall clock that cannot be read in runtime mode is *counted*: the frame is refused, never processed with an unknown expiry.
* A wall clock that reads but is wrong makes frames expire early or late, and is *undetectable*.
* A monotonic read that fails, or that reads earlier than one already held, is treated as failed: a bounded operation that depends on it ends as expired and is *counted* (`+req~ssr-platform-contract~2+`); a monotonic clock that reads but runs at the wrong rate is *undetectable*.
* For a generator with a 32-bit sequence, a wall clock that reads but does not move makes ID generation refuse, and count, after 2^31^ IDs within one 64 ms bucket, so it never repeats an ID; its effect on expiry is still *undetectable*.
* For such a generator, a wall clock set more than ±4.36 years from its reading when the route was set up, as a clock that starts at zero is by its first time sync, leaves IDs from good reads unaffected, and makes an ID needed while the clock cannot be read refused and *counted*, never stamped with a time decades off.
* A generator that keeps a 64-bit counter and the full last good time, as every supported profile's does at this revision (`+req~ssr-atomic-windows~2+`), has neither figure: an ID needed while the clock cannot be read carries the last good time, and the early expiry that follows is *undetectable* by the element (`+req~ssr-ids-unique~4+`).
* Wall clocks that disagree by more than a request's TTL make a late request look fresh, or every request look expired: *undetectable* by the element.

[horizontal]
ASIL:: B
Status:: Draft

*Rationale.*
Clock reads and clock correctness are separate obligations: a readable but incorrect wall clock can make both expiration and correlation misleading.

A provider that reported uptime as wall time would pass every read while making each TTL decision wrong.
So the substitution is refused where it is known rather than left for a reader to notice.

A clock call can fail after initialization succeeded.
So its failure is handled, fail-closed, instead of assumed away.

== Waivers are approved with an interference argument

[.specitem,oft-sid="aou~seooc-waiver-approval~2",oft-title="Waivers are approved with an interference argument",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
For each permit a binding ships (for iceoryx2, `+UPW-iceoryx2-1+`), the deployment's owner *SHALL* review the allocation it covers, file a waiver record approved by someone other than its author, and argue how interference from that allocation is excluded: by partition, by qualification, or by analysis.

* *Review again.* The waiver *SHALL* be reviewed again when the middleware version or the deployment changes.
* *Heap sizing.* The deployment *SHALL* size the heap the permit draws on for the bound it states: on iceoryx2 an allocation that fails during a peer change aborts the process (`+UPD-IOX2-0006+`).
* *Strict mode.* In strict mode, the Enforce state refuses a waiver that does not name its interference argument's kind and a reference, and the report lists each waiver with its approver and its argument.
--

*Violation:*

* A missing waiver is *refused at setup*, naming the permit, and a record that names its author as approver is refused at the transition (`+req~ssr-waiver-record~1+`).
* In strict mode, a waiver without its argument's kind and reference is *refused at setup*.
* Whether the approver really reviewed it, and whether the interference argument holds, is *undetectable*.
* A heap too small for the permit's bound aborts the process during a peer change, which is *undetectable* until then.
* A known anomaly, such as iceoryx2's port-mutex panic (`+UPD-IOX2-0001+`), is not a waiver and is never filed as one.

A waiver records that the deployment accepts an allocation.

== The integrator decides which routes need end-to-end protection

[.specitem,oft-sid="aou~seooc-e2e-protection~7",oft-title="The integrator decides which routes need end-to-end protection",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
The integrator *SHALL* decide which routes carry data that needs end-to-end protection, and *SHALL* supply protection on each of them and justify it for the item.

* *In this delivery.* In this delivery that protection is the integrator's own mechanism: the SDK's E2E wire `+E2e<W>+` is deferred and not part of it. The integrator states which faults its mechanism detects, the boundary it covers and the residuals it leaves, and its analysis of the route rests on that statement.
* *Above ASIL B.* Data above ASIL B that relies on such protection stays within the decomposition and coexistence duties of `+aou~seooc-integrity-levels~5+`.
* *Adds, and replaces nothing.* End-to-end protection adds to the element's own duties and replaces none of them: RPC correlation, TTL, ownership, and the refusal and error handling of every route hold whether a route is protected or not, and message IDs are not authentication (`+aou~seooc-peer-access~4+`).
* *Not required by the element.* Nothing in the element requires end-to-end protection on any route, including routes at an ASIL integrity level.
* *Strict mode.* In strict mode, on an ASIL route over a transport the integrator classifies as a black channel, the route names the integrator's own protection or, once the E2E wire is delivered and selected for it, uses that wire; the report lists the protection named for each route, and warns of an unclassified transport.

The duties that follow bind only a route that selects the SDK's E2E wire, once that wire is delivered. A route protected by the integrator's own mechanism, or not protected, is bound by none of them. Where the E2E wire is selected for a route, the integrator:

* declares each route's senders in deployment data, from which both sides derive the data IDs with the element's function (`+req~ssr-e2e-data-id~4+`), naming no wildcard, and making each receiver's declared senders equal to its route's declared peers; keeps the derived IDs distinct wherever a misaddressed frame can travel; and sets `+resync_frames+` where the default does not fit;
* *(b)* declares a sender's starts increasing only where every start of that sender has a greater start value than every earlier start's: a wall clock kept across restarts and boots, with restarts more than a millisecond apart, or a counter it keeps across restarts and boots and supplies at construction. Otherwise, it leaves the declaration at its default;
* runs one live sender per data ID at a time; builds each E2E value from its own role's addressing; puts at most one E2E wire on a route; and writes no wire of its own that shares one E2E value between roles;
* declares a deadline on each such route, within the item's fault tolerant time interval, because the wire's timeout is the route's deadline, or accepts that delay and silence on that route are undetectable. In default mode the element refuses no route for lacking a deadline;
* uses one sending thread per publish and request route, and one decoding thread per E2E route, at a time: the consuming thread on a pull binding, or one delivery thread on a push binding, as the binding's README states;
* accepts what the wire leaves unprotected: the message header (source, sink, type, ID, TTL, priority and token), and faults that no end-to-end check can see, such as a sender that puts wrong data under a correct check. On an RPC route, a response echoes its request's data ID, counter and incarnation, with its message type, result and status inside the CRC, and the client accepts only an exact match with its own call (`+req~ssr-e2e-rpc-echo~1+`). The Streamer's best-effort error responses carry no E2E header, so an E2E client refuses them and gives the slot back; absent a later acceptable response or protected final answer, the call ends at its TTL, which the client observes when it next services or waits on the call;
* accepts the residuals:
** *(b)* two equal incarnations across a restart, at about 2^-32^ per restart, the chance that 32 bits of initialization entropy repeat where that entropy meets its stated contract (`+req~ssr-platform-entropy~2+`);
** *(b)* one undetected corruption of a frame's header, at the CRC's undetected-error rate. A counter corrupted upward makes the receiver refuse the sender's later frames, until the counter passes the corrupted value or the sender restarts. For a sender declared increasing, an incarnation corrupted upward also retires the live sender, which is then refused as stale until it restarts, and it stays the newest;
** a replayed run of a displaced incarnation's old frames, after two faults;
** an RPC call whose every response copy is refused, which ends at its TTL, naming the refusal;
** in default mode, a late run of more than `+resync_frames+` requests, all inside their TTL, which is adopted and executed: for a client not declared increasing, from any incarnation but the reference; for one declared increasing, from one older than the retired one. The live client then pays `+resync_frames+` refused calls, answered. After a re-adoption, a replay can re-execute more requests inside the window;
** a request more than 63 counters late, refused as out of the window with an advisory answer, whose call ends at its TTL naming the refusal if no later acceptable response or protected final answer completes it;
** a false final answer across a server restart, behind a Streamer, which takes three faults at once;
** the TTL and the message ID outside the CRC, so the TTL's bound on a late run needs the two wall clocks to agree within the TTL (`+aou~seooc-clock~3+`);
** in strict mode, a client locked out by a false declaration of increasing starts: told, and counted at the server, until the server restarts;
** a request duplicated more than once, whose extra answers can overflow the client's response queue; the route's overflow policy then drops and counts the extra frame, and if that frame is the real response and no later acceptable response or protected final answer completes the call, it ends at its TTL, naming the repeat;
** where a client declares several servers for one method, an answer from another declared server to a misaddressed copy, which passes.

On a route that selects the E2E wire, strict mode adds these rules: every such receive route declares a deadline or `+event_only()+`; the clients of such an ASIL RPC route are declared increasing, from a counter kept across restarts and boots, never the wall clock, which the integrator makes durable before use and keeps per sender construction, never per boot, and after replacing a client ECU the integrator restarts its servers.

On such a strict ASIL RPC request route, the receiver refuses every incarnation older than the newest adopted, counts the refusal and answers under the final/advisory proof in `+req~ssr-e2e-refusal-answered~1+`; it never re-adopts an older incarnation through a run (`+req~ssr-e2e-resync~4+`). The persistent counter declaration alone does not provide that receive rule.

The report lists each E2E route's senders, data IDs, `+resync_frames+`, start declarations with their duty, thread duties and figures.
--

*Violation:*

_Every route._

* A route that needs protection and has none, and a residual of the integrator's own protection, are *undetectable* by the element.
* In strict mode, an ASIL route over a transport the integrator classifies as a black channel, with no protection named, is *refused at setup* in the Enforce state, and an unclassified transport draws a warning.

_A route that selects the E2E wire, once it is delivered._

* A corrupt frame, an undeclared data ID, a repeat, an out-of-sequence frame and a stale frame are refused and *counted* (`+req~ssr-e2e-detects~4+`, `+req~ssr-e2e-resync~4+`), and lost frames, gaps, restarts and resyncs are *counted* per sender in the wire's storage.
* On RPC responses, a corrupt, misaddressed, stale or unprotected response, one for another call, and one whose status does not match, are refused at arrival and *counted*, and the slot is given back to await a later acceptable response or protected final answer; if neither arrives, the call ends at its TTL naming the refusal.
* A refused request is answered, final or advisory, and *counted* at the server by kind; only a corrupt one goes unanswered.
* Delay and silence are *counted* by the route's deadline monitor where a deadline is declared, and are *undetectable* where none is.
* A second decoding thread, or a second sending thread, makes in-order frames look reordered or contended: they are refused and *counted*, never corrupted, and on a client a call that receives no later acceptable response or protected final answer ends at its TTL.
* A second live sender under one data ID, or a colliding ID, can take the slot: its frames are delivered as the declared sender's, which is *undetectable* by the wire, and the declared sender's frames are refused as stale, *counted*.
* *(b)* A false declaration of increasing starts lets a dead incarnation's late frames retire a live incarnation that is the reference when the first of them arrives.
Those late frames are then delivered as new data, which is *undetectable* by the wire, and the live incarnation is refused as stale, and *counted*, until it restarts; the deadline shows the silence.
* In default mode, a live incarnation that is not the reference at that frame is not locked out: it costs `+resync_frames+` refused frames, *counted*.
* On a strict ASIL RPC request route on the wire, every incarnation older than the newest adopted instead stays refused regardless of the run; every valid refused request is answered and counted, with finality only under the stated non-delivery proof.
* *(b)* An undetected corruption of a frame's header is *undetectable* by the wire.
The refusals that follow it are *counted*, and the deadline shows the silence.
* An adopted late run is *counted* as a resync.
* In strict mode, on a route that selects the E2E wire, a receive route with neither a deadline nor `+event_only()+`, and an ASIL RPC route whose clients are not declared increasing from a counter, are *refused at setup* in the Enforce state.

[horizontal]
ASIL:: B
Status:: Draft
ISO 26262:: 6-Annex D.2.4, 6-Annex E.3.2 (part-clause numbers only)

*Rationale.*
The wire protects a declared communication relationship.
It cannot establish the truth of the deployment declarations or supply protection on a route that does not use it.

The SDK's E2E wire is deferred and not part of this delivery.
So today the integrator's own mechanism is the only protection available, and strict mode accepts the protection the integrator names under its stated boundary.

_Why revision 7._
Revision 6 bound strict ASIL RPC clients and receivers to the wire's persistent start counters and receive rules even on a route the wire does not protect.
Revision 7 confines every duty that only the wire needs, its declarations, residuals, start counters and receive rules, to a route that selects it, and keeps unchanged what such a route must do.

The duty to decide which routes need protection, to supply it and to justify it, and the black-channel and decomposition rules, hold now for every route.
The deferred items keep their IDs and revisions and gain no implementation, gate or coverage credit.

== Bindings and wires pass their contracts

[.specitem,oft-sid="aou~seooc-qualified-bindings-and-wires~5",oft-title="Bindings and wires pass their contracts",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
The integrator *SHALL* use on the ASIL path only bindings and wires that pass the contract suites (`+assert_binding_contract+`, the QoS contract, `+assert_wire_contract+`) on the integrator's own target, at the exact versions and configuration whose evidence its supported configuration records, and *SHALL NOT* take evidence of one state, compiled, linked, exercised, source-reviewed, composition-verified or qualified, for another.

* *32-bit targets.* On a 32-bit target, those are only the bindings and wires whose contracts pass on that target. The iceoryx2 binding claims no 32-bit target, because iceoryx2 0.9 needs 64-bit atomics and its bare-metal port is a proof of concept.
* *Pull bindings and deadlines.* A pull binding used for a route with a deadline reports an arrival through `+RuntimePort::arrived+` only with evidence that a frame entered the route's queue, or that the queue's overflow policy discarded one, and within the latency it declares in `+QosSupport::arrival_reports+`. It never reports one on a wake hint alone. It reports each failure to read its own queue through `+RuntimePort::receive_failed+`. Its `+run_qos_contract+` deadline checks pass, on a subscriber and on a carrier ingress.
* *Response routes.* A push binding delivers one response route from one thread at a time, which the contract checks. A pull binding needs nothing: the element serializes the pulls of a response route itself.
* *Cores without coherent atomics.* A route between cores whose atomics are not coherent with each other (`+aou~seooc-target-environment~4+`) uses a transport whose qualification covers that.

The integrator accepts the limits and known anomalies that each binding's README states (`+req~ssr-binding-readme~1+`). For a deployment that uses iceoryx2, these include:

* allocation on a peer join or restart, under the waiver (`+UPW-iceoryx2-1+`);
* sizing of the expired-connection buffer: a receive route is refused at setup unless twice its retained budget fits in it;
* the service depth, which now comes from deployment data (`+req~ssr-binding-depth-from-deployment~1+`);
* the port mutex's panic path, on lock and on unlock, which no peer can reach (`+UPD-IOX2-0001+`, revision 2);
* the two `+blocking_send+` `+unwrap+`s, which only a failing OS clock call reaches (`+UPD-IOX2-0002+`);
* iceoryx2's other accepted panic paths: two process-private invariants; a descriptor that other code in the process closes while a socket is set up; `+close()+` failing on a departed peer's descriptor; and a sample counter's overflow on 64-bit targets, at over 580 years at 10^9^ sends per second (`+UPD-IOX2-0003+`, `+UPD-IOX2-0004+`, `+UPD-IOX2-0005+`);
* heap exhaustion during a peer change, which aborts, within the deployment's heap sizing under `+UPW-iceoryx2-1+` (`+UPD-IOX2-0006+`);
* arrival reports from its receive thread, within that thread's period plus its stated pass bound, on a drained notification of the route's data ID together with a sample in the queue or taken since the previous pass, or on the queue turning non-empty;
* a sender preempted between `+send+` and its notification delays the report, unless the queue was empty at the previous pass; a notification that fails at the sender while the queue holds samples leaves an arrival unreported, so a miss may be counted for a gap no longer than the deadline, and the sender counts the failure;
* while a new publisher's data connection is being set up, its notification can be reported while older samples are queued;
* iceoryx2 0.9.2 only logs a data connection that cannot be set up, under its default handler, and retries it only when the publisher list changes. So the binding installs a degradation handler on each port at setup: a failed connection is counted as `+receive_failed+`, or on the sending route, and the route then reports only a queue that turned non-empty, until the publisher list changes and an update runs clean; a queue that a healthy second publisher keeps non-empty meanwhile shows misses;
* the event IDs are read from the event service's static config, and a route whose lifecycle events share the data ID, or whose data ID is above the service's `+event_id_max_value+`, is refused at setup.

The README also says that a frame drop can wait for the port mutex. That is not an accepted limit, because `+req~ssr-binding-frame-drop~4+` forbids it. It is the binding's known failure `+UPF-IOX2-0001+`, open until the binding returns each dropped frame to iceoryx2 through its deferred return as pending cleanup, charged and isolated as `+req~ssr-release-lease-drop~3+` requires; a thread of its own is not by itself that isolation.

iceoryx2's other known failures are not accepted limits either, because `+req~ssr-binding-no-panic~4+` forbids them: its index bug on a connection change (`+UPF-IOX2-0002+`), until iceoryx2 fixes the index; its event-deadline panics, on QM transports only, since ASIL deployments turn those deadlines off, until iceoryx2 fixes them (`+UPF-IOX2-0005+`); and the paths through which a peer that writes values its own iceoryx2 never writes can panic its survivors, until iceoryx2 validates what peers write (`+UPF-IOX2-0004+`).

The wait thread's descriptor-set panics (`+UPF-IOX2-0006+`) remain until its own poll loop replaces that set, or a reviewed equivalent with a source-backed argument is adopted in its place, and unsafe name and queue-size configuration (`+UPF-IOX2-0007+`) remains until setup refuses it.

The expired-buffer failure is fixed by the twice-budget setup refusal; it is recorded separately as fixed, not as an accepted anomaly.

A wire or binding from elsewhere with `+unsafe+` code of its own, such as a wire over a C codec, is a separate element, and the integrator qualifies its `+unsafe+` (`+req~ssr-unsafe-inventory~3+`). The bindings this project ships keep their own inventories under the same gate (`+req~ssr-binding-unsafe-inventory~1+`).

In strict mode, the Enforce state refuses a binding or wire that is not on the integrator's qualified list, an ASIL process that reaches a deviation not acknowledged at its current revision, and any known failure, whatever is acknowledged; while iceoryx2's known failures stand, that refuses each affected route at ASIL, including publishers affected by shared-state faults. The report lists each binding's README limits, deviations and known failures.
--

*Violation:*

* A wire that declares heap use on a native route, or a binding that declares middleware heap use without a waiver, is *refused at setup*.
* On iceoryx2, a route whose lifecycle events share its data ID, or whose data ID is above the service's range, is *refused at setup*.
* A binding or wire that breaks its contract while declaring that it keeps it, for example with a frame destructor that frees on a native route, is *undetectable* at runtime: the contract test is the only check.
* A known anomaly accepted here is not a waiver.
* In strict mode, a binding or wire off the qualified list, an unacknowledged deviation, and any known failure are *refused at setup* in the Enforce state.

Status:: Draft

*Rationale.*
A declaration of capability needs target-specific contract evidence.
An accepted anomaly has a bounded justification, whereas an open known failure remains a failure.

Evidence attaches to the exact pins and configuration it was produced on.
A newer middleware release or a private variant does not inherit it, compiling is not running, and a source review is not a timing analysis.

== The target environment is verified

[.specitem,oft-sid="aou~seooc-target-environment~4",oft-title="The target environment is verified",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
The target *SHALL* be one that a supported configuration's package names, with the exact compiler release, target, options and library scope, OS or RTOS, BSP and hardware revision it was verified on.

* *What verification is.* Upstream support for a target, a compiler qualification for another scope and a successful build are each distinct from that verification. The package's maintainers supply that verification, and the evidence for the conditions below, for the parts, cores, execution contexts and participants the package names; for a supported configuration the integrator confirms that the deployment matches them, and supplies an argument of its own only for a context or participant the package does not cover.
* *Profiles.* The current SDK profiles are macOS ARM64, Linux x86-64, Linux ARM64, Windows x86-64, Cortex-M7 and RV32IMAC; QNX 7.1 and 8.x are future work, separate from each other, whose backend exists only as source. A profile is not a claim that every binding runs on it, and no profile carries an ASIL of its own.
* *Atomics.* The target *SHALL* have 32-bit atomics with compare-and-swap; 64-bit atomics are not needed, and a target's backend keeps the element's semantics without an atomic width the target lacks (`+req~ssr-atomic-width~2+`). The RH850, AURIX TriCore, Cortex-M3, Cortex-M4, Cortex-M7 and e200 class qualifies, and so does Cortex-M23 (ARMv8-M Baseline), which has 32-bit compare-and-swap: the element selects by `+target_has_atomic+`, never by a list of targets. Cores without compare-and-swap, such as Cortex-M0 and Cortex-M0+, do not.
* *Atomic lowering.* Each atomic read-modify-write the element uses is atomic on the target's core. On RH850G3K the toolchain lowers compare-and-swap to `+CAXI+`, never to an `+LDL.W+`/`+STC.W+` loop, which that core executes as a plain load and store. On any other core it lowers to a sequence that is atomic on that core.
* *Several cores.* Where one instance of the element, or a route's memory, spans several cores, these operations are coherent across those cores. Where the cores' data caches are not kept coherent by hardware, the element's memory is placed where they are, or where it is not cached. Parts whose cores' exclusive accesses are not shown to be coherent, such as STM32H7-class parts that pair a Cortex-M7 with a Cortex-M4, run a separate instance on each core, and a route between those cores uses a transport that synchronises them by its own means (`+aou~seooc-qualified-bindings-and-wires~5+`).
* *Different ABIs.* Cores of different ABIs, such as a 64-bit Cortex-A beside 32-bit Cortex-R or Cortex-M cores, share no native representation: data between them takes a copying route, through a transport that synchronises the cores by its own means, and the element refuses a native wire between peers of different ABIs at setup (`+req~ssr-native-abi-agreed~1+`). For cores of one ABI that share memory, each core observes the other's atomic operations coherently. The element cannot detect a violation of that.
* *Interrupt masks.* A private interrupt mask excludes only what it masks: an unmasked interrupt, a non-maskable interrupt, a fault handler or a DMA engine that the deployment actually has and that can reach the element's memory needs an argument of its own, from the package where it names that participant.
* *Backends and custom platforms.* The element ships backends for Linux and macOS, and one for QNX that exists only as source: no toolchain or device has run it. A target or configuration that no package supports needs a custom platform, an explicit extension (`+aou~seooc-integrator-platform~4+`).
* *Stacks and departures.* The integrator sizes the stacks of threads that call the element using its upper estimates, and analyses where the environment the element was verified in departs from the target.
* *Strict mode.* In strict mode, the Enforce and Locked states apply the target, dependency, ownership, known-failure and deviation checks to every configuration, and refuse, naming the claim and the missing evidence, a safety-assurance scope that a route or process explicitly requires where its configuration's package does not establish it (`+req~ssr-qos-no-downgrade~2+`). An integrity level or the Enforce state is not such a request: a configuration without an assurance package is not refused for that alone, and its report says that its assurance is Draft and unassessed. The report lists the coherence duty on multi-core parts and the stack-sizing duty.
--

*Violation:*

* A target without 32-bit compare-and-swap fails to build, which counts as *refused at setup*.
* A compare-and-swap lowered to a sequence that is not atomic on the core, or not coherent across the cores that share it, can corrupt the element's state words, and the element does not detect it: *undetectable*.
* A native wire between peers of different ABIs is *refused at setup*.
* A target with no shipped backend builds (the bare-metal core gate passes), and runtime code then runs on whatever platform the integrator supplies; whether that platform keeps its rules is *undetectable* by the element.
* In strict mode, an explicitly required assurance scope that the configuration's package does not establish is *refused at setup* in the Enforce state, by name; a configuration without an assurance package is not refused for that alone.
* The behaviour of an unverified backend, a participant that a private mask leaves unmasked, a toolchain or target outside its package's verified scope, and a stack overflow are *undetectable*.

[horizontal]
ASIL:: B
Status:: Draft
ISO 26262:: 6-9.4.5, 6-10.4.7 (part-clause numbers only)

*Rationale.*
The protocol requires atomicity and coherence on the actual hardware, not just a type that the compiler accepts.
A native representation also requires matching ABIs.

A profile's support and a configuration's assurance are separate.
A profile without an assurance package keeps its functional support, and no OS, architecture or compiler confers an ASIL.

Strict mode is usable before any assurance package exists.
Enforce keeps checking what a configuration declares, and refuses an assurance scope only where it is requested and unsupported.
So an ASIL-labelled development configuration proceeds as Draft and unassessed.

The MCU profiles run their images on an emulator, which shows functional behaviour, not physical timing or a qualified board.

== The ASIL binary is built from its claimed graph, with the ASIL profile

[.specitem,oft-sid="aou~seooc-build-configuration~5",oft-title="The ASIL binary is built from its claimed graph, with the ASIL profile",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
The integrator *SHALL* build the ASIL binary so that, at run time, it depends only on its claimed safety dependency graph: `+up-rust-core+`, the ASIL Streamer crate where it is used, the bindings, wires and platform backends its configuration qualifies, and any optional layer its configuration admits with its own evidence (`+req~ssr-crate-core-only-binary~2+`).

* *Nothing from outside the graph.* It *SHALL NOT* link code from outside that graph into the binary's image. A crate belongs to the graph by what it actually brings into the image, with its features and target-selected paths, never by its name: a compatibility re-export is judged by the dependencies it brings, and code outside the graph, such as the `+up-rust+` compatibility facade, an async integration or the classic Streamer, keeps its ordinary use, which claims no assurance scope.
* *Toolchain.* It *SHALL* use the exact compiler release, target, library modules and options that its configuration records for the release, with the supplier's qualification evidence for that scope where the claim needs it; the minimum supported Rust version, 1.88 today, and the availability of an API are not that evidence.
* *Profile.* It *SHALL* use the ASIL profile: `+panic = "abort"+` and `+overflow-checks = true+`.
* *Strict mode.* In strict mode's locked build, `+--cfg up_rust_strict+` in the integrator's build configuration allows only the Enforce state, and refuses a crate or route that the declared graph does not admit, naming its replacement (`+req~ssr-strict-lock~2+`). Strict mode also refuses an ASIL process built with unwinding, and `+assert_asil_build!()+` gives any ASIL binary the Streamer binary's check; its report lists overflow checks as a checklist item.
--

*Violation:*

* A build of the ASIL Streamer binary with unwinding fails to compile (`+req~ssr-build-panic-abort~3+`), which counts as *refused at setup*.
Test builds are not refused: they need unwinding, and none of them compiles that binary.
* An application binary that links only `+up-rust-core+` can carry the same check in its own `+main+`, and the safety manual gives it.
Without it, a build with unwinding or without overflow checks is *undetectable*, and so is code from outside the claimed graph linked into the binary without the lock.
* In the locked build, a crate that the declared graph does not admit is refused, which counts as *refused at setup*, and strict mode refuses an ASIL process built with unwinding at setup.
* A toolchain outside its configuration's recorded scope is *undetectable* by the element.
* The safety crate's own build cannot be changed by another crate's features (`+req~ssr-crate-isolated~1+`).

[horizontal]
ASIL:: B
Status:: Draft
ISO 26262:: 1-3.22 (part-clause numbers only)

*Rationale.*
Only the crates of the claimed graph are developed and qualified for the element's requirements.
So other code in the binary would run code that no requirement covers.

The element enforces the profile only in the ASIL Streamer binary, which refuses to compile with unwinding (`+req~ssr-build-panic-abort~3+`).
So for any other ASIL binary the build configuration is the integrator's to get right.

A toolchain qualification covers an exact release, target, library modules and options.
A build that succeeds elsewhere, or a newly available language feature, is not covered by it.

== Deployment data is in range, verified and protected

[.specitem,oft-sid="aou~seooc-deployment-data~5",oft-title="Deployment data is in range, verified and protected",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
The integrator *SHALL* produce the deployment data within the admissible ranges the element publishes, and verifies it for the item. The data covers:

* routes and their QoS;
* each transport's integrity level;
* RPC client lists and expected peers;
* capacities;
* iceoryx2 service depths;
* for each route that uses the E2E wire, its senders, from which its data IDs are derived, its `+resync_frames+`, and, *(b)*, for each sender, its start value's source and whether its starts are declared increasing;
* the selection of compiled-in waivers.

The integrator protects the data against unintended change between release and use, and delivers the Streamer's deployment data with an integrity code over its content, which the Streamer checks.

Every peer that a route *SHALL* accept is declared at startup, because setup is impossible at runtime: adding an RPC client on a lending transport means restarting the server with new deployment data.

In strict mode, the Enforce state refuses deployment data without a matching integrity code, and the report shows the data's digest, and what was declared and checked.
--

*Violation:*

* Data that is out of range, unknown, missing where required or inconsistent is *refused at setup*, naming the field.
* Streamer deployment data whose integrity code does not match its content is *refused at setup* (`+req~ssr-streamer-config-integrity~1+`).
* In strict mode, deployment data without a matching integrity code is *refused at setup* in the Enforce state.
* Data that is valid but wrong for the item, such as a route to the wrong peer delivered with a matching code, is *undetectable*.

[horizontal]
ASIL:: B
Status:: Draft
ISO 26262:: 6-Annex C, 6-C.4.6, 6-Table C.1 (part-clause numbers only)

*Rationale.*
Correct runtime behavior depends on the addresses, capacities and relationships declared before activation.
A checksum cannot establish that those declarations fit the application.

== Capacities are sized for the worst case

[.specitem,oft-sid="aou~seooc-capacity-sizing~3",oft-title="Capacities are sized for the worst case",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
The integrator *SHALL* declare the item's worst-case semantic load for each route: its traffic, payload and token sizes, retention, peers and calls in flight.

* *What the element computes.* The element computes from those declarations the implementation capacities it needs, slots, queue depth, held messages, peer and call tables, registration storage for pending asynchronous operations, the backlog of retained owners, deferred releases and deferred destructions, and startup memory, states what each figure measures, and checks them at setup (`+req~ssr-memory-computable~3+`); the integrator does not derive the element's internal sizes, and the supported configuration's package states the sizes that depend on its scheduler, allocator or stacks.
* *Exhaustion.* In runtime mode exhaustion is a refusal, not a failure of the element; capacity that a release still pending holds is exhausted the same way, and fixed capacity promises neither its recovery nor sustained throughput within a time unless the supported configuration's package establishes the release progress on which such a claim relies (`+req~ssr-release-lease-drop~3+`). Whether the item tolerates that refusal is the integrator's question.
* *Strict mode.* In strict mode, the report lists the startup memory each setup computes, and every route's capacities.
--

*Violation:*

* Capacity that cannot be reserved is *refused at setup*.
* Exhaustion in runtime mode is *counted* or returned as an error.
* Exhaustion that the item cannot tolerate is *undetectable* by the element, and so is a declared load below the item's real one.

[horizontal]
ASIL:: B
Status:: Draft
ISO 26262:: 6-7.4.13 (part-clause numbers only)

*Rationale.*
Every capacity is fixed at setup, and in runtime mode a full one returns an error instead of growing (`+req~ssr-refuse-before-heap~2+`).
So only the integrator, who knows the item's load, can say what it must carry.

The element knows its own layout, so it computes the sizes that the declared load needs (`+req~ssr-memory-computable~3+`).
An application team is not asked to guess them, and a live-object count is not offered as the retained or physical footprint.

== The application reacts to what the element reports

[.specitem,oft-sid="aou~seooc-application-reacts~4",oft-title="The application reacts to what the element reports",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
The application *SHALL* handle every error the element returns, and reads the counters it relies on, within its own fault reaction time.

* *What the element reports.* The element reports every refusal and loss it can see. A loss it cannot see, such as a drop-oldest eviction inside iceoryx2, is declared in that route's report instead (`+req~ssr-error-no-silent-loss~3+`). For such losses, and for silence, the application uses available deadline and end-to-end observations only within their declared detection limits; neither promises to detect every hidden loss.
* *Shared routes, and routes without a deadline.* Another peer can keep a shared route's aggregate deadline refreshed while one peer is starved, so required peer-specific progress detection follows `+aou~seooc-peer-rates~2+`. A route without a deadline, including an explicit `+event_only()+` route, supplies no deadline-based silence or delay detection.
* *The reaction is the application's.* The element does not decide the item's reaction. Reading a route's report is the application's own observation: its delay adds to the item's reaction, outside the element's detection bound (`+req~ssr-qos-deadline~4+`), and the element places no servicing duty on the application for that bound.
* *Reading counters.* The application takes differences of the flow counters (`+carried+`, `+busy+`, `+parked+`) between reads fewer than 2^32^ increments apart. It reads a fault counter at 2^32^ − 1 as saturated: at least that many, which `+RouteCounters::since+` reports as saturated, not as a difference.
* *Keeping up.* A route's deadline measures arrivals at its queue, not the application's reads. An application that needs to know whether it keeps up *SHALL* read the observable discard counters and account for the route's disclosed unobservable-loss limits; zero counts alone do not establish that no frame was lost.
* *Bad data.* Bad data is reported by its own refusal counters, which the application acts on: a peer that sends only frames refused when read shows there, and on an E2E route in E2E's figures, not in `+deadline_missed+`.
* *One-word tick monitors.* Where a route's monitor uses the one-word tick representation, which at this revision only the model tests do, the application services that route at least once per 2^29^ of its monitor's ticks, 2^18^ of its thresholds; a thread blocked in the transport's `+wait+` meets this, because `+wait+` runs the service between inner waits of at most 2^28^ ticks of the shortest-scaled route on the transport. A full-width monitor needs no such servicing to keep its count.
* *Strict mode.* In strict mode, the report lists for each route the counters the application reads and what each means, the E2E figures included.
--

*Violation:*

* Every refusal and loss the element can see is reported, as an error or a *count*.
* Losses it cannot see are declared, not counted.
* An application that ignores either is *undetectable*.
* On a one-word tick monitor, a route not serviced for 2^29^ of its ticks can leave a silence uncounted, and arrivals unrecorded for up to 2^30^ ticks after it: *undetectable*.
Without servicing, that is 0.54 s at the shortest admitted threshold (1.024 µs), 4.3 s at 10 µs, 34 s at 100 µs, 4.6 minutes at 1 ms, 73 minutes at 10 ms and 9.8 hours at 100 ms.

[horizontal]
ASIL:: B
Status:: Draft

*Rationale.*
Reporting a fault cannot itself restore the application function.
The application must observe the report within the reaction budget and choose its response.

A middleware visibility disclosure conveys a limit, not a discard measurement or a proof of peer progress.

The element's detection bound ends where the count becomes visible.
How soon the application looks is its own part of the reaction.

A servicing duty belongs to the representation that needs it, so it is stated only for that representation.
Every current profile's runtime monitor is full width (`+req~ssr-atomic-windows~2+`), so the duty binds no current configuration.

== A custom platform keeps the platform's rules

[.specitem,oft-sid="aou~seooc-integrator-platform~4",oft-title="A custom platform keeps the platform's rules",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
A supported configuration's platform backend is its maintainers' (`+aou~seooc-target-environment~4+`), and an application team that selects one supplies no backend of its own. An integrator that supplies a platform for a target or configuration that no package supports *SHALL* treat it as an explicit extension, with its own authoring contract and evidence boundary, and supply:

* a runtime platform that keeps the rules of `+req~ssr-platform-contract~2+`: no heap, no panic, no thread creation and no global state that needs first-use setup; clock reads that report a failure instead of panicking or substituting another time base; a wait that never loses a wake; and the contracts that a package states, written down for this platform;
* an initialization-only platform for prefault, and for entropy from a declared source with its stated contract, reported as failed rather than replaced by a fixed value (`+req~ssr-platform-entropy~2+`);
* a source-level safety argument for its synchronization and its atomic or exclusion mechanism, covering every participant that can reach that mechanism's storage (`+req~ssr-atomic-width~2+`).

It passes the platform contract test in `+test-util+` on that target.

In strict mode, the Enforce state refuses an integrator platform that names no contract-test evidence, and the report lists the entropy duty and the platform contract test.
--

*Violation:*

* A breach of the platform's rules is *undetectable* by the element.
* Entropy that repeats across starts more often than its stated contract allows is *undetectable* by the element.
On a route with the deferred E2E wire, once it is delivered, its incarnations can then be equal at a restart, so the new incarnation's frames are refused and *counted* as out of sequence until its counter passes the old one's.
Message IDs can also repeat across restarts (`+req~ssr-ids-unique~4+`).
* In strict mode, an integrator platform without contract-test evidence is *refused at setup* in the Enforce state.

[horizontal]
ASIL:: B
Status:: Draft

*Rationale.*
A custom backend is responsible for the same clock, waiting and initialization contracts as a shipped backend.

Routine supported use selects a package instead.
So an application team does not have to invent a synchronization backend or an OS scheduling proof, and this assumption does not apply to a supported configuration used unchanged.

== Peer rates on shared routes are the integrator's

[.specitem,oft-sid="aou~seooc-peer-rates~2",oft-title="Peer rates on shared routes are the integrator's",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
On routes that several peers share, the integrator *SHALL* bound each peer's message rate, by deployment and scheduling, or accept that one faulty peer can fill a route's depth and so starve the others there.

* *What the element does.* The element applies the route's overflow policy and counts each discard it or its binding can observe; losses entirely inside middleware that the binding cannot observe are explicitly disclosed in the route's report (`+req~ssr-qos-overflow~3+`, `+req~ssr-error-no-silent-loss~3+`). It has no per-peer quota.
* *Peer-specific progress.* Where the item's safety reaction requires detecting a particular peer's lack of progress, the integrator *SHALL* supply peer-specific progress expectations and application checks, or deployment and scheduling measures that meet that requirement; an aggregate route deadline does not supply that detection.
* *Strict mode.* In strict mode, the report warns of an ASIL route with several declared senders and no declared per-peer rate, and lists each shared route with what one faulty peer can starve there.
--

*Violation:*

* Observable discards are *counted*; middleware-unobservable losses are disclosed, not counted.
* Starvation of one peer while another keeps the route arriving is *undetectable* by the aggregate route deadline, even when a deadline is declared.
* General drop counts may reveal congestion but do not identify, or guarantee detection of, the starved peer.
* Required detection depends on the integrator's peer-specific progress checks or deployment and scheduling measures.

[horizontal]
ASIL:: B
Status:: Draft

*Rationale.*
The route aggregates arrivals from its peers.
A flooding peer can refresh its deadline continuously while other peers lose every useful frame.

Observable discard counts reveal only the congestion they measure, and hidden middleware losses cannot be reconstructed from counter fields.

Per-peer quotas remain absent.
Rate bounds and any required peer-progress detection belong to the integrator's deployment, scheduling and application measures.

== Applications build every transport and role before the last transition

[.specitem,oft-sid="aou~seooc-build-order~2",oft-title="Applications build every transport and role before the last transition",oft-needs="uman",oft-tags="SafetyManual,SafetyGateUpRust"]
--
An application *SHALL* build every transport and every role it will use before the last of the transports that share one startup memory enters runtime mode; for the Streamer, before it calls `+enter_runtime_all+`.

A setup kept alive without ever entering runtime mode is a defect of the application.

In strict mode, the Enforce state refuses a setup still alive and not entered when `+enter_runtime_all+` returns, and the report lists every such setup.
--

*Violation:*

* A setup built afterwards on that memory is *refused at setup* (`+req~ssr-memory-sealed~3+`).
* A setup still alive and not entered when `+enter_runtime_all+` returns is reported then, and in strict mode is *refused at setup*; without `+enter_runtime_all+` it is *undetectable*.

[horizontal]
ASIL:: B
Status:: Draft

*Rationale.*
Once a transport that shares startup memory enters runtime mode, the caller's handle places nothing more.
The memory is sealed for every handle when the last setup sharing it has entered runtime mode (`+req~ssr-memory-sealed~3+`).

A setup that never enters runtime mode keeps its claim.
So the memory is never sealed for every handle, and nothing that rests on the seal holds.

== Only authorized operators reach the Streamer's operator interface

[.specitem,oft-sid="aou~seooc-operator-access~2",oft-title="Only authorized operators reach the Streamer's operator interface",oft-needs="uman",oft-tags="SafetyManual"]
--
The integrator *SHALL* restrict the Streamer's operator interface (`+req~ssr-streamer-operator-control~1+`) to the parties allowed to disable or re-enable routes.

It *SHALL* treat an operator's disable of an ASIL route as a loss of that route's function, which the item *SHALL* tolerate.

In strict mode, the Streamer's own checks refuse an operator interface that names an ASIL route unless `+operator_may_disable+` acknowledges it, and the report lists which ASIL routes an operator can disable.
--

*Violation:*

* Every change made through the interface is *counted* and reported with its cause, so an unintended disable is seen.
* In strict mode, an operator interface that names an ASIL route without `+operator_may_disable+` is *refused at setup*.
* Who made a change is *undetectable* by the element.

[horizontal]
ASIL:: B
Status:: Draft

*Rationale.*
The operator interface can switch an ASIL route off at run time (`+req~ssr-streamer-operator-control~1+`).
So whoever can reach it can remove that route's function.

The element counts and reports every change with its cause, but cannot tell who made it.
So who may make one is the integrator's to control.

== Monitor thresholds allow for peers' restarts

[.specitem,oft-sid="aou~seooc-monitor-thresholds~2",oft-title="Monitor thresholds allow for peers' restarts",oft-needs="uman",oft-tags="SafetyManual"]
--
The integrator *SHALL* set each Streamer monitor's thresholds, in deployment data, above the worst-case restart time of the peers on the routes that monitor trips, or accept that a peer's normal restart trips such a route.

A tripped route stays disabled until an operator re-enables it, and a route that the operator interface does not name can then be re-enabled only by restarting the Streamer.

In strict mode, the deployment data *SHALL* also declare each peer's worst-case restart time: in the Enforce state, setup refuses a monitor threshold below the declared restart time of a peer on that monitor's routes, unless `+outage_on_restart+` names the accepted outage, and strict mode's report lists every monitored route that only a Streamer restart clears.
--

*Violation:*

* A threshold below a peer's worst-case restart trips the route on that restart.
* The trip is *counted* with its cause, and the mode report shows degraded.
* The route stays disabled until an operator re-enables it, or, where the operator interface does not name it, until the Streamer restarts.
* In strict mode, a threshold below a peer's declared restart time is *refused at setup* in the Enforce state, unless `+outage_on_restart+` names the accepted outage.
* Whether that outage is acceptable for the item is *undetectable* by the element.

[horizontal]
ASIL:: B
Status:: Draft

*Rationale.*
A peer recovers from a fault by restarting, since the element has no recovery inside a process (`+aou~seooc-supervisor-restart~4+`).
A monitor's trip holds until an operator re-enables the route (`+req~ssr-streamer-monitors~4+`).
So a threshold below a peer's worst-case restart turns that peer's normal restart into an outage of the route, and only the item's own analysis can say whether that outage is acceptable.

Declared restart times make the duty checkable.
Setup can compare every threshold with them, and refuse a short one unless its outage is accepted by name, before any route carries traffic.
