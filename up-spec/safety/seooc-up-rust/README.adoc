= up-rust SEooC: scope, modes and verification
:toc: preamble

The software safety requirements and assumptions of use of one safety element out of context (SEooC): up-rust's runtime data path, with the Streamer's data plane, the end-to-end protection wire and strict mode.

* The element is developed for ASIL B capability, and claims it only for a supported configuration whose evidence establishes it (<<claims>>).
* No item is known yet, so the requirements are assumed ones, and the assumptions of use say what an integrator has to provide (10-9).

The conventions, tags and status words are in xref:../README.adoc[the safety area's README].
Every item is still Draft.

This directory holds what is specific to the element: its scope and boundary, its claims, its modes, memory, build and platform rules, and the index of its assumptions of use.
The items that concern a protocol layer are filed with that layer, in xref:../up-l1/README.adoc[the transport layer's part] and xref:../up-l2/README.adoc[the communication layer's part].
They are items of this element and of the parts that work with it all the same, and <<files>> lists them.

== The element

|===
| Part | What it is | Crate

| E1. The runtime path of `up-rust-core`
a|
* The two mode types and the transition between them.
* The L2 handles once activated: publisher, subscriber, notifier, notification listener, RPC client and server.
* The L1 carrier routes: receive, send, park and the capacity check.
* Inbound slots, ready queues, the RPC call table, the peer table, QoS checks, TTL checks, the deadline monitor, message IDs, waiver records, route reports and counters, heap-free errors.
* Header and envelope parsing.
* The SDK side of the wire contract: the checked payload writer, and decoding into startup slots.
* Core's end-to-end protection hooks, opaque call tag, protected refusal answers and route counters, with unprotected responses counted separately.

| E2. The lending and handoff runtime contracts
a|
* The traits a binding implements: binding setup, lending runtime, handoff runtime, frame, lent transmit storage.
* The SDK services a binding calls: the runtime port.

The contract is in the element.
Each binding's implementation of it is not.
| `up-rust-core`

| E3. Startup memory
| Startup memory, its regions, placement and seal.
| `up-rust-core`

| E4. Platform
a|
* The runtime platform: `now`, `unix_time_ms`, `wait`, `wake_one`, `wake_all`.
* The initialization-only platform: `entropy`, `prefault`.
* The shipped backends, chosen by `cfg`: Linux; macOS; QNX, source only and future work.
A supported configuration names the backend it uses (`+aou~seooc-target-environment~4+`).
* The shared signal.
| `up-rust-core`

| E5. The Streamer's data plane
a|
* The ASIL Streamer's route table, admission, validation and forwarding loop, in a `no_std` crate of their own.
* The `std` binary that creates its worker threads.
* The SDK side: the carrier primitives.
| The carrier primitives in `up-rust-core`; the ASIL Streamer crate and its binary in `up-streamer-rust`

| E6. The end-to-end protection wire
a|
`E2e<W>`, an opt-in wire that wraps any other wire.

* It carries a data ID, a counter, its sender's incarnation and a CRC in the payload, and uses the route's deadline as its timeout.
* Whether and where to use it is the integrator's choice (`+aou~seooc-e2e-protection~7+`).
* Deferred: the wire is not part of this delivery.
Its items keep their IDs and revisions, two of them with an updated citation of that assumption of use, and no gate or current obligation of another item depends on it.
| `up-wire-e2e`, a `no_std` member of `up-rust` that depends only on `up-rust-core`

| E7. Strict mode
a|
An opt-in check, in initialization mode only, of the integrator's setup against the rules that the assumptions of use name.

* It has four states: Off, the default; Report; Enforce; and Locked, which is Enforce alone, under `+--cfg up_rust_strict+`.
* Its findings name the rule, the route, the requirement IDs and the fix.
* It accepts a deviation only when it is acknowledged by ID and revision.
* Every run produces a compliance report (`+req~ssr-strict-init-only~1+`, `+req~ssr-strict-report~2+`).
| `up-rust-strict`, a `no_std` member of `up-rust` that depends only on `up-rust-core`; in core, read-only views of each route's declarations and one hook
|===

The initialization-mode code of E1 to E7 is part of the element too: builders, admission, the validation of deployment data, and the transition.
Its faults show before traffic starts, but a wrong admission decision becomes a runtime fault, so the transition is safety-relevant.

== Outside the element

=== Classic routes

`UTransport`, `UMessage` routes and the classic L2 building blocks allocate in the SDK's own code, so no waiver can admit them, and they never enter runtime mode.
They stay QM.

=== Async integrations

* The planned executor-independent async layer (working name `up-rust-async`) keeps futures and executor hooks above core's synchronous seam, and keeps the asynchronous contract of `+req~ssr-async-seam~3+`.
* The existing `up-rust-tokio` is the integration that layer is to replace.
* Core, synchronous use and the async layer itself require no particular executor.
* An executor's own resources are outside the element's claims.
So a native resource claim for an asynchronous path rests on a configuration package that establishes its executor's behaviour.
* The layer is planned work, to be tested with Tokio and with Embassy before the async API is frozen.
Nothing here claims that it exists yet.

=== Middleware internals

iceoryx2, Zenoh, vSomeIP, DDS, MQTT, LoLa.
Allocation inside middleware needs a declared permit and a named waiver, and each binding's README says what its middleware cannot guarantee.

=== QM convenience crates

The QM convenience crates are:

* `up-rust` itself: the classic API, heap-backed startup memory, configuration helpers, the prelude;
* the optional `up-rust-std` and `up-rust-alloc` layers, with the allocation providers that plug into them;
* `up-wire-protobuf` and the other `std` wires;
* `test-util`.

On the ASIL path an application links only its claimed safety dependency graph (`+req~ssr-crate-core-only-binary~2+`).

* The graph is judged by what each crate actually brings into the image, with its features and target-selected paths, never by its name.
`up-rust` as published brings dependencies outside that graph, and a compatibility re-export is judged by the graph it brings.
* Ordinary use keeps all of them.
* An optional layer joins a claimed graph only where a configuration admits it with its own allocated requirements and evidence (`+req~ssr-crate-core-only-binary~2+`).
At this revision none does.
* `up-rust-core` itself has no dependencies, no Cargo features and no `alloc`.
The optional `alloc`, `std` and application layers are separate crates, the `alloc` layer experimental on Rust 1.100 while the others keep the 1.88 minimum supported version.

=== Other things outside the element

* *The classic `UStreamer`*, its dynamic routes and its cross-family adapters.
* *Wires and bindings from elsewhere* with `unsafe` code of their own.
Their integrator qualifies that code.
* *A custom platform backend that an integrator supplies*, an explicit extension held to the platform's rules by `+aou~seooc-integrator-platform~4+`.
* *The application's own logic and the item's safety function.*
The element carries data.
What the data means, and how the item reacts to a failure, are the integrator's.
* *The OS, hardware, supervisor, clock source and deployment data, and the choice of routes that need end-to-end protection*: these are assumptions of use.

== What the element relies on but does not contain

* *Bindings and wires* are separate elements.
Their code runs inside the element's calls, but each is developed and verified on its own, against the contract suites in `test-util`.
The items allocated to them are in xref:../up-l1/bindings.adoc[`bindings.adoc`] and xref:../up-l1/wires.adoc[`wires.adoc`] of the transport layer's part, and `+aou~seooc-qualified-bindings-and-wires~6+` restricts an integrator to those that pass.
The end-to-end protection wire is a wire too, but it is shipped as the element's safety mechanism, so it is part E6, with its own items.
* *Derive macros* (`up-rust-macros`: `ZeroSlot`, `StablePayload`, `StablePayloadInit`) are tools.
The code they generate becomes part of the element and is held to its requirements.
* *`test-util`* (the heap guard, the C-level observer, the contract suites, the in-memory bindings) is verification tooling.
The in-memory bindings are test doubles, not bindings, so evidence that rests on one says which.

[[claims]]
== Claims

A deployment can ask for four independent properties, and each route's report keeps them apart (`+req~ssr-qos-no-downgrade~2+`):

* *Functional communication and monitoring*: the protocol and ownership semantics, deadline gaps counted from true arrivals, and reports that can be read whenever execution permits.
Every supported profile offers it, with no timing or safety package.
* *Native resource behaviour*: no heap acquired or released, and no forbidden wait, panic or corruption, on a native path and in the work it causes.
* *A finite timing bound*: a stated endpoint reached within a bound, under a supported configuration whose execution model, workload envelope and evidence establish it.
* *Safety assurance*: the element's contribution to an item's safety requirements, at a stated ASIL and context, with its requirements, analyses, verification, qualification and assessment.

=== The properties are not a ladder

* No OS family, architecture, compiler or middleware confers a timing bound or an ASIL, and a dependency's certificate does not qualify this element.
* A timing bound or an assurance scope that a route explicitly requires is admitted under its configuration or refused at setup by name.
Its absence never refuses ordinary use.
* An integrity level, an ASIL label or a strict-mode state is not such a request.
Strict mode checks what a configuration declares before any assurance package exists, and reports assurance that is not established as Draft and unassessed.
* A passing setup or strict-mode check shows that its observable predicates held.
It is not a qualification or an assessment.

=== Ordinary ownership and stronger resource guarantees

A serialized or owned route may carry values that own what they hold, heap memory included.
Most wire formats decode into such values, and a route that declares its allocation carries them with no timing or safety package (`+req~ssr-heap-guarantees~1+`).

* *What every route keeps.*
Memory safety and the ownership rules, the functional semantics a route offers, the native rule and the duties of element code hold on every route, whatever it is labelled.
A fault against one of them is a defect, never a missing package.
* *What a route declares.*
Its heap class, and the resource and failure policy of whatever allocates, as its allocator's contract states them (`+req~ssr-heap-declared~3+`).
An allocator that can wait for a lock or end the process on exhaustion is declared as one.
* *What a route may require.*
Panic-free cleanup, non-waiting acquisition, non-waiting release and recoverable exhaustion, each by name and each for its own operations only.
A required guarantee is admitted on evidence for the exact type, wires, binding, provider, build and contexts, or the route is refused at setup by name.
Each route's report states a guarantee as required or not, established or not, and admitted or not.
A guarantee is admitted only where it is both required and established.
One that a route does not require refuses nothing by its absence, and evidence that establishes it stays reported.
* *What is neither a request nor evidence.*
An integrity level, an ASIL label, a strict-mode state, an operating system, a toolchain, or the name of a crate, wire format or provider.

=== Supported configuration packages

The element's maintainers provide versioned supported configuration packages: the platform backend, its synchronization and execution model, startup checks, sizing, supported contexts, build settings, dependency scope, evidence and limitations.

* An application team selects a package and declares its semantic traffic, routes, payload and retention bounds and the timing and safety outcomes it requires.
It does not invent a synchronization backend or an OS scheduling proof for supported use.
* A custom platform is an explicit extension (`+aou~seooc-integrator-platform~4+`).
* The item's hazards, its fault tolerant time interval, its actual workload, its safe state and everything outside the package stay the integrator's.

=== Evidence states

Evidence is reported by its state, never as another: design feasibility, implementation present, compiled, linked, exercised, source-reviewed, composition-verified, and qualified or assessed, each with its exact pins and limitations.

* Compiling does not show execution.
* A source review does not show timing.
* An emulator does not show physical timing.

The current SDK profiles are macOS ARM64, Linux x86-64, Linux ARM64, Windows x86-64, Cortex-M7 and RV32IMAC.
QNX 7.1 and 8.x are future work, source only, each its own profile.

=== Whom the assumptions of use bind

The assumptions of use bind an integrator that claims safety assurance for a configuration.
Ordinary use need not carry out safety integration procedures.

A safety manual states the integration contract.
It is not a safety case, an assessment or a certificate.

== Operating modes

Runtime mode belongs to a transport.

* A transport is in runtime mode from the moment its own transition returns.
* Its transition is all or nothing for that transport alone: where several transports enter together, one that has entered stays in runtime mode if a later one is refused (`+req~ssr-mode-entry~5+`).
* Every requirement stated for runtime mode binds that transport from then on, whatever the process's other transports are doing.

A process is in runtime mode once every transport it built is, and for the Streamer when `enter_runtime_all` returns.
The process-level definition is used for three things only:

* sealing shared startup memory;
* the Streamer's startup report;
* process-level statements for integrators.

=== Initialization

Begins:: Process start, or a restart.
Ends:: The transport's transition succeeds, or the process exits.
Allowed::
* Construction.
* Route declaration and admission.
* Startup memory placement.
* Waivers.
* Forcing lazy state.
* Cleaning up after a dead predecessor.
* SDK startup memory from static or caller-provided regions, or, outside the ASIL path, from the optional `up-rust-std` or a declared `up-rust-alloc` provider (`+req~ssr-memory-static~2+`).
Impossible:: Traffic.

=== Transition

Begins:: `enter_runtime` on a transport's setup, or `enter_runtime_all` on several.
Ends:: Success gives runtime mode. Failure gives an error, still in initialization.
Allowed:: Checks and refusals, one way only.
Impossible:: Going back.

=== Runtime

Begins:: The transport's transition returns.
Ends:: Process exit, crash or kill, and nothing else.
Allowed::
* Activating the handles, and the Streamer, without heap.
* Traffic.
* Refusals and counters.
* Bounded waits.
* Deadline service.
* The Streamer's route gates.
* On a serialized or owned route, only two kinds of heap use: the allocation that its declared heap class admits, after the refusals that can come first; and the release, exactly once, of what that allocation produced when its ownership ends.
That release runs under the route's declared policy on a path of that route.
On a route that requires non-waiting release it runs at once only where it cannot wait, and otherwise on the route's release service, where it may stay pending, charged and isolated, with no completion deadline (`+req~ssr-heap-declared~3+`, `+req~ssr-heap-guarantees~1+`, `+req~ssr-heap-slot-types~3+`, `+req~ssr-release-lease-drop~4+`).
Impossible::
* Setup.
* Heap use on a native path, in the work it causes, or beyond a route's declared class.
* Heap use to decide, report or count a refusal, a discard or a peer's failure.
* Releasing a route, role, table, startup region or other runtime resource.

=== No shutdown mode and no degraded mode

There is no shutdown mode: in runtime mode a process leaves by exit, crash or kill, and in the ASIL build a panic aborts it.

There is no degraded mode with rules of its own.
A refusal, a counted drop, a missed deadline or a lost peer affects one route, and the others carry on.
The Streamer's "degraded" is a reported state: its safe state is fail-silent per route, through its route gates.

== Verification methods

Each item's "Verification" names methods from this table.

* A method runs on its default lanes unless brackets after it name others, for example `+heap-window[linux-stable, macos-stable]+`.
* Where an item's methods need detail, the line names the methods and a list below it says what each one covers.

[cols="2,5,3",options="header"]
|===
| Method | Meaning | Default lanes

| `compile-fail` | A trybuild case that must not compile, with its `.stderr` checked. It shows that an operation is absent from a type | `stable`, `1.88`
| `heap-window` | A test that counts every allocation and every free on all threads, with the Rust allocation guard and the C-level observer. The window opens when that transport's own transition returns, and a positive control shows that the gate fires | `linux-stable`, `linux-1.88`, `macos-stable`, each with both observers
| `miri` | The test run under Miri | `miri-sb`, `miri-tb`: Stacked Borrows and Tree Borrows, on Linux, with nightly as a tool only
| `fault-injection` | A test that injects the fault the item covers: a peer process killed or restarted, a malformed or hostile frame, a flood, a publisher writing to a sample while it is read, a primitive left lazy on purpose | `linux-stable`
| `test` | A requirements-based test of behaviour, with boundary values | `linux-stable`, `linux-1.88`
| `gate` | A static check in CI over source or build output: a sysroot without `alloc` or `std`, the panic-link check, a symbols check, the `unsafe` inventory, a token scan, manifest checks, compile-time assertions, workspace lints | `stable`, `1.88`
| `review` | An inspection, recorded in a review log | a record
|===

The lane names are `linux-stable`, `linux-1.88`, `macos-stable`, `miri-sb`, `miri-tb`, `miri-strict-provenance`, `stable` and `1.88`.

=== The shipped profile

Evidence lanes (heap windows, fault injection and the panic-link gate) run the ASIL profile: `panic = "abort"` and `overflow-checks = true`.

Contract suites that rely on catching a panic run on an unwinding test profile, for diagnosis only, and their evidence counts only as part of an item's evidence.

=== macOS

macOS has functional support, and, like every profile today, no configuration that claims assurance.
Its lanes are pthread evidence: they catch lazy first-use allocation that Linux futexes hide.

=== When an item is verified

An item is verified only when each method it lists has evidence for the paths it names.
A test that passes on another path is not evidence.

=== How a test names what it verifies

A test names what it verifies with OFT's own coverage tag, and the method after it on the same line, for example `+// [utest->req~ssr-qos-ttl~4] method: test+`.

* OFT reads the bracket.
* The method is for the check that each listed method has its evidence, which OFT does not do.
* Code that meets an item carries `+// [impl->req~ssr-qos-ttl~4]+`.
