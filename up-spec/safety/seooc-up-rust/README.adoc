= up-rust SEooC: scope, modes and verification
:toc: preamble

The software safety requirements and assumptions of use of one safety element out of context (SEooC).

NOTE: A safety element out of context is developed without a known item, in ISO 26262's sense: its requirements are assumed ones, and its assumptions of use say what an integrator has to provide (10-9).

The conventions and tags are in xref:../README.adoc[the safety area's README].
xref:../../contract-generations.adoc[Which requirements an implementation follows] says how these items relate to the protocol chapters.

NOTE: This directory holds what is specific to the element: its scope and boundary, its claims, its modes, memory, build and platform rules, and the index of its assumptions of use.
The items that concern a protocol layer are filed with that layer, in xref:../up-l1/README.adoc[the transport layer's part] and xref:../up-l2/README.adoc[the communication layer's part].
They are items of this element and of the parts that work with it, and <<files>> lists them.

== The element

[[req-ssr-element-boundary]]
=== The parts of the element, and element code

[.specitem,oft-sid="req~ssr-element-boundary~2",oft-title="The parts of the element, and element code",oft-needs="uman",oft-tags="SafetyUpRustCore"]
--
*The parts.*
The element is the up-rust SEooC.
It has the parts E1 to E7, each with its initialization-mode code: its builders, its admission, its validation of deployment data and its transition.

* *E1, the runtime path.*
** The two mode types and the transition between them.
** The handles of the communication layer once activated: publisher, subscriber, notifier, notification listener, RPC client and RPC server.
** Inbound slots, ready queues, the RPC call table and the peer table.
** The QoS checks, the TTL checks and the deadline monitor.
** Message identifiers, waiver records, route reports, counters and errors.
** The element's share of the handling of a frame's header, envelope and metadata.
** The element's side of the interface to a wire: the checked payload writer, and decoding into startup slots.
** The native wire.
** The element's hooks for end-to-end protection: the opaque call tag, protected refusal answers and route counters, with unprotected frames counted separately.
* *E2, the lending and handoff runtime contracts.*
The interfaces that a binding implements, which are binding setup, the lending runtime, the handoff runtime, the frame and lent transmit storage, and the service of the element that a binding calls, the runtime port.
No binding's implementation of them belongs to E2.
* *E3, startup memory.*
Its regions, their placement and their seal.
* *E4, the platform.*
The runtime platform (`now`, `unix_time_ms`, `wait`, `wake_one`, `wake_all`), the initialization-only platform (`entropy`, `prefault`), the shared signal, and each platform backend that is shipped with the element.
* *E5, the carrier primitives.*
Receive, send, park and the capacity check of a carrier route (xref:../up-l2/streamer.adoc#req-ssr-carrier-route[A carrier route takes each frame at its ingress and sends it at its egress]).
* *E6, the end-to-end protection wire (the E2E wire).*
An opt-in wire that wraps another wire (xref:e2e-wire.adoc#req-ssr-e2e-not-required[The element requires end-to-end protection on no route, outside strict mode's black-channel rule]; xref:e2e-wire.adoc[The end-to-end protection wire]).
* *E7, strict mode.*
An opt-in check, in initialization mode only, of the integrator's setup, in a component of its own (xref:crate-isolation.adoc#req-ssr-crate-core-only-binary[The checked policy stays in the safety crate, and no admitted optional layer bypasses or reimplements it], clause "Strict mode's component"), with the read-only views of each route's declarations and the hook in the runtime path that it uses.
Its states, the severities of its findings and its rules: xref:build.adoc#req-ssr-strict-states[Strict mode has four states]; xref:build.adoc#req-ssr-strict-init-only[Strict mode checks in initialization only]; xref:build.adoc#req-ssr-strict-lock[The locked build allows only enforcement]; xref:build.adoc#req-ssr-strict-rules[The rules that strict mode checks]; xref:build.adoc#req-ssr-strict-ack-revision[An acknowledgement names a deviation by ID and revision]; xref:build.adoc#req-ssr-strict-report[Strict mode reports on every run].

*Element code.*
Element code is the code of the parts that belong to the element.
Code that runs on a runtime path but that the element does not own, such as the destructor of an owned value, an allocator's release or a dependency that they reach, is not element code.

*Each part keeps its own requirements.*
Whom a requirement binds is stated in xref:../README.adoc#req-ssr-requirements-bind[A requirement binds the actors to which it gives a duty].
Belonging to the element moves no duty from one part to another.

*Outside the element.*
These are parts of their own, each with its own requirements, and none is a part of the element:

* each binding, with its middleware (xref:../up-l1/bindings.adoc#req-ssr-binding-scope[What a binding is, and the binding contract]);
* each wire other than the native wire and the end-to-end protection wire (xref:../up-l1/wires.adoc#req-ssr-wire-scope[What a wire is, and the wire contract]);
* a platform backend that an integrator supplies (xref:assumptions-of-use.adoc#aou-seooc-integrator-platform[A custom platform keeps the platform's rules]);
* the Streamer and the Streamer binary (xref:../up-l2/streamer.adoc#req-ssr-streamer-scope[What the Streamer is, and the bounded-runtime Streamer profile]);
* each optional layer, such as an allocation-aware layer or an asynchronous layer, and the scheduler that drives an asynchronous layer;
* each memory provider, scheduler integration and adapter (xref:../../sdk/owned-frame/README.adoc#req-sdk-owned-frame-contract[The owned-frame SDK contract binds the parts that declare it]).

The Streamer uses the carrier primitives of E5.
A requirement whose statement gives a duty only to the element, to element code or to a part of the element gives the Streamer no duty.
The application's own logic, the safety function of the item, in ISO 26262's sense, with its hazards, its fault tolerant time interval, its workload and its safe state, the operating system, the hardware, the supervisor, the clock source and the deployment data are outside the element too, and the assumptions of use cover them.

*Composition.*
A deployment conformance claim (xref:../README.adoc#req-ssr-contract-transition[What a part declares and claims, and when a replacement takes effect]) covers the parts that the deployment's profile selects (<<req-ssr-element-configurations,The ASIL path and supported configurations>>).
Running in one process, being linked into one binary or being kept in one repository establishes no claim and merges no requirements.
A composition that is claimed as one unit has its own explicit boundary, the revisions of its parts and of their named profiles with their dependency closure, its lifecycle, its assumptions of use and its evidence.

*The derive and test tooling.*
The element's derive is a build input, and no part of the element at run time.
What holds for the code that it generates, and who accounts for that code, is stated in xref:memory-safety.adoc#req-ssr-unsafe-inventory[Every `unsafe` is inventoried and justified].
The application code around generated code is not element code.
Test tooling, such as heap observers, contract suites and test doubles, is no part of the element.
--

[horizontal]
ID:: `+req~ssr-element-boundary~2+`
ASIL:: B
Allocated to:: the element
Verification:: review (each statement and allocation that names the element, element code, one of the parts E1 to E7, a part outside the element or a composition of parts, read against this item)

*Rationale.*
Faults of initialization-mode code show before traffic starts, but a wrong admission decision becomes a runtime fault, so the transition is safety-relevant.
Parts that are built, released and qualified apart can be combined in many ways, so a duty stays with the part to which its requirement gives it, whatever is linked or deployed beside it.

[[req-ssr-element-configurations]]
=== The ASIL path and supported configurations

[.specitem,oft-sid="req~ssr-element-configurations~2",oft-title="The ASIL path and supported configurations",oft-needs="uman",oft-tags="SafetyUpRustCore,SafetyStreamer"]
--
*The ASIL path.*
A configuration is on the ASIL path where an integrator claims the element's safety-assurance scope for it (xref:assumptions-of-use.adoc#aou-seooc-assumptions-bind[An assumption of use binds the integrator who claims the scope, and replaces no requirement]).
An ASIL application, an ASIL process, an ASIL binary, an ASIL image and the ASIL build are the applications, processes, binaries, final images and build of a configuration on the ASIL path.
Each of these words names the scope that the integrator claims, and qualifies nothing by itself.
What ordinary use is, and what holds for it, is stated in xref:assumptions-of-use.adoc#aou-seooc-assumptions-bind[An assumption of use binds the integrator who claims the scope, and replaces no requirement].

*Supported configurations.*
A supported configuration package is a versioned package that states a configuration's platform backend, its synchronization and execution model, startup checks, sizing, supported contexts, build settings, dependency scope, evidence and limitations.
A supported configuration is one for which the element's supplier provides such a package.
The package is released with the element, and a configuration that has none is not a supported configuration.
In each supported configuration package that it provides, the element's supplier *MUST* state each size on which the configuration's sizing relies and that the element's own computation does not give, such as the storage of a scheduler's tasks and timers, an allocator's overhead and each thread's stack, and *MUST* name each such size that the package does not establish (xref:startup-memory.adoc#req-ssr-memory-computable[Startup storage is computable before start]).
A platform profile is a class of target, an operating system or a bare-metal environment with an architecture, that a supported configuration package names.

*The deployment profile.*
A deployment profile is the selection that a deployment declaration names (xref:../README.adoc#req-ssr-contract-transition[What a part declares and claims, and when a replacement takes effect]):

* the parts that the deployment composes, each with its declaration;
* the interfaces between them;
* the services that the deployment requires, and those that it leaves optional;
* how many of each part it has;
* the assumptions of use that apply to it.

A part that the profile does not select is outside the deployment's claimed scope.

*Optional layers.*
The ASIL path admits no optional layer: a deployment profile on the ASIL path selects none.
What a configuration needs to admit an optional layer, and what an admitted layer must not do, is stated in xref:crate-isolation.adoc#req-ssr-crate-core-only-binary[The checked policy stays in the safety crate, and no admitted optional layer bypasses or reimplements it].
The contracts that items give an optional layer, such as those of an asynchronous layer, remain its own, and none of them admits it to the ASIL path.
That is a boundary of the ASIL path.
It lifts no contract of an optional layer, of a classic route or of a wire that the ASIL path leaves out, it says nothing of their integrity level, and it leaves their ordinary use as it is.
--

[horizontal]
ID:: `+req~ssr-element-configurations~2+`
ASIL:: B
Allocated to:: the element's supplier, for the sizes that it states in each supported configuration package; the element, as the subject of the definitions
Verification:: review
* Each statement and allocation that names the ASIL path, an ASIL application, process, binary, image or build, a supported configuration or its package, a platform profile, a deployment profile or an optional layer, read against this item.
* Each supported configuration package: each size on which its sizing relies and that the element's computation does not give, stated or named as not established.

*Rationale.*
The assumptions of use bind the integrator that claims the element's assurance for a configuration (xref:assumptions-of-use.adoc#aou-seooc-assumptions-bind[An assumption of use binds the integrator who claims the scope, and replaces no requirement]), so the words of the ASIL path name exactly that claimed scope.
A package states once what a supported configuration offers, so that every application team that selects one relies on that statement for its platform.
The element computes its own startup storage, and the sizes that depend on a scheduler, an allocator or a thread's stack are known only to whoever puts the configuration together, so the package's supplier states them or says that they are not established.
A deployment that names what it composes can be checked against that selection, and what merely runs beside it gains no place in the claim.

[[req-ssr-verification-methods]]
== The verification methods, and what a Verification line asks for

[.specitem,oft-sid="req~ssr-verification-methods~2",oft-title="The verification methods, and what a Verification line asks for",oft-needs="uman",oft-tags="SafetyUpRustCore,SafetyStreamer,SafetyBinding,SafetyWire"]
--
*The methods.*
The "Verification" line of each requirement of this area names one or more methods of this table, and no other method:

[cols="2,5,4",options="header"]
|===
| Method | What it shows | Default scope

| `compile-fail` | A case that fails to compile, with the compiler's diagnostic checked against the one expected. It shows that the use that the case attempts is ruled out at compile time, such as an operation that is absent from a type | With the current stable compiler, and with the minimum supported version
| `heap-window` | A test that counts every allocation and every free on all threads, with an observer at the Rust global allocator and another at the C library's allocation functions. The window opens when the transition of the transport under test returns. A positive control, a deliberate heap use inside the window, makes the window fail | On Linux, whose OS locks are built on futexes, with the current stable compiler and with the minimum supported version. On macOS, a pthread target, with the current stable compiler. Each with both observers
| `miri` | The test, run under Miri | Under Stacked Borrows and under Tree Borrows, on Linux. The toolchain that Miri needs is a tool only
| `fault-injection` | A test that injects a fault that the line's requirement covers, such as a peer process killed or restarted, a malformed or hostile frame, a flood, a publisher writing to a sample while it is read, or a primitive left lazy on purpose | On Linux, with the current stable compiler
| `test` | A requirements-based test of behaviour, with boundary values | On Linux, with the current stable compiler and with the minimum supported version
| `gate` | A static check over source or build output, such as a build on a sysroot without `alloc` or `std`, the panic-link check, a symbols check, the `unsafe` inventory check, a token scan, manifest checks, compile-time assertions or workspace lints | With the current stable compiler, and with the minimum supported version
| `review` | An inspection, recorded in a review log | A record
|===

*A method with no qualifier.*
A method that a "Verification" line names with no qualifier has the default scope of its row.
A case that no qualifier holds for has the default scope of its method's row.

*Qualifiers, paths and cases.*
A line details a method in words after it, or in the list under the line.
An entry of the list that begins with a method details that method, which the line names, together with the entries under it.
Any other entry details each method that the line names.
Words that state where or how the method is applied, by naming a platform, a target or a class of either, a compiler, or a model such as Stacked Borrows, are a qualifier of that method.
Words that name a kind of target as the condition that a case puts under test, without stating where the method is applied, name that case.
The other words name the paths or cases of the line's requirement that the method covers, or say how those cases run.
A method whose line names no path or case for it covers the paths and cases that its requirement's statement names.
A qualifier holds for the case whose words hold it.
A qualifier that stands apart from every case, after the method or at the head of an entry, holds for every case of the method or of that entry.
In each case that it holds for, a qualifier changes the method's scope as its words state, for what it names, and for the rest the method keeps the default scope of its row.
An entry that begins with a method and stands under another entry details the paths and cases of that entry.
For them it has the default scope of its own method's row, as the qualifiers that hold for its cases change it, and it takes no other platform, target, compiler or model from the entry that holds it.
Where a method's description introduces cases with "including", in the line or in its list, those cases are added: the method still covers the cases that the statement names.
Where a line offers a choice of methods for different cases, such as test or compile-fail, each method covers the cases that it can observe.
A line that names several methods without such a choice keeps each method's stated coverage.

*Profiles and toolchains.*
The scope of a heap window, under whichever method a line names it, of a test that a line names under `fault-injection` or whose words say that it injects a fault, and of the panic-link check includes the ASIL profile (xref:build.adoc#req-ssr-build-panic-abort[The ASIL build aborts on panic and checks overflow]), whatever a qualifier states.
A contract suite that relies on catching a panic runs on an unwinding test profile in place of the ASIL profile, for diagnosis only.
Its result supports a requirement's evidence, and shows no requirement by itself.
A run that a line places under Miri uses the toolchain that Miri needs, in place of the compilers of its method's row.

*What a result shows.*
A result directly shows the path, the platform, the target, the backend, the binding and the configuration that it ran on.
Using it for another scope rests on an argument of its own, and no such argument replaces a run that a Verification line requires on a named platform, target, backend or configuration.
A result on a test double is evidence for the code under test, within what the double observes.
It is no evidence that a real part of that kind meets its requirements (xref:../up-l1/bindings.adoc#req-ssr-binding-scope[What a binding is, and the binding contract]).

*The evidence.*
The supplier of each part that a requirement of this area binds *MUST* show, in its evidence for the duties that the requirement gives that part, each method that the requirement's "Verification" line names, in the scope that the method has for the requirement, applied to the paths and cases of those duties that the method covers.
The evidence of a component conformance claim (xref:../README.adoc#req-ssr-contract-transition[What a part declares and claims, and when a replacement takes effect]) is that evidence for each requirement that the claim rests on.
Revision 1 of this item gave the duty to show that evidence to each part that a requirement of this area names; this revision gives it to that part's supplier.
The supplier *MUST* report each piece of evidence by its state, which is what was done to obtain it, with the exact inputs, tool and configuration revisions that it was obtained with, its observation scope and its limitations, and *MUST NOT* present evidence of one state as evidence of another.
The supplier *MUST* name the test double in each piece of evidence that rests on one.
Compiling shows no execution, a source review shows no timing, and an emulator shows no physical timing.
The names of the states are those of the part's versioned qualification record.

*When a requirement is verified.*
A requirement is verified only when its evidence shows each method of its line, in the scope that the method has for the requirement, applied to the paths and cases that the method covers, and those methods between them cover every path and case that its statement names.
A result on another path is no evidence for the requirement.
A method that cannot show a duty of the statement is no evidence for that duty, and the requirement is then not verified.

*Rationale.*
Every "Verification" line of this area names its methods by a word, so each word needs one meaning, stated once, and in an item that meaning has a revision that rises when it changes.
Several suppliers verify the parts that this area binds, each with its own runs, runners and tool versions, which change from one release to the next; a default that names compilers by their role, and no run, runner or tool version, holds for all of them.
A heap window on a pthread target catches lazy first-use allocation that OS locks built on futexes hide, so the default of the heap window has a platform of each kind.
In the ASIL profile a panic ends the process and an arithmetic overflow panics, so a heap window, a test that injects a fault or the panic-link check shows how the ASIL build behaves only when it uses that profile.
A suite that catches a panic needs unwinding, which that profile turns off.
A result shows how the path that ran behaves, and another path, another platform or a stand-in for a part can run other code under other conditions.
The code of a part performs its duties, and its supplier is the party that can produce and answer for the evidence.

.A case and a qualifier in one Verification line
====
A line may read `+test (a service that keeps history refused at setup, on a 32-bit target)+`.
The words "a service that keeps history refused at setup" name the case, and "on a 32-bit target" is a qualifier.
The test then runs on a 32-bit target, with the current stable compiler and with the minimum supported version.
