= up-rust SEooC: Modes and the transition
:toc: preamble

The key words "*MUST*", "*MUST NOT*", "*REQUIRED*", "*SHALL*", "*SHALL NOT*", "*SHOULD*", "*SHOULD NOT*", "*RECOMMENDED*", "*MAY*", and "*OPTIONAL*" in this document are to be interpreted as described in https://www.rfc-editor.org/info/bcp14[IETF BCP14 (RFC2119 & RFC8174)]

Conventions, tags and status words: xref:../README.adoc[the safety area's README].
Scope and element boundary: xref:README.adoc[the SEooC's README].

[[req-ssr-mode-two-types]]
== Two modes, as two types

[.specitem,oft-sid="req~ssr-mode-two-types~1",oft-title="Two modes, as two types",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Each lending and each handoff transport *MUST* have an initialization mode and a runtime mode, and each mode *MUST* be a distinct non-generic type.

A transport built directly in code and one built from deployment data *MUST* have the same types, so transports chosen at run time can sit in one list.
--

[horizontal]
ID:: `+req~ssr-mode-two-types~1+`
ASIL:: B
Allocated to:: the element
Verification:: test, review
Status:: Draft
ISO 26262:: 6-6.4.2 g, 6-7.4.5 (part-clause numbers only)

*Rationale.*
Giving each mode its own type lets the compiler refuse setup after the transition and traffic before it (<<req-ssr-mode-no-setup-at-runtime,Setup is impossible in runtime mode>>; <<req-ssr-mode-no-traffic-before-runtime,Traffic is impossible before runtime mode>>).

Non-generic types let a forwarder such as the Streamer hold transports chosen from configuration at run time in one list.

[[req-ssr-mode-no-setup-at-runtime]]
== Setup is impossible in runtime mode

[.specitem,oft-sid="req~ssr-mode-no-setup-at-runtime~1",oft-title="Setup is impossible in runtime mode",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Once a transport is in runtime mode, it *MUST NOT* be possible to declare, prepare or change a route, role, wire, QoS setting, integrity level, waiver, peer list or capacity, through the transport or through any handle activated from it.

The API *MUST NOT* offer the operation, and misuse *MUST NOT* compile.
--

[horizontal]
ID:: `+req~ssr-mode-no-setup-at-runtime~1+`
ASIL:: B
Allocated to:: the element
Verification:: compile-fail
Status:: Draft
ISO 26262:: 6-6.4.2 g (part-clause numbers only)

*Rationale.*
Runtime mode runs only what setup admitted and placed.
A change after the transition could be neither checked nor given storage without the work of initialization (<<req-ssr-mode-entry-admission,Every route is admitted before runtime mode>>).

The transition consumes the setup value, so no setup call can be written afterwards (<<req-ssr-mode-entry,Entering runtime mode is one all-or-nothing operation>>).

[[req-ssr-mode-no-traffic-before-runtime]]
== Traffic is impossible before runtime mode

[.specitem,oft-sid="req~ssr-mode-no-traffic-before-runtime~1",oft-title="Traffic is impossible before runtime mode",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
A send, receive, publish, notify, invoke, respond, wait or forward operation *MUST NOT* exist on an initialization-mode value.

A handle that can carry traffic *MUST* be obtained only by activating its setup against a transport in runtime mode.

Misuse *MUST NOT* compile.
--

[horizontal]
ID:: `+req~ssr-mode-no-traffic-before-runtime~1+`
ASIL:: B
Allocated to:: the element
Verification:: compile-fail
Status:: Draft
ISO 26262:: 6-6.4.2 g (part-clause numbers only)

*Rationale.*
Traffic before the transition would run before every route is admitted and its storage placed, which is what the transition checks (<<req-ssr-mode-entry-admission,Every route is admitted before runtime mode>>).

So every traffic operation belongs to a handle activated from a transport in runtime mode, and a role's setup value has no way to send.

[[req-ssr-mode-backstop]]
== Run-time refusal only where types cannot reach

[.specitem,oft-sid="req~ssr-mode-backstop~1",oft-title="Run-time refusal only where types cannot reach",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Where the type system cannot enforce the mode, the element *MUST* refuse the operation at run time with a named error and change nothing.
This covers:

* activating a handle against another transport's runtime;
* placing from startup memory after it is sealed;
* any C ABI entry point added later.
--

[horizontal]
ID:: `+req~ssr-mode-backstop~1+`
ASIL:: B
Allocated to:: the element
Verification:: test
Status:: Draft

*Rationale.*
Types keep the modes apart inside Rust, but they cannot follow a call through a C ABI.
Every transport's runtime also has the same type (<<req-ssr-mode-two-types,Two modes, as two types>>).
So those cases need a check when the call is made.

A named error for each case, such as a wrong transport or a sealed region, tells the caller which rule the call broke.

[[req-ssr-mode-entry]]
== Entering runtime mode is one all-or-nothing operation

[.specitem,oft-sid="req~ssr-mode-entry~5",oft-title="Entering runtime mode is one all-or-nothing operation",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*One operation.*
A transport *MUST* enter runtime mode only through one operation that consumes its initialization value.

*All or nothing, per transport.*
The operation is all or nothing for that transport: it succeeds only when every entry condition holds for every route declared on it.
Otherwise it returns an error, no runtime-mode value exists for that transport, and that transport starts no traffic.

*Several transports.*
Where several transports enter together, each one's transition is its own.
A transport that has entered stays in runtime mode if a later one is refused, and its runtime duties bind it from its own transition.

*The entry conditions.*
The entry conditions are these, each a requirement of its own, named here without its revision:

* every route admitted, with its storage placed (`+req~ssr-mode-entry-admission+`);
* the wall clock read, from a time provider that passed its setup check (`+req~ssr-mode-entry-clock+`);
* no declaration admitted whose traffic would be refused for a reason setup already knows (`+req~ssr-mode-entry-no-latent-refusal+`);
* every heap class declared and admissible for its route, and no decoded type that owns heap on a route whose class forbids it (`+req~ssr-heap-declared+`, `+req~ssr-heap-slot-types+`);
* lazy state forced, in the SDK and in each binding (`+req~ssr-heap-lazy-forced+`, `+req~ssr-binding-lazy-forced+`);
* a waiver for every permit, complete and approved by someone other than its author (`+req~ssr-waiver-required+`, `+req~ssr-waiver-record+`);
* QoS that can be honored, means something, and agrees between declarations, and every timing or assurance claim that a route requires admitted under its configuration (`+req~ssr-qos-no-downgrade+`, `+req~ssr-qos-invalid-refused+`, `+req~ssr-qos-consistent-declarations+`);
* integrity levels declared, and every crossing they imply admissible (`+req~ssr-integrity-declared+`);
* all runtime storage placed under the startup-memory policy of the configuration, static or caller-provided on the ASIL path (`+req~ssr-memory-static+`);
* in strict mode's Enforce state, no forbidden finding and no unacknowledged denied finding (`+req~ssr-strict-init-only+`).
--

[horizontal]
ID:: `+req~ssr-mode-entry~5+`
ASIL:: B
Allocated to:: the element
Verification:: compile-fail, test
* *compile-fail*: the setup value is consumed.
* *test*
** A refused transition leaves no runtime-mode value for that transport and starts no traffic on it.
** One refusal for each condition.
** With several transports entering together, a later refusal leaves an entered transport in runtime mode under its own duties.
Status:: Draft
ISO 26262:: 6-6.4.2 g, 6-7.4.5 (part-clause numbers only)

*Rationale.*
The list is in the statement, and a new condition raises this item's revision.

The transition is a conjunction of its prerequisites.
Checking only some of them cannot establish readiness for runtime.

All or nothing holds for each transport, not for a group.
A transport that has entered runtime mode cannot be taken back (<<req-ssr-mode-one-way,There is no way back>>), so a group's later refusal does not roll it back, and a refusal ends the process for a restart.

[[req-ssr-mode-entry-admission]]
== Every route is admitted before runtime mode

[.specitem,oft-sid="req~ssr-mode-entry-admission~1",oft-title="Every route is admitted before runtime mode",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Before a transport enters runtime mode, the element *MUST* have admitted every declared route, against its binding's declared capability.

Every route *MUST* have passed the setup checks on envelope, payload bound and capacity, and have its storage placed.

A route that fails any of them *MUST* make the transition fail, naming the route and the setting.
--

[horizontal]
ID:: `+req~ssr-mode-entry-admission~1+`
ASIL:: B
Allocated to:: the element
Verification:: test
Status:: Draft

*Rationale.*
The SDK owns admission, as it owns the mode state machine and the startup slots.
So every binding's routes meet the same checks.

A route that cannot be served then fails setup by name instead of failing its first message.
A refused carrier leg, for one, reports the route, the binding and the reason.

[[req-ssr-mode-entry-clock]]
== The wall clock is read before runtime mode

[.specitem,oft-sid="req~ssr-mode-entry-clock~2",oft-title="The wall clock is read before runtime mode",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
A transport *MUST* enter runtime mode only after both of these:

* the wall clock of the platform's time provider has been read successfully;
* the provider has passed the setup check of its package's stated contract (xref:platform.adoc#req-ssr-platform-contract[Every platform backend keeps the platform's rules]).

A provider known to fall short of that contract, such as one that supplies uptime or a fixed value as wall time, *MUST* fail the check.

If the clock cannot be read, or the provider fails its check, the transition *MUST* fail with an error that says so.
--

[horizontal]
ID:: `+req~ssr-mode-entry-clock~2+`
ASIL:: B
Allocated to:: the element
Verification:: test (an unreadable clock; a provider that supplies uptime as wall time; a provider that passes its check)
Status:: Draft

*Rationale.*
Message IDs carry a timestamp (xref:../../basics/uuid.adoc[UUID]), and a message's expiry is judged against its creation time plus its TTL (`+dsn~up-attributes-ttl-timeout~1+`).
Both are in wall time.

Reading the clock once before the transition makes a clock that cannot be read fail setup instead of every later message.

A board without a synchronized wall clock is a real configuration.
Quietly using uptime there would make every TTL decision wrong while appearing to work.
So the provider's contract is checked where it can be, and a known substitution is refused.

Simulated time and test seeds establish only the behaviour of a test harness.

[[req-ssr-mode-entry-no-latent-refusal]]
== Nothing is refused at runtime for a reason setup already knew

[.specitem,oft-sid="req~ssr-mode-entry-no-latent-refusal~1",oft-title="Nothing is refused at runtime for a reason setup already knew",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Setup *MUST* refuse any declaration whose traffic the element would refuse in runtime mode for a reason already known at setup, naming the route and the setter, instead of admitting a route that can never carry traffic.
--

[horizontal]
ID:: `+req~ssr-mode-entry-no-latent-refusal~1+`
ASIL:: B
Allocated to:: the element
Verification:: test, review (each runtime refusal reason checked for whether setup could have known it)
Status:: Draft

*Rationale.*
A route admitted only to refuse all its traffic looks healthy at setup and fails only in operation, where the cause is harder to see.

Setup refuses, for example:

* a wire with no size bound when the route also has no payload bound;
* a variable-size wire on a binding that cannot carry a short payload.

[[req-ssr-mode-one-way]]
== There is no way back

[.specitem,oft-sid="req~ssr-mode-one-way~1",oft-title="There is no way back",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
An operation *MUST NOT* take a transport, a handle or the Streamer from runtime mode back to initialization mode.

Runtime mode *MUST* end only when the process ends.
--

[horizontal]
ID:: `+req~ssr-mode-one-way~1+`
ASIL:: B
Allocated to:: the element
Verification:: compile-fail (the setup value is consumed), review (no such operation exists)
Status:: Draft
ISO 26262:: 6-6.4.2 g (part-clause numbers only)

*Rationale.*
A way back would reopen setup, which runtime code never reaches (<<req-ssr-mode-no-setup-at-runtime,Setup is impossible in runtime mode>>).
Every guarantee that rests on setup being over would then need a run-time check.

Comparable systems make the change of phase one-way too:

* the first call to AUTOSAR's `+StartOS+` does not return (https://www.autosar.org/fileadmin/standards/R24-11/CP/AUTOSAR_CP_SWS_OS.pdf[AUTOSAR CP SWS OS]);
* an RTIC application's `+idle+` task, which runs after `+init+`, never returns (https://rtic.rs/2/book/en/by-example/app_idle.html[the RTIC book]).

So a transport that started cannot be taken back out of runtime mode, and a refusal means the process exits and is restarted.

[[req-ssr-mode-init-failure]]
== Initialization failure

[.specitem,oft-sid="req~ssr-mode-init-failure~4",oft-title="Initialization failure",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*Refusals are errors.*
Every refusal during initialization or the transition, including one that a memory source, region helper or allocation provider used by setup reports, *MUST* be returned as an error that names its cause, the route where there is one, and the setter to change.

*No panic or abort.*
Element code in initialization *MUST NOT* panic or abort.
Where setup relies on a memory source, helper or provider, its stated contract, not the shape of its interface, decides what a request to it can do.

* A request that the contract lets panic or end the process, for a condition that setup can check, *MUST NOT* be sent unless setup has first excluded that condition, such as by checking the request against the limit the contract states.
Otherwise setup refuses it by name before relying on it.
* An outcome that the contract permits and that setup cannot exclude, such as an allocator that may end the process on exhaustion or wait for a lock, is that provider's declared policy (xref:heap.adoc#req-ssr-heap-declared[The heap class is declared, with no default]).
Setup reports it, and *MUST* refuse by name a configuration that requires the guarantee it violates (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name]).

Reporting a contract establishes nothing beyond it.

*One stated disposition.*
A refusal *MUST* leave each resource and each initialized value that setup acquired with one stated disposition:

* returned to its owner;
* destroyed once; or
* retained under the configuration's stated retention policy.

Setup *MUST* have that disposition before it takes or creates what it might have to dispose of, and the stated disposition *MUST* be the one that happens:

* _Returned._
A value that a caller handed to setup is returned to that caller untouched, or the refusal comes before setup takes it, such as by reserving what the value needs first.
* _Destroyed._
Setup destroys a value itself, once, within setup and on the refusing path, and the refusal then says that setup destroyed it.
It does so only in one of two cases:
** nothing in the configuration requires panic-free cleanup or non-waiting release of that value (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name]), and then what the destruction does is the value's own, under its declared policy where it has one, and the element establishes nothing about it;
** a route or a claim requires one of those guarantees of the value, and the guarantee is established for it.
* _Retained._
Setup retains only startup storage and what is placed in it, where every other duty of this item holds.

Where none of these is available for a value, setup *MUST* refuse before taking it.
A refusal never reports a value as untouched or turned away where setup has destroyed it or still owns it.

*No release service for a refusal.*
Setup *MUST NOT* hand anything to a release service, or leave it as pending cleanup, to dispose of a refusal.
It returns the refusal itself within setup's logical bound.

*What a refusal leaves behind.*
A refusal *MUST NOT*:

* release storage that a successful owner can still reach;
* leave a runtime-mode value;
* start traffic; or
* leave anything that stops a successor process from initializing.
--

[horizontal]
ID:: `+req~ssr-mode-init-failure~4+`
ASIL:: B
Allocated to:: the element
Verification:: test, review, fault-injection
* *test*
** Each refusal names its route and setter.
** A refusal injected at each placement and provider request, with every acquired value returned, destroyed once or retained as stated and no storage of a successful owner released.
** A refused caller input returned untouched, refused before it was taken, or destroyed once and reported as destroyed.
** Where a route requires panic-free cleanup or non-waiting release, no value for which it is not established destroyed by setup.
** Nothing handed to a release service.
** A request that a provider's contract lets panic for a condition setup can check prevented, or the provider refused by name.
** A provider whose contract permits an outcome that setup cannot exclude reported with it, and refused by name where the configuration requires the guarantee it violates.
* *review*
** No panic path in setup code.
** Every panic site in the middleware's setup read, and decided by group.
** Each relied-on source, helper and provider contract.
** Each destruction setup performs on refusal, including a dropped input, against its stated disposition and, where a guarantee is required, its evidence.
* *fault-injection*: a kill at each startup step.
Status:: Draft
ISO 26262:: 6-6.4.2 g (part-clause numbers only)

*Rationale.*
In a build that aborts on panic (xref:build.adoc#req-ssr-build-panic-abort[The ASIL build aborts on panic and checks overflow]), a setup mistake that panicked would end the process, and its restart would run straight into the same panic.
An error that names its cause, its route and the setter to change tells the integrator what to fix instead.

Leaving nothing behind lets a successor start cleanly, since it recovers what a dead predecessor left before it prepares a route (<<req-ssr-mode-restart,A restart is an initialization>>).

_Dispositions._
The fate of what a failed setup had acquired is stated, never left open.
A refusal may hand a value back to its caller, destroy one it took, or leave startup storage claimed, because startup memory is never given back in the process (xref:startup-memory.adoc#req-ssr-memory-sealed[Startup memory is sealed]).
Each is acceptable only when it is the stated one and also meets this item's other duties:

* none may free storage that an owner that succeeded still uses;
* a destruction during setup, such as dropping a refused input, is stated as what it is.

So naming an outcome does not by itself make it acceptable.

A value that setup was handed by value has to go somewhere when setup refuses.
Setup can hand it back untouched, or decide the refusal before it takes the value.
It cannot both own a value with a destructor and claim to have refused it untouched, so the disposition names the one that happens.
Where a route requires panic-free cleanup, the destruction is established or not performed, and elsewhere its behaviour is the value's own (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name]).

_Providers._
A standard allocation interface may let an allocator end the process on exhaustion or panic on a request it cannot serve, which a fallible call does not prevent.
So a provider's own contract decides what setup can rely on.

* A panic that setup can exclude by a check is excluded, on every configuration: sending a request that the contract says will panic would be a defect of setup.
* An outcome that no check excludes is the provider's stated behaviour.
An ordinary configuration runs with it reported, and a route that requires the guarantee which that outcome violates is refused by name, and no other route.

_Groups of transports._
This item does not ask a refused group of transports to roll back one that has already entered runtime mode (<<req-ssr-mode-entry,Entering runtime mode is one all-or-nothing operation>>).

_No release service._
Setup has no release service to lean on.
Using pending cleanup would let a setup failure leave work running after its refusal.
So a destruction that setup performs runs within setup, on the refusing path.
Where a route requires non-waiting release and the destruction could wait, the value is handed back or never taken.

_Ordinary setup._
An ordinary owning input and an ordinary allocator cannot show that a destruction can neither panic nor outlast setup's bound, or that exhaustion never ends the process.
So setup is not refused for want of those guarantees where no route or claim requires them.
Every refusal stays an error, element code stays free of panics, everything setup acquired gets one honest disposition, and the cleanup and exhaustion guarantees apply where a route or claim requires them.

[[req-ssr-mode-restart]]
== A restart is an initialization

[.specitem,oft-sid="req~ssr-mode-restart~1",oft-title="A restart is an initialization",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
* A restarted process *MUST* run the same initialization path as a first start.
* Each binding *MUST* recover or remove what a dead predecessor left before it prepares any route.
* The successor *MUST* reach runtime mode with stale predecessor state present.
* Peers that stayed up *MUST NOT* need anything from it.
--

[horizontal]
ID:: `+req~ssr-mode-restart~1+`
ASIL:: B
Allocated to:: the element
Verification:: fault-injection (a kill and restart at every startup step and during traffic)
Status:: Draft
ISO 26262:: 6-Table 15 (part-clause numbers only)

*Rationale.*
A process can die at any instruction (xref:../up-l1/peers.adoc#req-ssr-peer-failure-normal[Peer failure is normal input]), so what it held can be left in any state, and only the next initialization can deal with it.

Recovering through the one initialization path keeps a single tested way to start, instead of a second path that runs only after a failure.
A binding that cannot recover its predecessor refuses setup.

Other systems recover the same way:

* Hubris deliberately uses one code path to start a task at boot and to restart it (https://github.com/oxidecomputer/hubris/blob/da639495cb6a31cffda53b2b822334672dd0bd33/doc/tasks.adoc[Hubris's task documentation]).
* LoLa's take-over of shared memory runs on every start, with or without a crash before it (https://github.com/eclipse-score/communication/blob/f5e8f2c8a9247b025b1d425af399588e0264698a/score/mw/com/dependability/software_architectural_design/partial_restart/README.md[LoLa's partial-restart design]).

[[req-ssr-mode-no-shutdown]]
== No shutdown in runtime mode

[.specitem,oft-sid="req~ssr-mode-no-shutdown~1",oft-title="No shutdown in runtime mode",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
The element *MUST NOT* offer a shutdown, teardown or departure operation in runtime mode.

A process in runtime mode leaves by exit, crash or kill.
A correctness property of the element or of its peers *MUST NOT* depend on a destructor, an exit handler or a departure notice running.
--

[horizontal]
ID:: `+req~ssr-mode-no-shutdown~1+`
ASIL:: B
Allocated to:: the element
Verification:: review, fault-injection (peers survive a kill at representative points)
Status:: Draft
ISO 26262:: 6-7.4.5 (part-clause numbers only)

*Rationale.*
A process that crashes or is killed runs no destructor and no exit handler.
So a property that needed one would fail exactly when a peer fails.

Even without a crash, Rust does not promise that destructors run: `+mem::forget+` is safe, and `+process::exit+` skips them (https://doc.rust-lang.org/1.88.0/std/mem/fn.forget.html[Rust's `+mem::forget+` documentation]).

Liveness therefore comes from the service tick and the transport, never from a destructor.

[[req-ssr-mode-classic-excluded]]
== Classic routes never enter runtime mode

[.specitem,oft-sid="req~ssr-mode-classic-excluded~1",oft-title="Classic routes never enter runtime mode",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Classic `+UTransport+` and `+UMessage+` routes *MUST NOT* be able to enter runtime mode under any waiver.

Deployment data that puts a classic endpoint on an ASIL route, including a Streamer route, *MUST* be refused at setup by name.
--

[horizontal]
ID:: `+req~ssr-mode-classic-excluded~1+`
ASIL:: B
Allocated to:: the element
Verification:: compile-fail (a classic transport cannot stand where a two-mode setup is required), test (deployment data naming a classic endpoint)
Status:: Draft
ISO 26262:: 6-7.4.8 (part-clause numbers only)

*Rationale.*
The classic API allocates in the SDK's own code.
A waiver covers allocation inside a binding's middleware only, never in SDK or binding code (xref:waivers.adoc#req-ssr-waiver-scope[A waiver covers middleware and nothing else]).
So no waiver can admit a classic route.

The item keeps classic routes out of the two-mode contract.
It does not withdraw the classic API, which stays available for ordinary use outside that contract.
A compatibility re-export of a two-mode type from `+up-rust+` is not itself a classic route.

[[req-ssr-mode-bounded-startup]]
== Setup never waits without a bound

[.specitem,oft-sid="req~ssr-mode-bounded-startup~3",oft-title="Setup never waits without a bound",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*Bounded waits.*
An initialization step of the element's own *MUST NOT* wait without a bound.
A wait for a service or for the clock *MUST* have a bound from deployment data or from the binding's declared limit.
When the bound expires, setup *MUST* fail with an error naming what it waited for.

*Waits inside a declared allocation domain.*
A request to a memory source or allocation provider, and a destruction that a refusal performs, can wait inside the allocation domain that its declared policy names (xref:bounded-work.adoc#req-ssr-bound-wait[Every wait is bounded]).
That wait is the declared policy's, and setup reports it.
Each non-waiting guarantee limits its own operation in setup, and neither limits the other's (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name]):

* Where a route requires non-waiting acquisition, no request that setup makes for that route waits, or setup refuses the route by name.
* Where a route or a claim requires non-waiting release of a value, setup performs no destruction of that value that could wait, and disposes of it as <<req-ssr-mode-init-failure,Initialization failure>> states.
* Requiring one refuses nothing for the other: a declared wait in a request stands where only non-waiting release is required, and a declared wait in a refusal's destruction stands where only non-waiting acquisition is required.

*A missing peer.*
A missing peer *MUST NOT* fail setup: its route is admitted and reports that it waits for the peer, or its binding refuses the route by name.
In runtime mode, a route *MUST* treat a missing peer as silence, under its deadline.
--

[horizontal]
ID:: `+req~ssr-mode-bounded-startup~3+`
ASIL:: B
Allocated to:: the element
Verification:: test, fault-injection (a peer that never starts; a service that never appears)
* *test*
** A provider whose request can wait, reported on a route that does not require non-waiting acquisition, one that requires only non-waiting release included, and refused by name on a route that requires it.
** A refusal's destruction that can wait, performed and reported where nothing requires non-waiting release of the value, a route that requires only non-waiting acquisition included, and not performed where that guarantee is required of the value and not established.
Status:: Draft

*Rationale.*
Processes start and restart in any order (<<req-ssr-mode-restart,A restart is an initialization>>), so a peer that is not up yet is normal input, not a fault (xref:../up-l1/peers.adoc#req-ssr-peer-failure-normal[Peer failure is normal input]).

A wait without a bound would leave a process stuck in initialization with nothing to report.
A bound that expires ends setup with an error naming what was missing.

The bound is logical, as every wait of the element's own is (xref:bounded-work.adoc#req-ssr-bound-wait[Every wait is bounded]).
Setup fails with that error once it runs after the bound has passed, and a supervisor's own timeout covers a process that the OS does not run at all.

A destruction that setup performs on a refusal runs within setup, on the refusing path (<<req-ssr-mode-init-failure,Initialization failure>>).
Setup has no release service, so pending cleanup (xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]) does not reach it.

_An allocation domain's wait._
The bound is on the element's own waits.
A wait inside a declared allocation domain, an allocator's own lock included, is treated as xref:bounded-work.adoc#req-ssr-bound-wait[Every wait is bounded] states, because an ordinary provider cannot promise a bound for it.
