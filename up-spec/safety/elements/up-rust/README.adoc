= up-rust SEooC: Element Boundary and Overview
:toc: preamble

The key words "*MUST*", "*MUST NOT*", "*REQUIRED*", "*SHALL*", "*SHALL NOT*", "*SHOULD*", "*SHOULD NOT*", "*RECOMMENDED*", "*MAY*", and "*OPTIONAL*" in this document are to be interpreted as described in https://www.rfc-editor.org/info/bcp14[IETF BCP14 (RFC2119 & RFC8174)]

The element boundary, claims, build controls, strict mode and assumptions of use of one safety element out of context (SEooC).

NOTE: A safety element out of context is developed without a known item, in ISO 26262's sense: its requirements are assumed ones, and its assumptions of use say what an integrator has to provide (10-9).

== The element

[[req-ssr-element-boundary]]
=== The parts of the element, and element code

[.specitem,oft-sid="req~ssr-element-boundary~3",oft-title="The parts of the element, and element code",oft-needs="uman",oft-tags="SafetyUpRustCore,SafetyStreamer,SafetyBinding,SafetyWire"]
--
*The parts.*
The element is the up-rust SEooC.
It has the parts E1 to E7, each with its initialization-mode code: its builders, its admission, its validation of deployment data and its transition.

* *E1, the runtime path.*
** The two mode types and the transition between them.
** The handles of the communication layer once activated: publisher, subscriber, notifier, notification listener, RPC client and RPC server.
** Inbound slots, ready queues, the RPC call table and the peer table.
** The QoS checks, the TTL checks and the deadline monitor.
** Message identifiers, waiver records, route reports, counters and errors.
** The element's share of the handling of a frame's header, envelope and metadata.
** The element's side of the interface to a wire: the checked payload writer, and decoding into startup slots.
** The native wire.
** The element's hooks for end-to-end protection: the opaque call tag, protected refusal answers and route counters, with unprotected frames counted separately.
* *E2, the lending and handoff runtime contracts.*
The interfaces that a binding implements, which are binding setup, the lending runtime, the handoff runtime, the frame and lent transmit storage, and the service of the element that a binding calls, the runtime port.
No binding's implementation of them belongs to E2.
* *E3, startup memory.*
Its regions, their placement and their seal.
* *E4, the platform.*
The runtime platform (`now`, `unix_time_ms`, `wait`, `wake_one`, `wake_all`), the initialization-only platform (`entropy`, `prefault`), the shared signal, and each platform backend that is shipped with the element.
* *E5, the carrier primitives.*
Receive, send, park and the capacity check of a carrier route (xref:../../../up-l2/streamer.adoc#req-ssr-carrier-route[A carrier route takes each frame at its ingress and sends it at its egress]).
* *E6, the end-to-end protection wire (the E2E wire).*
An opt-in wire that wraps another wire (xref:../../../up-l1/wires/e2e.adoc#req-ssr-e2e-not-required[The element requires end-to-end protection on no route, outside strict mode's black-channel rule]; xref:../../../up-l1/wires/e2e.adoc[The end-to-end protection wire]).
* *E7, strict mode.*
An opt-in check, in initialization mode only, of the integrator's setup, in a component of its own (xref:build.adoc#req-ssr-crate-core-only-binary[The checked policy stays in the safety crate, and no admitted optional layer bypasses or reimplements it], clause "Strict mode's component"), with the read-only views of each route's declarations and the hook in the runtime path that it uses.
Its states, the severities of its findings and its rules: xref:strict-mode.adoc#req-ssr-strict-states[Strict mode has four states]; xref:strict-mode.adoc#req-ssr-strict-init-only[Strict mode checks in initialization only]; xref:strict-mode.adoc#req-ssr-strict-lock[The locked build allows only enforcement]; xref:strict-mode.adoc#req-ssr-strict-rules[The rules that strict mode checks]; xref:strict-mode.adoc#req-ssr-strict-ack-revision[An acknowledgement names a deviation by ID and revision]; xref:strict-mode.adoc#req-ssr-strict-report[Strict mode reports on every run].

*Element code.*
Element code is the code of the parts that belong to the element.
Code that runs on a runtime path but that the element does not own, such as the destructor of an owned value, an allocator's release or a dependency that they reach, is not element code.
Admitting a selected startup-provisioning helper or a selected serialized owned-value runtime adapter on the ASIL path (xref:../../profiles/up-rust-asil-b.adoc#req-ssr-element-configurations[The ASIL path and supported configurations]) does not enlarge element code and does not bring that helper, adapter, allocation provider or any dependency that it reaches into parts E1 to E7.

*Each part keeps its own requirements.*
Whom a requirement binds is stated in xref:../../../contract-generations.adoc#req-ssr-requirements-bind[A requirement binds the actors to which it gives a duty].
Belonging to the element moves no duty from one part to another.

*Outside the element.*
These are separately composed parts of their own outside element code, each with its own boundary, declarations, requirements, source-bound records and evidence, and none is a part of the element:

* each binding, with its middleware (xref:../../../up-l1/bindings.adoc#req-ssr-binding-scope[What a binding is, and the binding contract]);
* each wire other than the native wire and the end-to-end protection wire (xref:../../../up-l1/wires/README.adoc#req-ssr-wire-scope[What a wire is, and the wire contract]);
* each platform backend not shipped with the element, including a platform backend that an integrator supplies (xref:assumptions-of-use.adoc#aou-seooc-integrator-platform[A custom platform keeps the platform's rules]);
* the Streamer and the Streamer binary (xref:../streamer.adoc#req-ssr-streamer-scope[What the Streamer is, and the bounded-runtime Streamer profile]);
* each selected startup-provisioning helper and each selected serialized owned-value runtime adapter (xref:../../profiles/up-rust-asil-b.adoc#req-ssr-element-configurations[The ASIL path and supported configurations]), and every other optional layer, such as an allocation-aware layer, an application-role layer or an asynchronous layer, together with the scheduler that drives an asynchronous layer;
* each memory or allocation provider, scheduler integration and adapter (xref:../../../contract-generations.adoc#req-sdk-owned-frame-contract[The owned-frame SDK contract binds the parts that declare it]).

The Streamer uses the carrier primitives of E5.
A requirement whose statement gives a duty only to the element, to element code or to a part of the element gives the Streamer no duty.
The application's own logic, the safety function of the item, in ISO 26262's sense, with its hazards, its fault tolerant time interval, its workload and its safe state, the operating system, the hardware, the supervisor, the clock source and the deployment data are outside the element too, and the assumptions of use cover them.

*Composition.*
A deployment conformance claim (xref:../../../contract-generations.adoc#req-ssr-contract-transition[What a part declares and claims, and when a replacement takes effect]) covers the parts that the deployment's profile selects (xref:../../profiles/up-rust-asil-b.adoc#req-ssr-element-configurations[The ASIL path and supported configurations]).
Running in one process, being linked into one binary or being kept in one repository establishes no claim and merges no requirements.
A composition that is claimed as one unit has its own explicit boundary, the revisions of its parts and of their named profiles with their dependency closure, its lifecycle, its assumptions of use and its evidence.

*Composition-package releaser and role accountability.*
Across the element and the separately composed parts that work with it, accountability is divided among five distinct roles:

* *Component producers.*
  Each component producer (supplier of a part composed with the element) *MUST* retain responsibility for its component's allocated requirements, source-bound records, proof obligations, evidence and source-level `+unsafe+` obligations for the code that it owns (xref:../../assurance.adoc#req-ssr-unsafe-inventory[Every `unsafe` is inventoried and justified]; xref:../../assurance.adoc#req-ssr-binding-unsafe-inventory[A binding inventories its own `unsafe`]; xref:../streamer.adoc#req-ssr-streamer-memory-safety[The Streamer's own code cannot cause undefined behaviour, and its `unsafe` is inventoried]).
  Tests and runs under Miri do not substitute for those source-level `+unsafe+` obligations.
* *Releaser of a supported composition package.*
  The composition-package releaser's canonical normative duties—owning and answering for the package's compatibility statement, assembled supplier evidence, sizing disclosures, helper or adapter scope declarations, composition-package deviation records (identifier, revision, scope, bounds, evidence and lapse date) and known-failure separation—are stated in xref:../../profiles/up-rust-asil-b.adoc#req-ssr-element-configurations[The ASIL path and supported configurations].
* *Element supplier.*
  For each element-supported configuration package that it provides, the element's supplier is that releaser and retains release responsibility for that package under xref:../../profiles/up-rust-asil-b.adoc#req-ssr-element-configurations[The ASIL path and supported configurations].
* *Explicit extension composer.*
  An explicit extension composer's canonical normative duties when assembling and releasing a composition package or extension beyond an element-supported configuration package—including assuming composition-supplier responsibility and not silently labeling or presenting that extension as element-supplier-supported—are stated in xref:../../profiles/up-rust-asil-b.adoc#req-ssr-element-configurations[The ASIL path and supported configurations].
* *Integrator.*
  The integrator matches its deployment against the selected package or extension and validates every applicable assumption of use for the item (xref:assumptions-of-use.adoc#aou-seooc-assumptions-bind[An assumption of use binds the integrator who claims the scope, and replaces no requirement]).
  A bundle of individually reviewed or evidenced parts is not proof of their combination; where no supplier offers a needed composition, that gap is recorded; an application user is not silently made a supplier, and an integrator assumes extension-supplier duties only where it deliberately creates and declares a custom extension.

*The derive and test tooling.*
The element's derive is a build input, and no part of the element at run time.
What holds for the code that it generates, and who accounts for that code, is stated in xref:../../assurance.adoc#req-ssr-unsafe-inventory[Every `unsafe` is inventoried and justified].
The application code around generated code is not element code.
Test tooling, such as heap observers, contract suites and test doubles, is no part of the element.

*Scoped replacement.*
This revision replaces revision 2 of this item for the element and for each component producer (supplier of a part composed with the element), preserving parts E1 to E7 and element code unchanged while explicitly classifying selected startup-provisioning helpers, serialized owned-value runtime adapters, memory and allocation providers and non-shipped platform backends as separately composed parts outside element code and establishing component-producer accountability and element boundary separation (with composition-package-releaser and explicit-extension-composer obligations kept canonically in xref:../../profiles/up-rust-asil-b.adoc#req-ssr-element-configurations[The ASIL path and supported configurations]).

*Rationale.*
Faults of initialization-mode code show before traffic starts, but a wrong admission decision becomes a runtime fault, so the transition is safety-relevant.
Parts that are built, released and qualified apart can be combined in many ways, so a duty stays with the part to which its requirement gives it, whatever is linked or deployed beside it.
Keeping admitted startup-provisioning helpers, serialized owned-value runtime adapters and memory or allocation providers outside element code prevents optional helper admissions from silently enlarging the safety element's boundary, while separating component-producer duties here from the composition-package-releaser and explicit-extension-composer duties in xref:../../profiles/up-rust-asil-b.adoc#req-ssr-element-configurations[The ASIL path and supported configurations] and the integrator duties in xref:assumptions-of-use.adoc#aou-seooc-assumptions-bind[An assumption of use binds the integrator who claims the scope, and replaces no requirement] ensures each responsibility has one canonical normative home.
