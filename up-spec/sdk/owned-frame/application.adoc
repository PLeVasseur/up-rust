= Owned-frame SDK: application roles and scheduler integration
:toc: preamble

The key words "*MUST*", "*MUST NOT*", "*REQUIRED*", "*SHALL*", "*SHALL NOT*", "*SHOULD*", "*SHOULD NOT*", "*RECOMMENDED*", "*MAY*", and "*OPTIONAL*" in this document are to be interpreted as described in https://www.rfc-editor.org/info/bcp14[IETF BCP14 (RFC2119 & RFC8174)]

Conventions and tags: xref:README.adoc[the owned-frame SDK area's README].

This page holds what an SDK offers an application above its core, on owned-frame routes:

* the application roles, the handles that an application keeps for them, and their defaults;
* what a layer above the core leaves as it is: the route, and each result of the core;
* the kinds of message operation, the asynchronous layer, and the scheduler integrations that join that layer to a scheduler.

What the SDK, the core and a layer above the core are, and whom an item of this area binds, is stated in xref:README.adoc#req-sdk-owned-frame-contract[The owned-frame SDK contract binds the parts that declare it].

[[req-sdk-owned-frame-roles]]
== Each application role is offered on its own, as one family for both kinds of route

[.specitem,oft-sid="req~sdk-owned-frame-roles~1",oft-title="Each application role is offered on its own, as one family for both kinds of route",oft-needs="impl,utest,uman",oft-tags="OwnedFrameSdk"]
--
*The roles.*
The application roles take their names and messaging patterns from the xref:../../up-l2/api.adoc[Communication Layer APIs] of uP-L2: publisher, subscriber, notifier, notification listener, RPC client and RPC server.
The application-role layer is the layer above the core through which an application declares and uses roles on owned-frame routes.
It is not the classic Communication Layer APIs, which keep their contract beside it (xref:README.adoc#req-sdk-owned-frame-classic-apis[The classic APIs keep their contract beside owned-frame routes]).

*On its own.*
Where an SDK offers an application-role layer, the layer *MUST* let an application declare and use any subset of the roles that it offers.
The layer *MUST NOT* make a role require an object of another role.
The layer *MUST NOT* make an object that carries every role a precondition of using a role.

*Peers apart.*
The layer *MUST NOT* require, for the use of a role, its peer role (the other role of its messaging pattern) in the same application or process.
The layer *MUST NOT* require, for the use of a role, a declaration of its peer role, or a declaration object that is created once for both.
The topic or method and its message types, on which peers agree, are no such declaration.

*One family.*
Where the layer offers a role on native and on serialized routes, the layer *MUST* offer it as one family for both: one way to declare the role and one set of operations, apart from the differences that the route's form makes (xref:../../safety/up-l1/payload-paths.adoc#req-ssr-payload-route-form[A route's form is fixed at setup, by what the route declares and never by a name]) in how a payload is written, read, owned and allocated, and in what encoding and decoding can return.
The layer *MUST* state in its documentation, with the role, each such difference.

*Both levels.*
The layer *MUST* make each role usable by an application that implements no binding, no wire and no memory provider of its own.
Use without the application-role layer: a layer above the core is one that an application can leave out (xref:README.adoc#req-sdk-owned-frame-contract[The owned-frame SDK contract binds the parts that declare it]); where the core is the element, xref:../../safety/seooc-up-rust/crate-isolation.adoc#req-ssr-crate-core-only-binary[The checked policy stays in the safety crate, and no admitted optional layer bypasses or reimplements it] keeps the element's checked policy usable without any optional application layer.
--

Allocated to:: the SDK's application-role layer
Verification:: test, review
* *test*
** Each role declared and used alone, by an application that declares no other role.
** Each role used with its peer role in another process, and with no peer.

*Rationale.*
An application often needs one role, such as a publisher, while the peers of that role run in other processes and are deployed on their own.
A role that needed another role's object, its peer in the same process or a declaration made once for both peers would make such an application build and run what it does not use.
Peers still agree on their topic or method and its message types, which is what lets them talk.
One family for both kinds of route lets an application change a route's wire while it keeps how it declares the role and which operations it uses.
Only what the route's form decides can differ: how a payload is written, read, owned and allocated, and what encoding and decoding can return.
Most applications only send and receive messages, so a role that needed them to implement a binding, a wire or a memory provider would keep them from using it.

[[req-sdk-owned-frame-handles]]
== A role's handle names no binding, wire, provider or scheduler, and setup makes those choices

[.specitem,oft-sid="req~sdk-owned-frame-handles~1",oft-title="A role's handle names no binding, wire, provider or scheduler, and setup makes those choices",oft-needs="impl,utest",oft-tags="OwnedFrameSdk"]
--
*Handles.*
The application-role layer *MUST NOT* name a binding, a middleware, a wire or its codec, a memory provider or a scheduler in the type of the handle that an application keeps for a role, or in that handle's operations.
In the type of a role's handle and in that handle's operations, the layer *MUST NOT* name anything of the application's domain other than the role and the message types of its topic or method.

*Choices at setup.*
A role's transport, wire, QoS and memory provider are chosen in initialization, when the role is declared.
Where the core is the element, none of them changes in runtime mode (xref:../../safety/seooc-up-rust/runtime-modes.adoc#req-ssr-mode-no-setup-at-runtime[Setup is impossible in runtime mode]), and how a route's QoS is declared or given its one documented default is stated in xref:../../safety/seooc-up-rust/qos.adoc#req-ssr-qos-declared[QoS is declared per route at setup].
The layer *MUST NOT* require the application to name one of them again, or to name a scheduler, in an operation on a handle.

*No placeholder.*
The layer *MUST NOT* require, to declare a role, a value or a type that names a binding, a middleware, a wire or its codec, a memory provider or a scheduler that the application has not chosen for the role.

*Every wire alike.*
Where the SDK lets an application select a wire, the SDK *MUST* offer that selection through interfaces that are the same for every wire.
An interface that names one wire or one payload format *MAY* be offered by that wire's own part.
The SDK *MUST NOT* make such an interface part of its core or of a layer above its core.
--

* *test*

** A handle of each role kept in a type of the application's own that names no binding, middleware, wire, codec, memory provider or scheduler.

** Each role declared with only the choices that the application made.

* *review*: each handle's type and operations, which name no binding, middleware, wire, codec, memory provider or scheduler, and of the application's domain at most the role and its message types; each role's declaration, which takes no value or type that names a choice not made; the interfaces that select a wire, the same for every wire; the core and each layer above it, which hold no interface that names one wire or one payload format.

*Rationale.*
An application keeps its handles in its own types and passes them through its own code.
A handle that named its binding, wire, memory provider or scheduler would carry a deployment choice into every place that holds it, so changing that choice would change the application.
Making each choice once, at setup, keeps it in one place.
A value that names an engine or a codec that the application never chose is a value with no meaning that the application still has to write.
One way of selecting every wire keeps the core and the roles free of any one format, while a wire's own part can still offer a shorthand for it.

[[req-sdk-owned-frame-defaults]]
== Each default is stated where it applies, with the way to change it

[.specitem,oft-sid="req~sdk-owned-frame-defaults~1",oft-title="Each default is stated where it applies, with the way to change it",oft-needs="impl,utest,uman",oft-tags="OwnedFrameSdk"]
--
*First use.*
The application-role layer *MUST* let an application declare and use a role by stating only what has no default.

*A default is a stated choice.*
Wherever the layer makes a choice that the application did not state, the layer *MUST* state in its documentation, at the interface where the choice applies, what the default is and how the application changes it.

*One setting at a time.*
Where an application states one more setting, the layer *MUST NOT* require it to restate a setting that the new one does not depend on, or to use another role family or another kind of handle.
The layer *MUST* state in its documentation, with each setting, the other settings that it depends on.

*No default where a declaration is required.*
The layer *MUST NOT* supply a default for a setting that an item requires to be declared (xref:../../safety/seooc-up-rust/heap.adoc#req-ssr-heap-declared[The heap class is declared, with no default]).

*Shown.*
Where the core is the element, what a route got, the QoS in force among it, is in its report: xref:../../safety/seooc-up-rust/errors.adoc#req-ssr-error-route-report[Each route reports what it got].
--

[horizontal]
ID:: `+req~sdk-owned-frame-defaults~1+`
Allocated to:: the SDK's application-role layer
Verification:: test, review
* *test*
** Each role declared and used by stating only the settings that have no default.
** One more setting stated with only the settings that its documentation says it depends on, and with the same role family and kind of handle.
** A declaration that leaves unstated a setting that an item requires to be declared, such as a route's heap class, with no default supplied for it.

*Rationale.*
An application starts with the few settings that have no default, and adds others when it needs them.
A default that the documentation does not state where it applies is a choice that the application makes without knowing it.
Adding one setting without restating the rest keeps a small change small, and a setting that depends on another says so where it is documented.
A setting that an item requires to be declared has no default, because a default would let a route pass as declared when nothing was declared.

[[req-sdk-owned-frame-layer-results]]
== A layer above the core keeps its route as admitted, and passes on each result with its meaning

[.specitem,oft-sid="req~sdk-owned-frame-layer-results~1",oft-title="A layer above the core keeps its route as admitted, and passes on each result with its meaning",oft-needs="impl,utest",oft-tags="OwnedFrameSdk"]
--
*The same route.*
Each layer above the core *MUST* run each operation that it offers on the route that setup admitted, in the route's admitted form.
The layer *MUST NOT* change an operation's wire, form or QoS, or who owns what the operation takes or returns.
The layer *MUST NOT* serve an operation in a form other than the route's admitted form, such as a native operation by a serialized one, or a view by a copy (xref:../../safety/up-l1/payload-paths.adoc#req-ssr-payload-route-form[A route's form is fixed at setup, by what the route declares and never by a name]).

*Nothing added.*
On the path of an operation that it offers, the layer *MUST NOT* add:

* a copy or a staging of the payload (xref:../../safety/up-l1/payload-paths.adoc#req-ssr-payload-written-once[A payload is written once, into the storage that carries it]);
* in runtime mode on a native route, an allocation or a free of the layer's own, or one that it causes in a memory provider (xref:../../safety/seooc-up-rust/heap.adoc#req-ssr-heap-none[No heap in runtime mode on a native path]);
* in runtime mode on another route, where the core is the element, an allocation or a free of the layer's own, or one that it causes in a memory provider and that the route's heap class does not admit (xref:../../safety/seooc-up-rust/heap.adoc#req-ssr-heap-declared[The heap class is declared, with no default]);
* a retry of an operation that may already have been submitted.

What the scheduler work that an operation causes keeps on a native path of the element is stated in xref:../../safety/seooc-up-rust/build.adoc#req-ssr-async-seam[The asynchronous interface has a written, executor-independent contract]; on another route, its scheduler integration states what that work can allocate and what heap memory it can release (<<req-sdk-owned-frame-scheduler-integration,A scheduler integration supplies wake-ups, timers and contexts through public interfaces>>).
What the layer may offer as a nonblocking attempt or as a progress step: <<req-sdk-owned-frame-operation-kinds,Each message operation is a nonblocking attempt, a bounded wait or asynchronous, and none hides a wait>>.

*Pending state.*
A layer that offers an operation that completes later *MAY* keep the state that represents the operation while it is pending, within the limits of the list above.
Where the core is not the element, the layer *MUST* submit or give back each transmit loan before its operation returns pending.
For the element, xref:../../safety/seooc-up-rust/build.adoc#req-ssr-async-seam[The asynchronous interface has a written, executor-independent contract] states this.

*Results.*
The layer *MUST* pass on each result of the core's operation with its meaning: a refusal with its cause, a count with what it covers and whether it is complete, and a loss or a partial delivery as that (xref:../../safety/seooc-up-rust/errors.adoc#req-ssr-error-no-silent-loss[No silent loss, and each loss counted once]).
The layer *MUST* pass a result that arrives after the operation returned pending to the caller in the operation's completion.
The layer *MUST NOT* report an unknown or partial delivery as delivered or consumed.

*Modes.*
The layer *MUST* offer setup only in initialization, and traffic only in runtime mode (xref:../../safety/seooc-up-rust/runtime-modes.adoc#req-ssr-mode-no-setup-at-runtime[Setup is impossible in runtime mode]; xref:../../safety/seooc-up-rust/runtime-modes.adoc#req-ssr-mode-no-traffic-before-runtime[Traffic is impossible before runtime mode]).
Where the types of its interface cannot rule out a setup operation after the transition, or a traffic operation before it, such as at an entry point of a C interface, the layer *MUST* refuse that operation with a named result and change nothing.
Where the SDK's core is not the element, the core *MUST* meet each duty of this clause for the setup and traffic operations that it offers.

A layer above the core is where an application meets its routes, so whatever the layer adds, every application that uses it gets.
A copy, an allocation or a retry added there would change what a route does, while the core's guarantees still appeared to hold.

An operation that completes later needs its state while it is pending, and keeping that state changes nothing that the route does, where a transmit loan held across the wait would.
A retry of an operation that may already have been submitted can deliver a message twice.
A result whose meaning changed on its way up would have the application react to something that did not happen.
Where the language or the interface cannot keep the two modes apart by type, a refusal by name is what keeps them apart.

[[req-sdk-owned-frame-operation-kinds]]
== Each message operation is a nonblocking attempt, a bounded wait or asynchronous, and none hides a wait

[.specitem,oft-sid="req~sdk-owned-frame-operation-kinds~1",oft-title="Each message operation is a nonblocking attempt, a bounded wait or asynchronous, and none hides a wait",oft-needs="impl,utest,uman",oft-tags="OwnedFrameSdk,OwnedFrameScheduler"]
--
*Message operations.*
A message operation is an operation that the SDK offers on an owned-frame route to send, publish, notify, receive, invoke or respond.
An idle wait, which xref:../../safety/seooc-up-rust/bounded-work.adoc#req-ssr-bound-wait[Every bounded wait has a logical deadline] permits where the transport's documented contract supports it and while no bounded operation, timeout or deadline check is due, is not a message operation.

*Waiting.*
In this item, a call waits where, before it returns, it waits for a peer, for middleware, for route capacity or for time, or makes a blocking operating-system call.
A wait inside a route's declared allocation domain is no wait in this sense on a serialized route whose declared heap class admits allocation, where the route's declared policy states it, and not in an acquisition on a route that requires non-waiting acquisition or in a release on a route that requires non-waiting release; for the element, xref:../../safety/seooc-up-rust/bounded-work.adoc#req-ssr-bound-wait[Every bounded wait has a logical deadline] states when it admits such a wait.
A wait inside the scheduler work that a call causes, as its scheduler integration states that work (<<req-sdk-owned-frame-scheduler-integration,A scheduler integration supplies wake-ups, timers and contexts through public interfaces>>), is no wait in this sense either.

*Three kinds.*
For each message operation that it offers, the SDK *MUST* state in its documentation which one of three kinds the operation is:

* A nonblocking attempt is a call that returns without waiting, with the operation's result or with a result that says that the operation cannot proceed now.
* A bounded synchronous wait is a call that can wait in its caller, and that takes a logical deadline.
* An asynchronous operation proceeds by progress steps, each a call that returns without waiting, with a completion or with pending.

*Kept apart.*
The SDK *MUST* offer each message operation whose call can wait as a bounded synchronous wait, separate from its nonblocking attempts and its asynchronous operations.
In a nonblocking attempt or in a progress step on an owned-frame route, the SDK *MUST NOT* make a call that waits, the call of a bounded synchronous wait included.

*Every layer.*
A part offers an operation as a nonblocking attempt or as a progress step where its documentation, or the contract of the interface through which it offers the operation, says that the operation returns without waiting.
Each layer above the core, each adapter and each scheduler integration *MUST NOT* offer, as a nonblocking attempt or as a progress step, a call that waits.

*Bounded synchronous waits.*
Where the SDK's core is the element, how the element's own waits take and keep a logical deadline is stated in xref:../../safety/seooc-up-rust/bounded-work.adoc#req-ssr-bound-wait[Every bounded wait has a logical deadline].
For each other bounded synchronous wait that it offers on an owned-frame route, the SDK, each layer above the core and each adapter *MUST* meet what the clauses "Every other wait" and "What a deadline decides" of that item require of the element for a wait of its own.

*Overflow.*
Where a route's overflow policy waits (xref:../../safety/seooc-up-rust/qos.adoc#req-ssr-qos-overflow[Overflow acts as declared]), the SDK *MUST* make that wait only in a bounded synchronous wait.
In its place, the SDK *MUST* have a nonblocking attempt return a result that says that it cannot proceed now, and a progress step return pending.

*Progress steps of the element.*
Where the SDK's core is the element, a progress step of the element, or of an asynchronous layer that implements the element's asynchronous interface, is governed by xref:../../safety/seooc-up-rust/build.adoc#req-ssr-async-seam[The asynchronous interface has a written, executor-independent contract], and the clauses of this item on progress steps do not apply to it.

*The Communication Layer.*
What uP-L2 requires of each implementation of its Communication Layer APIs: xref:../../up-l2/api.adoc[Communication Layer APIs].

*Rationale.*
A caller that runs many tasks in one context needs to know whether a call can hold that context.
A call that looked nonblocking but waited inside would stop every task in that context until the wait ended.
Keeping each wait in an operation of its own kind, with a logical deadline, lets the caller choose where waiting happens.
Whether a call waits is what matters: an asynchronous receive that awaits a peer across its steps makes no call that waits, while a step that blocks does.
A wait inside a route's declared allocation domain, such as an allocator's lock, is the domain's only where the route's declared policy states it, and a route that cannot accept it requires the guarantee that excludes it.
A scheduler's own work in a wake-up or a timer is stated by its integration, and is the scheduler's rather than the step's.
An idle wait serves a transport while nothing is due and carries no message, so it is none of these kinds.
The element's progress steps already have their contract in the safety area, so this item adds nothing to them.

[[req-sdk-owned-frame-async-layer]]
== Asynchronous operations come from one layer that needs no host library and no allocator

[.specitem,oft-sid="req~sdk-owned-frame-async-layer~1",oft-title="Asynchronous operations come from one layer that needs no host library and no allocator",oft-needs="impl,utest,uman",oft-tags="OwnedFrameSdk"]
--
*The asynchronous layer.*
The asynchronous layer is the layer above the core that offers asynchronous operations on owned-frame routes over the core's synchronous or polled ones (xref:../../safety/seooc-up-rust/crate-isolation.adoc#req-ssr-crate-sync-path[Traffic is synchronous or polled]).

*One layer.*
An SDK that offers asynchronous operations on owned-frame routes *MUST* offer them through one asynchronous layer, with the same operations and the same contract whichever scheduler runs them, apart from an operation that a configuration cannot support, as "Unsupported compositions" states.
For asynchronous operations on owned-frame routes, the SDK *MUST NOT* offer, for one scheduler, an operation, an ownership rule or a deadline rule that differs from the one that it offers for another.

*Its contract.*
Where the SDK's core is the element, the asynchronous layer's contract is the one that xref:../../safety/seooc-up-rust/build.adoc#req-ssr-async-seam[The asynchronous interface has a written, executor-independent contract] states.
Any other SDK that offers asynchronous operations on owned-frame routes *MUST* state, in the documentation of its asynchronous layer, a contract that names, for each asynchronous operation, what that item requires the element's contract to name.
That SDK's asynchronous layer *MUST* keep, with that SDK in the element's place, what that item requires under "1. Progress" of a step that returns pending, its properties "2. Concurrent waiters", "3. Abandonment and commit" and "5. Deadlines", and what it requires under "4. Lifetime" of an operation that safe code forgot.
In that item, for a route of that SDK that has no declared policy, the policy that is stated by the memory provider to which the SDK sends the operation's requests, as xref:providers.adoc#req-sdk-owned-frame-provider-selection[The selected memory provider is the only one used, and selecting it claims nothing] states, takes the place of the route's declared policy.

*What it does not need.*
The asynchronous layer *MUST NOT* require a particular scheduler, a host operating system's library or an allocation provider.
A scheduler integration can need a host operating system's library or an allocation provider for its own work; what it states of that work: <<req-sdk-owned-frame-scheduler-integration,A scheduler integration supplies wake-ups, timers and contexts through public interfaces>>.

*Unsupported compositions.*
Where a configuration cannot give an asynchronous operation on owned-frame routes what it needs, such as storage for its pending state, wake-ups, timers or a context to run in, the SDK *MUST* either not offer that operation in that configuration or refuse it at setup with a result that names what is missing.

*Without it.*
The SDK *MUST* keep a role's synchronous operations usable with no scheduler and without the asynchronous layer.

*Apart from roles.*
The asynchronous layer is not the application-role layer.
What a role is, and how it is declared, are stated by <<req-sdk-owned-frame-roles,Each application role is offered on its own, as one family for both kinds of route>>, <<req-sdk-owned-frame-handles,A role's handle names no binding, wire, provider or scheduler, and setup makes those choices>> and <<req-sdk-owned-frame-defaults,Each default is stated where it applies, with the way to change it>>, for synchronous and asynchronous use alike.

*A scheduler's resources.*
What the scheduler work that an operation causes means for a native path of the element is stated in xref:../../safety/seooc-up-rust/build.adoc#req-ssr-async-seam[The asynchronous interface has a written, executor-independent contract].
--

ID:: `+req~sdk-owned-frame-async-layer~1+`
Allocated to:: the SDK, for offering any asynchronous operations on owned-frame routes through one asynchronous layer, alike for every scheduler, for stating that layer's contract where its core is not the element, for not offering, or refusing by name, such an operation that a configuration cannot support, and for keeping a role's synchronous operations usable with no scheduler and without that layer; the SDK's asynchronous layer, for requiring no particular scheduler, no host operating system's library and no allocation provider, and, where the SDK's core is not the element, for keeping the properties of the asynchronous interface's contract that the clause "Its contract" names
Verification:: test, gate, review
* *test*
** The same controls of the asynchronous layer under two scheduler integrations of different kinds, one of them for a target with no host operating system's library and no allocation provider, with the same results.
** A configuration that cannot give an asynchronous operation storage for its pending state, a wake-up, a timer or a context: the operation not offered, or refused at setup with what is missing named.
** A role's synchronous operations used with no scheduler, in a build without the asynchronous layer.
** For an SDK whose core is not the element, under each scheduler integration that it ships: readiness before, during and after registration; spurious and coalesced notifications; several waiters on one route, an older one abandoned after a newer registration; abandonment before and after submission; a forgotten operation; and a completion first offered after its deadline, refused.
* *gate*: the dependencies of the asynchronous layer, which include no particular scheduler, no host operating system's library and no allocation provider.
* *review*
** The asynchronous operations that the SDK offers on owned-frame routes, all through one asynchronous layer, with no operation, ownership rule or deadline rule offered for one scheduler that differs from the one offered for another.
** For an SDK whose core is not the element: the documented contract of its asynchronous layer, which names for each asynchronous operation what the element's contract names, and the layer's steps, registrations, notifications, completions and handles, against the properties that the clause "Its contract" names.

*Rationale.*
Applications run under very different schedulers, from a host's thread pool to one loop on a device with no operating system and no heap.
One layer with one written contract lets the same application code, and the same verification, serve all of them.
A layer for each scheduler would multiply the contracts and let their rules drift apart.
Another SDK's asynchronous layer can miss a notification, overwrite another operation's registration or accept a late result as easily as the element's, so it keeps the same properties.
A layer that needed a host library or an allocator would exclude the smallest targets.
A configuration that lacks what an operation needs learns so at setup, where a substitute chosen without a word would change the operation.
Synchronous operations that need no scheduler leave the simplest deployments free of one.

[[req-sdk-owned-frame-scheduler-integration]]
== A scheduler integration supplies wake-ups, timers and contexts through public interfaces

[.specitem,oft-sid="req~sdk-owned-frame-scheduler-integration~1",oft-title="A scheduler integration supplies wake-ups, timers and contexts through public interfaces",oft-needs="impl,utest,uman",oft-tags="OwnedFrameScheduler,OwnedFrameSdk"]
--
*A scheduler integration.*
A scheduler integration is the part that joins the asynchronous layer to one scheduler.
It turns the layer's notifications into that scheduler's wake-ups, supplies the timers that cause another progress step, and runs progress steps in that scheduler's contexts.

*Selection.*
An SDK that offers asynchronous operations on owned-frame routes *MUST* let an application select a scheduler integration.
How it offers that selection, so that any party can write one: xref:providers.adoc#req-sdk-owned-frame-extension-public[A part that an application selects is selected through public interfaces alone].
The SDK *MUST NOT* use, in a scheduler integration that it ships, an interface that is not public and documented.

*Wake-ups.*
For each pending operation that registered for a notification, a scheduler integration *MUST* turn the notification into a wake-up that gives that operation another progress step.
It *MAY* turn several notifications into one wake-up, and *MAY* deliver a wake-up for which no notification came.
How each pending operation keeps its own registration, through replacement and abandonment, is stated in xref:../../safety/seooc-up-rust/build.adoc#req-ssr-async-seam[The asynchronous interface has a written, executor-independent contract], under "Concurrent waiters"; for an SDK whose core is not the element, <<req-sdk-owned-frame-async-layer,Asynchronous operations come from one layer that needs no host library and no allocator>> applies it.

*Timers and outcomes.*
A scheduler integration *MUST NOT* decide an operation's outcome, its deadline or its lateness.
What a scheduler's timer may do is stated in xref:../../safety/seooc-up-rust/build.adoc#req-ssr-async-seam[The asynchronous interface has a written, executor-independent contract], under "Deadlines"; for an SDK whose core is not the element, <<req-sdk-owned-frame-async-layer,Asynchronous operations come from one layer that needs no host library and no allocator>> applies it.

*Contexts.*
A scheduler integration *MUST* call the layer only from the contexts that the layer's contract admits (<<req-sdk-owned-frame-async-layer,Asynchronous operations come from one layer that needs no host library and no allocator>>).
It *MUST* state, in the documentation that is released with it, the contexts in which it runs progress steps.

*Resources.*
A scheduler integration *MUST* state, in the documentation that is released with it, for the scheduler work that an operation causes (its registration, its wake-ups, its timers and the end of its task), what that work can allocate, what heap memory it can release and whether it can wait or panic.
It *MUST* state as unknown what it does not know.
That statement establishes no guarantee (xref:../../safety/seooc-up-rust/build.adoc#req-ssr-async-seam[The asynchronous interface has a written, executor-independent contract]; xref:../../safety/seooc-up-rust/heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name, and admitted or refused]).

*No added service.*
For the element, that using the asynchronous interface adds no service duty to the application is stated in xref:../../safety/seooc-up-rust/build.adoc#req-ssr-async-seam[The asynchronous interface has a written, executor-independent contract], under "Service".
--

[horizontal]
ID:: `+req~sdk-owned-frame-scheduler-integration~1+`
Allocated to:: each scheduler integration; the SDK, for letting an application select a scheduler integration where it offers asynchronous operations on owned-frame routes, and for using only public, documented interfaces in the scheduler integrations that it ships
Verification:: test, review
* *test*
** A scheduler integration written outside the SDK, against its public, documented interfaces alone, selected by an application and driving the asynchronous layer's operations.
** Each notification for a pending operation that registered for it turned into a wake-up, with that operation taking another progress step.
** Several notifications turned into one wake-up, and a wake-up for which no notification came, with every outcome unchanged.
** A timer that fires before, at and after an operation's deadline, with the operation's outcome and lateness decided as the layer's contract states, and not by the scheduler integration.
** Progress steps called only from the contexts that the layer's contract admits.
* *review*: the interfaces that each scheduler integration that the SDK ships uses, which are public and documented; each scheduler integration's statements of the contexts in which it runs progress steps and, for the scheduler work that an operation causes, of what that work can allocate, what heap memory it can release and whether it can wait or panic, an unknown as unknown, including task-end work that releases heap memory without acquiring any; no path on which a scheduler integration decides an operation's outcome, its deadline or its lateness.

*Rationale.*
The asynchronous layer cannot know how each scheduler wakes a task, keeps time or assigns contexts, so a separate part supplies that for one scheduler.
An SDK whose asynchronous operations ran on one scheduler alone would lock its applications into it, so an application selects the integration, and any party can write one.
A lost wake-up would leave an operation pending for ever, while an extra one, or one that stands for several notifications, costs only a progress step.
Outcomes and deadlines are decided under the layer's contract, so that they do not change with the scheduler.
A scheduler's own work can allocate, free heap memory, wait or panic where the layer cannot see it, so the integration states what that work does.
