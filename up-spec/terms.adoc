== General Terms

.General Terms
|===
|Term |Definition

|https://mqtt.org/[MQTT] |A transport for messages that follows the publish/subscribe pattern and needs few resources
|https://www.rfc-editor.org/rfc/rfc3986[URI] |Uniform Resource Identifier, as RFC 3986 defines it
|https://oauth.net/2/[OAuth 2.0] |The protocol that industry uses as its standard for authorization.
|https://en.wikipedia.org/wiki/Hostname[hostname] |A label given to a device on a computer network, by which that device is identified in electronic communication of various kinds
|https://en.wikipedia.org/wiki/Domain_name[Domain Name] |A textual identifier that marks out a part of the Internet in which an administration has autonomy, authority or control. Domain names are put to use in many settings of networking, and for the naming and addressing that particular applications need. As a rule, a domain name stands for a network domain
|https://en.wikipedia.org/wiki/Domain_Name_System[Domain Name System (DNS)] |The naming system, hierarchical and decentralized, that identifies the computers, services and other resources that can be reached over the Internet or another Internet Protocol (IP) network
|FQDN |Fully qualified domain name 
|https://en.wikipedia.org/wiki/Entity-control-boundary[Entity-Control-Boundary Pattern (ECB)] a|
A pattern of software architecture, used in object-oriented design that is driven by use cases. It sorts the classes that make up the software by the responsibility that each of them has when a use case is realized:

* an _Entity_ is information that lives long and matters to the stakeholders; most of it derives from the objects of the domain, and it is usually persistent;
* a _Boundary_ handles the system's exchanges with external actors: users or other systems;
* a _Controller_ ensures the processing that the execution of a use case and its business logic requires, and coordinates, sequences and controls the other objects that take part in the use case;
* an _Actor_ stands for an object that interacts with the system; such objects, the actors, stand for roles, such as users or external systems.

|Protocol |A set of rules governing the exchange or transmission of data between software components
|https://aws.amazon.com/what-is/routing/[Routing] |Selecting a path in a network of any kind
|Packet |A block of data transmitted across a network
|Binding |See xref:up-l1/README.adoc#communication-protocol-binding[_communication protocol binding_] in xref:up-l1/README.adoc[Transport & Session Layer (uP-L1)], and a binding of the up-rust SEooC in xref:safety/up-l1/bindings.adoc[uP-L1 safety: Allocated to each binding].
|Communication Protocol |A protocol, such as MQTT or HTTP, that carries messages between communicating parties. It defines its own message exchange patterns and its own protocol data unit (PDU) for control information and user data. A uProtocol transport library binds uProtocol to a communication protocol.
|Application Protocol |A protocol by which the processes of an application exchange messages. It defines the kinds of message, such as requests and responses, how each kind is structured and what its fields mean, and when a process sends a message or answers one.

|Transport Protocol |A specification for providing transparent transfer of data from point-2-point, providing reliable data transfer services to the upper layers. 
|https://en.wikipedia.org/wiki/Network_socket[Network Socket] a|
An endpoint for sending and receiving data across a computer network: a structure in the software of a node of that network. An application programming interface (API) of the networking architecture defines how a socket is structured and what properties it has. A socket is created only during the life of a process of an application that runs in the node.

The word _socket_ also names the software endpoint of inter-process communication (IPC) within one node, which often uses the same API as a network socket.

|https://cloudevents.io/[CloudEvents] |A specification of one common way to describe the data of events
|CloudEvent (CE) |One event, described in the way that the CloudEvents specification defines
|https://en.wikipedia.org/wiki/Quality_of_service[QoS] |A description or a measurement of how well a service performs as a whole, above all as the network's users experience it. The service may be, for example, a network for telephony or for computers, or a service of cloud computing
|https://en.wikipedia.org/wiki/Business_logic[Business Logic] (Domain Logic) |The part of a program in which the real-world rules of the business are encoded: the rules that govern the creation, storage and change of data. It is distinguished from the rest of the software, which may handle details at a lower level: the management of a database, the display of the user interface, the infrastructure of the system or, more generally, the linking of the program's parts.
|===

== uProtocol Terms

.uProtocol Terms
|===
|Terms |Definition

|*C2D* |Cloud-2-Device Communication
|*D2C* |Device-2-Cloud Communication
|*D2D* |Device-2-Device Communication
|*uDevice* |Independent software execution environment that will implement uProtocol and contain a collection of uEntities along with dispatcher(s)
|*Device Proxy Router (DPR)* |See xref:up-l2/dispatchers/README.adoc#dispatcher-types[Types of Dispatchers]
|*uDomain* |Collection of uDevices using DNS nomenclature
|*Message* |Protobuf defined data structure used for communication in the uProtocol
|*Property* |An attribute, quality, or characteristic of a uThing that are stored in the uDiscovery database
|*Resources* a|
Something that can be manipulated/controlled/exposed by a service. Resources are unique when prepended with device and service.
*Static Topic:* Resource that is declared in the service proto in Resource enum and known at compile time (ex. door, window, etc...)
*Dynamic Topic:* Created at runtime and not defined in the service proto (ex. geo-fence locations)
|*uBus* |See xref:up-l2/dispatchers/README.adoc#dispatcher-types[Types of Dispatchers]
|*uStreamer* |Device-2-Device event dispatcher to enable seamless communication between uEntities on different devices which might talk different transport layer protocols. Performs various additional functionality such as file transfer, event buffering and more. i.e. when events need to move form one transport to the next it flows through the streamer (can be equated to an IP router) 
|*uDiscovery* |Provides a means for uEntities to discover each other, their location (address), properties, and more.
|*Topic* |What applications subscribe to and services publish to. It is represented as a uProtocol URI containing authority, sw entity, and resource information
|*uApplication* |A uEntity that acts as a _service consumer_
|*uService* |A uEntity that acts as a _service provider_. The interface describing the provided service operations is defined by means of https://protobuf.dev/[proto3]
|*uThing* |URI addressable stuff that can be accessed by the uProtocol. Examples of uThings are devices, domains, service, and resources.
|*Cloud Gateway* |Component that lives in the cloud that devices connect with to communicate with the Back-office domain/device
|*uEntity* |A piece of software that communicates with other uEntities using uProtocol; might be abbreviated as `uE` especially in diagrams.
|*uP-L1* |uProtocol Transport & Session Layer
|*uP-L2* |uProtocol Communication Layer
|*uP-L3* |uProtocol Application Layer
|===
