NOTE: A serialized wire encodes a value into the bytes of a format, and decodes such bytes into a value (xref:README.adoc#req-ssr-wire-scope[What a wire is, and the wire contract]).
The decoded value is _owned_: its slot owns it, then the lease that an application holds, and it borrows nothing from the frame that it came from (<<req-ssr-wire-encode-decode,A serialized wire encodes once into the storage it is given, and decodes into a value that its slot owns>>, "An owned value").

This page holds:

* the two requirements of each serialized wire;
* encoding, owning and heap use (<<owning>>);
* the rules of other pages that a serialized route rests on, in the order in which a payload meets them (<<index>>);
* allocation, and each stronger guarantee (<<guarantees>>);
* what fails, and where (<<failures>>);
* a worked example, Protobuf (<<protobuf>>).

[[req-ssr-wire-serialized-format]]
== A serialized wire reads and writes one stated format

[.specitem,oft-sid="req~ssr-wire-serialized-format~3",oft-title="A serialized wire reads and writes one stated format",oft-needs="impl,utest",oft-tags="SafetyWireSerialized"]
--
Each serialized wire, apart from the end-to-end protection wire, answers for each duty of this item.

*One format.*
The wire *MUST* state the one format that it writes and reads:

* the payload encoding identifier of that format, which is one that the registry lets a sender originate (xref:README.adoc#encoding-identifier[the encoding identifier is the registry's]);
* the specification of the format at a fixed version: a public one, or, for a private-use identifier, the deployment agreement that defines it.

*Only that format.*
Every encoding that the wire writes *MUST* be an encoding, in that format, of the value that it was given.
Decoding *MUST* accept what the format makes an encoding of a value of the type; what it refuses is stated in xref:README.adoc#req-ssr-wire-no-panic[Encoding and decoding never panic].

*The format decides.*
Which inputs are encodings, and of which values, is the format's to say: for a malformed input, for an input that ends early, for an empty input, and for an input with elements that the type does not know.

* The wire *MUST NOT* add a default or a lenient reading of its own.
* The wire, where it accepts less than a public format allows, *MUST* state that narrower format as its own.

*Type identity.*
A format's bytes need not say which type they encode, and an encoding identifier never does.
The type of a serialized payload is the type that its route declares, on the sending side and on the receiving side.
Neither the bytes of a payload, nor their length, nor a decode that succeeds establishes another type, or shows that the sender meant that one.

* What agrees the type of a payload between a sender and a receiver, and what the wire checks of it, the wire states in its README, as xref:README.adoc#req-ssr-wire-readme[A wire's README says what its format is and what it cannot detect] requires.
* The wire *MUST NOT* present a decode that succeeds as proof that the sender meant that type.

*Heap use and ownership.*
A format and its identifier say nothing about heap use or about ownership.
The wire declares those apart (xref:../../basics/resources.adoc#req-ssr-heap-declared[The heap class is declared, with no default]).

*The end-to-end protection wire.*
This item does not bind the end-to-end protection wire.
For that wire it retires revision 1 of this item, which named each serialized wire: the format that the end-to-end protection wire itself writes and reads, what it accepts and what it refuses are stated by its own items (xref:e2e.adoc#req-ssr-e2e-wraps-any-wire[The E2E wire wraps any wire and leaves its bytes alone], "The rules for serialized wires"), and a serialized wire that it wraps stays bound by this item.
--

[horizontal]
ID:: `+req~ssr-wire-serialized-format~3+`
ASIL:: B
Allocated to:: each serialized wire, apart from the end-to-end protection wire
Verification:: test, review
* *test*
** The wire contract suite, with each expected result stated from the format before the wire runs (xref:README.adoc#req-ssr-wire-no-panic[Encoding and decoding never panic]).
** Encodings that the wire writes, decoded by an independent reader of the format.
** Encodings that the format allows and the wire's own encoder never writes, decoded by the wire.
** The identifier that the wire declares, compared with the registry's for its format.
* *review*: the wire's statement of its format and version, and of what agrees a payload's type.

*Rationale.*
A receiver can decode a sender's bytes only if both mean the same format.
A wire that wrote a variant of its own, or read more leniently than its format, would agree only with itself.

_The format decides._
The wire names the format, at a version, so that a test can state each expected result from the format and so that a second implementation can be checked against the same text.

_Type identity._
Many formats do not carry the name of the type that they encode, and a payload encoding identifier names a format, never a type.
So bytes of one message type can decode as another type without an error.
The wire cannot always prevent that, so it says what does agree the type, and it does not claim more.
A route's declaration is what the sender and the receiver agreed, so the type that it declares governs.

[[req-ssr-wire-encode-decode]]
== A serialized wire encodes once into the storage it is given, and decodes into a value that its slot owns

[.specitem,oft-sid="req~ssr-wire-encode-decode~3",oft-title="A serialized wire encodes once into the storage it is given, and decodes into a value that its slot owns",oft-needs="impl,utest",oft-tags="SafetyWireSerialized"]
--
Each serialized wire, apart from the end-to-end protection wire, answers for each duty of this item.

*Sizing.*
The wire *MUST* state truthfully the largest encoding that it can write for its type, or that it has none.
The wire *MAY* state the smallest encoding that it writes for its type, and a wire that states one *MUST NOT* write a shorter encoding.

* A size that it reports for a value as exact *MUST* be the number of bytes that encoding that value writes.
* A value whose encoding does not fit the route's bound, or the storage that the wire was given, *MUST* be refused before anything is sent.
* Whether setup admits a route whose wire states that it has no largest encoding is stated in xref:../runtime.adoc#req-ssr-mode-entry-no-latent-refusal[Nothing is refused at runtime for a reason setup already knew], "A wire with no largest encoding".

*Encoding.*
Encoding *MUST* write the value once, in order, through the payload writer that the element gives it, into the storage that carries the frame (xref:../payload-paths.adoc#req-ssr-payload-written-once[A payload is written once, into the storage that carries it]).

* The wire *MUST NOT* build the encoding in storage of its own and copy it out.
* A value that the format cannot represent *MUST* be an error, with nothing sent.
* Encoding *MUST* leave the value as it was, so a refused send can be tried again with the same value.

*Decoding.*
Decoding *MUST* replace the value in the slot that the element gives it.

* The result *MUST* depend on the input alone, and not on what the slot held before.
* What the slot held before *MUST* end exactly once, as its route's class says (xref:../runtime.adoc#req-ssr-heap-slot-types[A decoded value is destroyed once, as its route's class admits]).
* A decode that fails *MUST* leave a valid value in the slot and nothing half-owned.

*An owned value.*
A decoded value *MUST NOT* borrow from the input, from the frame or from the wire, so it stays valid after the frame is returned.
It *MAY* refer to static data, or to data whose shared ownership it holds, that stays valid independently of all three, where that is consistent with the route's heap class and with the ownership of the value (xref:../../basics/resources.adoc#req-ssr-heap-declared[The heap class is declared, with no default]; xref:../runtime.adoc#req-ssr-heap-slot-types[A decoded value is destroyed once, as its route's class admits]).
Such a value is what the up-rust SEooC requirement family calls _owned_.

*Owning heap memory.*
Whether a decoded value owns heap memory is a property of its type and of the wire.
What the wire declares of it for each direction, what a route that declares allocation admits, and what a declared class of none requires of the wire are stated in xref:../../basics/resources.adoc#req-ssr-heap-declared[The heap class is declared, with no default], xref:../../basics/resources.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name, and admitted or refused] and xref:README.adoc#req-ssr-wire-heap-claim-tested[A heap-free claim is true, and encoding is repeatable].

*Errors.*
Each refusal *MUST* be a returned error of fixed size (xref:README.adoc#req-ssr-wire-no-panic[Encoding and decoding never panic]; xref:../../basics/error_model.adoc#req-ssr-error-fixed-size[Errors are fixed-size diagnoses]).

*The end-to-end protection wire.*
This item does not bind the end-to-end protection wire.
For that wire it retires revision 1 of this item, which named each serialized wire: the end-to-end protection wire's own sizing, encoding, decoding and refusals are stated by its own items (xref:e2e.adoc#req-ssr-e2e-wraps-any-wire[The E2E wire wraps any wire and leaves its bytes alone], "The rules for serialized wires"), and a serialized wire that it wraps stays bound by this item.
--

[horizontal]
ID:: `+req~ssr-wire-encode-decode~3+`
ASIL:: B
Allocated to:: each serialized wire, apart from the end-to-end protection wire
Verification:: test, heap-window, review
* *test*
** The largest encoding that the wire states, against a value built to reach it, and an exact size against the bytes written.
** Where the wire states a smallest encoding: no encoding that it writes, over values built to reach it, is shorter.
** A value one byte too large for the route's bound: refused, with nothing sent and the value unchanged.
** A value that the format cannot represent: an error, with nothing sent.
** A value encoded twice: unchanged by each encode.
** Decoding into a slot that holds each of several earlier values, with the same result every time.
** A decode that fails part-way, with the slot's value valid afterwards and each acquisition released once.
** A decoded value used after its frame was returned and its storage reused.
* *heap-window*: where the wire claims a class of none for its decode direction, a decode into a slot that holds an earlier value, with that value ended as its route's class says and no heap use.
* *review*: no storage of the wire's own between the value and the element's writer.

*Rationale.*
_Once, into the storage that carries it._
A wire that built its encoding in a buffer of its own and then copied it would work, and would cost a second pass over the payload and a place to keep the buffer.
The element cannot see inside a wire, so the duty is the wire's.

_Sizing._
The element reserves storage before a wire encodes.
A size reported as exact that was wrong would leave bytes of an earlier frame in the payload, or cut the encoding short.
The element checks the writer afterwards and trusts no byte count (xref:README.adoc#req-ssr-unsafe-wire-untrusted[No wire can break the element's memory safety]), and the wire still owes an honest size, so that a refusal can come before anything is written.
A wire with no largest encoding gives the element no size to reserve, so its route declares a bound.
Without one, nothing sizes the route's storage, and setup refuses the route rather than admit one that fails only in operation (xref:../runtime.adoc#req-ssr-mode-entry-no-latent-refusal[Nothing is refused at runtime for a reason setup already knew]).

_Owned._
A frame goes back to its transport as soon as decoding is done, and its storage is then reused.
A decoded value that still pointed into it would read another message.
So a decoded value borrows nothing from the frame.

_Owning heap memory._
One format can be decoded into a value that owns heap memory, or into one that holds everything in storage of fixed capacity.
So the format does not say whether a route allocates.
The wire says it, for each direction, and a deployment that needs more than ordinary ownership requires it by name (xref:../../safety/elements/up-rust/assumptions-of-use.adoc#aou-seooc-resource-guarantees[A resource guarantee the item relies on is required by name]).

== A worked example: Protobuf

NOTE: The statements of the column "On Protobuf" about the format rest on the Protocol Buffers documentation, in the revision `d75b49a09168103d132dcccf7dc9d6e126ba1f98` of its source (8 October 2026).
The binary encoding is described in "Encoding" (https://github.com/protocolbuffers/protocolbuffers.github.io/blob/d75b49a09168103d132dcccf7dc9d6e126ba1f98/content/programming-guides/encoding.md[`content/programming-guides/encoding.md`], sections "Message Structure", "Missing Elements", "Repeated Elements", "Last One Wins", "Groups", "Field Order", "Implications" and "Encoded Proto Size Limitations").
Required fields, field presence, default values and the form of a repeated field that an encoder writes by default are described in "Language Guide (proto 2)" (https://github.com/protocolbuffers/protocolbuffers.github.io/blob/d75b49a09168103d132dcccf7dc9d6e126ba1f98/content/programming-guides/proto2.md[`content/programming-guides/proto2.md`], sections "Required is Strongly Deprecated" and "Default Field Values"), "Application Note: Field Presence" (https://github.com/protocolbuffers/protocolbuffers.github.io/blob/d75b49a09168103d132dcccf7dc9d6e126ba1f98/content/programming-guides/field_presence.md[`content/programming-guides/field_presence.md`], sections "Presence in Tag-value stream (Wire Format) Serialization" and "Semantic Differences") and "Feature Settings for Editions" (https://github.com/protocolbuffers/protocolbuffers.github.io/blob/d75b49a09168103d132dcccf7dc9d6e126ba1f98/content/editions/features.md[`content/editions/features.md`], sections `features.field_presence` and `features.repeated_field_encoding`).
The binary encoding that "Encoding" describes is what RFC 9996 (Media Types for Protocol Buffers, July 2026, section 7.1) identifies as version 1 of the wire encoding.
The language edition of a message's schema (proto2, proto3 or an edition) is a separate matter, and a row says where a statement depends on it.
What a wire, a route or the element does is stated by the item that the row links, and not by those documents.

.The rules for serialized wires, worked through for Protobuf
====
[cols="2,5,3",options="header"]
|===
| Matter | On Protobuf | Rule

| The format
| The Protobuf binary encoding of one message type. The wire states the identifier that the registry assigns to it
| <<req-ssr-wire-serialized-format,A serialized wire reads and writes one stated format>>

| An empty input
| For a message type with no required field, the empty input is the encoding of the message with no field set, whose readers then give each field its default. So a Protobuf wire decodes it to that message, and does not refuse it. Required fields exist in proto2, and in an edition through its legacy setting
| xref:README.adoc#req-ssr-wire-no-panic[Encoding and decoding never panic], "An empty input"

| An input that ends early
| One that ends inside a tag, a field or a group is malformed, and is an error. One that ends after a complete field can still be the encoding of another message, where every required field of the type is present, and a decoder cannot tell from such bytes that they were cut
| xref:README.adoc#req-ssr-wire-no-panic[Encoding and decoding never panic], "Invalid input"

| Fields that the type does not know
| Where they are well formed, they are part of a valid encoding, and are no error
| <<req-ssr-wire-serialized-format,A serialized wire reads and writes one stated format>>, "The format decides"

| Several encodings of one value
| A value can have more than one encoding: its fields in another order, a repeated field of a numeric, boolean or enumeration type, packed or not, and, for a field that does not track presence, its default value written or left out. A wire accepts each, and no test asks its encoder for one of them. Whether a field tracks presence, and which form of a repeated field an encoder writes by default, depend on the schema's language edition and settings
| xref:README.adoc#req-ssr-wire-no-panic[Encoding and decoding never panic]

| Repeatable encoding
| The format does not fix one encoding of a value, and its documentation warns that serialization need not be deterministic. A Protobuf wire fixes each choice that the format leaves open, so that it writes the same bytes each time it encodes the same value
| xref:README.adoc#req-ssr-wire-heap-claim-tested[A heap-free claim is true, and encoding is repeatable], "Repeatable encoding"

| Sizing
| The size of an encoding is computed from the value and from the encoder's choices, and a wire can report it as exact. The format caps every encoding below 2 GiB, and a type with a string, a bytes or a repeated field reaches no smaller maximum. A wire for such a type states, as its largest encoding, that cap or a smaller limit that it enforces, and a value whose encoding does not fit its route's payload bound is refused before anything is sent
| <<req-ssr-wire-encode-decode,A serialized wire encodes once into the storage it is given, and decodes into a value that its slot owns>>, "Sizing"

| Decoding into a slot
| A library call that merges an input into an existing message depends on what that message held. A wire that uses one starts from the cleared message
| <<req-ssr-wire-encode-decode,A serialized wire encodes once into the storage it is given, and decodes into a value that its slot owns>>, "Decoding"

| Ownership and the heap
| Whether a decoded message owns heap memory depends on its wire and its type, and not on the format. A wire that decodes strings, byte fields or repeated fields into growable storage decodes into values that own heap memory. It declares allocation for the decode direction, with its allocator's policy, and its route declares it too. A wire for a message type whose fields all have a fixed size can decode without the heap where it keeps no field that the type does not know, and can then claim a class of none
| <<req-ssr-wire-encode-decode,A serialized wire encodes once into the storage it is given, and decodes into a value that its slot owns>>; xref:../../basics/resources.adoc#req-ssr-heap-declared[The heap class is declared, with no default]; xref:../../basics/resources.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name, and admitted or refused]

| Type identity
| The bytes do not carry the name of their message type. A payload of one message type can decode as another without an error
| <<req-ssr-wire-serialized-format,A serialized wire reads and writes one stated format>>, "Type identity"

| On a transport
| A Protobuf wire runs on a lending binding and on a handoff binding alike. On a lending binding it encodes into a loan
| xref:../payload-paths.adoc#req-ssr-payload-written-once[A payload is written once, into the storage that carries it]
