= The XCDR2 Little-Endian Appendable Profile
:toc: preamble

The key words "*MUST*", "*MUST NOT*", "*REQUIRED*", "*SHALL*", "*SHALL NOT*", "*SHOULD*", "*SHOULD NOT*", "*RECOMMENDED*", "*MAY*", and "*OPTIONAL*" in this document are to be interpreted as described in https://www.rfc-editor.org/info/bcp14[IETF BCP14 (RFC2119 & RFC8174)]

[NOTE]
====
This page holds the XCDR2 little-endian appendable serialized-format profile requirements of the up-rust SEooC requirement family (`+req~ssr-xcdr2-*+`, `ASIL:: B`, `SafetyXcdr2` tag).
Filing on this page does not broaden any requirement to all uP-L1 implementations: whom each item binds, and how the repository's requirement families meet, is stated in xref:../../contract-generations.adoc[Which requirements an implementation follows] (xref:../../contract-generations.adoc#req-ssr-requirements-bind[A requirement binds the actors to which it gives a duty]; xref:../../contract-generations.adoc#req-ssr-item-reading[How an item is read]).

Conventions and tags: xref:../../safety/README.adoc[Safety and assurance view].
The duties of every wire: xref:README.adoc[uP-L1 wires].
The duties of every serialized wire: xref:serialized.adoc[serialized wires, and the values they own].
====

NOTE: This page states one serialized format.
Its encodings are those of a standard representation: version 2 of the extended Common Data Representation (XCDR2), little-endian, as that standard encodes a structure that can grow at its end, with a delimiter header before its fields.
The profile admits fewer types than the standard does.
In the standard's words (<<dds-xtypes,DDS-XTypes 1.3>>), a type of this profile is a structure type of the extensibility kind APPENDABLE (7.2.3), a field is a member (7.2.2.4.4), the delimiter header is the DHEADER (7.4.3.4.1), the encoding format is DELIMITED_CDR (7.4.2), and the encapsulation identifier and the options are those of 7.6.3.1.2.

== Whom the items bind

* Each item's statement names whom it binds: here, each wire of the XCDR2 little-endian appendable profile, as <<req-ssr-xcdr2-types,The profile encodes structures of fixed-width fields, and nothing else>> defines it (xref:../../contract-generations.adoc#req-ssr-requirements-bind[A requirement binds the actors to which it gives a duty]).
* The duties of every wire and of every serialized wire hold beside them.
* The rules of a native type: xref:native.adoc[the native wire].

[[req-ssr-xcdr2-types]]
== The profile encodes structures of fixed-width fields, and nothing else

[.specitem,oft-sid="req~ssr-xcdr2-types~2",oft-title="The profile encodes structures of fixed-width fields, and nothing else",oft-needs="impl,utest",oft-tags="SafetyXcdr2"]
--
*The profile and its wires.*
The XCDR2 little-endian appendable profile is the serialized format that the six requirements of this page state.
A wire of the profile is a serialized wire that states the profile as its format (xref:README.adoc#req-ssr-wire-scope[What a wire is, and the wire contract]; xref:serialized.adoc#req-ssr-wire-serialized-format[A serialized wire reads and writes one stated format]).

*A structure of fields.*
A type of this profile is a structure with a fixed list of fields, in a fixed order.
The list can be empty.
Each field has a name, which no other field of the type has, and a field type.
A field's index is its place in the list, counted from zero, and its member identifier, in the standard's sense, is that index.

*Field types.*
A field type is one of these:

* one of the eleven primitive types: a signed or an unsigned integer of 8, 16, 32 or 64 bits; a floating-point number in the binary32 or the binary64 format; a boolean;
* an array: a fixed number of elements of one primitive type, in one or more dimensions, each dimension of a fixed length of at least one.

Two field types are the same only where they are one primitive type, or are arrays whose elements have one primitive type and whose dimensions have the same lengths in the same order.

*Arrays.*
An array is one field with all of its dimensions.
A declaration that nests fixed arrays of a primitive type declares that one array, its outermost dimension first: an array of three arrays of two integers is the array of two dimensions, three by two.
The profile has no array whose elements are arrays: a declaration that the standard reads as such an array, such as an array of a named array type in its interface definition language, declares no type of this profile.

*Types outside the profile.*
A wire of the XCDR2 little-endian appendable profile *MUST* refuse a type that is not a type of this profile, when the wire is built or at setup, and *MUST NOT* encode or decode it.
Such types include:

* a type with a string, a sequence, a map, or any other field whose size depends on its value;
* a type with an optional field, a union or an enumeration;
* a type with a structure as a field, or as an element of an array;
* a type with a character, or with an integer or a floating-point number of a width that the list above does not name;
* a type with an array that has a dimension of length zero;
* a type in which two fields have the same name, or in which a field's member identifier is not its index;
* a type with more than 268 402 688 fields, whose last member identifier would be greater than 268 402 687;
* a type whose body length (<<req-ssr-xcdr2-length,The encoded length of a type is exact>>) is greater than 4 294 967 295 bytes, the greatest value that the delimiter header can hold;
* a type whose encoding writes a header before each field, so that fields can be left out or written in another order.

*However a type is mapped.*
A wire's mapping between a program's type and a type of this profile is part of the wire, whether a derive or a generator produces it or it is written by hand.
The wire *MUST* meet the six requirements for a type whichever way its mapping is made, and *MUST* keep in its mapping each name, field type, order, default and mandatory mark that the program's type declares (<<req-ssr-xcdr2-evolution,A type grows only by fields added at its end, and a receiving end reads only the types that it admits>>).

*Rationale.*
Every field has one size, so a type has one body length and each field has one place.
That is what lets a wire state its size exactly and find each field without a count or a length of its own in the input.

_Arrays._
The standard representation writes an array of integers, of floating-point numbers or of booleans as its elements alone, whatever its dimensions, and in version 2 gives an array whose elements are arrays a delimiter header of its own.
The profile admits the first and not the second, so a nested declaration has one encoding.
The standard gives each dimension a length greater than zero, so an array of no elements is no type of the representation.
That rule is the format's, and says nothing of a native type of size zero (xref:native.adoc[the native wire]).

_Names and identifiers._
An encoding carries no name and no member identifier.
Distinct names, and an identifier that is the index, make a field's name, place and identifier agree, and those are what the standard compares when it decides whether two types are compatible.
The standard leaves at least the member identifiers up to 268 402 687 to application types, so a type whose identifiers are its indexes and that has at most 268 402 688 fields keeps every identifier in that range.

[[req-ssr-xcdr2-encoding]]
== An encoding is an encapsulation header, a delimiter header and the fields in order, little-endian and aligned

[.specitem,oft-sid="req~ssr-xcdr2-encoding~2",oft-title="An encoding is an encapsulation header, a delimiter header and the fields in order, little-endian and aligned",oft-needs="impl,utest",oft-tags="SafetyXcdr2"]
--
*The parts.*
A wire of the XCDR2 little-endian appendable profile *MUST* write the encoding of a value as the four parts that this item states, in this order, with nothing before, between or after them: the encapsulation header, the delimiter header, the body and the trailing padding.
Offsets are counted from the first byte of the encapsulation header, which is offset 0.

*The encapsulation header.*
The encapsulation header is four bytes, at offsets 0 to 3:

* the encapsulation identifier: the two bytes `00 09`;
* the options: two bytes, in which the two lowest bits of the second byte hold the number of bytes of trailing padding, from zero to three, and every other bit is zero.

*The delimiter header.*
The delimiter header is an unsigned integer of 32 bits, least significant byte first, at offsets 4 to 7.
Its value is the length of the body in bytes.
It counts the padding inside the body, and counts neither itself nor the trailing padding.

*The body.*
The body starts at offset 8.
It holds the fields in the order of the type's list, each written as follows, with nothing between them but padding:

* an integer: in two's complement, least significant byte first;
* a floating-point number: its binary32 or binary64 bit pattern, least significant byte first;
* a boolean: one byte, `00` for false and `01` for true;
* an array: its elements in order, with no count and no header of its own; where it has more than one dimension, the last index changes fastest.

The body ends with the last byte of the last field, and a type with no field has a body of no bytes.

*Alignment.*
Each value starts at the first offset, at or after the end of what precedes it, that is a multiple of its alignment, whether the value is a field or an element of an array.
The alignment of a value of one byte is one, that of a value of two bytes is two, and that of a value of four or of eight bytes is four.
An array is aligned as its elements are, so padding comes before its first element only.

*Padding.*
The bytes that alignment skips are padding, and they are part of the body.
The trailing padding is the fewest bytes, from zero to three, that bring the length of the encoding to a multiple of four.
Padding holds no part of a value.
The wire *MUST* write each byte of padding, in the body and after it, as `00`.

*One encoding of a value.*
These rules leave a wire no choice of a byte: the options, the delimiter header and each byte of padding follow from the type, and every other byte from the value.
Which inputs decode to a value is stated by <<req-ssr-xcdr2-decoding,Decoding refuses a wrong length, a wrong header or a wrong boolean byte>>.
--

_One encoding._
The standard representation leaves to the writer what padding inside the body holds, and every bit of the options but the two that count the trailing padding.
Zero in each makes an encoder write one encoding of each value, so values whose fields have equal bit patterns are written as equal bytes.

_Alignment._
An alignment of at most four, counted from the start of the encoding, is the standard's for version 2.
The body starts at offset 8, a multiple of four, so counting from the start of the body gives every value the same place.

[[req-ssr-xcdr2-length]]
== The encoded length of a type is exact

[.specitem,oft-sid="req~ssr-xcdr2-length~2",oft-title="The encoded length of a type is exact",oft-needs="impl,utest",oft-tags="SafetyXcdr2"]
--
*Fixed by the type.*
The body length of a type is the offset at which its last field ends, less eight, and zero for a type with no field.
The encoded length of a type is its body length, rounded up to a multiple of four, plus eight: the encapsulation header, the delimiter header, the body and the trailing padding together.
Every value of the type has that body length and that encoded length.

*Computed without overflow.*
A wire of the XCDR2 little-endian appendable profile *MUST* compute body lengths and encoded lengths with arithmetic that cannot overflow.
The wire *MUST* refuse, when it is built or at setup, a type whose encoded length is greater than the largest size that the wire can represent.

*Stated as exact.*
The encoded length is the size of the largest encoding, which a serialized wire states for its type (xref:serialized.adoc#req-ssr-wire-encode-decode[A serialized wire encodes once into the storage it is given, and decodes into a value that its slot owns], "Sizing").
The wire *MUST* also state it as the exact size of every encoding that it writes of the type.

*At a receiving end.*
A receiving end can admit writer types whose encoded lengths are not its reader type's (<<req-ssr-xcdr2-evolution,A type grows only by fields added at its end, and a receiving end reads only the types that it admits>>).
The wire *MUST* state, for a receiving end, the greatest encoded length among the writer types that the end admits, as the largest input that it accepts.
--

_Overflow._
The encoded length of a type whose body is close to the greatest value of the delimiter header needs more than 32 bits.
A wire whose sizes have 32 bits refuses such a type, rather than state a size that has wrapped around.

[[req-ssr-xcdr2-decoding]]
== Decoding refuses a wrong length, a wrong header or a wrong boolean byte

[.specitem,oft-sid="req~ssr-xcdr2-decoding~2",oft-title="Decoding refuses a wrong length, a wrong header or a wrong boolean byte",oft-needs="impl,utest",oft-tags="SafetyXcdr2"]
--
*What is refused.*
A wire of the XCDR2 little-endian appendable profile *MUST* refuse, in decoding, an input:

* that is shorter than eight bytes, the empty input among them;
* whose first two bytes are not the encapsulation identifier `00 09`;
* whose length differs from the sum of eight, the value of its delimiter header and the count of trailing padding that its options give;
* whose length is not a multiple of four;
* whose delimiter header is not the body length of a writer type that the receiving end admits (<<req-ssr-xcdr2-evolution,A type grows only by fields added at its end, and a receiving end reads only the types that it admits>>);
* in which a byte of a boolean of the input's admitted writer type, as a field or as an element of an array, is neither `00` nor `01`, whether or not the receiving end's reader type has that field.

*Checked first.*
The wire *MUST* make the first five of those checks before it reads any field, with arithmetic that cannot overflow.
The wire *MUST NOT* report a value as decoded unless the input passed all six.
What a refusal returns: xref:README.adoc#req-ssr-wire-no-panic[Encoding and decoding never panic]; xref:serialized.adoc#req-ssr-wire-encode-decode[A serialized wire encodes once into the storage it is given, and decodes into a value that its slot owns], "Errors".

*Padding and options.*
The wire *MUST* accept any value in a byte of padding, in the body and after it: an input whose padding is not zero decodes to the same value.
The wire *MUST* read the two lowest bits of the second options byte as the count of trailing padding, and *MUST* accept any value in every other bit of the two options bytes.

*Other inputs.*
Every bit pattern of an integer and of a floating-point number is a value, and the wire *MUST* yield the value with exactly the bit pattern of its bytes.
The wire *MUST* decode every input that passes the six checks, and *MUST NOT* refuse an input for any other property of its bytes.
--

*Rationale.*
The header and the lengths are checked before any field is read, so no field is read past the end of the input or of the body.
A boolean is the only kind whose byte can hold a pattern that is no value.

_Lengths._
The delimiter header, the options and the input's own length each say where an encoding ends.
An input in which they disagree, or which holds bytes after its trailing padding, could carry a second encoding that a reader of the first would never see.
So the three agree exactly, or the input is refused.

_Booleans that a reader skips._
The receiving end's declaration names the writer type whose body length an input has, so the wire knows where each of that type's booleans lies, in the fields that it skips too.
An input in which one of them is no value is no encoding of an admitted type, whatever the reader then keeps.

_Padding and options._
If each reader chose whether to refuse non-zero padding, or an options bit that it does not know, two readers of this page could disagree on the same bytes.
One rule for every reader keeps them the same.

[[req-ssr-xcdr2-evolution]]
== A type grows only by fields added at its end, and a receiving end reads only the types that it admits

[.specitem,oft-sid="req~ssr-xcdr2-evolution~1",oft-title="A type grows only by fields added at its end, and a receiving end reads only the types that it admits",oft-needs="impl,utest",oft-tags="SafetyXcdr2"]
--
*What a type can declare for a field.*
Beside a field's name and field type, a type can declare:

* a default for the field: a value of the field's type;
* that the field is mandatory: no type without the field is compatible with a type that has it.

A field that a type declares, in the standard's terms, as a key member or as a member that a reader must understand is mandatory.

*Compatible types.*
Two types are compatible where one of these holds:

* their lists of fields are equal: at each index, the same name and the same field type; two types with no field are compatible;
* the list of the one is the beginning of the list of the other: at each index of the shorter list, the two fields have the same name and the same field type, the shorter list has at least one field, and no field that only the longer list has is mandatory.

A default, and the mandatory mark of a field that both types have, decide nothing of compatibility.
No other types are compatible.
A wire of the XCDR2 little-endian appendable profile *MUST NOT* take two types as compatible for any other reason, among them:

* that the values of two fields could be converted, as between integers of two widths or of two signednesses, between an integer and a floating-point number, or between the two floating-point formats;
* that two arrays have the same number of elements in other dimensions;
* that two fields at different indexes have one name, or that a field seems to have been inserted, removed, moved or renamed;
* that one of two types has no field while the other has fields;
* that the encodings of the two types have equal lengths.

*What a receiving end admits.*
A sending end writes one type, its writer type.
A receiving end decodes into one type, its reader type.
The writer types that a receiving end admits are its reader type and each type that the route's declaration names for that end at setup.
The wire:

* *MUST* refuse at setup a declaration that names, for a receiving end, a writer type that is not compatible with the end's reader type;
* *MUST* refuse at setup a declaration under which a receiving end admits two writer types that have different lists of fields and the same body length;
* *MUST NOT* admit a writer type for any other reason, and never from the bytes of an input, from its delimiter header or from its length.

*The admitted writer type of an input.*
An input's admitted writer type is a writer type that the receiving end admits and whose body length the input's delimiter header gives.
All such types have one list of fields, because a declaration that admits two lists of one body length is refused; their defaults and mandatory marks play no part in decoding.
The body length chooses among the lists of fields that the declaration admits, and identifies no type (<<req-ssr-xcdr2-identity,The bytes name no type, and a changed type is another type>>).

*A writer type with fewer fields.*
Where an input's admitted writer type lacks fields of the reader type, the wire *MUST* decode the fields that both types have, and *MUST* give each other field of the reader type its default: the default that the reader type declares for the field, or, where it declares none, zero for an integer, positive zero for a floating-point number, false for a boolean, and, for an array, that default in each of its elements.
Such a field never keeps what the slot held before (xref:serialized.adoc#req-ssr-wire-encode-decode[A serialized wire encodes once into the storage it is given, and decodes into a value that its slot owns], "Decoding").

*A writer type with more fields.*
Where an input's admitted writer type has fields beyond the reader type's, the wire *MUST* decode the reader type's fields and skip the rest of the body.
The wire *MUST NOT* take a value from the bytes that it skips; what it checks of them is stated by <<req-ssr-xcdr2-decoding,Decoding refuses a wrong length, a wrong header or a wrong boolean byte>>.

*Nothing else is a missing field.*
A field is absent only where the admitted writer type lacks it.
The wire *MUST NOT* give a field its default for any other reason: an input that ends before the length that its delimiter header and its options give, an input whose delimiter header is the body length of no admitted writer type, and an input in which a byte of a boolean is no value are each refused (<<req-ssr-xcdr2-decoding,Decoding refuses a wrong length, a wrong header or a wrong boolean byte>>).

** An encoding of an admitted writer type with fewer fields, decoded by a reader type that adds a field of each of the eleven primitive types and an array, some with a declared default and some with none, into a slot that held other values: each added field has its default, and each field that both types have has its value.
** An encoding of an admitted writer type with more fields: the reader type's fields have their values; the same input with each skipped integer, floating-point value and byte of padding changed decodes to the same value; with a skipped boolean byte of `02`, it is refused.
** A declaration that names, for a receiving end, a type that is not compatible with the reader type because it differs by a field inserted or removed anywhere but at the end, by two fields that change places, by a field renamed, by a field of another primitive type, of another width, signedness or format among them, or by an array of other dimensions or of another element type: each refused at setup.
** A declaration that names a type whose added field is mandatory, for a reader type without that field, and one that names a type without a field that the reader type declares mandatory: each refused at setup.
** A declaration that names a type that is not compatible with the reader type and has its body length; one that names a type with no field for a reader type with fields; and one under which the receiving end admits two types with different lists of fields and one body length: each refused at setup.
** A declaration that names a type with the reader type's fields and other defaults and mandatory marks: admitted.
** An encoding of a type that the receiving end does not admit, whose body length is that of no admitted type: refused in decoding.
** A body that ends inside a field of the reader type, and one that ends inside the padding before a field: each refused, with no field given a default.
** A type with no field, written and read under that same type.

*Rationale.*
A type that could only be replaced as a whole would make every sender and every receiver of a route change at once.
Fields added at the end leave each earlier field at its place, so an older reader finds its fields in a newer encoding, and a newer reader finds the fields of an older encoding in its own.

_Declared._
The bytes show a length and nothing of a type.
A reader that took any shorter or longer body for a version of its type would read whatever arrived with a fitting length.
So a receiving end reads the types that its route declares, and no others.
An encoding of a longer admitted type that is cut back, with its headers rewritten, to the body length of a shorter admitted type is an encoding of that shorter type, and no reader can tell; end-to-end protection catches such a change where a route needs it (xref:../../safety/elements/up-rust/assumptions-of-use.adoc#aou-seooc-e2e-protection[The integrator decides which routes need end-to-end protection]).

_Mandatory fields._
The encoding puts no mark on a field, so a reader cannot see in the bytes that a field which it does not know must be understood.
The declaration is where such a type is refused.

_One body length, one list of fields._
Two admitted writer types with different lists of fields and one body length would leave the wire to guess whose booleans to check.
The body lengths of the beginnings of one list of fields rise with each field, so only types that branch apart can share one, and a declaration that admits such a pair is refused.

[[req-ssr-xcdr2-identity]]
== The bytes name no type, and a changed type is another type

[.specitem,oft-sid="req~ssr-xcdr2-identity~2",oft-title="The bytes name no type, and a changed type is another type",oft-needs="impl,utest,uman",oft-tags="SafetyXcdr2"]
--
*What the bytes hold.*
An encoding holds no name, identifier, version or description of its type or of a field.
The encapsulation identifier is the same for every type, and the delimiter header holds a length.

*What agrees the type.*
The type of a payload is what its route declares: the writer type at its sending end, and at its receiving end the reader type and each writer type that the end admits (<<req-ssr-xcdr2-evolution,A type grows only by fields added at its end, and a receiving end reads only the types that it admits>>).
Of that declaration the bytes show only the body length, which decoding checks (<<req-ssr-xcdr2-decoding,Decoding refuses a wrong length, a wrong header or a wrong boolean byte>>).

*Changed lists of fields.*
A change to the list of fields makes another type: a field added, removed, moved, renamed or given another field type.
The bytes do not show such a change.
Where two types have equal body lengths, a reader that admits one can decode an encoding of the other without an error, and what it reads need not be what was written.
A wire of the XCDR2 little-endian appendable profile *MUST NOT* state, in its README or in what it declares, that it reads an encoding of a type that its receiving end does not admit.

*No exchange of types.*
The profile takes from a standard the representation of its encodings and the type rules that its items state, and no mechanism of that standard: no discovery, no exchange of type identifiers or of type descriptions, and no other part of the Data Distribution Service.
The wire *MUST NOT* state that it provides any of them because it follows the profile.
Such a mechanism, where a wire provides one, is no part of the profile, and its own stated contract governs it.

*Its version.*
A wire of the profile *MUST* state the version of the profile by naming its six requirements by their identifiers, each with the revision that it ends in, for example `+req~ssr-xcdr2-types~2+` (xref:serialized.adoc#req-ssr-wire-serialized-format[A serialized wire reads and writes one stated format]).

*The identifier.*
A wire of the profile *MUST* state, as the payload encoding identifier of its format, the identifier that the registry assigns to the profile where it assigns one, and otherwise an identifier of the private-use range that the deployment agreement defines as the profile at the version that the wire states (xref:../../basics/payload_encoding_registry.adoc[the payload encoding registry]).
A private-use identifier means the profile only by that agreement.
An identifier that a wire's implementation builds in means nothing until an agreement defines it, and is no assignment: the wire *MUST NOT* state it as the registry's or as the profile's own.
The wire *MUST NOT* state for the profile an identifier that the same agreement defines as another format, or as the profile at another version.

*What revision 2 replaces.*
Revision 1 of the items `+req~ssr-xcdr2-types+`, `+req~ssr-xcdr2-encoding+`, `+req~ssr-xcdr2-length+`, `+req~ssr-xcdr2-decoding+` and `+req~ssr-xcdr2-identity+` binds each wire of the fixed-layout XCDR2 profile, and states that other format, each of whose encodings begins with the four bytes `06 00 00 00`.
Revision 2 of those five items, with <<req-ssr-xcdr2-evolution,A type grows only by fields added at its end, and a receiving end reads only the types that it admits>>, states the XCDR2 little-endian appendable profile in place of that format, in everything that revision 1 stated: the types of the format, its bytes, its length, its decoding and the identity of a type.
Revision 2 binds each wire of the XCDR2 little-endian appendable profile.
For each wire of the fixed-layout XCDR2 profile, revision 1 stays in force as the contract of that format: revision 2 neither retires its duties nor gives them to another part (xref:../../contract-generations.adoc#req-ssr-contract-transition[What a part declares and claims, and when a replacement takes effect], "Replacement").
No input is an encoding of both formats, because their first bytes differ.
A route moves from one format to the other only through a change of its declaration at both of its ends, because a wire of the XCDR2 little-endian appendable profile:

* *MUST NOT* read or write an encoding of the fixed-layout XCDR2 profile;
* *MUST NOT* choose between formats by the bytes of an input;
* *MUST NOT* convert an encoding of one of the two formats into an encoding of the other.

Evidence for revision 1 is no evidence for revision 2 (xref:../../contract-generations.adoc#req-ssr-contract-transition[What a part declares and claims, and when a replacement takes effect], "Component claims").
--

[horizontal]
ID:: `+req~ssr-xcdr2-identity~2+`
ASIL:: B
Allocated to:: each wire of the XCDR2 little-endian appendable profile
Source:: <<dds-xtypes,DDS-XTypes 1.3>>: 7.3.4 (type identifiers and type objects); 7.6.3.2 (the discovery built-in topics); 7.6.3.3 (the built-in type lookup service).
Verification:: test, review
* *test*: two types that are not compatible and have equal body lengths, each decoding the other's encoding without an error; an encoding of the fixed-layout XCDR2 profile, refused; and the identifier that the wire declares, compared with the registry's where the registry assigns one to the profile, and otherwise with the one that the test's deployment agreement gives the profile.
* *review*: the wire's statement of the types that a route declares and of what it checks; the version of the profile that it states; the identifier that it states, with the agreement that defines it; and that neither its README nor what it declares says that it reads a type that a receiving end does not admit, that the profile gives it an exchange of types, or that it reads or writes the fixed-layout XCDR2 profile.

*Rationale.*
A decode that succeeds shows that the bytes fit a type that the reader admits, and nothing about what the sender meant.
The delimiter header adds a length and no name, and types with other fields share lengths.
So what agrees the type is declared outside the bytes, and a wire that claimed more would mislead whoever decides which routes need end-to-end protection (xref:../../safety/elements/up-rust/assumptions-of-use.adoc#aou-seooc-e2e-protection[The integrator decides which routes need end-to-end protection]).

_The identifier._
An identifier of the private-use range has no meaning of its own, so two deployments can give one number to two formats.
Only an agreement that gives the number one format lets a receiver rely on it.
The first bytes of an encoding are a check of the format, and no way to choose one.

[[examples]]
== Worked encodings

The encodings below follow from the items above and state no rule of their own.
Bytes are written in hexadecimal, in the order in which they are sent.

.One unsigned integer of 64 bits
====
The type has one field, an unsigned integer of 64 bits, with the value `0x0102030405060708`.

`00 09` `00 00` `08 00 00 00` `08 07 06 05 04 03 02 01`

The parts are the encapsulation identifier, the options, the delimiter header and the field.
The body length is eight, there is no trailing padding, and the encoded length is sixteen.
====

.A type with no field
====
`00 09` `00 00` `00 00 00 00`

The body length is zero, and the encoded length is eight.
====

.Alignment to at most four, and trailing padding
====
The type has three fields: an unsigned integer of 8 bits with the value `0x11`, one of 64 bits with the value `0x2122232425262728`, and one of 8 bits with the value `0x31`.

`00 09` `00 03` `0D 00 00 00` `11` `00 00 00` `28 27 26 25 24 23 22 21` `31` `00 00 00`

The second field starts at offset 12, a multiple of four and not of eight, after three bytes of padding.
The body length is thirteen, which counts that padding.
Three bytes of trailing padding bring the encoded length to twenty-four, and the options say three.
====

.An array of two dimensions
====
The type has two fields: an unsigned integer of 8 bits with the value `0x01`, and an array of two by three unsigned integers of 16 bits, in which the element at the indexes _i_ and _j_ has the high byte _i_ + 1 and the low byte _j_ + 1.

`00 09` `00 02` `0E 00 00 00` `01` `00` `01 01 02 01 03 01` `01 02 02 02 03 02` `00 00`

One byte of padding comes before the array and none between its elements.
The three elements of the first index 0 come first, then the three of the first index 1.
The body length is fourteen, and two bytes of trailing padding bring the encoded length to twenty-four.
====

.Each count of trailing padding
====
[cols="4,1,1,5",options="header"]
|===
| Type and value | Body length | Trailing padding | Encoding

| An array of four unsigned integers of 8 bits: `01`, `02`, `03`, `04`
| 4
| 0
| `00 09 00 00 04 00 00 00 01 02 03 04`

| An unsigned integer of 16 bits, `0x1234`, then one of 8 bits, `0x56`
| 3
| 1
| `00 09 00 01 03 00 00 00 34 12 56 00`

| An unsigned integer of 16 bits, `0x1234`
| 2
| 2
| `00 09 00 02 02 00 00 00 34 12 00 00`

| An unsigned integer of 8 bits, `0x7F`
| 1
| 3
| `00 09 00 03 01 00 00 00 7F 00 00 00`
|===
====

.A field added at the end
====
The first type has two fields: an unsigned integer of 32 bits with the value `0x0A0B0C0D`, and a boolean that is true.
The second type adds a third field at the end: an unsigned integer of 16 bits with the value `0xBEEF`.

The first type: `00 09` `00 03` `05 00 00 00` `0D 0C 0B 0A` `01` `00 00 00`

The second type: `00 09` `00 00` `08 00 00 00` `0D 0C 0B 0A` `01` `00` `EF BE`

Both encodings are sixteen bytes long, with body lengths of five and of eight.
A receiving end whose reader type is the first, and which admits the second, decodes the two fields at offsets 8 to 12 of the second encoding and skips offsets 13 to 15.
A receiving end whose reader type is the second, and which admits the first, decodes the two fields of the first encoding and gives the third field its default.
====
